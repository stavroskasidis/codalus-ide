# Shell ↔ language service protocol

Language services run out of process and speak **LSP 3.17** over **stdio** (JSON-RPC 2.0, `Content-Length` framing), with a few `codalus/` extensions where LSP has no message ([ADR 0005](adr/0005-editor-and-language-services.md)). The shell's client is generic (`LanguageHostClient` in `src/Codalus.LanguageServices.Client`, AOT-safe), so any LSP server can serve a language; the C# service is `codalus-lshost` (`src/Codalus.LanguageServices.Host`, Roslyn). Contracts are in `src/Codalus.LanguageServices.Protocol`.

## Process model

- The workbench's `LanguageService` starts a language's host when the first file of that language opens, or when the first design-time build of one of its projects arrives. It never starts at shell startup.
- The host is supervised (`SupervisedProcess`): on a crash it restarts with backoff (at most 5 times a minute), and the client sends `initialize`, the projects (`codalus/projects/update`) and every open document (`didOpen` with the editor's current text) again. Diagnostics of a host that gives up are cleared.
- Notifications are handled in arrival order, and a request reads the server's state when it arrives, so it observes every earlier edit. Cancelled requests send `$/cancelRequest`. A response completes its request as soon as it is read (it never waits behind a slow handler), so it can be seen before the notifications sent ahead of it are handled; `JsonRpcConnection.WhenDispatchedAsync` waits for those (a build's result waits for its output and diagnostics, a build-host tool request such as Entity Framework, scaffolding or WCF for its output, and a C# Interactive submission for what it printed).

## LSP subset

| Method | Notes |
|---|---|
| `initialize` / `initialized` / `shutdown` / `exit` | `initializationOptions` take the same settings as `workspace/didChangeConfiguration`. |
| `textDocument/didOpen`, `didChange`, `didClose`, `didSave` | Incremental sync (`textDocumentSync: 2`). URIs are `file://` URIs. |
| `workspace/didChangeConfiguration` | `{settings: {analysisScope: "openDocuments" \| "currentProject" \| "solution", analysisProject: "<project file>", sourceLink: "true" \| "false"}}`. | `textDocument/completion`, `completionItem/resolve` | The list sets `itemDefaults.editRange` (the span being completed). Items carry no edit; `resolve` fills `textEdit`, `additionalTextEdits` (e.g. an added `using`) and `documentation`. XAML's and Razor's own items carry their edit; `resolve` fills the `documentation` of those that name a type, a member or a component (its summary, which may come from a referenced assembly's XML file). Items in a list in suggestion mode have empty `commitCharacters`. The client announces `snippetSupport`: items with `insertTextFormat: 2` expand as snippets (M12b). Items carry `codalusGlyph` and `resolve` fills `codalusDescription` too ([classified text](#classified-text-intellisense)). |
| `textDocument/hover` | Markdown: the signature in a `csharp` code block (with its overload count), then the documentation, each section's heading ("Returns:") once. Also `codalusDescription`, the same as [classified text](#classified-text-intellisense). |
| `textDocument/signatureHelp` | Parameter labels are substrings of the signature label. The members are as the call site sees them: a generic type's type arguments are substituted (`LayoutBuilderBase<PageModel, PageBuilder<PageModel>>.AddTab(…)`, not `LayoutBuilderBase<TModel, TBuilder>`). Each signature also has `codalusParts` ([classified text](#classified-text-intellisense)). |
| `textDocument/definition`, `textDocument/implementation` | `Location[]`. Definitions in source-generated files use `codalus-generated:` URIs; symbols defined in referenced assemblies point into a decompiled document (`codalus-metadata:` URI). |
| `textDocument/documentHighlight` | Definitions are `Write`, references `Read`. |
| `textDocument/foldingRange` | `startCharacter` is the end of the first line (the fold hides the rest); `kind` is `region`, `imports`, `comment` or absent; `collapsedText` labels regions and comments. |
| `textDocument/semanticTokens/full`, `/range` | See the token legend below. Clients should ask for the visible range. |
| `textDocument/references` | `Location[]`, ordered by file and position. |
| `textDocument/prepareRename`, `textDocument/rename` | `prepareRename` returns the identifier's range and name, or null where renaming isn't possible (keywords, symbols outside the solution). `rename` returns a `WorkspaceEdit`. |
| `textDocument/codeAction`, `codeAction/resolve` | Code fixes (`quickfix`) for the diagnostics on the range's line and refactorings (`refactor`) at the range: Roslyn's built-in providers and the projects' analyzer packages' fixes. Actions are listed without edits; `resolve` returns the `WorkspaceEdit`. Nested actions are flattened ("Parent: Child"). Each diagnostic also gets "Suppress {id} with #pragma" and "Configure {id} severity: …" (writes the nearest `.editorconfig`, M12b). Actions whose title ends in `…` may need options first: see `codalus/codeActionOptions`. |
| `textDocument/formatting`, `/rangeFormatting`, `/onTypeFormatting` | Roslyn's formatter with the project's `.editorconfig`. On type: after `}` (the block) and `;` (the statement or member). |
| `workspace/symbol` | Source declarations (types and members) matching the query (camel case or substring), at most 200. Code Search (M47) asks every running language service that offers it, besides its own index. |
| `textDocument/documentSymbol` (M12a) | `DocumentSymbol[]`, nested: namespaces, types, members (fields per declarator, indexers as `this[...]`). From syntax only. `detail` is the parameter types and return type (`(int) : string`), or a property's or field's type. |
| `textDocument/prepareCallHierarchy`, `callHierarchy/incomingCalls`, `/outgoingCalls` (M12a) | Methods, properties, events and fields; accessors stand for their property. `data` is the symbol's documentation id, so items without source (an empty `uri`) can be expanded too. Incoming: callers with the call sites (`fromRanges`). Outgoing: invocations, object creations and property and event uses in the declaration. |
| `textDocument/prepareTypeHierarchy`, `typeHierarchy/supertypes`, `/subtypes` (M12a) | Supertypes: the base class (including `object`) and the directly implemented interfaces. Subtypes: direct derived classes, or for an interface its direct implementations and derived interfaces. |
| `textDocument/inlayHint` (M12a) | For a range. Parameter names (`kind: 2`, `label: "name:"`, `paddingRight`) before literal, `null`, `default` and `new` arguments, unless the method name says the name or the parameter is `value`, `obj`, `item` or `argN`. Types (`kind: 1`, `label: ": T"`) after `var` declarations, `foreach` variables and deconstructions, and before untyped lambda parameters, unless the right-hand side is a `new`, cast, `as`, `default` or literal. Clients filter by kind (settings). |
| `textDocument/codeLens`, `codeLens/resolve` (M12a) | Lenses on type and member declarations (syntax only), without commands. `resolve` counts: `N references` (command `editor.action.showReferences`) and, for interfaces, abstract and virtual members, `N implementations` (`editor.action.goToImplementation`). The arguments are the document URI and the declaration's position. |
| `textDocument/selectionRange` (M12b) | For each position, nested ranges from the token outwards: a string's content, the token, then each enclosing node, with the inside of blocks, argument and parameter lists and type bodies before the whole. Expand and Shrink Selection. |
| `textDocument/publishDiagnostics` (server → client) | Open documents: compiler and analyzer diagnostics shortly after each edit, with the document `version`. Closed files: compiler diagnostics of the whole solution from a background pass (analyzers too with `analysisScope: solution`, or in the `analysisProject` project with `currentProject`). `code` is the diagnostic id; `codeDescription.href` its help link; `tags` mark unnecessary (faded) and deprecated code. Hidden diagnostics are sent only when they mark unnecessary code, as hints. |
| `window/logMessage` (server → client) | Analyzer load failures, analyzer exceptions, project problems. |

Shapes narrowed from LSP's unions (documented on the C# types): `documentation` is always `MarkupContent`, parameter labels are strings, diagnostic codes are strings.

### Classified text (IntelliSense)

The C# service adds properties to three LSP results so the editor draws signatures and documentation in its own syntax colors, and to completion items for commit characters and target type matches ([ADR 0081](adr/0081-intellisense-popups.md)). Other clients ignore them and use the standard fields; other servers don't send them, and the editor then falls back to the label and Markdown.

| Property | On | Shape |
|---|---|---|
| `codalusParts` | `SignatureInformation` | `ClassifiedRun[]`: the label as runs. The runs of parameter *i* have `parameter: i`, and their text is that parameter's `label`. Generic type arguments are the call site's. |
| `codalusDescription` | `Hover`, a resolved `CompletionItem` | `{signature: ClassifiedRun[], sections: [{kind, text: ClassifiedRun[]}], glyph?, overloads}`. `signature` is the declaration without its overload count, which is `overloads`. `kind` is `summary`, `typeParameters`, `anonymousTypes`, `usage`, `returns`, `value`, `exceptions`, `remarks`, `captures`, `nullability` or `other`. A section's `text` has no heading: the client writes "Returns:" and the others, once. |
| `codalusGlyph` | `CompletionItem` (in the list) | The symbol's kind, finer than LSP's `kind`: `namespace`, `class`, `struct`, `interface`, `enum`, `enumMember`, `delegate`, `module`, `typeParameter`, `method`, `extensionMethod`, `property`, `field`, `event`, `constant`, `local`, `parameter`, `keyword`, `snippet`, `operator`, `label` or `text`. The completion list's icons and filters use it. |
| `codalusMatchesTargetType` | `CompletionItem` (in the list) | `true` when the item's type (a variable's or member's type, a method's return type) converts implicitly to the type expected where it goes: an argument (the active overload's parameter, as signature help picks it), the target of an assignment or initializer, a return value or expression body, an operand of `==` or `!=`. The list prefers such items and has a filter for them. C# only. |
| `codalusSoftSelection` | `CompletionItem` (in the list) | `true` on a preselected item that Roslyn doesn't select hard (its `SelectionBehavior` isn't `HardSelection`): while nothing is typed, it is selected softly, so a commit character doesn't commit it. |
| `codalusEnterKeyRule` | `CompletionItem` (in the list) | `always` or `afterFullyTypedWord`: whether Enter, after committing the item, also starts a new line (Roslyn's `EnterKeyRule`: the item's, else the language's, which is never for C# and always for Visual Basic). Absent: never. |
| `codalusCommitCharacter` | `CompletionItem` sent to `completionItem/resolve` | The character typed to commit the item. The server computes the edit for it (Roslyn's `GetChangeAsync(…, commitCharacter)`) and leaves out the description. Since M56 the editor doesn't send it: a commit never waits for the server, so the edit for the character would come after it (`TODO(issue)`: apply it late, as the item's own resolve is). The C# host still answers it. |
| `codalusIncludesCommitCharacter` | resolved `CompletionItem` | `true` when the edit already inserts the commit character, so the editor doesn't type it again. |

The C# service's list sets `commitCharacters` on an item only when Roslyn's `CommitCharacterRules` change the defaults (`allCommitCharacters`), and to `[]` on every item in suggestion mode (a new name, a lambda's parameter), where typing commits nothing.

A `ClassifiedRun` is `{text, kind, parameter?}`. `kind` is a [semantic token type](#semantic-token-legend) name, `text` for plain text, or `lineBreak` between lines. The editor colors each run as it colors that token type in code.

| `codalus/hotReload/update` (M55) | request | `{session}` → `{status: none \| ready \| blocked, updates: [{moduleId, project, metadataDelta, ilDelta, pdbDelta, updatedTypes}], rudeEdits, errors, projectsToRestart}` | The edits since the session's start or its last commit (the open documents' text included). `updates` (base64 deltas, by the module's MVID) go to the adapter's `codalus/applyChanges`; `rudeEdits` (`{id, message, location?}`, `ENC…`) need `projectsToRestart` restarted; `errors` (`blocked`) are compile errors. Hot Reload's semantics: no active statements, so a frame already in a changed method finishes in its old version. |
| `codalus/hotReload/commit`, `codalus/hotReload/discard`, `codalus/hotReload/end` (M55) | request | `{session}` → `bool` | After an update: the debugger applied it (the next one is made from it), or didn't. `end` when the program ended (a pending update is discarded first). |
| `codalus/workspaceStatus` | notification (server → client) | `{state: loading \| ready, projects, documents}` | `ready` after a background pass has compiled every project once loading ended; status bar and the `language_ready_ms` benchmark. The pass compiles projects in parallel, dependencies first and the open documents' projects first, and skips projects unchanged since the last pass (their dependent version, references and analyzers). |

**`ProjectData`** `{path, name, language, targetFramework, arguments, outputPath?, outputRefPath?, projectReferences?}` is a design-time build's result (the build host's `project/compilerInputs`, [project-protocol.md](project-protocol.md)): the compiler command line, with sources relative to the project directory. The server parses it like the compiler does. A reference to another project's output (or reference assembly), or to the assembly of a referenced project built for another target framework, becomes a project reference. Only one target framework per project is loaded: the active one, chosen in the editor's project-context picker.

**Razor files** (M16a, ADR 0023). The server also takes `.razor` and `.cshtml` documents (language `razor`). They are additional files of their projects: their text drives the Razor source generator. Completion, hover, signature help, definition, highlights and references in their C# run on the generated document and are mapped back. In markup, completion offers components, parameters and directives, and hover and definition work on components and parameters. Diagnostics are published for the Razor file. Semantic tokens (full and range) cover the whole file: the C# by Roslyn's classification of the generated documents, mapped back, and the markup with Razor's own token types (below). A tag is a `razorComponentElement` when the generated code renders that component (`OpenComponent<T>`) or writes it as a child content parameter, and a `razorTagHelperElement` when a tag helper applies to it there, in document order; a component's mapped parameter names and capitalized attributes are `razorComponentAttribute`. Other requests answer empty. Locations in Razor-generated C# are reported in the Razor file.

**Avalonia XAML** (M19a, ADR 0047). The server also takes `.axaml` documents (language `axaml`). Like Razor files they are additional files of their projects (Avalonia's targets add every `AvaloniaXaml` item), so the editor's text drives Avalonia's name generator. Completion (elements, attributes, values, markup extensions, resource keys, binding paths from `x:DataType`, selectors), hover, definition, `prepareRename`/`rename` (`x:Name`, with the code-behind's uses of the generated field), formatting and range formatting (`options.tabSize`, `insertSpaces`), folding ranges and document symbols come from the server's own XAML engine on the project's compilation. Diagnostics (source `XAML`, codes `XAML0001` to `XAML0006`: syntax, undeclared prefix, unknown type, unknown member, invalid enum value, a compiled binding's unknown path member) are published 250 ms after an edit of the file and 600 ms after other edits. Other requests answer empty.

**Projects and files.** Files of loaded projects get full semantics. Files outside any loaded project, and every file of an untrusted folder, go to a "Miscellaneous Files" project with framework references only. Open documents move between the two as projects arrive. Closed files are reloaded when they change on disk.

## Semantic token legend

Indices 0–21 are the LSP standard token types. Indices 22 and up are Roslyn classifications LSP has no name for: `delegate`, `record`, `recordStruct`, `field`, `constant`, `local`, `label`, `excludedCode`, `preprocessor`, `punctuation`, `stringEscape`, `xmlDocComment`, `controlKeyword`, `extensionMethod`, `stringVerbatim`. Then Razor's markup types, with the names the Razor language server gives them (Razor files only): `razorComponentElement`, `razorComponentAttribute`, `razorTagHelperElement`, `razorTagHelperAttribute`, `razorTransition`, `razorDirective`, `razorDirectiveAttribute`, `razorDirectiveColon`, `razorComment`, `razorCommentTransition`, `razorCommentStar`, `markupTagDelimiter`, `markupElement`, `markupAttribute`, `markupAttributeQuote`, `markupAttributeValue`, `markupOperator`, `markupComment`, `markupCommentPunctuation`. Then `xmlDocText`, the text of a documentation comment (its delimiters and names stay `xmlDocComment`). The legend is append-only. Modifiers: `static`. Tokens are single-line and don't overlap: multi-line Roslyn spans are split, and nested spans (an escape inside a string) win over their container.

Range requests matter: on the 100k-line fixture, classifying the whole document took 1.6–15 s and returned 549k tokens; a 150-line range takes 5–50 ms (ADR 0002).

## Other language servers (ADR 0016)

The same client talks to every language server: the C# host, the markup host and the servers plugins declare (`contributes.languageServers`, [plugins.md](plugins.md#languages-grammars-and-language-servers)). A server serves the [language ids](adr/0016-language-platform.md) it lists; the shell starts it when the first document of one of them opens.

**What the client sends.**
- `initialize` declares the client's capabilities: completion without snippets, Markdown documentation, offset parameter labels, no location links, prepare-rename support, code action literals, semantic tokens in the relative format with the standard legend, publish diagnostics with tags.
- It sends `rootUri` and `workspaceFolders` (the solution's folder) and the server's `initializationOptions`.
- Servers with `textDocumentSync: 1` (full) get the whole text on every change.

**What it answers.**
- `workspace/configuration` returns the settings under each requested section, as an object nested at the dots. A server's `settingsSection` is used when an item has no section.
- `client/registerCapability`, `client/unregisterCapability`, `window/workDoneProgress/create` and the `workspace/*/refresh` requests are accepted.
- `window/showMessage`, `window/showMessageRequest` and `window/logMessage` go to the Language Services log.

**Normalization.** Results are rewritten into the narrowed shapes above (`LspNormalizer`):

| From the server | Becomes |
|---|---|
| Options objects in capabilities (`hoverProvider: {}`, `textDocumentSync: {change}`, `renameProvider: {prepareProvider}`) | Booleans and the sync kind; `prepareRenameProvider` records whether rename has a prepare step. |
| A completion array; plain-string documentation; insert/replace edits; snippets | A list; Markdown; the replace range; plain text. |
| Hover contents as strings, marked strings or arrays | One Markdown string. Links that run an editor command (`command:` URIs, such as FsAutoComplete's "Open the documentation") are removed. |
| Parameter labels as `[start, end]` offsets | Substrings of the signature label. |
| `Location`, `Location[]` or `LocationLink[]` | `Location[]` (a link's target selection range). |
| A prepare-rename range or `{defaultBehavior}` | `{range, placeholder}`, or null. |
| `WorkspaceEdit.changes` | `documentChanges`. A created file becomes an edit of a new, empty file; renamed and deleted files become `resourceOperations` `[{kind: rename \| delete, uri, newUri?}]`, which the client applies after the text edits (through the build host, so project items follow). |
| Bare `Command`s among code actions; numeric diagnostic codes | Dropped; strings. |
| `WorkspaceSymbol` with only a URI | A location at the start of the file. |
| Flat `SymbolInformation[]` for `documentSymbol` (M12a) | A `DocumentSymbol` tree, each symbol a child of the innermost earlier symbol whose range contains it. |
| Inlay hint label parts; a string tooltip (M12a) | One string; plain-text markup. |
| `codeLensProvider: {}` without `resolveProvider` | `resolveProvider: false` (lenses must come with their commands). |

**Semantic tokens.** A server's legend is mapped onto ours by name; types we have no name for are left uncolored. FsAutoComplete's own types are mapped too (M36): `member` as `method`, `module` as `class`, `cexpr` as `keyword`.

**Server settings.** A server is sent the shell's settings with `workspace/didChangeConfiguration`, unless its descriptor has its own (`LanguageServiceDescriptor.Settings`): FsAutoComplete gets an `FSharp` section built from the `fsharp.*` settings (M36). `codalus/testCandidates`, `codalus/documentOptions` and the other `codalus/` requests aren't sent to servers that don't have them, or their failure is ignored.

Servers that implement `documentSymbol`, the hierarchies, `inlayHint` and `codeLens` get the Document Outline, the navigation bar, sticky scroll, the Hierarchy window, inlay hints and CodeLens (ADR 0017). The `codalus/` extensions (classified references, Go to Base, the inheritance margin, F1 help) are C# only.

## Markup host

`codalus-markuphost` (`src/Codalus.Markup.Host`, `CODALUS_MARKUPHOST` overrides) serves `json`, `jsonc`, `xml`, `msbuild`, `yaml` and `editorconfig`.
- It supports completion and hover, and publishes diagnostics 250 ms after edits.
- Initialization options (and `workspace/didChangeConfiguration` settings): `{schemaDownload, schemaCache, xmlSchemas}`, from the setting `json.schemaDownload`, the cache folder, and the setting `xml.schemas` as `[{pattern, schema}]` with absolute schema paths. XML files are validated against the local XSDs their root names with `xsi:schemaLocation` or `xsi:noNamespaceSchemaLocation` and those `xmlSchemas` associates (diagnostics `xml.schema`, and `xml.schemaLoad` for a schema that can't be read).

## Debug adapter client (M14c)

The shell is a DAP client of netcoredbg (ADR 0007) and of vscode-js-debug (ADR 0026). M14c (ADR 0039) adds:

- **`runInTerminal`.** When the shell has a terminal, `initialize` sends `supportsRunInTerminalRequest: true`. The reverse request is answered after the program starts in a new integrated terminal, with `{processId}`. Its `env` values of `null` unset variables. netcoredbg never sends it.
- **Programs held for the debugger.** Because netcoredbg can't `runInTerminal`, the shell starts a program in the terminal itself and netcoredbg attaches to it. The program's environment carries:
  - `DOTNET_STARTUP_HOOKS`: `Codalus.Debugging.StartupHook.dll` (in `debughost/`), before any hooks already set;
  - `CODALUS_DEBUG_WAIT`: an empty temporary folder.

  Before `Main`, the hook writes the process id to `<folder>/pid` (through `pid.tmp`, renamed) and polls for `<folder>/go`. The shell attaches, sets the breakpoints, waits for the program's module, and creates `go`; the hook then deletes the folder. `CODALUS_DEBUG_WAIT_SECONDS` (default 120) bounds the wait. The hook clears `CODALUS_DEBUG_WAIT` and `CODALUS_DEBUG_WAIT_SECONDS`, so the program's child processes don't wait.
- **Pipe transports.** On another machine, netcoredbg runs as `sh -c 'exec <path>/netcoredbg --interpreter=vscode'` through `ssh -T <destination>`, `<container tool> exec -i <container>` or `wsl.exe -d <distribution> --exec`. DAP flows over that process's stdin and stdout unchanged. Source paths are translated on the client (`PathMappingDebugAdapter`): `setBreakpoints` sources, and `source.path` in stack frames, `breakpoint` events and `output` events.
- **The Codalus debugger's requests** (M55, [ADR 0086](adr/0086-a-managed-coreclr-debugger.md)): `codalus-debughost --clr-dap` answers two requests of ours beside DAP's. `codalus/hotReloadCapabilities` (`{}` → `{capabilities}`) is what the debugged runtime can apply, by its version (CoreCLR's own list: the generic ones from .NET 7, `AddFieldRva` from .NET 10; empty for the .NET Framework). `codalus/applyChanges` (`{updates: [{moduleId, metadataDelta, ilDelta, pdbDelta}]}` → `{results: [{moduleId, status: applied \| pending \| failed, message?}]}`) applies the language host's deltas through `ICorDebugModule2::ApplyChanges`, stopping a running program for it, reads the PDB delta for the new version's lines and locals, and binds the breakpoints again in it. A module the program hasn't loaded yet keeps its deltas (`pending`) and takes them, in order, as it loads. A module loaded before an attach takes edits only when the program runs with `DOTNET_MODIFIABLE_ASSEMBLIES=debug`; otherwise `failed` with `CORDBG_E_ENC_MODULE_NOT_ENC_ENABLED`.
- **`CODALUS_NETCOREDBG_LOG=<folder>`** starts netcoredbg with `--engineLogging=<folder>/netcoredbg-<time>-<id>.log`, its DAP traffic, for diagnosis.
