# M44 checkpoint: MAUI on Windows and WinUI 3

Date: 2026-10-16. The Windows desktop phase's MAUI and WinUI milestone (D31, decided 2026-10-16: Windows-only features, the other OSes decided later), taken ahead of M41 at the maintainer's request. Decisions: [ADR 0074](../adr/0074-maui-on-windows-and-winui.md) (it amends ADR 0064, where MAUI's Windows target was out of scope, and ADR 0071's XAML dialects).

## Done

**Projects on every OS** (build host):
- **`ProjectInfo.UsesWinUI`** (`UseWinUI`) and **`ProjectInfo.WindowsPackageType`** (the Windows framework's evaluation, so MAUI's multi-targeted projects report theirs); **`RunInfo.WindowsPackageType`** and **`RunInfo.AppxManifest`** (`FinalAppxManifestName`, the `AppxManifest.xml` a packaged build writes).
- **WinUI off Windows:** WinUI's XAML compiler is a .NET Framework program the SDK runs as an executable, and its design-time pass (`DesignTimeMarkupCompilation`) failed the whole design-time build on Linux. There the build host now gives a WinUI project's design-time build the global property `CustomAfterDirectoryBuildTargets` (imported right after the package targets) pointing at a file it writes once (`Codalus.WinUI.DesignTime.targets`, an empty `DesignTimeMarkupCompilation`), and `WindowsAppSDKSelfContained=false` (a self-contained Windows App SDK needs a Windows runtime identifier). The project loads with WinUI's references and its `Page` and `ApplicationDefinition` XAML as additional files. The design-time cache's schema is now `codalus-designtime-3`. On Windows nothing changes.

**Where they run** (workbench, shell):
- **`MobileTargets`:** the Windows platform runs on Windows; **"Windows Machine"** (`MobileDeviceKind.ThisPc`) is in the device list there; with no framework chosen, runs on Windows go to the Windows framework, as other IDEs start MAUI apps; `maui-windows` joins the workloads and Check Environment.
- **The device picker** (`DevicePickerItems`): on Linux and macOS a project with a Windows framework lists "Windows Machine" marked "Windows only", visible but not a choice (picking it says why).
- **`WindowsDesktopProjects`:** WinUI projects run only on Windows and **build** only there (`BuildsOnlyOnWindows`): off Windows, Start, Start Without Debugging, Build and Rebuild say "*WinUIApp is a WinUI 3 project: it builds, runs and debugs only on Windows (WinUI's XAML compiler is a Windows program). On this OS it opens and edits, with XAML IntelliSense.*" and build nothing.

**Unpackaged apps** (`WindowsPackageType=None`): WinUI projects take the usual paths (build, `RunCommand`, netcoredbg, `dotnet watch`). MAUI's Windows target (`StartWindowsTargetAsync`) builds that framework alone (`TargetFramework` as a build property, so the other platforms' workloads aren't needed), then runs or debugs `RunInfo` for it, or runs `dotnet watch run --framework <tfm>` (`RunService.HotReloadPlan`'s new framework).

**Packaged apps** (`WindowsPackageType=MSIX`; `ShellHost.WindowsApps.cs`, `WindowsApps`):
1. **Developer Mode** (`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock`) first: off, the IDE says why it's needed (or `WindowsPackageType=None`), offers **Open Settings** (`ms-settings:developers`, through the new `ShellIntegration.OpenWindowsSettings`), and builds nothing.
2. The build, then the layout's manifest (`AppX\AppxManifest.xml`, else the build's `AppxManifest.xml`).
3. **Registration:** `powershell.exe … Add-AppxPackage -Path '<framework msix>'` (a higher version already installed, `0x80073D06`, is fine), then `Add-AppxPackage -Register '<manifest>' -ForceApplicationShutdown -ForceUpdateFromAnyVersion` (`-DependencyPath` with `-Register` takes layouts only: `0x80073CF9` for an `.msix` on the first Windows run), the Windows App SDK runtime's framework package from the restored `Microsoft.WindowsAppSDK.Runtime` (`tools\MSIX\win10-<arch>`). The command and its output go to the Run channel; a failure says so with a hint (Developer Mode, `0x80073CFF`; a missing dependency, `0x80073CF3`).
4. **Activation:** the AUMID from the manifest (the package family name, with the publisher id computed as Windows does: SHA-256 of the publisher in UTF-16LE, 8 bytes, Crockford's base 32; `!App`), started by **`codalus-debughost --activate-app <AUMID> [--arguments …]`** (`AppActivation`, source-generated COM: `IApplicationActivationManager::ActivateApplication`), which prints the process id. Why the debug companion: it ships in every package, already starts debug-related processes, and keeps COM interop out of the Native AOT shell.
5. **Start Without Debugging** follows the process (`RunService.Track`: running until it exits; Stop ends it); **Start** attaches netcoredbg (`DebugService.AttachAsync`). **Hot Reload** says it isn't available for packaged apps.
- Launch profiles with `"commandName": "MsixPackage"` (MAUI's and WinUI's templates) are runnable.

**Check Environment** (on Windows, with Windows App SDK apps in the solution): **Developer Mode** when an app is packaged (fix: the Settings page); the **Windows App SDK runtime** of each `Microsoft.WindowsAppSDK` channel, from `Get-AppxPackage Microsoft.WindowsAppRuntime.*` (fix: winget's `Microsoft.WindowsAppRuntime.<channel>`, or the download page).

**WinUI XAML editing** (C# host, ADR 0074; `XamlContext.IsWinUI`, `IsWpfStyle` for what WPF and WinUI share): a `.xaml` file is WinUI's when its compilation references WinUI and not Avalonia, and not MAUI unless the file is under `Platforms/Windows`. WPF's, MAUI's and Avalonia's files keep their dialects (their tests pass unchanged).
- **Types and members:** the presentation namespace maps to `Microsoft.UI.Xaml`'s namespaces (WinUI has no `[XmlnsDefinition]`), `using:` to the project's; the projection's attached properties (static `XxxProperty` properties with `GetXxx`: `Grid.Row`, `ToolTipService.ToolTip`, `VisualStateManager.VisualStateGroups`), user dependency properties, `[ContentProperty(Name = …)]`, `Microsoft.UI.Colors` and `FontWeights`.
- **`x:Bind`:** paths from the page's class (named elements first, members of any access) or the closest data template's `x:DataType`; properties, fields and methods. A member that isn't there is an **error** (`XAML0006`, as WinUI's `WMC1110`); function bindings, casts, attached properties and static paths aren't checked. Completion, hover and Go to Definition follow the same rules. `{Binding}` paths stay warnings, from `d:DataContext` or a data template's `x:DataType`.
- **Directives:** `x:Load` (Boolean or `x:Bind`, checked), `x:DefaultBindMode` (checked, completed), `x:Phase`, `x:Uid`, `x:FieldModifier`, `x:DataType`.
- **Markup extensions** `x:Bind` (with `Mode`, `BindBack`…), `Binding`, `StaticResource`, `ThemeResource`, `CustomResource`, `TemplateBinding`, `RelativeSource`, `x:Null`; WinUI's `BindingMode`, `UpdateSourceTrigger` and `RelativeSourceMode` values.
- **Resources:** keys from the file, `App.xaml` and the dictionaries merged by `ms-appx:///` (the project's root; a library's under its assembly name) or relative sources, completed and navigated, never reported missing (the framework's theme resources aren't listed in any file). A dictionary's `Source` completes as `ms-appx:///…`.
- **WinUI's XAML compiler errors** (`WMC…`) map to their files from builds (`XamlBuildDiagnostics` takes any `.xaml`) when they name one. From `dotnet`'s MSBuild they don't: the Windows App SDK's `XamlCompiler.exe` embeds its messages as `Microsoft.Windows.UI.Xaml.Build.Tasks.ErrorMessages.resources` and looks them up as `Microsoft.UI.Xaml.Markup.Compiler.ErrorMessages`, so every error comes back as `WMC9999` ("Could not find any resources…") on the compiler task's line in the package's targets (the first Windows run; 1.8.260528001 through 1.8.260803003 and 2.3.9 alike). Its in-process task, which has the messages, isn't instantiated by .NET's MSBuild (`MSB4061`, `CompileXaml..ctor` not found).

**Templates and items:** no template pack (the only MIT one, `VijayAnand.WinUITemplates` 1.0.3, makes Windows App SDK 1.2 projects with `win10-*` runtime identifiers, which .NET 8 and later reject), so New Project has no WinUI template (a gap). **Add New Item** has **Blank Window**, **Blank Page**, **User Control** and **Resource Dictionary (WinUI 3)** built in (`ItemTemplateProject.IsWinUI`, from `UseWinUI`), with `using:` for the folder's namespace and the code-behind nested.

**Fixtures:**
- `samples/WindowsDesktop/WinUIApp` ([README](../../samples/WindowsDesktop/README.md)), `WinUIApp.slnx`: a WinUI 3 app on Windows App SDK 1.8.260529003 (the version MAUI 10.0.110 uses), `net11.0-windows10.0.19041.0`: `App.xaml` merging `XamlControlsResources` and `ms-appx:///Themes/Colors.xaml`, `MainWindow.xaml` hosting `MainPage.xaml` (`x:Bind` with modes, a function binding, a named element, `x:Load`, `x:DefaultBindMode`, a typed data template, theme and static resources, attached properties, an event handler), a user control with two dependency properties. Unpackaged and self-contained by default (with this machine's runtime identifier on Windows); `WinUIAppPackaged=true` makes it MSIX.
- `samples/Maui/TodoApp`: `net10.0-windows10.0.19041.0` on Windows (as the template conditions it; `net10.0` like the fixture's other frameworks), unpackaged, with `Platforms/Windows` (`App.xaml`, the manifests) and a "Windows Machine" launch profile.

## Tests

- **Language host integration** `WinUIXamlTests` (5, on `WinUIApp.slnx` in the real build and C# hosts, **every OS**: the Windows App SDK restores everywhere): no false alarms in the five XAML files; `x:Bind` errors from the page, a data template, a named element and `x:Load`, unknown types, `x:DefaultBindMode` values, setter properties, and no report for an unknown resource; elements, attributes (the projection's attached properties, WinUI's directives), values (enums, colors, font weights, bind modes), `using:` namespaces; markup extensions, resources through `App.xaml` and `ms-appx:///`, `x:Bind` paths (members, methods, named elements, the view model's, the data template's), `Mode`, `BindBack`, dictionary sources; hover and definition (WinUI's types, `x:Bind` into the page and the view model, the user control, a resource, an event handler).
- **Build host integration** `WindowsDesktopTests` (2 new, every OS): the design-time targets written off Windows only; the WinUI fixture loads (flags, `WindowsPackageType`, items, XAML as additional files, run info) and, switched to packaged, reports MSIX with its `AppxManifest.xml`. On Windows (skipped elsewhere) it also builds, and a planted `x:Bind` error fails the build with the compiler's `WMC9999` (its message lost, above), not in `MainPage.xaml`.
- **Workbench** `WindowsAppsTests` (11): which projects are Windows App SDK apps and packaged, `MsixPackage` profiles; the Windows target and "Windows Machine" per OS, the choice rule, `maui-windows`; the device list per OS; publisher ids (Microsoft's `8wekyb3d8bbwe`, the fixture's `b1n3b429t8b64`), manifests and AUMIDs (the fixture's own); the layout to register; the framework packages, PowerShell's quoting, the activation's arguments and output, failure hints; Developer Mode, runtimes from `Get-AppxPackage`'s JSON, Check Environment's rows and plans; Hot Reload's framework; WinUI's items; `WMC` errors as squiggles. `MobileTests` gains the Windows rules.
- **Debugging** `AppActivationTests` (2): `--activate-app`'s usage, "only on Windows" off Windows (exit 3), Windows' refusal of an id no package has on Windows (exit 1), in process and as the companion's process.
- **Headless UI** `WinUIShellTests` (5): every OS: the fixture opens as WinUI with `x:Bind` completion, off Windows Start, Start Without Debugging and Build say Windows only and build nothing, and Add New Item makes a WinUI page with its code-behind; the device picker's "Windows Machine" (Windows only on Linux; current on a stand-in Windows); a packaged app explains Developer Mode first and opens its Settings page, with no Hot Reload. Windows only (skipped here): the unpackaged app runs, runs under `dotnet watch`, and F5 stops at a breakpoint in the view model; with Developer Mode (skipped with that reason on a runner without it) the packaged app is registered, started by Windows, followed and stopped, then attached to and paused, and the test removes the package afterwards. `MobileShellTests` choose Android explicitly on Windows, where the fixture now targets Windows too.
- **Smoke** `maui.windows` (Windows; skipped elsewhere): the WinUI fixture opens, `MainPage.xaml` completes an `x:Bind` path (`winui-xaml.png`), and Start Without Debugging builds and runs the unpackaged app until it's stopped.

- A WinUI previewer (Microsoft has none either) and XAML Hot Reload, by design; UWP stays a non-goal.
