# M20a checkpoint: .NET MAUI devices, runs, workloads and XAML

Date: 2026-10-15. The first part of M20 (D6: go, for Android, iOS and Mac Catalyst). Codalus IDE now does the following for MAUI apps:
- loads them and knows where they can run;
- installs what they need, with the user's consent;
- runs them on a device, emulator or simulator through the platform SDK's own `Run` target;
- edits their XAML with the M19 engine.

The debugger is M20b (the Mono soft-debugger adapter). ADR 0064 records the decisions.

## Done

**Projects** (build host): `ProjectInfo.UsesMaui` (`UseMaui`), and `ProjectInfo.MissingWorkloadPacks` (the SDK's `MissingWorkloadPack` items from the evaluations: what the project needs and the SDK lacks). MAUI's item types (`MauiXaml`, `MauiImage`, `MauiFont`…) and the platform items show in the Solution Explorer.

**Devices and runs** (workbench `Mobile/`):
- **`MobileTargets`:**
  - target frameworks → platforms (`net10.0-ios18.0` → iOS);
  - where each runs (Android everywhere, iOS and Mac Catalyst on macOS, WinUI out of scope);
  - the framework a run uses (the active one when this machine runs it);
  - the workloads a project needs (MAUI's or the bare platform's, and `maui` covers them all);
  - the run arguments: `dotnet build <project> -t:Run -f <framework>`, with `AdbTarget=-s <serial>`, `_DeviceName=:v2:udid=<udid>` for a simulator, or `RuntimeIdentifier=ios-arm64` plus `_DeviceName` for an iPhone;
  - `InstallAndroidDependencies` with the SDK and JDK folders and the license acceptance.
- **`AndroidToolchain`:**
  - the SDK, found from the setting, `ANDROID_HOME`/`ANDROID_SDK_ROOT`, Android Studio's folder, then the distributions' folders;
  - the JDK, found from the setting, `JAVA_HOME`, then the Microsoft, Adoptium, `/usr/lib/jvm` and macOS folders (newest first), then Android Studio's runtime;
  - `adb` and the emulator;
  - Check Environment rows with the SDK platform and the JDK version.
- **`MobileDevices`** parses:
  - `adb devices -l` (emulators, devices, and the unauthorized, offline and no-permission states with what to do);
  - `adb emu avd name`;
  - `emulator -list-avds`;
  - `simctl list devices available --json` (iOS runtimes only, newest first);
  - `devicectl list devices --json-output` (unpaired devices say so).
- **`AppleSigning`:** identities from `security find-identity -v -p codesigning` (with their team), and provisioning profiles from both profile folders. The plist is read out of the CMS envelope; each profile has its team, application identifier with wildcards, and expiry.
- **`MobileService`:**
  - the device list;
  - the device per platform (an emulator remembered by its AVD, so the choice survives its start);
  - starting an emulator and waiting for `sys.boot_completed`;
  - booting a simulator and opening the Simulator app;
  - `dotnet workload list`;
  - the run and install plans, with `ANDROID_HOME`, `JAVA_HOME` and `USER` (the workload's SDK installer fails without `USER`, as in containers).
- **Settings:** `android.sdkDirectory`, `android.jdkDirectory` (user).

**The shell** (`ShellHost.Mobile.cs`, `BuiltIns.Mobile.cs`, `DevicesViewModel`):
- **The toolbar's device picker,** next to the startup project when it's a mobile project. It lists the platforms' devices; choosing another platform's device switches the active framework. The choices are kept in the solution's session.
- **Start and Start Without Debugging** on a mobile project check, in order:
  1. the workloads (an offer to run `dotnet workload restore` in the terminal);
  2. the Android SDK and JDK (an offer to install them);
  3. the device (an emulator that isn't running is started).

  Then `dotnet build -t:Run` runs in the project's Run channel, and Stop ends it. Start says that the debugger isn't available yet and runs without it.
- **The Devices window:** devices with the runs' target marked; Start, Run Here, Refresh, and Install the Android SDK; the SDK and JDK paths.
- **Commands:** `mobile.selectDevice` (Debug → Other Debug Targets), `mobile.showDevices` (View → Other Windows), `mobile.refreshDevices` and `mobile.installAndroidSdk`. The context keys are `mobileStartup` and `mobileProjects`.
- **Installing the Android SDK:** a dialog with the exact command, the folders and the Android SDK's license link. It runs the workload's target in an output channel, then records the folders in the settings.
- **Help → Check Environment** lists each workload the solution's mobile projects need (`dotnet workload install <id>` in the terminal), the Android SDK and the JDK.
- **The New Project dialog** lists the MAUI templates with readable names (`maui`, `maui-blazor`, `mauilib`, `android`, `ios`) when the workload brings them.

**MAUI XAML** (C# host, the M19 engine with a dialect):
- **When it applies:** the compilation references `Microsoft.Maui.Controls`.
- **Properties:**
  - bindable properties with CLR wrappers (the wrapper's type), and those without;
  - attached properties as a `BindableProperty` field with a static `Get…` (MAUI's, `Grid.Row`, and the project's own);
  - `[ContentProperty("…")]` on the class.
- **Markup extensions:** `IMarkupExtension` and `BindingBase`.
- **Values:** `Colors`' named fields for `Color` and brushes; `BindingMode`.
- **Namespaces:** the XAML 2009 `x:` namespace is read as 2006's. `xmlns` completion offers MAUI's namespaces and `clr-namespace:` for the project's. Bindings under `x:DataType` are always compiled.
- **Files:** `.xaml` files are the new `xaml` language, colored as XML and served by the C# host. Their projects pass them as additional files (`MauiXaml`).

**Fixture** `samples/Maui`:
- `MauiViews`, a plain `net10.0` library with `Microsoft.Maui.Controls` 10.0.110: a page with compiled bindings, an item template, attached properties, a named element and an event; a view model; a model; a control with a bindable and an attached property. It builds without workloads.
- `TodoApp`, the MAUI app, from `dotnet new maui`, trimmed: Android, plus iOS and Mac Catalyst on macOS; platform files under `Platforms/`.
- `MauiViews.slnx`, the library alone, for the C# host's tests.

**Tests:**
- **`MobileTests`** (workbench, 6):
  - frameworks, platforms and workloads;
  - the run and install arguments;
  - recorded output of `adb`, the emulator, `simctl` and `devicectl`;
  - identities and a profile in a CMS-like envelope;
  - finding the SDK and JDK on each OS;
  - the service with stand-in tools: devices, a choice that survives the emulator's start, `dotnet workload list`, and the plans.
- **`MauiXamlTests`** (C# host, 3, on `MauiViews.slnx`):
  - no false alarms, and errors (an unknown attribute and type, a binding path the data type lacks);
  - completion of elements, properties, events, attached properties (MAUI's and the library's), values, compiled binding paths in the page and the item template, and `xmlns` values;
  - hover, and definitions into the view model, the control and the code-behind.
- **`MobileShellTests`** (shell, 2, on `samples/Maui`):
  - the app is a MAUI project with a device picker, its missing packs agree with `dotnet workload list`, `.xaml` is XAML, Check Environment has the workload, SDK and JDK rows with fixes, and the Devices window shows;
  - with stand-in tools, the run goes to the emulator through `-t:Run` with its serial and the SDK, or, without the workload, offers to install it.
- **The smoke step `maui.devices`:**
  - the MAUI solution opens, and TodoApp has the device picker;
  - `TodoPage.xaml` completes the view model's members;
  - the Devices window shows, and its screenshot is `maui-devices.png`.
