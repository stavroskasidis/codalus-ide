## Done

**The diagnostic port in the override** (`Workbench/Containers/ComposeApp.cs`, `Shell/ShellHost.Compose.cs`): on Linux, with the engine on this machine's kernel (Docker or Podman; not an engine in WSL), each .NET service fast mode runs mounts `.codalus/state/<solution>/diag` at `/codalus-diag` and gets `DOTNET_DiagnosticPorts=/codalus-diag/<service>.sock,connect,nosuspend` (after a port the compose file names), debugged or not. The folder is `rwx--x--x`: the service's user (`$APP_UID`) passes through it to the socket. A debugged program gets the variable in its launch's environment; the debugger and its companion in a container start without it (`RemoteShell`: the Codalus debugger is a .NET program, whose runtime would connect first). Off Linux neither is added.

**Why the runtime connects and the IDE listens** (ADR 0102): a runtime's own listening socket is 0600 for the image's user, which the IDE's user can't open; the host's socket is opened to every user, and a connecting runtime needs no discovery (the socket has the service's name). `nosuspend`: the runtime retries while nothing listens, without waiting, so the profiler attaches whenever asked and no container is recreated; suspending would hold a restarted service until a resume nobody sends. So a service is profiled **attached**, not from its start, and the UI says so.

**The diagnostics host by socket** (`Diagnostics.Host/Sessions/PortConnections.cs`, `DiagnosticsPort.cs`; protocol 2 in [diagnostics-protocol.md](../diagnostics-protocol.md)): `diag/counters/start`, `diag/trace/start` and `diag/heap/snapshot` take `diagnosticPort`. The host listens there with `DiagnosticsClientConnector.FromDiagnosticPort("<path>,listen")` (the client library's public way to a socket; `DiagnosticsClient` takes a process id only), opens the socket to every user, binds a path too long for a socket through a link to its folder in the temp folder, shares one listener among a socket's sessions and closes it with the last, so a restarted service's new runtime is accepted by the next start. Nothing connecting in 30 s says why (no fast mode, or Docker Desktop's file sharing).

**The profiler** (`Shell/ShellHost.Profiling.cs`, `ViewModels/ProfilingViewModels.cs`): the Performance Profiler's running-process list starts with the fast-mode services (`back (compose service)`) for every tool but File I/O and the full dump; **Profile Compose Service…** (`containers.composeProfileService`, Debug → Other Debug Targets) starts CPU Usage and .NET Counters on one; a session's target is `service`. M60's agent tools: `profile_start` and `memory_snapshot` take `service` (a small change, done).

**M21a's deferred remote profiling** is closed for containers where it applies: a compose service fast mode runs, from a local window, on a Linux engine. It stays open for the Container (Dockerfile) launch profile, remote windows, and Docker Desktop.
