# M22c checkpoint: plugin distribution on NuGet

Date: 2026-10-13. Decision: [ADR 0060](../adr/0060-plugin-distribution.md). Follows M22a ([m22a](m22a.md)) and M22b ([m22b](m22b.md)). M22d remains: the Components page with an offline layout, and plugin performance attribution.

## Built

**The package**: NuGet type `CodalusPlugin`, the plugin under `plugin/`. The template's project packs one (`dotnet pack`: build output without the API, `PackageId` and `Version` as in the manifest).

**The gallery** (workbench `Plugins/`):
- `PluginGallery` is a NuGet v3 client on `HttpClient`: the service index, `SearchQueryService` with `packageType=CodalusPlugin`, and `PackageBaseAddress` for versions and downloads.
- `PluginInstaller` checks the signature with `dotnet nuget verify --all` when the source requires one, and reads the `.nuspec` (type, id, version, authors).
- It extracts `plugin/` into staging, refusing paths outside it, and reads the plugin as an installed one would load (`PluginDescription.Read`). The id and version must match.
- A new plugin moves into `<data>/plugins/<id>/` and loads at once. An update or uninstall waits in `.pending.json`; `ApplyPending` runs first in plugin discovery.
- `PluginStore` searches every source, downloads, installs, checks for updates and stages them. Gallery plugins remember their source in `.codalus-source`.

**The Plugin Gallery window** (Tools → Browse Plugins…, `ShellHost.PluginGallery.cs`, a declarative view):
- Search, a version picker, and Install. A dialog first shows the source, authors, signature and declared permissions, saying they aren't enforced.
- Updates, with Update All, and the plugins installed from galleries, with Uninstall.
- The changes waiting for a restart, with Cancel This Change and Restart Now.
- Settings: `plugins.sources`, `plugins.requireSignature` (`nugetOrg`, `all`, `none`), `plugins.autoUpdate` and `plugins.prerelease`.
- At startup, at most once a day, gallery plugins are checked. With auto-update the newer versions are staged and the user is told; **Check for Plugin Updates** checks now.

**Permissions**: the manifest's `permissions` (`network`, `processes`, `fileSystem`, `secrets`). An unknown one is a warning.

**Per workspace**: `plugins.disabled` may be set in a workspace's settings too, and the lists add up. A plugin turned off for the open workspace isn't activated there.

**Bisect Plugins** (`plugins.bisect`, `PluginBisect` and `ShellHost.PluginBisect.cs`):
- Each round turns half of the suspects off for the workspace (the user's settings with no folder open) and restarts. A notification asks Still There / Gone / Stop.
- It ends with the culprit, offering to turn it off, and the original list back. The state survives restarts in `<state>/plugin-bisect.json`.

## Tests

- **Plugins**:
  - `PluginStoreTests` against `MockNuGetFeed` (`tests/Shared`, a v3 feed of packages built in memory): search filtered by package type, with versions and authors; install now and update at the next start; uninstall and cancel; permissions and the unknown-permission warning; unsigned packages refused when a signature is required (a stand-in verifier), and the signing policy per source; a package whose manifest isn't its id refused.
  - `PluginBisectTests`: the culprit in three rounds for eight plugins wherever it is; one plugin; stop; the state's file.
  - `PluginTemplateTests` now also packs the generated plugin and opens it with the installer.
- **Headless UI** `PluginGalleryTests`: search, details, the permissions dialog, install (its setting appears at once), uninstall waiting for a restart.

**Validation**: Windows green on the affected classes. The full suite and the other OSes come with the push (CI runs all three).
