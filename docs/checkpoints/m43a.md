# M43a checkpoint: .NET Framework projects, builds, IntelliSense and running

Date: 2026-10-17. The first part of M43, the last milestone of the Windows desktop phase (D31, decided 2026-10-16: Windows-only features, the other OSes decided later; M43 with its debugger). Decisions: [ADR 0075](../adr/0075-net-framework-projects-and-builds.md) (it amends ADR 0004, 0006, 0012 and 0030). M43b (the desktop-CLR debugger, after its spike, and tests on VSTest's .NET Framework hosts) follows.

## What M43a found first

- **SDK-style `net4x` projects already built on Linux** with the .NET 11 RC2 SDK: the SDK adds `Microsoft.NETFramework.ReferenceAssemblies` (MIT, 1.0.3) to the restore wherever the targeting pack is missing, Roslyn's targets default to C# 7.3, and `UseWindowsForms` works for `net48` without `EnableWindowsTargeting`. The package is added in a target (`IncludeTargetingPackReference`), so evaluations don't see it, and its targets add an `mscorlib` reference that the Dependencies node showed as an assembly.
- **Old-style projects** evaluate with the SDK's `Microsoft.CSharp.targets` but fail in `GetReferenceAssemblyPaths` (MSB3644). Their `TargetFrameworkIdentifier` is empty until the common targets default it, after `CustomBeforeMicrosoftCommonTargets` and before `FrameworkPathOverride` is computed: that's where the reference assemblies can be given to them.
- **`dotnet restore -p:RestorePackagesConfig=true` restores nothing** ("Nothing to do"): `packages.config` restore is in the classic IDE's and nuget.exe's NuGet only.
- **MSBuild's project collections read the environment when they're created:** the first attempt set the global packages folder after the session's collection existed, and evaluations didn't see it (design-time builds, whose nodes get the environment per build, did).
- **A `net472` project can't reference a `net48` one** (the fixture's library targets both).
- **The SDK's templates don't target .NET Framework;** `--target-framework-override net48` gives code C# 7.3 rejects (top-level statements, implicit usings, nullable).

## Done

**SDK-style `net4x` projects** (build host): the usual path on every OS. The Dependencies node shows the reference assemblies package under Frameworks, from the assets file (or the installed framework's moniker when the Developer Pack was used), and hides the `mscorlib` reference the package's targets add.

**Non-SDK-style projects** (build host, `ProjectEvaluator.EvaluateNonSdk`, `NetFramework`):
- **Load** for .NET Framework instead of "Only SDK-style projects are supported": `ProjectInfo.IsNonSdkStyle`, one evaluation, the moniker of `TargetFrameworkVersion` as the framework (`v4.7.2` → `net472`, `v3.5` → `net35`), their items, and Dependencies of the framework (`Microsoft.NETFramework.ReferenceAssemblies.net472` 1.0.3, or the installed `.NETFramework,Version=v4.7.2`), the `packages.config` packages (their folder in the repository path, resolved once there), the `<Reference>` items (hint paths resolved when the file is there) and project references. `UsesWindowsForms`/`UsesWpf` from their references. Other non-SDK-style projects stay unsupported, saying why.
- **Reference assemblies:** at start the build host writes `Codalus.NetFramework.targets` (temp folder) and sets `CustomBeforeMicrosoftCommonTargets` to it (unless the user's environment sets it) and `CodalusNuGetPackageRoot` to the solution's global packages folder, as environment variables before any project collection exists. For a non-SDK-style .NET Framework project without installed reference assemblies (`GetPathToStandardLibraries` empty: a Developer Pack wins) the file sets `TargetFrameworkRootPath` to the package's `build/` folder, turns off `FrameworkPathOverride`, sets `NoStdLib` and references `mscorlib` (implicitly defined), as the package's targets do for SDK-style projects. Evaluations, design-time builds, builds and their nodes all see it.
- **Restore** (`SolutionSession.NetFramework`, `NuGetClient.InstallAsync`): after `dotnet restore`, on open, Restore and before builds that restore, the build host installs the missing `packages.config` packages into the repository path (NuGet's `repositoryPath`, else `packages` next to the solution; packages.config's layout; the global packages folder first, then the solution's sources with package source mapping and credentials) and the reference assemblies packages into the global packages folder (its v3 layout), through the SDK's NuGet libraries. Each package is a restore output line; failures fail the restore with a count. The projects are evaluated and design-time built again; the design-time cache's fingerprint now includes `packages.config` and the hint paths' files. Restore on open isn't skipped while a non-SDK-style project lacks packages.
- **The classic IDE's own targets** (`ProjectInfo.CannotBuildReason`): an import (not `Condition="false"`) whose expanded path is under `Microsoft/VisualStudio` and doesn't exist. The project loads; its design-time build loads it with missing imports ignored (`DesignTimeBuilder.Request.IgnoreMissingImports`, a `ProjectInstance`), so it has IntelliSense; solution builds and restores leave it out (the build filter that leaves out compose projects) with "*LegacyWebApp is left out of the build. LegacyWebApp imports the classic IDE's own MSBuild targets (WebApplications/Microsoft.WebApplication.targets), which come only with the classic IDE and its Build Tools. It opens and edits here, but doesn't build: Codalus IDE builds with the .NET SDK's MSBuild, and the classic IDE's is proprietary.*"; building it alone fails with the reason.
- **Run information:** a non-SDK-style project's `RunInfo.TargetFramework` is its moniker; its `TargetPath` (the `.exe`) starts, as it has no `RunCommand`. The design-time result names the moniker too (`Request.FrameworkLabel`).

**Running** (workbench `NetFrameworkProjects`, `WindowsDesktopProjects`, `DotnetFrameworks`; shell `ShellHost.NetFramework.cs`):
- .NET Framework projects (non-SDK-style, or every framework .NET Framework's) **run only on Windows**: off Windows, Start, Start Without Debugging, multiple startup projects and the profiler say "*ConsoleApp targets .NET Framework (net48): it runs, debugs and tests only on Windows (running it on Mono isn't supported). On this OS it opens, edits and builds.*" and build nothing.
- **On Windows**, Start Without Debugging builds and starts the `.exe` (the SDK's `RunCommand`, or an old-style project's target path) on the desktop CLR; `RuntimeSelection` leaves .NET Framework programs alone (no `DOTNET_ROOT`).
- **F5 on Windows** says "*… debugging the desktop CLR comes in a later release. Start Without Debugging (Ctrl+F5) runs it now.*" with a **Start Without Debugging** button, and builds nothing (netcoredbg debugs CoreCLR only; M43b).
- **Hot Reload** says "*Hot Reload needs .NET 6 or later: ConsoleApp targets net48 (.NET Framework).*"; `DefaultCSharpVersion` is 7.3 for .NET Framework.
- **The test plugin** leaves out test projects whose every framework is .NET Framework's off Windows: "*… targets .NET Framework (net48): its tests run only on Windows.*" On Windows they take the usual VSTest path, unvalidated until M43b.

**Convert to SDK-style** (workbench `SdkStyleConverter`, shell `ConvertToSdkStyleAsync`; command `project.convertToSdkStyle`, "Convert to SDK-Style…", on the context menu of non-SDK-style projects, context key `explorerProjectNonSdkStyle`):
- Our own converter in the spirit of try-convert (MIT; its approach, none of its code), pure (XML and file reads): `Microsoft.NET.Sdk`, `TargetFramework`, `OutputType`, `RootNamespace`/`AssemblyName` when they differ from the file name, `UseWindowsForms`/`UseWPF` from the references, `Platforms` for configurations other than AnyCPU.
- Left out: `ProjectGuid`, `ProjectTypeGuids`, `FileAlignment`, the classic IDE's test project properties, ClickOnce's (with a note), the SDK's defaults (`Deterministic`, `AutoGenerateBindingRedirects`, `WarningLevel` 4, `ErrorReport`, and per configuration `PlatformTarget`, `DebugSymbols`, `DebugType` (note), `Optimize`, `OutputPath`, `DefineConstants`); the other configuration properties stay in a normalized conditioned group.
- Items: globbed `Compile`, `EmbeddedResource`, `None` (and WPF's `Page`/`ApplicationDefinition`) left out; with metadata, an `Update` (conventional `SubType` and `DependentUpon` dropped: `X.Designer.cs` upon `X.cs`, `X.resx` upon `X.cs`); linked, outside or wildcard items as they were; `Content` kept; `Folder`, `Service`, `BootstrapperPackage` and packages' `Analyzer` items dropped. Files in the folder that weren't in the project get a `Remove`; folders of other projects and `packages` get `Compile`, `EmbeddedResource` and `None` removes.
- References: the SDK's implicit framework references (and Windows Forms' or WPF's with `UseWindowsForms`/`UseWPF`) left out, others kept; hint paths into a `packages.config` package dropped. `packages.config` → `PackageReference` (development dependencies with `PrivateAssets` all; a package another listed package depends on is left out when its `.nuspec` is in the repository path), and the file is deleted. `ProjectReference`'s `Project` and `Name` dropped. NuGet's imports of package targets, `EnsureNuGetPackageBuildImports`, `Microsoft.Common.props` and `Microsoft.CSharp.targets` imports dropped; the classic IDE's imports conditioned on `Exists` dropped with a note; `BeforeBuild`/`AfterBuild` targets kept with a note; other targets, imports and comments kept.
- `AssemblyInfo.cs`: string-literal attributes the SDK generates become properties (`AssemblyTitle`, `Description`, `Company`, `Product`, `Copyright`, `AssemblyVersion`, `FileVersion`, `InformationalVersion`; `AssemblyConfiguration` and empty `AssemblyTrademark`/`AssemblyCulture` dropped); a paragraph whose attributes all moved goes with its comment; what's left (`ComVisible`, `Guid`) stays, or the file is deleted. A wildcard version or a non-literal stays with `Generate…Attribute` false (and `Deterministic` false).
- Refused, with the reason: SDK-style projects, projects on the classic IDE's targets, non-.NET Framework projects.
- The shell shows the result in the refactoring preview (`Dialogs` with details): the converter's notes, then line-diff edits of the project file and `AssemblyInfo.cs` (`LineEdits`, on the workbench's `LineDiff`) and the deletions; **Convert** applies it as a workspace edit (`packages.config` to the trash through the build host) and restores the project.

**Solution Explorer:** "(non-SDK-style)" after an old-style project; "(non-SDK-style, can't build here)" with the reason as the project's first child for one on the classic IDE's targets.

**New Project** (the templates plugin, `NetFrameworkTemplates`): **.NET Framework Console App** and **.NET Framework Class Library**, SDK-style, `net48` by default (or `net481`, `net472`, `net462`), C# 7.3 with `Main`, the console app's `App.config` with `supportedRuntime`; written by the plugin (the SDK's templates don't target `net4x`). Off Windows they come last, marked Windows only.

**Check Environment** (on Windows, with .NET Framework projects): **.NET Framework** from the registry's `Release` DWORD (`HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full`, 4.5 to 4.8.1) against the highest version the projects target (found, missing, or older), and **.NET Framework 3.5** (`NDP\v3.5` `Install`) for projects of 2.0 to 3.5; the fix is the download page.

**Fixture** `samples/NetFramework` ([README](../../samples/NetFramework/README.md)): `ConsoleApp` (SDK-style `net48`), `Library` (`net48;net472`), `ConsoleApp.Tests` (xUnit 2 on `net48`), `LegacyApp` (old-style `v4.7.2`: `packages.config` with `Codalus.Sample.Legacy` 1.0.0, `AssemblyInfo.cs`, `App.config`, a project reference, a stray `Drafts/NotInProject.cs` with `#error`), `LegacyWebApp` (old-style, imports `$(VSToolsPath)\WebApplications\Microsoft.WebApplication.targets`), `WinFormsApp` (SDK-style `net48`, a form in the classic IDE for .NET Framework's designer style). `feed/Codalus.Sample.Legacy.1.0.0.nupkg` (a `net45` library) from the fixture generator, which can now write one package of its feed (`packages <feed> <id>`); generated packages use block-scoped namespaces (C# 7.3).

**Found by PR #26's Linux CI, not M43a's:** `DotNetTestCoverageTests` (xUnit v2 on VSTest) reported `Add` uncovered. VSTest coverage runs didn't load Coverlet's in-process collector (`dotnet test --collect` adds it; run settings given to vstest.console don't), so the instrumented assemblies wrote their hits on the test host's exit, which VSTest cuts short 100 ms after the session: a loaded runner lost them. Reproduced with `VSTEST_TESTHOST_SHUTDOWN_TIMEOUT=1` (xUnit v2 or NUnit failed on each run); the run settings now add the in-process collector (`InProcDataCollectionRunSettings`, its codebase in the bundled collector's folder), and the coverage tests pass with the 1 ms timeout.

**Found by PR #27's Linux CI:** `NetFrameworkTests.Net_framework_projects_restore_load_and_build_on_every_os` failed now and then with `LegacyWebApp`'s design-time build failed (MSB4019, the classic IDE's web targets not found). A batch of six projects or more builds on worker nodes too, and the project instance loaded without its missing imports went to one, which loaded the project again from its file. Such a build now has in-process node affinity (`DesignTimeBuilder.InProcess`). The test's build host uses four design-time nodes (`CODALUS_DESIGNTIME_NODES`): it failed on 5 of 6 runs of M43b's fixture and 2 of 4 of M43a's before, and passes on every run since.

**Found by PR #26's Windows CI:** `NetFrameworkTests.An_old_style_net35_library_gets_its_reference_assemblies_from_codalus_restore` failed now and then with the reference assemblies package unresolved under Dependencies, though the compiler's references were already from it. A test bug: the test waited for the design-time build, then read the evaluation. A design-time build evaluates the project again in its build node, so one queued before the evaluation that follows the restore (the first one, or the watcher's when the package's folder appeared under the project) can see the installed package and report first; the evaluation catches up straight after. A timeline of 12 parallel Linux runs with fresh NuGet HTTP caches showed it once (that design-time result 35 ms ahead of the evaluation). The restore, fixture and converted-project tests now wait for the evaluations they assert on together with the design-time builds, and a timeout gives the restore's states and those evaluations' references. The fixture test could hit the same race (PR #27's Windows CI read M43b's `NUnitTests` test platform before that project's evaluation after the restore).

**Found by PR #26's Windows CI and develop's nightly, not M43a's:** `DebugStartAgainTests` failed now and then after exactly 60 s (`A_start_that_keeps_timing_out_fails_after_the_last_attempt` in PR #26 job 117477392978; `A_later_startup_project_that_keeps_timing_out_is_left_out_after_the_last_attempt` in develop's push run, job 117494070309, without "starting again (3 of 3)"). Only the late-runtime wait lasts a minute there: it followed the adapter's first listed child (`ProcessTree.Children`), and on Windows a snapshot entry keeps its parent's id after the parent ends, ids are reused, and the snapshot usually lists older processes first, so a process left by an earlier holder of the adapter's id (a build server, from the tests alongside) came before the scripted program and never ended. Windows doesn't reparent orphans; Linux and macOS do. The Windows listing leaves out processes created before the parent, as `Process.Kill`'s tree walk does. The check reads both creation times from process handles as UTC file times (`GetProcessTimes`): `Process.StartTime` converts to local time, which goes back an hour when daylight saving time ends and would have left out a real child started in that hour, and `Process.GetProcessById` lists every process when it can't open one. A child created in the same clock tick as its parent stays, and one whose time can't be read stays (`ProcessTreeTests`: a started process is its parent's child on every OS; an older one is left out, later or unknown ones stay).

**Needs validating on Windows** (CI's windows-latest runner): `WindowsDesktopShellTests.Windows_runs_debugs_and_tests_the_desktop_apps` timed out once in PR #26 (job 117494115864) waiting 240 s for F5 to stop at the view model's breakpoint, and passed on the same code in PR #27 and on develop. The process tree check can't leave out the debuggee (netcoredbg creates it, so it is newer than netcoredbg), and nothing else M43a changed is on that path; the run gave nothing else to go on. The test's debug waits now say the session's state, the programs running, the notifications, the build F5 ran first and the Debug Console. Also: `NetFrameworkShellTests.Windows_starts_the_net48_console_app_without_debugging` (Start Without Debugging runs the `.exe` on the desktop CLR and its output comes back; F5 offers Start Without Debugging), the smoke step `netfx.projects`'s run, Check Environment's registry read, a Developer Pack winning over the package for old-style projects, and the build host tests there (`RunCommand` is the `.exe`). **macOS:** the cross-OS tests above.

## Gaps
