**Large solutions** (item 5), measured locally on the maintainer's `Epsilon.Web.Pylon.slnx` (94 projects, 20,000 C# files, a 20-thread machine) with a headless open (not kept: numbers from a developer's machine don't set budgets):
- *Where the time went:* evaluation about 6 s, design-time builds about 3 s, then the C# host's first background pass (every project compiled and its compiler diagnostics taken) 85–98 s from a cold language cache; 12 s on a second open with nothing changed (M34c's cache). The processors were 36% busy on average during the pass.
- *Server GC for large solutions:* the host binds on many threads, which waited on the workstation collector's single-threaded collections. With the server collector the pass took 50 s (ready at 59 s against about 100), at the same peak (about 6 GB). On 50 small projects it was ready in 4.7 s against 8.4 but kept 395 MB idle against 248, which `editor-100k`'s memory budget (one file, so one project) wouldn't take. So the shell starts the C# host with `DOTNET_gcServer=1` only for a solution of `ShellHost.ServerGcProjects` (20) projects or more (`ShellHost.WithServerGc`, `LargeSolutionPerformanceTests`). A larger gen0 budget on the workstation collector (64 MB) was tried: 64 s, +32 MB idle on 50 projects.
- *References in parallel:* loading 53 projects took 2.1 s, 1.5 s of it creating metadata references one at a time, the host's messages waiting; `WorkspaceManager.ApplyReferences` creates them in parallel first (under 1 s).
- *Packages another SDK restored:* 41 of the 94 projects are in another repository whose `global.json` pins SDK 10.0.303; their assets files were written by it, and the solution's SDK, 10.0.204, failed in `ResolvePackageAssets` (a NullReferenceException in `LockFile.GetTarget`, reproduced with `dotnet msbuild`). They had no IntelliSense and missed the design-time cache at every open, while the open-time check found their packages up to date. Comparing the SDK that restored a project (`runtimeIdentifierGraphPath` in its assets file) with the evaluating one was tried and dropped: the build host's SDK and `dotnet restore`'s differ whenever the newest SDK is newer than the host can load, so it would restore at every open. Instead, a design-time build failing with `ResolvePackageAssets`, NETSDK1004, NETSDK1005 or NETSDK1060 starts one forced restore per session in the solution's folder (`SolutionSession.RepairRestore`), and the projects whose assets files it rewrites build again. The build host's log says why it restores on open. Test: a step of `Design_time_builds_come_from_the_cache_until_their_inputs_change`.
- *Tried, no gain:* each project's diagnostics right after its compilation instead of after every project's (89 s against 84–98).
