# M55a checkpoint: Apply Code Changes while debugging, the core

Date: 2026-10-29. The first part of the roadmap's [M55](../roadmap.md#m55--a-managed-coreclr-debugger-phase-2-apply-code-changes-while-debugging), D48's phase 2 ([ADR 0086](../adr/0086-a-managed-coreclr-debugger.md)): Hot Reload while a program is debugged under the Codalus debugger. Two pull requests: the deltas and `codalus/applyChanges` (`feat/m55a-apply-changes`), then the triggers and rude edits in the IDE. M55b (the terminal, the console window, test debugging, attached programs, a Blazor Web App's server, the offer under netcoredbg, the smoke test, the docs) is next.

## The spike

Run on Windows before PR 1, in a scratch program against a real build:
- **Roslyn's Hot Reload service is internal.** `Microsoft.CodeAnalysis.ExternalAccess.HotReload`'s `HotReloadService`, the one `dotnet watch` uses, is internal (visible to `dotnet watch` only). It is published only on the `dotnet-tools` feed, which `nuget.config` drops at .NET 11 GA, and it depends on MSBuild workspaces. It is a thin wrapper of about 250 lines over `Microsoft.CodeAnalysis.Features`' Edit and Continue service, which the language host already references.
- **The language host calls that service itself.** Krafs.Publicizer (MIT, build-time) compiles the host against Features with the `Microsoft.CodeAnalysis.EditAndContinue` and `Contracts.EditAndContinue` namespaces made public, and marks the assembly `IgnoresAccessChecksTo`, which the runtime honors. The host is JIT-compiled and untrimmed. Publicizing all of Features clashed with the protocol's `CompletionOptions`, so only those namespaces are.
- **What the scratch run showed:**
  - The session started from the build, and an edit's deltas applied in the running program with `MetadataUpdater.ApplyUpdate`: a changed body, then a second edit that adds a method.
  - A changed base type came back as `ENC0004`, with the project to restart.
- **The runtime's capabilities**, read from `MetadataUpdater.GetCapabilities` on .NET 8, 9, 10 and 11: the base set, the three generic ones from .NET 7, and `AddFieldRva` from .NET 10. None of them has `AddExplicitInterfaceImplementation`.
- **The Blazor Web App's server beside `dotnet watch`** needs the adapter's `codalus/applyChanges`, so it is tested by M55b's PR 4 on every OS, not here.

## Done

**PR 1: deltas and `codalus/applyChanges`.**
- **The language host** (`HotReloadFeature`, `docs/protocol.md`):
  - `codalus/hotReload/start` begins a Roslyn Edit and Continue session for a debugged program's projects, from their build. Each project's `CompilationOutputInfo` is now its output assembly, so the baseline is that assembly and its PDB.
  - `update` gives the edits since as deltas per module, or rude edits with the projects to restart, or compile errors. `commit`, `discard` and `end` follow the debugger's answer.
  - Hot Reload's semantics: no active statements.
- **The adapter** (`codalus-debughost --clr-dap`):
  - `codalus/hotReloadCapabilities` gives the runtime's capabilities by its version.
  - `codalus/applyChanges` applies each module's deltas through `ICorDebugModule2::ApplyChanges`, stopping a running program for it.
  - `ClrModuleInfo` keeps each edit's generation: methods' sequence points and locals by the generation that last changed them, and the names of methods an edit added. A frame in an older version reads its own lines. ICorDebug numbers a method's version by the module's generation that last changed it, plus one.
  - Breakpoints bind again in the new version, beside the old one's, which serves frames still running it.
  - The user's modules get Edit and Continue's JIT flags as they load, when the debugger runs the program from its start.
- **Two finds:**
  - The editor's text reached the language host as a `SourceText` without an encoding, and emitting an edit's debug information needs one (`CS8055`). Open documents now get their file's encoding (its byte order mark, else UTF-8) and SHA-256 checksums.
  - mscordbi crashed the adapter applying an edit to a program that hadn't stopped yet: it reads the module's metadata through an importer that a stop's stack walk creates. The adapter now asks for the importer first. `An_edit_applies_to_a_program_that_hasnt_stopped_yet` failed without that (Windows, .NET 11 RC3).
- **Tests** (`HotReloadDebuggingTests`, the real build host and language host on `samples/Debugging/HotReload.slnx`, in the `debug-codalus` shard):
  - a launched program stopped before a call takes an edit, and a breakpoint on a line only the new version has stops there with the new local's value
  - a second edit on the first, while it runs
  - a program that hasn't stopped yet
  - a frame already in the method finishes in its old version
  - an attached program takes edits with `DOTNET_MODIFIABLE_ASSEMBLIES=debug`, and without it is refused with `CORDBG_E_ENC_MODULE_NOT_ENC_ENABLED`
  - a rude edit's diagnostic and its project to restart
  - Visual Basic

**PR 2: the triggers and rude edits in the IDE.**
- **DebugService and `DebugHotReload`** (Workbench): when a debug session under the Codalus debugger runs, `DebugHotReload` starts the language host's session at once (its baseline is the files as built), with the runtime's capabilities, which the adapter knows from the runtime's version before any module loads (the core library's version for a self-contained program). An apply asks the language host for the edits since, has every Codalus debugger of the session apply them (a compound session can have several; `IDebugAdapter.Adapters`), then commits or discards. `DebugService.BeforeResume` applies the edits made while stopped before Continue, a step or Run to Cursor lets the program go on.
- **The shell** (`ShellHost.DebugHotReload.cs`):
  - Apply Code Changes (`Alt+F10`, the toolbar's Hot Reload button) applies the editors' text as it is, saved or not, while a Codalus session takes edits (the `hotReloadRunning` context). Continue applies first while stopped; a save applies while the program runs, with `debug.hotReload` on.
  - The status bar's Hot Reload item says the last outcome ("applied at", "not applied (compile errors)", "restart needed"); the Debug Console says each apply.
  - A rude edit asks: Restart (built and debugged again), or Continue with the Old Code. Its diagnostics, and compile errors, are in the Error List (source "Hot Reload") until the next apply or the session's end.
  - F# and XAML edits saved while debugging get one Debug Console line: they run after a restart.
- **Three finds:**
  - The shell's apply before Continue ran through `Ui.RunAsync` with an expression lambda, whose value chose the overload that doesn't wait for the task: Continue raced the apply. A block lambda waits.
  - Roslyn checks that a document matches the build by its PDB checksum, and with no text to compare it reads the file: a file saved with an edit before the first apply then didn't match, and its edits were ignored as out of sync. The language host now answers with the text the session started from (`IPdbMatchingSourceTextProvider`), as the classic IDE does.
  - `Breakpoints.Clear()` raised "every file changed" after emptying its files, so a debug session sent no file's breakpoints and the program kept stopping at them: it now raises each cleared file.
- **Tests** (`DebugHotReloadTests`, the Shell on `HotReload.slnx`): Continue applies an edit made while stopped, Apply Code Changes one made while running, with the status bar; a save applies while running; a rude edit asks, shows in the Error List, Continue with the Old Code keeps the program running, and Restart builds and debugs it again; under netcoredbg nothing takes edits.
