# M33 checkpoint: older .NET, .NET Core 2.0 to .NET 10

Date: 2026-10-11. Decision: [ADR 0030](../adr/0030-older-dotnet.md) (D23). One checkpoint: the work fit without a split. The support table is [Older .NET versions](../user-guide/dotnet-versions.md) in the user guide.

## What M33 found first

Every framework was put through the product before anything was changed. With the current SDK, projects of every version already opened, built, ran, debugged (netcoredbg 3.2.0 stops at breakpoints on .NET Core 2.0) and tested. What didn't work:

- **Older SDKs pinned in `global.json`:** the build host's builds of the .NET 5 SDK and older hung (their MSBuild never connects to the worker nodes it starts from a host on .NET 10), their builds stopped on the first diagnostic (the logger read `HelpLink`, added in MSBuild 16.8), their restores failed (`--nologo`, MSB1001), and the 2.0 SDKs can't compile on a newer .NET at all (their compiler task starts `csc.exe` directly).
- **A `global.json` that asks for a missing SDK:** silent, or the build host crashed in `Microsoft.Build.Locator`.
- **Linux:** .NET Core 2.x to 3.1 stop at start on Ubuntu 24.04 ("Couldn't find a valid ICU package"), and .NET Core 2.x to .NET 5 need OpenSSL 1.x for cryptography and HTTPS.
- **Coverage:** Coverlet 10's collector doesn't load into test hosts before .NET 8.
- **Apple silicon:** .NET 5 and earlier run as x64; netcoredbg 3.2.0 has no macOS x64 build.
- **Hot Reload:** offered for every framework, though `dotnet watch` applies changes only from .NET 6.

## Built

**The build host and older SDKs** (`src/DaedalusStudio.Projects.Host`)
- **The floor is the .NET SDK 2.1.200** (`SdkSelection.Floor`). Below it, the newest SDK stands in, and `sdkWarning` names the SDK the solution asked for, its `global.json`, and why.
- **In-process builds for MSBuild before 17** (`SolutionBuilder.InProcess`; `DAEDALUS_BUILD_IN_PROCESS=1` for any SDK): the build host's own node, as design-time builds already use.
- **The build logger** reads `HelpLink` in a method of its own, so MSBuild without it reports the diagnostic instead of failing.
- **Restore** without `--nologo` (`DOTNET_NOLOGO` instead).
- **`global.json` checks** (`GlobalJsonSdk`): the nearest file, with comments, and dotnet's roll-forward rules. When it asks for an SDK that isn't installed, the build host lists the SDKs from elsewhere (the locator throws in that folder), uses the newest, and warns.
- **On Linux,** the CLI of SDKs before 5.0 (restores, tools) and the build host itself (whose in-process builds run those SDKs' compilers) get the system's ICU (`CLR_ICU_VERSION_OVERRIDE`), based on the SDK `global.json` resolves.
- **The Dependencies node:** the implicit `Microsoft.NETCore.App` and `NETStandard.Library` packages go under Frameworks, with their version.
- **The package manager's versions** (`FrameworkCompatibility`, `packages/details` `targetFrameworks`): each version says whether its dependency groups cover the project's frameworks (`compatible`), and the details open on the newest that does. The version picker marks the others "not for netcoreapp2.1" and the newest compatible one "latest compatible".

**Running and debugging** (workbench `Build/RuntimeSelection.cs`, `Projects/DotnetFrameworks.cs`, `Debugging/DebugService.cs`; `DaedalusStudio.Debugging`)
- **`DotnetFrameworks`:** a framework's .NET version, its default C# version, why Hot Reload can't run it, and whether it runs as x64 on Arm64.
- **`RuntimeSelection`**, for Run, Debug and the plan the integrated terminal runs:
  - an apphost gets the SDK's root in `DOTNET_ROOT` (`DOTNET_ROOT_<ARCH>` from .NET 6) unless it is set, as `dotnet run` does;
  - on Arm64, .NET 5 and earlier (macOS) and .NET Core 3.1 and earlier (Windows) run as x64: the x64 `dotnet`, or the x64 root for an apphost, found in `<root>/x64`, `/etc/dotnet/install_location_x64` or the default location; without it, Run says what to install;
  - on Linux, .NET Core 2.x to 3.1 get `CLR_ICU_VERSION_OVERRIDE` with the system's ICU, unless the launch sets it or invariant globalization;
  - each change is a note in the program's output (`LaunchPlan.Notes`).
- **netcoredbg's own process on Linux** (`DebugService.AdapterEnvironment`) gets the launch's ICU choice, or the system's ICU (for attaching too): it reads symbols on the debuggee's runtime, in its own process.
- **A debug session ends when netcoredbg exits** even when its debuggee still holds its output (on Unix the debuggee inherits the adapter's pipes), and disconnecting and disposing are bounded.
- **The x64 debugger:** `DebugAdapterLocator.ResolveX64` (`DAEDALUS_NETCOREDBG_X64`, `debugger/x64/`, `.work/netcoredbg-x64`). `DebugService` uses it for a plan that runs as x64 and for any x64-only Mach-O program. `eng/get-netcoredbg.sh --x64` downloads netcoredbg 3.1.3-1062's macOS x64 build (pinned by SHA-256); `eng/package.sh` puts it into the macOS package.
- **Hot Reload needs .NET 6:** context key `hotReloadSupported`; for an older startup project, Start with Hot Reload is disabled and the Debug menu shows "Start with Hot Reload (needs .NET 6 or later)". Invoked anyway, it says why; with the `run.hotReload` setting, Ctrl+F5 runs without it and the output says so.
- **Lists:** `net5.0` to `netcoreapp2.0` in the target framework completion; C# 9, 8 and 7.3 in `LangVersion` (completion and the property pages).

**Tests and coverage** (the .NET test plugin)
- **`OlderFrameworks`:** per framework group, VSTest test hosts of .NET 5 and earlier run as x64 on an Arm64 Mac (`TargetPlatform`), and on Linux those before .NET 5 get the system's ICU.
- **Coverlet's netstandard2.0 collector** (6.0.4, MIT) ships in `coverage/collector-netstandard2.0` and serves test hosts before .NET 8 (`CoverageTools.CollectorFolder`).

## Found along the way

- **The test process's `DOTNET_ROOT_X64`:** `dotnet test` starts a test apphost with `DOTNET_ROOT_X64` set to its own `dotnet`, and apphosts of .NET 6 and later read it before `DOTNET_ROOT`. A `net7.0` app started from the suite ran on the machine's `dotnet`, which has no .NET 7 (0x80008096). The suite sets it to the matrix's root; Daedalus itself leaves a set variable alone, as `dotnet run` does.
- **The system ICU's version on Linux** first parsed `libicuuc.so` (unversioned) too, and threw: every run, debug session and test run of .NET Core 2.x and 3.x failed in WSL. Fixed in the three places that read it.
- **OpenSSL:** a first probe suggested .NET Core 3.1 and .NET 5 load OpenSSL 3; they don't (the probe never generated a key). The restore of the 5.0 SDK in WSL said so: "No usable version of libssl was found". The table, the ADR and the containers' expectations follow the real behavior.
- **inotify instances on Linux:** the language host held one watcher (one inotify instance) per project, 38 for `samples/TargetFrameworks`, and dotnet watch one per folder; the default limit is 128 for all of a user's processes. With the suite beside the shell's tests in WSL, `dotnet watch` in the Hot Reload tests stopped with "The configured user limit (128) on the number of inotify instances has been reached". The language host now shares one watcher among a solution folder's projects, and the suite makes `dotnet watch` poll on Linux.
- **The old SDKs' compilers on Linux:** builds with the SDKs before 5.0 run in the build host's process, and their compiler runs on .NET Core 2.1 to 3.1, which stopped at start in WSL for want of ICU. The build host gives its own process the system's ICU for those SDKs, as it already did for their CLI.
- **Debugging .NET Core 2.x and 3.x in WSL:** the program got the ICU override, yet the session printed "Couldn't find a valid ICU package" and never stopped. The message came from netcoredbg itself (exit code 134): it runs its symbol reader on the debuggee's runtime. And the session then stayed "running" forever, and stopping it hung: the orphaned debuggee kept netcoredbg's output pipe open, and a pipe read can't be cancelled on Unix. Both fixed (above).
- **.NET Core 2.0 on Linux needs the system's `libunwind`** (later runtimes bring their own): the Ubuntu 18.04 container lacked it. The user guide says so.
- **The suite's design-time builds:** it first read the design-time build from before the restore, which has no package references; .NET Core 2.x and 3.0 get even their framework from packages. It waits for the one after the restore now.

## Not done, and gaps

- **macOS: run by the coordinator.** The logic is unit-tested on a simulated Arm64 Mac; the suite's Mac run is pending (snapshot below).
- **OpenSSL 1.x on current Linux distributions** (a documented gap): programs of .NET Core 2.x to .NET 5 fail when they hash, encrypt or call HTTPS, and those SDKs can't restore. Daedalus can't supply the library; the user guide says what to install. For the suite, `eng/get-runtimes.sh` unpacks Ubuntu 20.04's OpenSSL 1.1 (pinned) into the matrix's root and the suite puts it on `LD_LIBRARY_PATH`, so the SDKs from 2.1.300 to 5.0 restore and build in WSL; the 2.1.202 SDK runs on .NET Core 2.0, which needs OpenSSL 1.0, and is skipped there. `eng/compat-containers.sh` covers the runtimes on their own distributions.
- **Attaching to an x64 process on Apple silicon** uses the Arm64 debugger. `TODO(issue)`: pick the debugger by the process's architecture.
- **SDKs before 6.0 on Apple silicon:** x64-only, so the Arm64 `dotnet` doesn't resolve them; a `global.json` that pins one counts as not installed. Documented.
- **The 2.0 SDKs and the 2.1.1xx band** are below the floor (their compiler task can't run on a newer .NET); the 1.x SDKs are out of scope with `netcoreapp1.x`.
- **The package manager's compatibility** is an estimate from dependency groups; packages without them say nothing. `TODO(issue)`: read the `lib/` folders of a downloaded package for an exact answer.
