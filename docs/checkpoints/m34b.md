# M34b checkpoint: performance pass

Date: 2026-10-12. Pulled forward by the maintainer on 2026-10-12, beside M34a (the UI pass, built in parallel); the roadmap entry is under [M34](../roadmap.md#m34--ui-polish). No new ADR: the changes keep ADR 0004 and 0005's design (MSBuild in the build host, Roslyn in the language host, the shell relaying design-time builds) and make it faster.

## The report

The maintainer's own solution (96 projects, mostly Blazor and ASP.NET Core, Razor and other source generators, central package management) sat on "Loading C# projects…" for about two minutes after opening, and its four open files showed 78 errors on types that resolve. Their solution was used only to measure and diagnose; nothing from it is in the repository.

## Where the time went

Measured with a probe that drives the build host and the C# language host through the workbench, as the shell does (`SolutionService` and `LanguageService`, Debug builds, a warm disk cache, the four documents the maintainer had open):

| Phase (96 projects) | Before | After, cold (no cache) | After, warm |
|---|---|---|---|
| Solution file → structure | 0.5–0.8 s | 0.5 s | 0.5 s |
| Evaluation of every project | 2.4 s | 2.3–2.5 s | 2.3 s |
| Restore on open | 7 s of `dotnet restore` beside the design-time builds, then all 96 projects evaluated again | skipped when the packages are up to date | skipped |
| Design-time builds | 21 s, one at a time | 11–15 s | 1.6 s (keys and cache reads; nothing builds) |
| Loading the projects into Roslyn | 60 s (96 updates, each slower than the last) | about 1 s per batch | 1.1 s (one update) |
| Open documents' first real diagnostics (from opening) | 89–109 s | 52 s | 35–38 s |
| The whole solution compiled once ("ready") | 112–139 s | 76 s | 53–58 s |
| False errors in the Error List while loading | 78, for 80–100 s | 0 | 0 |
Loading the projects into the language host was the largest cost: each finished design-time build was sent on its own, and every update re-applied every project's references, reading each referenced file's timestamp again (96 projects × ~300 references per update, so the 96th update took 1.2–2.6 s and blocked every request behind it). Next came the background diagnostics pass: one project at a time, restarted by every update, and `ready` was reported after any pass, even one over 0 projects. Then the design-time builds, one at a time, and a restore that ran on every open and evaluated every project again afterwards.

What remains is Roslyn compiling the solution: 16 s to create every compilation in parallel, longer on the critical path (a chain of four Razor projects of 8–14 s each, mostly source generators), then 30 s of diagnostics. The open documents sit at the top of that chain.

## The 78 errors were false

They were exactly the four open files' errors in **Miscellaneous Files** (12 + 21 + 26 + 19): while their project had not reached the language host, each file was compiled on its own with framework references only, so every type from the solution was missing (CS0246, CS0234). They stayed for 80–100 s because loading the projects took that long, then disappeared. Nothing was wrong with references or generated sources: once loaded, the solution showed no such error.

Now, while the solution loads, those documents get syntax diagnostics only, and so does any project whose referenced projects haven't arrived yet; the Error List never showed the 78.

Three errors remain after loading, and they are false too, for another reason: CS4014 ("this call is not awaited") on a `Task`-returning call in a non-`async` method, which the solution turns into an error (`WarningsAsErrors`). The language host's Roslyn (5.9, preview) reports CS4014 there; the SDK's compiler (5.6, SDK 10.0.303) doesn't, and `dotnet build` of the solution succeeds with 0 errors. Reproduced with a three-line program on Roslyn 5.9 at any language version. A compiler version ahead of the SDK's can disagree with the build; `TODO(issue)`: report diagnostics the SDK's compiler wouldn't (a pinned Roslyn per SDK band, or a filter for known differences).

## Built

**Language host** (`src/DaedalusStudio.LanguageServices.Host`)
- `WorkspaceManager.ApplyReferences` reads each referenced file's timestamp once per update instead of once per project; an update of 96 projects takes about a second (it logs a breakdown when one takes longer).
- **Loading state** (`ProjectsUpdateParams.Loading`, `docs/protocol.md`): while the shell says the solution is loading, documents in Miscellaneous Files and projects that reference a project not loaded yet (directly or not; `WorkspaceManager.IsIncomplete`) get syntax diagnostics only, the background pass waits, and the host reports `loading`, never `ready`. When loading ends, the open documents are analyzed again.
- **The background pass** (`DiagnosticsService`) waits until the solution has loaded (passes over part of it were cancelled by the next update and took the processors from the design-time builds); then every compilation first, in parallel (half the processors), dependencies before the projects that reference them and the open documents' projects and their dependencies before the rest; then each project's diagnostics in parallel. A project unchanged since the last pass (its dependent version, metadata references and analyzers) keeps its diagnostics without being compiled again, and only files whose diagnostics changed are published.

**Relay** (`LanguageService` in the workbench): design-time build results gather for 150 ms and go to the host as one update; the update carries the loading state (evaluation or design-time builds still running, or results not sent yet), also sent on its own when it changes and when a host (re)starts.

**Build host** (`src/DaedalusStudio.Projects.Host`)
- **Parallel design-time builds** (`DesignTimeBuilder.NodeCount`; 96 projects: 16 s in process with the subset below, 11–15 s with worker nodes, 21 s before): a batch of six projects or more adds MSBuild worker nodes (half the processors at most, `DAEDALUS_DESIGNTIME_NODES`), and asks for the subset of the project state it reads (`ProvideSubsetOfStateAfterBuild`), so nothing large crosses from the nodes. Small batches (an edit) stay in process; MSBuild before 17 always does (ADR 0030).
- **The design-time build cache** (`DesignTimeCache`, `Fingerprint`): each successful result in the project's `obj/daedalus.designtime.json`, per configuration, platform and target framework, under a key of the project's evaluation fingerprint (SDK, global properties, every evaluated item including globbed ones, sorted and with one path separator: on Linux and macOS MSBuild spells `obj\Debug` as `obj/Debug` only once the folder exists, which the first WSL run caught; the project file, its imports and the assets file with timestamps and sizes), the solution's properties and every referenced project's fingerprint. A warm open sends the cached compiler inputs right after evaluation. An entry is used only while its sources (generated ones in `obj/` included), analyzers and references outside the solution exist; a corrupt file is a miss; an explicit `build/designTime` request never reads it; `DAEDALUS_DESIGNTIME_CACHE=0` turns it off.
- **Restore on open only when needed** (`SolutionSession.PackagesUpToDate`): skipped when NuGet's last restore succeeded (`project.nuget.cache`), every package file it expects exists, and the assets file, or `obj/daedalus.restore.stamp` written after each restore we run, is newer than the project file and every import outside `obj/` (`Directory.Build.props`, `Directory.Packages.props`, the SDK). The state goes straight to `succeeded`.
- After a restore, only projects whose assets file changed are evaluated again; an evaluation that changes nothing sends no `project/evaluated` (each one refreshed several views in the shell); an evaluation that leaves nothing to build says so (`designTimeProgress {0, 0, true}`), so the shell knows loading ended.

**Shell:** the status bar counts: "Loading C# projects 34/96…" during design-time builds, then "Analyzing C# projects…" until the language service is ready. The bench event `designtime_done` marks every project's compiler inputs known.

**Benchmarks:** `open-solution-50` opens each copy twice, cold (no cache) and warm (the same copy again, as after a restart), with the metrics `designtime_done_ms`, `language_ready_ms` and their `warm_*` twins; `DAEDALUS_BENCH_SHELL_DIR` measures another published shell (the before numbers below). New budgets in `benchmarks/budgets.json`.

## Tests

- `DesignTimeCacheTests` (unit, the cache file linked into the test project): keys change with the project, framework, properties and every referenced project; entries come back only under their key and while their files exist; failed builds aren't cached; corrupt files are misses; options and absolute Unix paths are told apart.
- `BuildHostIntegrationTests.Design_time_builds_come_from_the_cache_until_their_inputs_change` (the real build host on `samples/ProjectSystem`): a second open builds nothing, gives the same compiler inputs and doesn't restore again; a new source file in a referenced project (a glob, no project file change) builds it and the projects that reference it; asking for design-time builds bypasses the cache; a corrupt cache file builds that project.
- `LoadingTests` (the real language host): a document outside any project gets its syntax error but not CS0246 while loading, and no `ready`; once loading ends, CS0246 and `ready`.

## Deviations and gaps

- **The open documents still wait for Roslyn.** On the maintainer's solution the first real diagnostics of a top-level project come 30 s after loading: its compilation needs the chain of Razor projects below it, each 8–14 s of source generators. `TODO(issue)`: persist Roslyn's state between sessions, or use built reference assemblies for projects outside the open documents' chain until they compile.
- **Open documents' projects first in design-time builds** was not done: with the cache a warm open has no design-time builds, and a cold one is now 14 s for 96 projects; the scheduler takes the order MSBuild chooses.
- **CS4014 from a newer Roslyn** (above).
- **The cache key leaves out environment variables**, which MSBuild reads as properties; a changed variable keeps the old design-time result until a project or import changes, or an explicit `build/designTime`.
- **Measurements of the maintainer's solution** ran while another IDE had it open: its restores rewrote assets files during our cold runs. The warm numbers didn't restore.
