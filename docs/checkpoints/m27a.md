# M27a checkpoint: EF Core integration

Date: 2026-10-11. Decision: [ADR 0036](../adr/0036-ef-core-integration.md). M27 is split per the roadmap's rule 5: M27a (EF Core, this checkpoint) and M27b (the database explorer, the query editor, the SQL language service and SQL database projects; ADRs 0037 and 0038).

## Built

**The build host** (`SolutionSession.EntityFramework.cs`, `EntityFramework/EfTool.cs`)
- `ef/*` requests (`docs/project-protocol.md`) run the user's own `dotnet ef` as a child process in the startup project's folder, with `--json --prefix-output`: `ef/status`, `ef/contexts`, `ef/contextInfo`, `ef/migrations` (applied or pending on the chosen connection; again with `--no-connect` when the database can't be reached), `ef/addMigration`, `ef/removeMigration` (with `--force` to revert first), `ef/script` (from/to, idempotent, without transactions), `ef/updateDatabase` (apply or revert), `ef/bundle`, `ef/scaffold`, `ef/optimize`, `ef/model`.
- Trusted solutions only; the startup project's configuration and active target framework are passed; one EF process at a time (dotnet-ef copies its own build host into the output on every run, and two runs collided on those files); a cancelled request kills the process tree; `ef/output` streams the messages to the Entity Framework output; connection strings are never echoed; `-33104` says dotnet-ef is missing.
- **`daedalus-efagent`** (`src/DaedalusStudio.EntityFramework.Agent`, net8.0, no dependencies, shipped in `buildhost/efagent/`): started with the app's `deps.json` and `runtimeconfig.json` like dotnet-ef's `ef.dll`, it creates the context with EF's `DbContextActivator` (the app's host builder or a design-time factory), reads `IDesignTimeModel.Model`, and writes entities, properties, keys, foreign keys, navigations (skip navigations too), indexes, owned types and `DebugView.LongView` as JSON, all through reflection on member names stable since EF Core 3.1.

**The language host**: `daedalus/ef/contexts` finds every DbContext with the semantic model, with the provider and connection name from `OnConfiguring`, `AddDbContext<T>`-style registrations anywhere in the solution, or Aspire's `Add…DbContext<T>("name")`; its `DbSet`s; design-time factories.

**The workbench** (`Data/`): `EntityFrameworkService` (builds the startup project through `BuildService` first, so errors land in the Error List, then passes `--no-build`; skips the build until something changes; the update range and script), `ConnectionDiscovery` (connection strings from `appsettings*.json` and user secrets, the engine guessed from the keywords, passwords masked for display), `DatabaseEngines`.

**The shell** (`ShellHost.EntityFramework.cs`)
- **The Entity Framework window**: contexts (Roslyn's at once, `dbcontext list` on Refresh), the connection the migrations apply to (the app's configuration, or one of the startup project's connection strings), the provider and database, the dotnet-ef and EF Core versions, the migrations (applied, pending, unknown, with their dates); Add Migration, Update Database, Update to This Migration (double-click), Remove Last Migration, Script, Model, Bundle, Compiled Model, Reverse Engineer, Go to Context, Install dotnet-ef.
- **SQL before applying**: Update Database and reverts show the exact script (`migrations script <applied> <target>`) with Apply (Revert), Open in Editor and Cancel.
- **Scripts** open as unsaved `.sql` files next to the project; **bundles** go where the user saves them; **compiled models** open their model file.
- **The model view** (a document): a diagram (an entity per box with its table, `PK`/`FK` columns and types; owned types dashed next to their owner; a line per relationship with its multiplicity and delete behaviour; join entities of many-to-many relationships) and the debug view.
- **Reverse Engineer** (a document): project, a known connection string or a typed one, provider, output folder, context name, tables, schemas, data annotations, no `OnConfiguring` (default), database names, no pluralization, overwrite.
- **Install dotnet-ef**: `dotnet tool restore` when the manifest lists it, otherwise a local tool at the project's EF Core version.
- Commands (`ef.*`, category Entity Framework), the Project menu and the Solution Explorer's project menu (`efProject` context key), and new data icons (`database`, `table`, `view`, `column`, `key`, `function`, `procedure`, `schema`, `migration`, `diagram`, `plan`).

**Fixture**: `samples/Data`: `Blogging` (an ASP.NET Core app, EF Core 10.0.12 on SQLite, a context with an owned type, a cascade delete and a many-to-many, an `InitialCreate` migration, two connection strings and a `UserSecretsId`), dotnet-ef 10.0.12 as a local tool, and `Inventory/inventory.db` (from `inventory.sql`) for reverse engineering.

**Tests**
- `EntityFrameworkIntegrationTests` (build host + dotnet-ef, 2): status, `dbcontext list` and `info`, the update script, apply, Add Migration after a model change, the revert script and revert, remove, another connection; the model through the agent (owned type, FK with cascade, skip navigations, the unique index, the debug view), a compiled model, reverse engineering with two tables (no `OnConfiguring`, the connection string not echoed) and a bundle.
- `EntityFrameworkContextsTests` (language host, 2): provider, connection name, entities and location from `AddDbContext`; `OnConfiguring`, a design-time factory, abstract contexts skipped.
- `ConnectionDiscoveryTests` (workbench, 11): engine guesses, appsettings nested and flattened, comments, masking, provider ↔ engine, the update range.
- `EntityFrameworkShellTests` (headless UI, 1): the window lists the context and its pending migration; Update Database shows the SQL and applies nothing before Apply; Add Migration opens the migration; the model diagram draws 5 entity types; Reverse Engineer generates 3 files.
- **Smoke step `data.efMigrations`** (M27): the same flow in the published app, with screenshots `smoke-test-ef-update.png` and `smoke-test-ef-model.png`.

**Docs**: ADR 0036, `docs/user-guide/data.md` (linked from the guide's index), `docs/project-protocol.md`, `docs/protocol.md`, the roadmap (status, the M27 split, the parity row, the change log), CLAUDE.md.

## Not done, and deviations

- **Building first**: the window builds the startup project through the IDE's build (Error List, Build output) and passes `--no-build`, instead of letting dotnet-ef build (ADR 0036).
- **Connections with passwords** are passed to dotnet-ef with `--connection`, visible to local processes while it runs (as in a terminal); the default, the app's own configuration, passes none.
- `TODO(issue)`: DbContext discovery for Visual Basic and F# projects.
- `TODO(issue)`: a Package Manager Console-style EF prompt is not planned; the window and the commands cover it.
- `TODO(issue)`: the diagram's layout is a grid (principals first, owned types after their owner); labels on short lines are dropped. An automatic graph layout and zoom would help large models.
- M15c's scaffolding, which needs DbContext discovery, can now use `daedalus/ef/contexts`.
