# M49 checkpoint: the hosts' .NET runtime

Date: 2026-10-18. The maintainer's report of the same day: the installed nightly `0.4.0-nightly.20261018.224` was unusable on their Mac. Its hosts ask for the .NET 11 RC2 runtime (`11.0.0-rc.2.26504.105`, `rollForward` Major); the Mac had .NET 8–10 in `/usr/local/share/dotnet` and 10.0.12 and 11.0.0-rc.1 in `~/.dotnet`. Every host exited at once, and all the user saw was "[codalus.welcome] failed: The connection was lost." The scope is the roadmap's [M49](../roadmap.md#m49--the-hosts-net-runtime); the decisions are [ADR 0080](../adr/0080-the-hosts-dotnet-runtime.md) and D35 (proposed). Branch `claude/m49-host-runtime`, from `develop` at `4b1dacfb`.

## Done

**The runtime check before a host starts** (`Codalus.Rpc`, `HostRuntime/`):
- `FrameworkVersion` (SemVer 2, as the host reads folder names) and `FrameworkResolver`: hostfxr's resolution (`fx_resolver.cpp`, `fx_reference.cpp`), a pure component.
  - Disable, LatestPatch, Minor, LatestMinor, Major and LatestMajor.
  - A release reference prefers releases; a pre-release reference takes both. A release match rolls to its latest patch, and a pre-release match doesn't.
- `RuntimeConfig` reads `runtimeconfig.json` (`framework` and `frameworks`) with the host's precedence: `--roll-forward`, `DOTNET_ROLL_FORWARD`, the framework's `rollForward`, `runtimeOptions.rollForward`. It also applies `DOTNET_ROLL_FORWARD_TO_PRERELEASE=1` and `--fx-version`. A value the host would refuse makes it null: not judged.
- `DotnetRootResolver` finds the root the host would use:
  - the muxer's folder, with its links resolved;
  - for an app host: `DOTNET_ROOT_<ARCH>`, `DOTNET_ROOT(x86)`, `DOTNET_ROOT`, `/etc/dotnet/install_location[_<arch>]` or Windows' registry, then the default location.
- `HostRuntimeCheck.Check(ProcessLaunchInfo)` handles app hosts and `dotnet [exec] [--runtimeconfig …] [--roll-forward …] app.dll`. Installed versions need their `deps.json`, minus `DOTNET_DISABLE_RUNTIME_VERSIONS`. When it can't tell, it doesn't check: no runtimeconfig, self-contained, a root that doesn't exist, an SDK command. `CODALUS_SKIP_RUNTIME_CHECK=1` turns it off.
- `LocalProcessLauncher` runs the check, and a missing runtime throws `HostRuntimeMissingException`. `JsonRpcConnectionLostException` is unsealed, so existing catches take the subclass. `ProcessLaunchInfo.CheckRuntime` turns the check off for one launch.

**A host that exits says why** (`SupervisedProcess`, `JsonRpcConnection`):
- The first 50 lines of each start's standard error are kept. `JsonRpcConnection.ExplainLoss` (new) supplies the exception that pending and later requests fail with. The supervisor's waits up to 3 s for the exit and 1 s for the end of standard error (`IHostProcess.ErrorCompleted`, a default member). It returns `HostExitedException`: the exit code, the lines, whether the host was still starting, and the first 6 lines in its message.
- **Requests after the loss:** a request sent after reading stopped fails at once with the same exception. It used to wait.
- **The Output channel:** the raw lines go to it as before, followed by a summary line.
- **No restart after an exit during startup** (`SupervisionPolicy.RestartAfterStartupExit`, false by default).
  - Startup lasts until `Initialize` finishes.
  - Without `Initialize`, an exit counts only if it has a failure code and standard error output, before the first message and within `StartupWindow` (2 s).
- **`LastFailure`, and `Connection` after giving up,** throw the same kind of exception, not "X is not running".

**The IDE's runtime, one notification, and the hosts again** (Workbench `Setup/`, the shell):
- **`IdeRuntime.Requirements`:** what the nine hosts' `codalus-*.runtimeconfig.json` files ask for. Per framework, the highest version. The Windows-only designers run on the app's runtime and aren't counted.
- **Check Environment** gets a row of its own, `dotnet-runtime`, ".NET runtime for Codalus IDE".
  - It is resolved under the hosts' root (`HostsRoot()`).
  - When the runtime is missing, the row has `WantedVersion`, `WantedChannel`, and `Found` (each root's versions, shortened: `8.0.20, 9.0.9, 10.0.0–10.0.9 in /usr/local/share/dotnet; 10.0.12, 11.0.0-rc.1… in ~/.dotnet`).
  - The SDK row lost M30b's runtime comparison, which used plain version order.
- **`FindSdkRoot`** prefers a root with SDKs and that runtime: DOTNET_ROOT or the PATH's when it has it, otherwise an installers' folder that has it, otherwise as before.
- **`UseUserDotnet`** also sets `DOTNET_ROOT` when the app hosts would use another root than the chosen one: they don't look on the `PATH`. It logs a missing runtime.
- **One notification**, `OfferHostRuntimeAsync`, once per session until an install, whatever reports it:
  - the startup check (`CheckEnvironmentAsync`, not offered on its own when no SDK is installed at all);
  - a solution that can't open (its error isn't shown separately, and the solution reopens after the install);
  - the plugin hosts (`PluginManager.HostRuntimeMissing`, once per host group).
  - **The text:** "Codalus IDE needs the .NET 11.0.0-rc.2.26504.105 runtime, which isn't installed (found: …). Without it, plugins, builds, language services and debugging can't start."
  - **Its actions:** **Install .NET 11.0** and **Check Environment**.
  - A runtime missing for a program outside the IDE's folder (a designer on the app's runtime) isn't the IDE's.
- **Install .NET** runs M37's plan for the runtime's channel: `dotnet-install.sh --channel 11.0` into `~/.dotnet`, or winget's SDK package on Windows. The SDK brings the runtime. The new root becomes `DOTNET_ROOT`.
- **Then `RestartHostsAsync`:**
  - the plugins that failed with their host are activated again (`PluginDescription.FailedWithItsHost`, `RetryFailedHostsAsync`);
  - the language services that couldn't start are started (`LanguageService.RetryFailedAsync`);
  - the solution that couldn't open is reopened;
  - an Info notification says so. No restart is needed.
- **The plugin manager** reports a host that couldn't start (its runtime, or an exit during startup) once per group, with no "Plugin 'x' failed" per plugin.

**Updates** (ADR 0080's option A):
- `codalus-release feed-runtime <feed> <version> <app>` (new, `FeedRuntime`) writes `CodalusFrameworks` into the release's entries from the published hosts' runtimeconfig files. `eng/package.sh` runs it on every `releases.*.json` before signing, so the signature covers it.
- `UpdateRuntime.Requirements` reads it, with the same `DOTNET_ROLL_FORWARD*` variables. Feeds from before M49 ask for nothing. The Velopack and feed-only backends put it in `UpdateOffer.Requires`.
- `UpdateService.RuntimeCheck` is the shell's `EnvironmentCheck.RuntimeStatusFor`, satisfied under any .NET root. A missing runtime is `UpdateStatus.NeedsRuntime`, with no download, in a check or a channel switch.
- The shell warns: "Codalus IDE X is available, but it needs the .NET … runtime, which isn't installed (found: …)". Its actions are **Install .NET …** (the install, then a check again), **Update Anyway** (downloads), and **Release Notes**. Help → Check for Updates says it again.

**Smoke test:** step `setup.hostRuntime` (M49, after `plugins.host`):
- the shipped hosts' runtimeconfig files name `Microsoft.NETCore.App`;
- the runtime row is Found;
- the plugin host's own check passes.

On every OS the release runs on, this proves the check agrees with the hosts that just started.

## The review (2026-10-19)

An adversarial review of the branch (PR #48) confirmed 26 findings, five of them repeats, and contested 4. All are fixed, each with a test where one can show it. M49 gates 0.4.0.

**Resolution:**
- **A wrapper or launcher's folder taken as the muxer's root** (Homebrew's Cellar script, snap's `/usr/bin/snap`) refused programs that start. `ForMuxer` now needs `host/fxr` in the folder, and otherwise the check stands aside. Test: `HostRuntimeTests.An_app_host_uses_dotnet_root…`, the wrapper case.
- **`UseUserDotnet` sent the hosts from a root with their runtime to an SDK root without it** (a distribution's runtime-only package, Microsoft's runtime package). `EnvironmentCheck.ChooseDotnetRoot` points them at the chosen root only when that helps. Test: `HostRuntimeSetupTests.The_hosts_stay_on_a_root_with_their_runtime…`.

- **A `DOTNET_ROOT[_<ARCH>]` whose folder is gone** made a false Missing. It is passed over, as hostfxr does. Test: the stale variable in `An_app_host_uses_dotnet_root…`.
- **Setting only `DOTNET_ROOT` did nothing when `DOTNET_ROOT_<ARCH>` was set.** `PointHostsAt` sets that one too. Test: `An_architectures_own_dotnet_root_is_pointed_too…`.

**Processes:**

## The second review (2026-10-19)

A second review found 7 defects, and CI on `e1328a45` failed one test on Windows. All are fixed, each with a test.

- **Windows on Arm (high).** The win-x64 build is an x64 process there, and can't load the native .NET in `%ProgramFiles%\dotnet`.
