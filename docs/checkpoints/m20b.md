# M20b checkpoint: the Mono debug adapter (partial)

Date: 2026-10-14. Builds on [M20a](m20a.md). Decision and findings: [ADR 0065](../adr/0065-mobile-debugging-through-a-mono-adapter.md).

**Status: partial.** The adapter, the Android session flow and their tests are built. On the Android emulator here, though, the runtime's debugger agent isn't dependable (see the findings), so F5 on a mobile app still says debugging isn't available. `CODALUS_MOBILE_DEBUG=1` turns the session on, for working on it.

## Built

**The vendored debugger libraries** (`src/ThirdParty/debugger-libs`, MIT): Mono.Debugger.Soft, Mono.Debugging and Mono.Debugging.Soft.
- They come from the fork that .NET Meteor and DotRush maintain, at a recorded commit, built on `net10.0` without our analyzers.
- One behavioural change: assembly loads are requested without suspending the VM.
- The README lists the changes and how to update.

**`codalus-monodbg`** (`src/Codalus.Debugging.Mono`), a Debug Adapter Protocol server on stdio over Mono.Debugging:
- `DapServer`: `Content-Length` framing, one request at a time. Any failure becomes an error response, never a crash.
- `MonoAdapter`:
  - initialize, with capabilities and the `initialized` event after the response;
  - attach, answered at once and connected in the background;
  - breakpoints with conditions, hit counts and logpoints; exception filters (all and unhandled);
  - threads, stack trace, scopes, variables, evaluate, exception info;
  - continue, next, step in and out, pause, disconnect (detach).
- `ListeningAgentArgs`:
  - connects to an agent that listens (through `adb forward`) and greets it with `start debugger: sdb`, retrying while the app starts;
  - keeps the connection open with a version request every two seconds;
  - leaves the live connection open when Mono.Debugging cancels the launch.
- stdout carries only the protocol: the libraries' `Console.WriteLine` goes to stderr, or to `CODALUS_MONODBG_LOGFILE`.
- Shipped in `monodbg/` next to the shell; `CODALUS_MONODBG` overrides it (`MonoDebugger.Resolve`).

**The session** (`AndroidRunner.DebugAsync`, `DebugService.AttachMonoAsync`, `DebugAdapter.AttachAsync<T>`, `MonoAttachArguments`):
1. Install as for a run.
2. Forward a free port; set `debug.mono.connect` and `am set-debug-app`.
3. Start the attach, then the app (its runtime listens for only two seconds).
4. On the session's end: stop the app, clear the property and the mark, and remove the forward.

## Findings

Established with probes against the runtime: a raw socket, Mono.Debugger.Soft alone, Mono.Debugging alone, and the agent's own log through `debug.mono.extra` and `debug.mono.log`. ADR 0065 has the details.
- **Idle drop.** The agent drops a connection that sends it nothing for about eleven seconds. Fixed by the version keepalive.
- **Suspending on assembly loads.**
  - At policy All, one event never reaches the client, and the agent then stops answering until the connection drops (`MONO_THREADS_SUSPEND` doesn't matter). Fixed by policy None.
  - Policy EventThread makes the agent assert.
- **Filtered type loads never fire.** By source file (name or full Windows path) or by type name, though unfiltered ones do and the runtime has the app's symbols. Not fixed.
- **Breakpoints and stalls.** An unfiltered type-load request can bind a breakpoint, and it is hit. After resuming from it, the app stalls until the connection drops. Not fixed.

## Tests

- **Debugging** `MonoAdapterTests` (3), on the real adapter process through the DAP client:
  - initialize with capabilities, then breakpoints before an attach;
  - an attach where no agent listens ends the session with the address;
  - unknown requests fail without ending the session.
- **End to end** `MobileShellTests.A_maui_app_is_debugged_on_an_android_emulator`: runs with `CODALUS_TEST_ANDROID=1` and `CODALUS_MOBILE_DEBUG=1`, and doesn't pass yet (the findings).

**Validation**: Windows.
