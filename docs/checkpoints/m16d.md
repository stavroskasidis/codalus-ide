# M16d checkpoint: web front-end depth (M16 complete)

Date: 2026-10-10. Decision: [ADR 0027](../adr/0027-web-front-end-depth.md). With M16a–M16c this completes M16 (Razor, Blazor and web front-end). M31 follows; it publishes, so the maintainer confirms it first.

## Built

**Debugging the server and the page together** (`DaedalusStudio.Debugging`, workbench `DebugService`, shell `ShellHost.BrowserDebug.cs`)
- **`CompoundDebugAdapter`:** several adapters as one `IDebugAdapter`.
  - The primary (netcoredbg) is launched with the session. Others join (`AddAsync`) and get its breakpoints, function breakpoints and exception settings replayed.
  - Ids are the adapter's times four plus its index, so each request goes to its adapter. A joined adapter's threads are named `Browser: …`.
  - A breakpoint is bound when any adapter bound it.
  - One stop shows at a time; another waits until the shown one resumes. Break All pauses every adapter, and Continue from it continues them all.
  - The session ends when any adapter ends: the others are disconnected, terminating their debuggees.
  - An adapter that can't join leaves the session running.
- **`DebugService`:** `LaunchCompoundAsync`, `AddBrowserAsync`, `IsCompound`.
- **`LaunchPlanner.PageDebugTarget`:** a profile with `inspectUri` (a Blazor Web App with WebAssembly components) always debugs its page; one that launches a browser does when `debug.javaScript` is on (the default).
- **F5 on a web app:** the server starts under netcoredbg. Once it prints "Now listening on", the browser joins through `js-debug` (with the proxy's `inspectUri` when there is one). Without a browser the server debugs alone, and a WebAssembly app says why.
- **Debug a Web Page** (`debug.webPage`): an http, https or file URL, or an HTML file, in the browser under `js-debug`. F5 on an open HTML file with no startup project, and Debug in Browser on an HTML file in Solution Explorer, do the same.
- **The web root** for scripts is the project's `wwwroot` when it has one, for M16c's WebAssembly apps too.
- **Diagnostics:** `DAEDALUS_JSDEBUG_TRACE=<folder>` writes js-debug's logs (`BrowserLaunchArguments.Trace`).

**HTML and CSS inside Razor** (workbench `RazorHtmlProjection`, shell `ShellHost.RazorHtml.cs`)
- **The projection:** a Razor file's HTML, same length and positions, C# and Razor syntax blanked. Markup inside `@if`/`@foreach` blocks and `@:` lines stays; `@@` becomes `@`.
- **The HTML server** gets it as `Counter.razor__virtual.html`, opened and updated on demand.
- **The editor:**
  - at a markup position it asks the HTML server too, and merges completion and hover with the C# host's;
  - `<`, `"`, `/` and `=` trigger completion in Razor files;
  - the projection's diagnostics are dropped.
- **Install offer:** opening a Razor file offers the web language servers.

**Scoped CSS** (`ScopedCss`, `ShellHost.ScopedCss.cs`): in `X.razor.css` (and `.cshtml.css`) selectors, completion adds the class names and ids of the component's markup, and `::deep`. Nesting under the component already worked.

**npm** (workbench `Npm`, shell `ShellHost.Npm.cs`, `TaskRunnerViewModel`/`View`)
- **Packages:** `package.json` files under the solution's and projects' folders, with their scripts and `"-vs-binding"` bindings.
- **Which npm:** the user's (npm.exe shims, npm-cli.js beside node.exe, `cmd /c npm.cmd`, or `npm` on Unix), or the built-in Node.js's.
- **The Task Runner Explorer:** run (`npm run` in a terminal of its own), restore (`npm install` into the npm output), open `package.json`. Also the commands Run npm Script… and Restore npm Packages, with a context menu on `package.json`.
- **Bindings:** Before Build (a failure stops the build), After Build, Clean, Project Open.
- **Restore on open:** `npm.restoreOnOpen` (ask, always, never). `npm.runtime` (auto, builtIn).

**ESLint** (`LanguageService` linters, `Eslint`)
- **Linter services:** `IsLinter`, `Accepts`, `ScopedConfiguration` and `AcceptedRequests` on `LanguageServiceDescriptor`. A linter gets the documents it accepts next to their language service, and its quick fixes join the lightbulb.
- **The ESLint server:** vscode-eslint's (in `vscode-langservers-extracted`), for files under an ESLint configuration; setting `web.eslint`.
- **The client:**
  - pull diagnostics (`textDocument/diagnostic` after open, change and save, and on `workspace/diagnostic/refresh`);
  - `workspace/configuration` per `scopeUri`;
  - `workspace/applyEdit` and `workspace/executeCommand`;
  - a server's own requests acknowledged and logged.
- **`DiagnosticsStore`** keeps each source's diagnostics of a file.

**Prettier** (`Prettier`, `ShellHost.Prettier.cs`): Format Document and format on save run the project's Prettier (installed and configured) on Node.js. Only the changed middle of the text is replaced. Setting `web.prettier`.

## Found along the way

- **js-debug's browser connection:** it goes through the `inspectUri` proxy, so the server must answer when the browser joins. It does: the browser opens `about:blank` and navigates once it is attached.
- **Fingerprinted scripts don't map:** a script referenced through `@Assets["app.js"]` is served as `app.<hash>.js`, which js-debug can't map back to `wwwroot/app.js`. The fixture references `app.js`.
- **.NET 11 RC1's Blazor templates** have no `inspectUri` and no `UseWebAssemblyDebugging`: M30b.
- **Pull diagnostics only:** vscode-eslint's server in `vscode-langservers-extracted` 4.10 never publishes diagnostics. The language service now pulls from servers that declare a `diagnosticProvider`.
- **One source per file:** `DiagnosticsStore` kept one source's diagnostics per file, so a second server (ESLint) would have replaced the first's (TypeScript).
- **Completion commits ignored an item's edit range:** a CSS pseudo-element (`::after` over `::af`) would have become `::::after`. Commits now replace the item's range, as snippets already did.
- **netcoredbg** can't evaluate `OperatingSystem.IsBrowser()` (a static call through implicit usings). The test evaluates a field.
- **The CI smoke test at 6db6e42 failed, on Linux only:**
  - right after the M16c tests, the C# service reported ready, then answered nothing: diagnostics, completion and inlay hints timed out, and `editor.editing` hung until the job's 40 minutes ran out;
  - the same commit's published app passes the whole smoke test on Windows (39 steps in under 2 minutes), and the Mac passed it with M16c before;
  - the first suspect was something the new browser tests leave running on Linux; CI at 12e0844 showed nothing left running, and the smoke test failed the same way (see Validation).
