# M30a checkpoint: .NET 11 projects

Date: 2026-10-10, on the .NET 11 SDK's first release candidate (11.0.100-rc.1.26425.128). Decision: [ADR 0025](../adr/0025-hosts-and-the-users-sdk.md) (D22). M30b follows at .NET 11 GA (November 2026): Daedalus itself moves to .NET 11.

**The split.** M30 can't finish before GA ("the milestone isn't done until it builds on the GA SDK"), and the language host's Roslyn has to wait for the GA packages on nuget.org.
- **M30a:** everything that works while Daedalus still runs on .NET 10.
- **M30b:** the move itself, listed under "Not done".

## Built

**Hosts and the user's SDK** (ADR 0025)
- **Every host** has `RollForward=Major`: .NET 10 when it is installed, else the next newer .NET.
- **The build host uses the SDK that `dotnet` resolves for the solution's folder**, `global.json` included, as `dotnet build` does there. It used to take the newest SDK it could load, which ignored a `global.json` that pins an older SDK.
- **A newer .NET's SDK:**
  - `BuildHostRuntime` (Workbench) runs `dotnet --version` in the solution's folder, only when an SDK newer than the hosts' .NET is installed (about 100 ms).
  - When that SDK is newer, the build host starts with `DOTNET_ROLL_FORWARD=LatestMajor`, plus `DOTNET_ROLL_FORWARD_TO_PRERELEASE=1` for a preview. So it runs on .NET 11 and loads the .NET 11 SDK's MSBuild.
- **When the SDK can't be loaded:** the host falls back to the newest SDK it can load. It says which SDK the solution asked for and why (`initialize`'s `sdkWarning`), in the Output window and the .NET SDKs panel.
- **Generators built for a newer compiler** (`SdkAnalyzers` in the language host): an SDK's analyzer folder whose assemblies reference a newer Roslyn than the host's is replaced by the same folder of the newest other installed SDK that the host can load. The Language Services output says so, with both compiler versions. Load failures for that reason are reported the same way, instead of as a bare failure.
  - **Found by the smoke test:** with the .NET 11 SDK installed, solutions without a `global.json` now get it, and its Razor generator (Roslyn 5.11) didn't load in the host (5.9). Razor in the `net10.0` Blazor fixture lost its C# features. The fallback brings back the .NET 10 SDK's generator, which also serves `net11.0` projects.

**.NET 11 projects**
- **Open, build, run, debug, test, Hot Reload:** they all work on SDK 11 RC1, with no product changes beyond the build host's SDK. Debugging uses the pinned netcoredbg on the .NET 11 runtime.
- **New Project:** asks for the target framework when the template offers a choice, from the SDK the location uses, the template's default first. `dotnet new` now runs in the location, so a `global.json` there applies.
- **Lists:** `net11.0` and its platform variants in the project-file completion; C# 15 in `LangVersion` (completion and the property pages).
- **.NET SDKs panel:** each SDK's support status (supported until, out of support since, preview) from a pinned lifecycle table (`DotnetSupport`). The warning above, when there is one.

**Fixture:** `samples/Net11`, with a `global.json` that pins the .NET 11 SDK (release candidates allowed):
- `Shapes`, a library for `net10.0` and `net11.0`;
- `App`, a `net11.0` console app with launch profiles (`Watch` for Hot Reload);
- `Components`, a `net11.0` Razor class library;
- `Shapes.Tests` (xUnit, VSTest, `net10.0;net11.0`) and `Shapes.MtpTests` (xUnit v3, MTP, `net11.0`).

**Tests**
- **Projects:** `DotnetVersionsTests`:
  - the Net11 fixture opens through the build host on the .NET 11 SDK (rolled forward), evaluates both frameworks, gets .NET 11 reference assemblies from the design-time build, builds, and runs on .NET 11;
  - a `global.json` that pins an older SDK (the oldest installed from 8.0 on) gets exactly that SDK;
  - which SDKs a runtime can load, and the warning's text.
- **Workbench:** the roll-forward environment, the check for a newer SDK, and the support statuses.
- **Language host:** `SdkAnalyzersTests`, on a fake SDK layout with generated assemblies: a generator for a newer compiler is replaced by an older SDK's, files missing there are left out, other folders stay, and without an alternative the reason is logged.
- **Headless UI:**
  - `Net11Tests`:
    - the language service with no false errors and a cross-project hover, a C# hover in a `.razor` file of the `net11.0` library, then F5 to a breakpoint on .NET 11;
    - tests on `net10.0` and `net11.0` (VSTest), and MTP with coverage of the library;
    - Hot Reload of a method body through the .NET 11 SDK's `dotnet watch`.
  - The .NET SDKs panel shows the SDK in use and every SDK's support status.
- **Plugins:** the framework choice (parsed from `dotnet new <template> --help`), and New Project with a framework.
- **Markup host:** `net11.0` in the target framework completion.
- **Smoke test:** step `dotnet.net11` (M30): the Net11 fixture opens with the .NET 11 SDK, builds, and runs on .NET 11.
- **The fixtures' SDK:** tests copy fixtures out of the repository, where no `global.json` applied. They used whatever SDK was newest, so installing SDK 11 would have moved every test to it. `tests/Shared/FixtureSdk.cs` now pins the repository's SDK above every copied fixture, and `samples/Net11` brings its own. The smoke test still uses the newest SDK, as a user would.

**CI and validation:** `ci.yml` and `release.yml` install the .NET 11 SDK next to the pinned one. `eng/validate.sh` (WSL and the Mac) installs it from `samples/Net11/global.json`.

**Docs:** ADR 0025, the build host protocol (`sdkWarning`, the roll-forward variables), [Moving to a new .NET release](../release/dotnet-upgrade.md) (the checklist for each release), the user guide (prerequisites; the SDK in use, support statuses, the .NET 11 gaps; New Project's framework).

## Found along the way

- **CI hung after M16b:** the Linux job's Shell tests ran until the job's 40-minute limit and were cancelled, without naming a test. Now:
  - CI runs the tests with MTP's hang dump (`--hangdump`, package `Microsoft.Testing.Extensions.HangDump`, MIT, test-only). A test process still running after 25 minutes is dumped, and the tests that were running are named.
  - The language requests in the Web, Blazor and Net11 tests have a 30-second token (`ShellFixture.RequestTimeout`). A server that never answers fails the test instead of blocking the UI thread forever.
  - **The hang's cause is still unknown.** The next CI run should name it. `TODO(issue)`.
- **The same run:** `GitDepthShellTests` asserted the Git Changes view model right after the status changed, but the view model follows through `Ui.Post`. It waits now.
- **`dotnet new <template> --help` differs by console width:** a wide console lists the frameworks in the option's placeholder (`--framework <net10.0|net11.0>`), a narrow one (Linux, redirected) only under it, after "Type: choice". The parser reads both (found by the WSL run).
- **Under the full suite's load on Windows,** `PluginTerminalTests.Text_sent_to_a_shell_runs_and_kill_ends_it` twice waited more than 30 seconds for `cmd`'s `42`; it passes on its own. The output is raw ConPTY text, so the likely cause is escape sequences on the result's line. The test now strips them and, if it still times out, prints what it got.

## Not done, and deviations

- **M30b, at .NET 11 GA (November 2026):**
  - Daedalus on .NET 11: `global.json`, `net11.0`, Native AOT on 11, the dependencies checked, budgets before and after;
  - Roslyn 5.11 (the .NET 11 SDK's compiler) in the language host and C# Interactive. nuget.org has 5.9.0 at most today. Until then:
    - C# 15 syntax shows errors in the editor (it builds);
    - Razor files use the .NET 10 SDK's Razor generator, because the .NET 11 SDK's references Roslyn 5.11. With only the .NET 11 SDK installed, they get no C# features. The targeting pack's generators (Roslyn 4.4 and 5.0) and the SDK's analyzers (4.14) load as they are.
  - the regular fixtures (`BuildAndRun`, `Debugging`, `Testing`) get `net11.0`, and `samples/LanguageFeatures` gets C# 15 features. They stay on .NET 10 until then, so the suite runs with only the .NET 10 SDK; `samples/Net11` covers .NET 11 meanwhile. This deviates from the roadmap's fixture list.
  - the markup host's `global.json`, `runtimeconfig.json` and MSBuild schemas: unchanged in M30a, apart from the new frameworks and C# 15, because no new keys are known for .NET 11. Check them against the GA documentation.
- **Out-of-support dates for .NET 11:** not announced yet; `DotnetSupport` shows ".NET 11.0 (STS)" without a date. The upgrade checklist covers filling it in.
- **An SDK whose runtime is missing** (only possible for a broken install) gets the fallback and the warning, but is not tested.
