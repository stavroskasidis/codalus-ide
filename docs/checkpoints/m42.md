# M42 checkpoint: WCF

Date: 2026-10-16. Decision: [ADR 0069](../adr/0069-wcf-references-and-test-client.md). The first milestone of the [Windows desktop](../roadmap.md#proposed-phase-windows-desktop) phase; nothing in it is Windows-only, so it didn't wait for D31.

## Done

**Add Service Reference for WCF** (build host: `SolutionSession.Wcf.cs`, `ProjectManagement/WcfConnectedServices.cs`; [project-protocol.md](../project-protocol.md#wcf-references)):
- `wcfReferences/status`, `install`, `list`, `add`, `update`, `remove`, and the `wcfReferences/output` notification.
- **The tool is the user's**: `dotnet-svcutil` as a local tool (the manifest) or a global one, run as `dotnet svcutil` in the project's folder, trusted solutions only (it builds the project to reuse its types), one run at a time, killed with its process tree on cancel, telemetry off. **Install** asks, then installs it as a local tool (a manifest first) or restores the manifest's tools.
- **Visual Studio's layout**: svcutil generates `Connected Services/<name>/Reference.cs`, and its `dotnet-svcutil.params.json` becomes Visual Studio's `ConnectedService.json` (the options under `ExtendedData`, `inputs` first then alphabetical; the WCF provider's id and version). **Update** writes changed options into that file and runs `svcutil --update` on the folder, which reads it. References in svcutil's own layout are listed and updated too. **Remove** sends the folder to the trash; the packages stay.
- **Options**: namespace (default: the name), collection and dictionary types (Visual Studio's lists), synchronous operations, type reuse, internal access.
- A project file svcutil changed (the `System.ServiceModel.*` packages) is evaluated again and restored.

**CoreWCF services**:
- New Project offers **Install the CoreWCF templates…** (`dotnet new install CoreWCF.Templates`) while the `corewcf` template isn't installed, as it offers Avalonia's; the known packs are a list (`TemplatePacks`), and the template shows as "CoreWCF Service".
- **The service's metadata at run time** (`WcfServiceDiscovery`): a CoreWCF project's endpoint paths from its `AddServiceEndpoint` calls, its addresses from the running program's "Now listening on" lines (Run, or the debugged program's output), asked for `?wsdl` on loopback only. Discover in Add Service Reference and Running Services in the test client use it.

**The WCF Test Client** (workbench `Wcf/`: `WsdlReader`, `XsdSchemaSet`, `SoapRequest`, `SoapClient`, `SoapResponse`, `WcfTestClient`; shell `WcfTestClientView`, `WcfViewModels.cs`, `ShellHost.Wcf.cs`):
- AOT-clean, in the shell's process: WSDL 1.1 and XSD read with `System.Xml.Linq` (imports followed, 64 documents and 16 MB each at most), SOAP over `HttpClient`. No `System.ServiceModel`.
- Endpoints with their binding: SOAP 1.1 (`text/xml`, `SOAPAction`), SOAP 1.2 (`application/soap+xml` with the action) with WS-Addressing 1.0 headers when the binding's policy wants them; an endpoint with WS-Security, reliable sessions or a non-HTTP address is listed with the reason; duplex callbacks are reported.
- A form per operation from the input message's schema: simple values (checked against their XSD types before sending), enumerations and booleans as choices, nested types, repeated elements with Add and Remove, `xsi:nil`; optional empty fields left out; RPC style too. The XML follows the form until edited, then is sent as it is.
- The response as a tree and as formatted XML; SOAP 1.1 and 1.2 faults with their code and reason; the status and time.
- Commands `wcf.testClient` (Tools menu) and `wcf.addServiceReference` (Project menu, Solution Explorer's Add menu); `web.serviceReferences` says WCF too. The Service References document's WCF page and a WCF reference's Save, Refresh, Open Document, Remove and Test Client.

**Configuration** (markup host `Schemas/system.serviceModel.xsd`, `Xml/ServiceModelConfig.cs`): in `app.config`, `web.config`, their transforms and `*.exe.config`, the `system.serviceModel` section's completion (elements, attributes, values, the file's own binding and behavior names), hover (the schema's documentation and values), and validation of the section as warnings.

## Gaps

- **The test client**: WS-Security (message security, `TransportWithMessageCredential`), reliable sessions, duplex contracts, NetTcp and named pipes, MTOM, metadata only through WS-MetadataExchange (MEX), and custom SOAP headers in the form. `TODO(issue)`
- **The service's metadata at run time** comes from the sources' `AddServiceEndpoint` calls with literal paths; endpoints added from configuration or computed addresses aren't found (the address can be typed). `TODO(issue)`
- **svcutil's packages**: `dotnet-svcutil` 8.0.0 adds `System.ServiceModel.*` 4.10.* to a `net10.0` project, even beside newer ones; the IDE leaves the tool's choice (the fixture pins 10.0.652802). `TODO(issue)`: offer to align them.
- **Installing svcutil** isn't covered by a test (it would download the tool); the code is `scaffold/install`'s path with another tool id.
- **The configuration schema** is ours and partial: custom binding elements, credentials and less common behaviors take any attribute; a `web.config` whose `<configuration>` has a namespace isn't checked. `TODO(issue)`: grow it with M43.
- **Service Configuration Editor** (Visual Studio's, proprietary) has no counterpart beyond the schema's completion.
