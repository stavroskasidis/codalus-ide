# M66 checkpoint: performance pass, round 4

Date: 2026-11-24. [M66](../roadmap.md#m66--11-performance-pass-round-4): the maintainer asked for a performance pass for every project type: load time, code analysis time, highlighting, and how each scales with solution size and project size in files.

## How the pass was done

- **A survey, then a review.** Ten surveys read the code area by area: the build host, the C# host's load, code analysis, highlighting, the other languages, the Solution Explorer, the workbench's services, the RPC layer, startup and memory, and the editor. An eleventh measured real fixtures in a Linux container (4 cores, Debug build, so the numbers are diagnostic only). Two reviewers checked each finding, one for whether its path is hot, one for whether its fix keeps behavior. 104 findings: 35 refuted, 69 kept, grouped into 34 units. Four units were left out by the plan, and the maintainer chose to build the rest, maybes included.
- **What the measurements showed** (local, Debug; never budgets):

  | Workload | Phase | Time |
  |---|---|---|
  | `Solution50`, cold | evaluated | 4.1 s |
  | | design-time built | 7.3–8.2 s |
  | | `language_ready` | 15.7–16.8 s |
  | `Solution50`, warm | `language_ready` | 5.3 s |
  | 300 projects, cold | evaluated | 12.9 s |
  | | design-time built | 35.3 s |
  | | `language_ready` | 65.6 s |
  | One project of 5,000 files | `language_ready` | 21.7–23.6 s |
  | `Large100k.cs` | colors | 4.5 s after the launch |

  The cold background pass is the long pole. The language host's CPU on `Large100k` went to diagnostics in the span (1.35 s), folding (1.1 s), the inheritance margin, inlay hints and semantic tokens.

## Done

28 of the 30 units, one commit each (two units took several); round 2 below took the other two and the deferred parts.

**Load time**
- **The Start drop-down no longer evaluates the project.** Each project change while a solution loaded refreshed the Start drop-down. The refresh asked the build host for the startup project's run information, a full MSBuild evaluation: about 1 CPU-s on a 50-project open and 3.5 on 300. The drop-down now reads `launchSettings.json` itself. Run and debug still ask the host, whose RunInfo handler now honors cancellation.
- **Multi-targeted projects merge their items through a set.** The per-framework item merge scanned the whole list for each item, which is quadratic: 175–378 ms on a few thousand files, about 5 ms now.
- **A warm open checks shared files once per batch.** Cache hits stat'ed every reference pack once per project, tens of thousands of identical checks on 300 projects. Each batch now checks a file outside the solution once; the solution's own files are still checked every time. Each project's configuration is looked up in a map, and the cache file is read as UTF-8 bytes.
- **The C# host's project loads:**
  - Projects' command lines are read in parallel, outside the workspace lock.
  - References with aliases or embedded interop types stay the same instance while their file is unchanged; a new instance at every update had dropped the project's compilation.
  - Projects take the reference pack that Miscellaneous Files already loaded.
  - Lookups of generated documents ask the projects under whose folder the document is first.
- **Parsing during the load.** The C# host parses the loaded projects' files while the solution is still loading, on one worker, parsing only. On a 50-project open the pass then had 1–2 s less to do, and 4–6 s less on 300 (the survey's estimate).
- **Design-time builds log critical events only** (errors and warnings). The start events of every project, target and task cost the worker nodes about a tenth of their time. Errors still name their project, in process and from a worker node; there is a test for each.
- **Kept reference images are read again only when they change.** The analysis solution's images of kept reference assemblies are read from disk again only when the file or its documentation changed.

**Code analysis**
- **One bind per project.** The background pass gets compiler and analyzer diagnostics in one call (`GetAllDiagnosticsAsync`) instead of binding the project twice. **Visible change:** a project's `DiagnosticSuppressor`s now hide compiler warnings in the editor too, as the build does (nullable, xUnit, Razor). The language state cache's schema moved to 3, so last session's entries aren't served.
- **A method body edited below a project keeps its diagnostics.** A project is kept when its own files and options are unchanged and the projects it references keep their semantic versions. Roslyn moves a semantic version only when something outside a member's body changes. If a referenced project's source generators wrote something else, the projects kept this way compile after all.
- **No more false republishes.** Diagnostics are compared by value with their tags: the tag arrays were compared by reference, so a closed file with a deprecated or unnecessary item was published again after every pass. Each message is also formatted once.
- **Reference assemblies are written after the pass publishes.** The pass used to emit them before publishing anything: about 1 CPU-s on 50 projects, 3.4 on 300. A single writer now emits them after the pass, carried over passes until written, and the host's shutdown waits for it within its time.
- **The compacting collection runs after bursts only.** The C# host ran a full blocking collection after any pause in typing; it now runs only after 256 MB of allocation or that much fragmentation.

**Highlighting**
- **A C# file's first colors come from its syntax** (the maintainer's choice). A cold file showed no colors until its project compiled, 1.6–5 s in.
  - If the full answer isn't ready within 150 ms, the first token request answers from the syntax alone: keywords, literals, comments, directives, excluded code, operators and punctuation, typed as the full answer types them. The answer is marked `resultId: "syntactic"`.
  - The editor shows these colors only where no full answer is shown, then asks again at once, and the service waits for the full answer from then on.
  - Clients opt in with the experimental capability `codalusSyntacticTokens` (docs/protocol.md). Sticky scroll and the diff view ask again for the full answer.
  - `file_highlight_ms` stays the full answer's colors; `syntactic_highlight_ready` is a new, separate event.
- **The colorizers:**
  - A TextMate token's type is found without reversing its scope list or making a string per scope.
  - A read-only viewer doesn't tokenize the same text again.
  - The semantic, grammar and diff colorizers stop at the furthest column a long line is ever drawn to.
- **C# folding** finds regions from the tree's directives and using groups from the compilation unit and namespaces only. Before, it walked every trivia of the file, documentation comments included, and every node.

**Solution size and project file count**
- **The Solution Explorer:**
  - A project keeps its files and folders while its evaluation and disk listing stand; new compiler inputs rebuild only its Dependencies node. Before, a 5,000-file project's tree was built again just to show its analyzers.
  - A missed reveal no longer walks every project's dependencies.
  - The same search, refreshed, patches its rows in place.
  - A build that kept every project's subtree keeps the index.
- **Find in Files and Replace All** skip files without the words (searches of words only, not regular expressions) and make a string only for matching lines.
- **The Task List** skips files and lines without a token.
- **Code Search**: an edit that keeps a document's declarations, such as typing in a method body, reuses the index snapshot instead of rebuilding it (144k declarations in a large solution).
- **Test Explorer**: an edit rebuilds its own project's tests only; `TestItemCollection.Replace` uses a set; traits are set only when they differ.
- **The status bar's error and warning counts** are kept as diagnostics change, instead of counting the whole solution's diagnostics at each change.

**The wire, the editor and startup**
- **JSON-RPC:**
  - Text goes out as UTF-8 with only what JSON needs escaped. Before, every non-ASCII character and each of `<`, `>`, `&`, `'` and `+` took six bytes.
  - Each incoming message is parsed once, and each frame is written with one write.
  - A remote window copies strings over 256 KB as they are.
- **The LSP client** leaves diagnostics and locations that are already narrowed as they are, without the round trip through `JsonNode`.
- **The editor:**
  - CodeLens resolves four at a time instead of one round trip after another.
  - Inlay hints no longer wait for the inheritance margin.
  - Camel-case matching allocates nothing until it matches.
  - The lightbulb asks the markers' tree.
  - Git's change markers split the index text into lines once per read of the index.
  - The diff view compares texts by length first.
- **Menus and key bindings:**
  - A command's key and a location's menu rules are lookups.
  - A non-default keyboard scheme is applied once at startup.
  - A burst of menu changes rebuilds the menu bar once (the native macOS menu too).
- **Git** asks for the git directory once per open, instead of at every status read and branch list.
- **XAML:**
  - One parse per text, and the element list walked once.
  - Resource keys are a set.
  - A C# edit re-checks only the open XAML files whose project has the file or references it.
- **JSON schemas**: catalog globs are compiled once, and `anyOf`/`oneOf` branches are validated once each.

## Round 2: the deferred work

The maintainer then asked for every deferred item, one at a time (2026-11-24). Each is its own commit with its tests.

**Built**
- **The Start page is the shell's own.** Welcome was the only built-in plugin that activated at startup, so the plugin host started at every launch for it alone (M56's open startup item). The Start page is now a tool window the shell fills itself (`ShellHost.StartPage.cs`): the same tree, commands (`welcome.*`), settings (`welcome.showOnStartup`, `welcome.onboarded`), Help menu entry and status item. The plugin host now starts only for a plugin that asks to. `PluginManager.RegisterBuiltInTree` lets a built-in fill a tree view through the plugins' own tree API, and the `Codalus.Plugins.Welcome` project is gone; `docs/plugins.md` points to another example.
- **Memory-mapped package assemblies.** The C# host maps the assemblies of restored packages (a folder with `.nupkg.metadata`) instead of reading them into memory. Not on Windows, where a mapped file can't be deleted and `dotnet nuget locals all --clear` would fail while the IDE runs. `CODALUS_MAP_PACKAGES=0` turns it off. It stays only if CI's A/B shows the memory gain.
- **The background pass:**
  - A cancelled pass keeps the projects it finished. The next pass serves them if nothing they depend on changed since they were analyzed.
  - An edited project re-analyzes only its changed documents (up to 8). The compilation-wide warnings (unused fields and events: CS0067, CS0169, CS0414, CS0649) carry over, and a full pass follows 10 s later. The log says "analyzed in part (their changed files only)".
- **The build host's design-time cache** looks up a batch's projects in parallel (more than 4). It stays only if CI's A/B shows a gain.
- **The C# host's `ProjectKeys`** has no lock.
- **The wire:** the debug adapter's connection and the remote window's stream write each frame with one write. `benchmarks/Codalus.Benchmarks.Rpc` (`codalus-rpcbench`) measures framing, escaping and round trips.
- **Search:**
  - Code Search updates its index incrementally and keeps the full build's order exactly. A removal falls back to a full build. A test compares 60 random steps against full builds.
  - Find in Files reads up to 8 files ahead, in order.
- **The Solution Explorer's folder view** is kept while its folders are unchanged (folder solutions).
- **The editor:**
  - Completion narrows from the last filter's matches when the typed text only grows.
  - The diff view of a file over 2,000 lines asks for the tokens of the shown lines, with 150 lines either side, and cancels the request when it closes.
  - The Error List rebuilds at once after a quiet stretch, then at most every 250 ms during a burst.
- **JSON schemas:** each schema's `$ref` targets and the patterns (up to 2,000) are kept.

**Closed without a change**
- **Sticky scroll keeping its runs.** No safe invalidation: background TextMate tokenization, diagnostics and bracket colors change the runs without an event, and visual lines are rebuilt at each scroll, so identity checks never hit. Keeping runs would show stale colors.
- **Streamed Git history** (M57's `TODO(issue)`). Measured on 50,000 commits: a page takes 188 ms at any skip without a commit-graph (the `--topo-order` sort, not the skip) and 4–30 ms with one. Streaming would save only later pages, which are off the UI thread already. Writing a commit-graph into a user's repository unasked was rejected. The comment in `GitService.History.cs` now says so.

**Left out by the plan:** sharing `project.assets.json` parses, one shared TextMate tokenizer, lazy overlays and the build output pump (low value or refuted in review).

## Numbers

Every timing above is local and diagnostic. The gains that decide anything come from CI, both versions on one runner in alternating rounds: `open-solution-50` (`designtime_done`, `language_ready`, `cpu_open_s`), `editor-100k` and `self-driven` (`file_highlight_ms` and `syntactic_highlight_ready`), `markup-100k`, `everyday`, `cold-start`, `binary-size`, `memory_idle` and `codalus-rpcbench`. The design-time logging change, the parallel cache lookups and the mapped packages stay only if they beat noise there.
