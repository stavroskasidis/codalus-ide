Date: 2026-10-30. The scope is the roadmap's [M56](../roadmap.md#m56--011-large-solutions-performance-pass-round-3-and-codelens-rows-from-the-first-frame), from the maintainer's request of that day:

- CodeLens that doesn't move the code when it arrives. Their screenshots show a file before and after its lenses came, and the classic IDE's empty rows above the declarations.

## Done

**CodeLens rows from the first frame** (item 1, [ADR 0017's amendment](../adr/0017-navigation-and-inline-information.md#amendment-2026-10-30-codelens-rows-from-the-first-frame)).
- **`CSharpLensScanner`** (`Codalus.LanguageServices.Client`) finds, from the text alone, the lines where the C# host's `textDocument/codeLens` will put lenses. It has two parts:
  - a light lexer: comments; regular, verbatim, raw and interpolated strings with their holes; characters; `#if` branches, taken as a Debug build on current .NET takes them;
  - a walk of the declarations that skips member bodies.
- **`CSharpLensScannerTests` checks it against the host itself.** Both run on the test's cases (types and members, strings and directives, top-level statements, extension blocks, code that doesn't compile yet) and on every C# file of the repository: 1,869 files, 33,707 lenses. They agree on every line. The scanner reads about 150 MB/s.
- **`EditorInsights` keeps those rows, empty, from the editor's first frame** until the service lists its lenses.
  - A listed lens keeps its row while it waits for its count; one that resolves to nothing keeps it empty.
  - An empty row holds a space in the titles' font, so it's exactly as tall as a row with titles. It isn't a link: clicking it does nothing until its counts show.
  - A file over 512 KB is scanned off the UI thread, so its rows can come after its first frame.
- **Rows are kept only where lenses will come** (`IEditorServices.ExpectsCodeLens`): a `.cs` file that isn't generated or read-only, CodeLens on, and a C# service that hasn't failed and, once it runs, offers CodeLens.
- **A file reloaded after a change outside the editor** gets its new text's rows at once. The reload replaces the whole text, which collapsed the lenses' segments.
- **Test:** `NavigationDepthTests.Lens_rows_keep_their_room_from_the_first_frame_until_their_counts_arrive`, with the real C# host. It records every frame from the editor's creation:
  - in the first frame every declaration has its row;
  - the last declaration never moves while the service lists and resolves the lenses, nor after a reload that adds a method.
  - The screenshots `codelens-placeholders` and `codelens-resolved` show both states.
- **Fixed before the commit:** the test's first version took its first look after the open had returned, and on a loaded machine the service's list was there by then. It now records from the editor's creation and passed 10 of 10 runs under CPU load.
- **Found by the validation:** two tests took a CodeLens row to mean its counts had come, which the empty rows broke under load ([ci-flakes](../ci-flakes.md)). `CodeLensDetailsTests.A_members_codelens_shows_its_git_history` failed in the suite; `NavigationDepthTests.Inline_information_shows_hints_lenses_and_inheritance_glyphs` had the same wait before clicking a row. Both now wait for the counts' text.

**How the large-solution costs were found** (items 2 and 3).
- **The solution:** a generated 300-project solution (`codalus-fixturegen solution <dir> 300`).
- **The probe:** opened in the headless shell by a probe test kept out of the repository, which then opened a file and typed in it.
  - A 4 ms heartbeat on the UI thread measured its stalls.
  - The UI thread's posted job was sampled every millisecond (`Ui.Watch`, `Ui.RunningJob`) and attributed to the line that posted it.
  - `dotnet-trace` samples of the test host gave the hot paths.
- **Where:** this cloud container, two runs before the changes and two after. Numbers from one machine decide nothing that CI gates ([benchmarks/README.md](../../benchmarks/README.md)); these only found the costs.

| Open of 300 projects, warm | Before (two runs) | After (two runs) |
|---|---|---|
| Every project evaluated | 11.2–13.2 s | 7.5–8.2 s |
| The C# service ready | 16.3–18.9 s | 15.1–15.7 s |
| UI thread stalls over 50 ms, summed (the longest) | 15.1–17.2 s (7.7–11.5 s) | 4.8 s (0.4–0.7 s) |
| UI thread time in posted jobs | 4.0–4.4 s | 0.19 s |

The C# service's readiness is mostly the host's own work, which this pass didn't change.

**After each pause in typing** (items 2 and 3). The C# service reports ready after the background pass that every edit starts, and the shell treated each of these like the end of a load.

  - The edited documents are indexed on their own, as before.
  - The index's snapshot is built off the UI thread (`CodeSearchIndex.ReplaceAsync`, `UpdateAsync`), and saving sorts and serializes it in the state store's queue (`SolutionStateStore.WriteAsync` with a factory).
  - What ran on the UI thread at each refresh, timed by a probe kept out of the repository (Release, this container, idle): 0.15–0.3 s to build the snapshot and 0.03–0.15 s to sort and serialize it, for an index of the 96-project benchmark's shape (5,760 files, 144,000 symbols, a 13 MB file).

  - After a load, every editor asks, as before.

**Everyday flows: the UI never hangs** (the second request: "anything a day to day user will do … Ui should never hang under any load").
- **How the costs were found:** a survey of the code per flow, each finding checked by a second reader against the code and Avalonia's and AvaloniaEdit's decompiled sources:
  - the flows: opening a large solution, Sync with Active Document and tabs, opening many and large files, editing, builds and tests, Git, debugging, startup and exit, and floods of output and rows;
  - a sweep for patterns that block the UI thread;
  - about 75 findings; about 70 held, some only in part, and none was refuted outright.
- **Fixed in packages,** each with tests that fail without its fix where that could be shown.
- **The maintainer's decisions** (asked one at a time):
  - Solution Explorer: the tree keeps its scroll position, and only an explicit reveal scrolls;
  - Test Explorer: during a run it updates about five times a second, and does no work while hidden;
  - Show All Files: a folder outside the project is listed once it's expanded, as in the classic IDE;
  - Class View: search stops at 1,000 results;

- **The other choices,** taken from the code, the ADRs and other IDEs' conventions: listed with each item below.

**The guard.**
- `UiStallMonitor` measures how long input waits during a flow. A thread of its own posts a probe at input priority every 10 ms, without counting the GC's pauses, and names the posted job the UI thread ran meanwhile.
- `EverydayResponsivenessTests` runs each flow once first (the JIT), then measured, on a solution large enough to show costs that grow with it. No input may wait over 1 s.
- Its second half, a CI benchmark scenario of the same flows in the real app: see *The CI benchmark scenario* below.

**Solution Explorer** (the maintainer's report: Sync and Track Active Item "traverse the tree").
- **The cause:** each row inserted or removed above the selected one moved the list's selection anchor, and Avalonia queued a scroll to the selected row for each, at a priority above input. The list walked through the rows, a frame each, then jumped back.
  - On the 300-project solution, Track Active Item while opening 43 files cost 45 s of UI stalls (headless, local).
  - `SolutionExplorerRevealTests` reproduced it: 199 scrolls and 209 anchor moves for a reveal above the selection.
- **Rows change as ranges,** one event each (`ResettableCollection.InsertRange`, `RemoveRange`).
- **The list doesn't follow its selection on its own** (the maintainer's choice). Reveals scroll in one step.
- **No rebuilds for expanding, collapsing and revealing:** they insert or remove only those rows, without building the tree again.
- **Track and Sync find the file through an index of the tree.** A project file finds its project.
- **Track Active Item reveals once per burst of activations.** It does nothing while the explorer is hidden, and catches up when it's shown.
- **The search box** matches off the UI thread once typing pauses.
- **Shown while any of its views shows it** (`ShownViews`): Dock builds a tool window's new view before the old one leaves.

**Error List.** Filters, severity and source toggles, group toggles and tab switches with Current Document built and sorted every row on the UI thread: up to a second each at 100,000 diagnostics, by the survey's estimate (not measured).
- Rows are built off the UI thread.
- The search box waits for typing to pause.
- A group toggle regroups the rows already shown.

**Editors' project contexts:** one index per burst of project changes, instead of each editor scanning every multi-targeted project's items (the survey estimated 50–150 ms with 100 editors and 300 such projects; its check, nearer 25 ms).

**NuGet windows:** they read the packages again once per burst, and only for evaluations that changed a project's package references or restore (`PackageChanges`; a first evaluation counts, so an open reads once). Every evaluation used to make every window read every project: 300 reads of 300 projects during a large solution's open.

**Class View:**
- once per burst of project changes, keeping its nodes, so expansion and selection survive;
- search asks four projects at a time and stops at 1,000 results, with a row to refine it.

- the Test Explorer arranged and counted every test, shown or not.

- The Test Explorer rebuilds at most every 200 ms while shown (the maintainer's choice), and nothing while hidden.
- The .NET test plugin forgets a project's runner tests through an index.

**Git Changes with thousands of changed files.**
- **Status reads:** a read the watcher asks for raises the status change only when the status differs, a ref, HEAD or the stashes moved, or a file already listed changed; the index change only when the status differs or the index was written. Commands that write, and explicit refreshes, always raise both, so the Git Repository document and the stash list still follow tags, branch deletions, stash drops and fetches; the watcher also sees `packed-refs`, `logs/refs/stash` and `reftable/`. `bin/` stays watched. While a build runs, reads come at most every 2 s, plus one 400 ms after it ends if the watcher saw writes meanwhile (the old code read 8 times in 4 s). A read that fails or is cancelled gives back the watcher's flags.
- **Rows:** each section's TreeView is a virtualized ListBox of flattened rows (`GitChangeRow`), inside the same layout, built on the thread pool and applied with a keyed prefix and suffix diff, or one reset. A hidden window keeps Staged, Changes and Conflicts current for the commands, but builds no rows until shown (`ShownViews`). Folder counts in one pass; the filter waits 150 ms. Keyboard parity with the tree: the chevron, `Left`/`Right` (`Ctrl` for everything under), `+`, `-`, `*`, `/`, `Ctrl+Enter`, `Enter` (handled in the tunnel: the ListBox took it first, so Enter opened no file), double-click (a chevron's second click raises no Tapped), hover buttons, context menus and automation names.
- **Paths:** stage, unstage and discard take git's own relative paths from the status rows, and every pathspec goes on git's input (`--pathspec-from-file=- --pathspec-file-nul`, git 2.30+ per ADR 0008); `git clean` gets its paths in parts. A partial stash's paths stay on the command line (git stash gives them to the commands it runs on theirs anyway), and on Windows a stash past that limit (about 370 paths of 70 characters) is refused before git runs. Found by the tests: when git exits before reading its input (a locked index), the write threw "Broken pipe" and the lock retry never ran.
- **History:** the selection is ordered through a position lookup (Select All in 80,000 commits).
- **Tests:** `GitChangesRowsTests` (2,000 files: no rows while hidden, at most 150 realized, an identical refresh changes no row, a deletion is one Remove, every key and the chevron); `GitServiceTests` (status reads, the build throttle, a cancelled read, paths on git's input, LFS lookups); `EverydayResponsivenessTests.Git_changes_flows_on_ten_thousand_files` (15–60 ms at most, 300 rows realized for 11,002).

**The debugger.**
- **Long arrays (the maintainer's choice: ranges of 1,000):** up to 1,000 elements show directly; a longer array, and a collection's backing array under Raw View, shows ranges `[0..999]`, `[1000..1999]`…, each read with one DAP `variables` request (start and count) when expanded; past 1,000,000 elements ranges nest. The count is DAP's `indexedVariables`, or netcoredbg's `namedVariables` for an array (checked against netcoredbg 3.2: `int[2500]` reports namedVariables 2500 and pages by start and count without a filter). Children are built off the UI thread and applied with one reset; Locals and Autos replace their roots with one reset and cancel what still loads under the old ones. `CollectionViews` reads only the slots it shows. Pinned tips keep the counts, so a pinned long array opens in ranges too. Both adapters' `initialize` declares `supportsVariablePaging`.

**Editor text: long lines, large files, colorizers, folding.**
- **Long lines (the maintainer's choice: cut at 10,000 + large mode):** AvaloniaEdit builds a line over 3,000 characters as one text element without calling the element generators, so the cut is a visual line transformer kept after every colorizer (`LongLineCutter`): the text element is split at 10,000 characters (never inside a surrogate pair), and the rest replaced by one marker element, **… N more characters**. Colors stop there; the bracket lexer reads only the first 10,000 characters of a line. The caret can't stay hidden: placed in the hidden part within 20,000 characters it draws the line up to itself (typing at the marker shows the text in order, a Find hit shows selected); farther in it moves on the way it was going, to the line's end or back to the 20,000th character, so Find Next and Previous both get past a far match. The read-only viewers (Peek Definition and the others) cut too. The marker's text properties go through an `[UnsafeAccessor]`, guarded.
- **Large files:** over 20 MB of text or 300,000 lines (VS Code's limits) a document opens without grammar, bracket colors, folding, Git or service CodeLens and its language service (no `didOpen`; `IEditorServices.Client` is null), with a localized bar. Opening reads, decodes and builds the `TextDocument` off the UI thread and hands it over with `SetOwnerThread`.
- **Reloads:** the stat, read, decode and difference run off the UI thread, one reload at a time; only the differing part is replaced, never splitting a `\r\n` or a surrogate pair (a CRLF-to-LF reload gave the language server a range past the line's end). Typing during a watcher's reload raises the conflict prompt instead of being overwritten.
- **Bracket colors:** states kept through an edit, moved by the line delta, re-lexed from the edited line until a state matches; a line more than 1,000 lines past the known states, or past a 256K-character budget, shows the default color until a background pass over a snapshot (checked against an edit counter) fills the states and redraws. From an update's second edit on, the cache is cut instead of shifted, so Format Document and Replace All stay cheap.
- **Folding:** at most 5,000 regions, outermost first, then by position, plus every collapsed one.
- **TextMate:** grammars cached by scope and themes by name, cleared when the languages change; a hidden editor stops its tokenizer thread (its last listener removed; the paused state read from the model) and starts it when shown, redrawing after, with attach and detach coalesced.
- **Tests:** `EditorLargeTextTests` (16 cases: a 210,000-character line drawn to 10,001 columns with all its text selected and saved; the caret never staying hidden; Find both ways; surrogates at the cut; a large XML with no folding pass and no client; bracket states off the UI thread and through edits; reloads through a fake file system; the folding cap; one grammar read and one tokenizer thread for three editors). Each failed with its fix turned off.

**Startup, exit and tabs.**
- **Process starts off the UI thread:** `SupervisedProcess.StartCoreAsync` runs its launcher through `Task.Run`, which covers every supervised host; the environment check and the build host's SDK probe hop to the pool. A supervisor disposed while its launcher waited kills what it started.
- **The login shell (macOS, Linux, started outside a terminal):** the window no longer waits for it. `ProcessEnvironment` is a gate that local process launches, git, the environment check, the SDK probe, the icon converter and container runs wait on (6 s at most, with a log line when it runs out); `LoginShellPath` gives up a second after the shell exits, so a profile's background job holding its output no longer holds the read. The .NET root is chosen and the terminal profiles detected again once it's read. Quitting during the wait starts nothing afterwards (`ShellHost.IsClosing`). `TODO(issue)`: the terminal, external tools, `dotnet ef`, npm, MCP and ACP agents start without waiting (on user action, rarely in the first seconds).
- **Exit (my default: the window hides at once):** `MainWindow.OnClosing` cancels the close, saves the state, closes the single-instance listener, hides every window, and awaits the shutdown, bounded at 3 s as before, then ends the app; the shutdown can't fault (logged and reported, the restart still made). Hosts dispose in parallel. OS logout and programmatic shutdowns still wait in `Exit`, bounded.
- **Recent entries (my default: shown at once, ~1 s each, nothing removed):** `PathProbe` checks each on a thread of its own, one per path at a time, for 1 s; rows take their icon from the name until it answers. Open Recent on an entry that's gone or doesn't answer asks before removing it (it removed it unasked). The last-solution startup opens the first entry that's there, and nothing if something opened meanwhile.
- **Files opened together:** `OpenFilesAsync` reads the models first, then adds the tabs in one pass under `LayoutManager.DeferActiveDocument`, the last one active (20 files: 1 activation and 1 editor built, was 20). The OS's multi-open, a drop and `codalus <file>` requests within 150 ms go through it; dropping files opens them in editors. Images, hex, .resx, the designer and plugin editors in a batch open behind the active tab.
- **Close All:** each tab still closes through Dock, each group's active tab and the active document last, inside the deferral, so the active document is worked out once (30 tabs: 1 change, was 30).
- **Tool windows** restored in the layout get their content when Dock first presents their tab (`ToolWindowDockable`'s lazy constructor): a Test Explorer behind another tab no longer starts the test plugin's host at launch.
- **Tests:** `ProcessStartTests`, `StartupAndExitTests`, `StartupEnvironmentTests`, `StartWindowTests`, `EnvironmentCheckTests`, `LoginShellPathTests`; each new test failed with its fix reverted (two needed sharpening first). Not testable headless: the real app's close path (`ClassicDesktopStyleApplicationLifetime` shuts the dispatcher down) and the window showing before the shell; they need the smoke test or the Mac.

**Floods of output and rows.**
- **Output channels:** `OutputChannel.TextAppended` carries the text even when the channel trims, with a `Trimmed` count and a `Version` (snapshots too), so `OutputPresenter` keeps its document within 4M characters by removing about as many old lines as each batch adds, inside one update, instead of reloading the whole text about every 1M. A reader scrolled up, or with Scroll Lock on, keeps the lines in view. The decoder has its own lock, undo is off, and a hidden presenter pauses instead of clearing (shown again with nothing new, it reads nothing). The Output window, the Debug Console, C# Interactive's transcript and the Aspire console use it.
