# M56 checkpoint: 0.11, large solutions and CodeLens rows from the first frame

Date: 2026-10-30. The scope is the roadmap's [M56](../roadmap.md#m56--011-large-solutions-performance-pass-round-3-and-codelens-rows-from-the-first-frame), from the maintainer's request of that day:
- a performance pass on large solutions with many projects: startup, indexing, responsiveness;
- CodeLens that doesn't move the code when it arrives. Their screenshots show a file before and after its lenses came, and the classic IDE's empty rows above the declarations.

Branch `claude/practical-mendel-20hupn`, from `develop` at `c2579827`.

## Done

**CodeLens rows from the first frame** (item 1, [ADR 0017's amendment](../adr/0017-navigation-and-inline-information.md#amendment-2026-10-30-codelens-rows-from-the-first-frame)).
- **`CSharpLensScanner`** (`Codalus.LanguageServices.Client`) finds, from the text alone, the lines where the C# host's `textDocument/codeLens` will put lenses. It has two parts:
  - a light lexer: comments; regular, verbatim, raw and interpolated strings with their holes; characters; `#if` branches, taken as a Debug build on current .NET takes them;
  - a walk of the declarations that skips member bodies.
- **`CSharpLensScannerTests` checks it against the host itself.** Both run on the test's cases (types and members, strings and directives, top-level statements, extension blocks, code that doesn't compile yet) and on every C# file of the repository: 1,869 files, 33,707 lenses. They agree on every line. The scanner reads about 150 MB/s.
- **`EditorInsights` keeps those rows, empty, from the editor's first frame** until the service lists its lenses.
  - A listed lens keeps its row while it waits for its count; one that resolves to nothing keeps it empty.
  - An empty row holds a space in the titles' font, so it's exactly as tall as a row with titles. It isn't a link: clicking it does nothing until its counts show.
  - A file over 512 KB is scanned off the UI thread, so its rows can come after its first frame.
- **Rows are kept only where lenses will come** (`IEditorServices.ExpectsCodeLens`): a `.cs` file that isn't generated or read-only, CodeLens on, and a C# service that hasn't failed and, once it runs, offers CodeLens.
- **A file reloaded after a change outside the editor** gets its new text's rows at once. The reload replaces the whole text, which collapsed the lenses' segments.
- **Test:** `NavigationDepthTests.Lens_rows_keep_their_room_from_the_first_frame_until_their_counts_arrive`, with the real C# host. It records every frame from the editor's creation:
  - in the first frame every declaration has its row;
  - the last declaration never moves while the service lists and resolves the lenses, nor after a reload that adds a method.
  - The screenshots `codelens-placeholders` and `codelens-resolved` show both states.
- **Fixed before the commit:** the test's first version took its first look after the open had returned, and on a loaded machine the service's list was there by then. It now records from the editor's creation and passed 10 of 10 runs under CPU load.
- **Found by the validation:** two tests took a CodeLens row to mean its counts had come, which the empty rows broke under load ([ci-flakes](../ci-flakes.md)). `CodeLensDetailsTests.A_members_codelens_shows_its_git_history` failed in the suite; `NavigationDepthTests.Inline_information_shows_hints_lenses_and_inheritance_glyphs` had the same wait before clicking a row. Both now wait for the counts' text.

**How the large-solution costs were found** (items 2 and 3).
- **The solution:** a generated 300-project solution (`codalus-fixturegen solution <dir> 300`).
- **The probe:** opened in the headless shell by a probe test kept out of the repository, which then opened a file and typed in it.
  - A 4 ms heartbeat on the UI thread measured its stalls.
  - The UI thread's posted job was sampled every millisecond (`Ui.Watch`, `Ui.RunningJob`) and attributed to the line that posted it.
  - `dotnet-trace` samples of the test host gave the hot paths.
- **Where:** this cloud container, two runs before the changes and two after. Numbers from one machine decide nothing that CI gates ([benchmarks/README.md](../../benchmarks/README.md)); these only found the costs.

| Open of 300 projects, warm | Before (two runs) | After (two runs) |
|---|---|---|
| Every project evaluated | 11.2–13.2 s | 7.5–8.2 s |
| The C# service ready | 16.3–18.9 s | 15.1–15.7 s |
| UI thread stalls over 50 ms, summed (the longest) | 15.1–17.2 s (7.7–11.5 s) | 4.8 s (0.4–0.7 s) |
| UI thread time in posted jobs | 4.0–4.4 s | 0.19 s |

The C# service's readiness is mostly the host's own work, which this pass didn't change.

**A large solution's open** (item 2). Each project's evaluation raises `ProjectChanged` and progress, and several reactions walked every project, so an open ran each of them once per project.
- **Database Explorer's connection discovery** read every project's settings files and project file again, on the UI thread: 3.4–3.8 s of the posted jobs' 4.0–4.4 s. It now runs once a burst settles (`UiDebouncer`: 300 ms, at most 3 s), off the UI thread. The Aspire check reads the evaluated `IsAspireHost` instead of the project file.
- **The Solution Explorer** built every project's subtree again for each project. `SolutionTreeCache` keeps a project's subtree while its evaluation, compiler inputs and files are the same instances: 4.2 s of the traced UI thread down to 0.5 s.
- **These also follow the projects once a burst settles:** the toolbar's startup choices, the analysis scope, the tab colors and the editors' project contexts. The solution status during evaluation does too, and is set at once when evaluation completes.
- **An editor's overview ruler** redraws only for its own file's diagnostics. A background pass publishes every file's.
- **Tests:** `SolutionTreeCacheTests`, plus the existing Solution Explorer, Database Explorer and toolbar tests.

**After each pause in typing** (items 2 and 3). The C# service reports ready after the background pass that every edit starts, and the shell treated each of these like the end of a load.
- **Code Search** asked the host for every document's declarations and rebuilt its whole index on the UI thread ([ADR 0078's amendment](../adr/0078-code-search-and-its-persistent-index.md#amendment-2026-10-30-the-whole-solution-after-a-load-not-after-every-edit)).
  - The whole solution is now indexed when the service reports ready after loading (projects changed, a restart, a reload), and otherwise at most every three minutes, which catches files changed outside the editor.
  - The edited documents are indexed on their own, as before.
  - The index's snapshot is built off the UI thread (`CodeSearchIndex.ReplaceAsync`, `UpdateAsync`), and saving sorts and serializes it in the state store's queue (`SolutionStateStore.WriteAsync` with a factory).
  - What ran on the UI thread at each refresh, timed by a probe kept out of the repository (Release, this container, idle): 0.15–0.3 s to build the snapshot and 0.03–0.15 s to sort and serialize it, for an index of the 96-project benchmark's shape (5,760 files, 144,000 symbols, a 13 MB file).
- **Every open editor** asked again for its colors, inlay hints, CodeLens (counted across the solution), symbols and options.
  - After an edit's pass, other documents' editors ask again when they show (now, if they're showing). The edited document's editor already asked on its own.
  - After a load, every editor asks, as before.
- **Git** ran a status of the whole worktree after every write under `obj/`, where the C# service writes its state after each pass. `obj/` is .NET's intermediate output, which every .NET `.gitignore` leaves out. `GitService.ChangesStatus` decides which writes matter, tested by `Writes_under_obj_and_inside_git_but_its_index_and_refs_dont_ask_for_a_status`.

**Startup** (item 3).
- **The single-instance check:** `codalus <solution>`, Open with… and `codalus <file>` with no IDE running waited half a second before starting one. Connecting to a named pipe that nothing listens on retries until its timeout (502 ms measured on Linux).
  - The pipe's socket file (Linux, macOS) or its entry among the named pipes (Windows) is now looked for first (`SingleInstance.MayBeListening`). When that can't be told, it connects as before.
  - `DiffCommandTests` checks that a send with no shell is refused in under 250 ms.
- **Optional tools:** every start ran `git lfs`, `docker` and `podman --version`, though startup only offers to install the required tools. Podman's starts its machine's client: seconds of CPU.
  - Startup now checks only the required ones (`EnvironmentCheck.CheckRequiredAsync`): the SDK, the hosts' runtime and git.
  - Check Environment and the first-run setup's Tools step check the rest when they open.
  - `EnvironmentCheckTests` asserts that the required check runs only `dotnet` and `git`.
- **The login shell's `PATH`** (macOS and Linux, when started outside a terminal) is taken while the windowing system and the app's resources load, instead of before them. The shell waits for it before it starts anything.
- **A session's tabs come back behind the active one.** Each other tab makes its editor when it's first shown, instead of each being activated in turn, where every editor asked the language service for its colors, hints and CodeLens. Test: `SolutionStateTests.A_sessions_tabs_come_back_behind_the_active_one_and_make_their_editors_when_shown`.
