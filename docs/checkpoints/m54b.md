# M54b checkpoint: parity, and phase 1 done

Date: 2026-10-29. The second and last part of the roadmap's [M54](../roadmap.md#m54--a-managed-coreclr-debugger-phase-1), after [M54a](m54a.md): with it, D48's phase 1 ([ADR 0086](../adr/0086-a-managed-coreclr-debugger.md)) is built. The plan's PRs 3 to 5 became two: the terminal through the launcher (`feat/m54b-terminal-launcher`), then the rest of the parity set, the smoke test's second pass and the docs (`feat/m54b-parity`).

## Done

**The integrated terminal and the console window through the launcher** (PR 3). Under the Codalus debugger, DebugService gives the adapter the terminal (or Windows' console window launcher) and asks for `console` `integratedTerminal` (or `externalTerminal`); the adapter sends DAP's `runInTerminal` reverse request, and the IDE starts `codalus-debughost --launch` there, which starts the program. So a program in the terminal:
- gets the terminal's console (input, colors), stops on `Main`'s first line like any launch, and needs no startup hook (ADR 0039's hold and attach stay netcoredbg's);
- is ended by Stop (the adapter terminates it; the console window closes) and left running by Detach All, its exit code still the terminal's;
- runs in the terminal on macOS too: `ShellHost.ConsoleFor` keeps the Debug Console there only for netcoredbg. An x64 program on Apple silicon, which netcoredbg debugs, falls back to the Debug Console there.

The adapter's `DapServer` (shared with the Mono and .NET Framework adapters) runs requests in order on a chain of their own, off the read loop, so a handler can wait for the client's answer to a request of its own (`RequestAsync`). The first version ran a request on the read loop's thread when the one before had finished (an await of a finished task goes on synchronously), and `launch` waiting for `runInTerminal`'s answer blocked the loop that would read it: the terminal tests hung until their timeout. `NetFxDebugArguments.Console` is DAP's own field.

**The rest of the parity set** (PR 4). `eng/ci-debug-codalus.txt` names test classes, or one method (ending in `()`), by their full names; `eng/ci-test.sh` runs them project by project. The shard now builds the solution, as the others do (the Shell's tests need its hosts). Added: `TerminalLaunchTests` and `ConsoleWindowLaunchTests` (PR 3), the Shell's `DebugTests`, `DebugSessionsTests`, `CompoundDebugTests` and `BlazorWebAppHotReloadDebugTests`, and test debugging (`DotNetTestRunControlTests.Debugging_a_test_stops_at_its_breakpoint`, xUnit v2 and v3). They passed under the new adapter as they were: what they needed was built in M54a.

**The smoke test's second pass** (PR 4). The debug steps run again under the Codalus debugger (`debug.adapter` `codalus`, then back): `debug.session`, `debug.depth`, `debug.companion` and `debug.dataTip` on the Hello solution, `debug.compound`, `debug.terminal` (on macOS too) and `debug.roslyn` on the Sessions solution, and `blazor.compoundDebug` and `blazor.compoundHotReload`, each as `<id>.codalus`, requiring its first pass. Each checks that the Debug Console named the Codalus debugger. Their screenshots end in `-codalus`: the first pass's are the website's. `debug.remote` (remote targets keep netcoredbg) and `blazor.wasmDebug` (the browser's debugger only) don't run twice. Session, depth, companion and data tip were lambdas and are methods now; the compound and Blazor steps copy their samples once.

**Docs.** The user guide's terminal section (macOS under the Codalus debugger) and the preview's list; ADR 0007, 0039, 0076 and 0086 say what phase 1 changed.

## Phase 1's exit criteria

- Every parity test passes under the Codalus debugger on Windows, Linux x64, macOS and Linux arm64 on CI, and under netcoredbg as before: the `debug-codalus` shard on each pull request.
- The smoke test's debug steps pass under it in the smoke jobs (every OS) and the packages' smoke tests (each package platform, Linux arm64 included) of the next nightly.
- A program's own exit code on macOS (`ClrDebuggerTests`, the smoke test's `debug.session.codalus`), and `Main`'s first line in the integrated terminal (`TerminalLaunchTests`).
- The size gate: ClrDebug and dbgshim add about 4% to the Linux and macOS packages, under the gate's 5%. It runs on stable releases (or a manual dispatch of the benchmarks job), and new accepted values come only from CI: the next release's gate decides it.
- With `debug.adapter` left alone, nothing changes: the default shards' suites under netcoredbg, and `DebugAdapterChoiceTests`.
