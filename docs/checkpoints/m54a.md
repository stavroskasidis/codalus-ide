# M54a checkpoint: the Codalus debugger for CoreCLR, opt-in

Date: 2026-10-29. The first part of the roadmap's [M54](../roadmap.md#m54--a-managed-coreclr-debugger-phase-1), D48's phase 1 ([ADR 0086](../adr/0086-a-managed-coreclr-debugger.md)): a CoreCLR debug adapter of our own behind `debug.adapter`, netcoredbg still the default. Two pull requests: the adapter and its launcher (`feat/m54a-clr-adapter`), then the setting, the routing and the `debug-codalus` shard (`feat/m54a-adapter-setting`). M54b (the terminal through the launcher, the Shell's and Plugins' debugger suites, the smoke test under the new adapter) is next.

## Done

**The adapter** (PR 1). `codalus-debughost --clr-dap` runs ADR 0076's session (`NetFxDebugSession`, the evaluator, `ClrModuleInfo`) over `DbgShimDebugger`, a second `IClrDebugger` beside the desktop CLR's `CorDebugger`:
- *Launch:* the adapter starts the launcher (below), which reports the program's id while the program is suspended; the adapter registers for its runtime's startup, tells the launcher to resume it, and the startup callback's `ICorDebug` attaches (`DebugActiveProcess`).
- *Attach:* `EnumerateCLRs`, `CreateVersionStringFromModule`, `CreateDebuggingInterfaceFromVersion`; breakpoints bind on the attach's module loads.
- `CorDebugTarget` and its threads, frames and values serve both runtimes; only `CorDebugger`'s start path (mscoree, the bitness check, `supportedRuntime`) stays Windows-only.
- dbgshim comes from `Microsoft.Diagnostics.DbgShim.<rid>` 10.0.750501 (MIT) for win-x64, linux-x64, linux-arm64 and osx-arm64; ClrDebug ships on every OS again (0.3.0 had left it out of the Linux and macOS packages).

**The launcher** (PR 1). `codalus-debughost --launch <pipe> <program> [args]` starts the program through `CreateProcessForLaunch`, suspended, with the launcher's environment, working directory and standard handles, and over the pipe (`CurrentUserOnly`) sends `pid N`, waits for `resume`, and sends `exit C` when the program ends (`waitpid` off Windows, the process handle on Windows), then exits with that code itself. A pipe that closes first ends the program with `ProcessTree.Kill`, resumed or not, unless the adapter sent `detach`. It ignores Ctrl+C. Two things the tests found:
- On Windows a synchronous pipe handle serializes its reads and writes: the exit code's write waited behind the read that watches for the adapter going away, so the pipe is asynchronous.
- The debug host turns startup hooks off (`StartupHookSupport=false`): the launcher runs with the program's environment, and a `DOTNET_STARTUP_HOOKS` meant for the program would run in it.

**The setting and the routing** (PR 2). `debug.adapter` (`netcoredbg` or `codalus`) is in Options › Debugging as "Debugger for .NET programs", its description calling the Codalus debugger a preview; `CODALUS_DEBUG_ADAPTER` overrides it. Under `codalus`, DebugService sends local launches, attaches, a Blazor Web App's server (launched or attached to) and so test debugging and plugins' launches to `--clr-dap`, and the Debug Console's first line says "Debugging with the Codalus debugger (preview)." These stay on netcoredbg, the line saying why: x64 programs on Apple silicon (launched, or a process whose executable is x64), and programs in the integrated terminal or a console window (`TODO(issue)`: M54b's PR 3). Remote targets and .NET Framework programs don't follow the setting. Left alone, nothing changes and nothing is said. `CODALUS_CLR_DEBUGGER_LOG` names a folder for each session's DAP traffic and messages (`DapServer.Trace`).

**What the parity set found**, built in the shared session, so the .NET Framework debugger has it too:
- Thread names: CoreCLR's `Thread` keeps its name in `_name` (the desktop CLR's `m_Name`); breakpoint thread filters needed it.
- `decimal` and `DateTime` on CoreCLR: `_flags`, `_hi32` and `_lo64`, and `_dateData` (Visual Basic's `decimal` comparisons failed).
- The core library is `mscorlib` or `System.Private.CoreLib`.
- **`setExpression`**: a property through its setter (any type), an indexer through `set_Item`, a primitive in place, and a field, element or variable of a class type pointed at another object or null (`ICorDebugReferenceValue::SetValue`); a func-eval of a method that returns nothing (a setter) is a void result, not `CORDBG_S_FUNC_EVAL_HAS_NO_RESULT`.
- **A base type's members with the base's type arguments**: `Collection<string>`'s getters under `Inventory : Collection<string>` were called with `Inventory`'s (none) and threw `TypeLoadException`. `ClrType.BaseOf` reads the base as the runtime instantiated it (`ICorDebugType::GetBase`), and getters, setters and method calls take its arguments.
- An object's static members under one "Static members" node, last, named by the type, as netcoredbg lists them (the data tip's static group).
- A getter that throws shows its exception typed and expandable (the data tip marks it).
- **.NET 9 and later report a thrown exception from the runtime's managed exception dispatcher**: the stop's top frames were `System.Runtime.EH.DispatchEx`, `RhThrowEx` and native frames above the throw. The session leaves that run out, so the stop, a module condition's module, evaluation and Just My Code's first-chance decision see the throw. (Exception module conditions on .NET 11 now work: under netcoredbg 3.2.0 that test skips, its frames have no module.)

**CI** (PR 2). A fourth test shard, `debug-codalus` (`eng/ci-test.sh`), builds only `Codalus.Debugging.Tests` and runs `eng/ci-debug-codalus.txt`'s classes with `CODALUS_DEBUG_ADAPTER=codalus` and the adapter's logs in its results folder, on `ubuntu-latest`, `windows-latest`, `macos-latest` and, the only shard there, `ubuntu-24.04-arm`. **Docs and site.** The user guide's debugging page has "The Codalus debugger (preview)" (what it adds, what stays on netcoredbg, its expressions, the log variable) and `debug.adapter` in its settings; the Features page a line; `docs/environment-variables.md` both variables; ADR 0076 a dated note that ClrDebug ships everywhere again; `THIRD-PARTY-NOTICES.md` dbgshim.

## Tests

- `ClrDebuggerTests` (6, every OS): a launch stops on `Main`'s first line, binds breakpoints, reads locals, evaluates through func-eval, steps and ends with the program's own exit code (15, macOS included); arguments (a path with spaces), environment (non-ASCII) and working directory reach the program; an attach binds on module loads; the launcher reports exit codes, kills a program never resumed or still running when the pipe closes, and leaves it running after `detach`.
- `DebugAdapterChoiceTests` (3): the setting's launch through the new adapter and its Debug Console line, the two fallbacks and their lines, and nothing said when left alone.
- `The_host_carries_ClrDebug_and_dbgshim_for_each_package_platform` replaces the test of a host without ClrDebug.
- The parity set (`eng/ci-debug-codalus.txt`): 79 tests and a recording helper that runs only when asked (`Record_the_data_tips_fixtures`).

## Size

ClrDebug's ReadyToRun code adds about 15 MB to the Linux package and 16 MB to the macOS one, as before 0.3.0; dbgshim 0.3 to 0.4 MB there, 0.14 MB on Windows. About 4% of `shell_mb`, under the gate's 5%, which runs on stable releases (and a manual dispatch): the accepted values move only from CI.
