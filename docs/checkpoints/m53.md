**The cold first analysis** (item 5), measured, no change. With the 41 projects of the other repository loading now, the C# service analyzes all 94 projects: ready at 76 s from the open with the language cache on but empty (the first pass 67.5 s), at 15–24 s on the next open (M34c's cache). Two directions were measured:
- *More projects at a time:* the pass compiles `ProcessorCount / 2` projects at once (10 here). With 20, it took 71.9 s against 71.4 (both with the cache off), and the processors were less busy (30% on average against 36%). The pass isn't short of workers; it waits.
- *Reference assemblies of the projects' builds:* the analysis solution (M34c) compiles a project against its dependencies' reference assemblies when their last build is newer than every input. None of the 94 qualified (sources changed since their builds), so on this solution the pass compiled the whole dependency chain.
- A trace of the C# host (`dotnet-trace`, sampled over 70 s of the first pass) shows its busy threads binding method bodies and running source generators (mostly Razor's), and others waiting inside Roslyn's `GeneratorDriverInitializationCache`. Telling what the slowest projects (the Blazor clients, 27–29 s each) wait on needs a thread-time analysis with the waits attributed.

## Follow-ups (2026-10-28, `fix/0.10-followups`)

**Where the cold pass waits.** Each project's compile start and end, logged in a scratch build: the pass's compile phase (61 s of 70) is one chain of 11 projects of the solution that reference each other in turn (`wPylon.Client.Framework` → `Services` → `Component` → `INF` → `INF.eBanking` → `FIN` → `COM` → `CRM` → `ICM` → `Explorer.Client` → `Explorer.Server`), each waiting for the one below; `INF` alone took 16.5 s. Razor's source generator is 40–85% of each link's own time (`CODALUS_GENERATOR_TIMINGS`: 25 s over 36 projects), the rest binding declarations and emitting the metadata the next one compiles against. More processors can't shorten a chain. The analysis solution's reference assemblies would, but a project's cache key holds the keys of everything it references, so a change low in the chain (a pull) invalidates them all: reusing a project's reference assembly while its own inputs are unchanged is [#208](https://github.com/stavroskasidis/codalus-ide/issues/208), with its trade-off.
