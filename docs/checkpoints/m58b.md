# M58b checkpoint: the Codalus debugger by default

Date: 2026-11-11. The second part of the roadmap's [M58](../roadmap.md#m58--the-codalus-debugger-by-default), D49 ([ADR 0094](../adr/0094-the-codalus-debugger-by-default.md)): the default, remote targets and the debugger's two downloaded builds. One pull request, after [M58a](m58a.md)'s.

## Done

**The default.** `debug.adapter` is `codalus` (Options › Debugging: "Codalus debugger" and "netcoredbg (fallback)"); only `netcoredbg`, in the setting or in `CODALUS_DEBUG_ADAPTER` over it, chooses the fallback. The Debug Console's first line says which debugger a session uses. netcoredbg stays in the packages for one release.

**A program that isn't .NET.** A program that ends before a .NET runtime starts in it fails the start at once under the Codalus debugger, with its exit code ("… ended (exit code 3) before a .NET runtime started in it: is it a .NET program?"); it waited 30 seconds before.

**The debugger's bundle.** `codalus-debughost` published self-contained and trimmed for one platform (`-p:CodalusDebuggerBundle=true -r <rid>`; `eng/get-codalus-debugger.sh` in a source checkout): about 40 MB as a folder, 15 MB as an archive. It needs no .NET where it runs.

**Remote targets.** On a Linux machine over SSH, in a container and in WSL, a session under the default:
- asks once, copies the bundle through the target's shell and unpacks it under the debugger folder there (`codalus-<id>`; a new version is a new folder), as netcoredbg was copied; the packages carry it for `linux-x64` and `linux-arm64` (`remote/<rid>/debugger.tar.gz`, `debugger.id`), built by the shell's publish;
- starts the adapter there (`--clr-dap`) over the shell transport, with the IDE's paths mapped both ways, for every request M58a added too (Set Next Statement's targets, disassembly, dependent breakpoints, compiled expressions);
- starts the same binary as the companion host there, so `[DebuggerDisplay]`, hidden members and the members' icons are read from the modules on the target.

A macOS target keeps netcoredbg (no bundle is shipped for it). A remote window (the IDE's hosts on the other machine) gets the same bundle, copied on its first `F5` and started by its server. Its server bundle doesn't carry the debug host with the other hosts, as first built: the debug host has a native library of the client's platform only, so a Windows or macOS client couldn't have debugged on a Linux server.

**The other builds, as components.** Tools → Components lists them, on the OS they are for:
- **x64 programs on Apple silicon** (.NET 5 and earlier, under Rosetta 2): the `osx-x64` bundle;
- **32-bit .NET Framework programs** on Windows (x86, or `Prefer32Bit`): the `win-x86` bundle.

Each is a release asset (`codalus-debugger-<version>-<rid>.tar.gz`, `eng/package-debugger-component.sh`, called by `eng/package.sh` for nightly and stable builds), named with its SHA-256 in the package's `debughost/debugger-components.json`. The first session that needs one asks, downloads it, checks it and unpacks it into the cache. Declined or not available: an x64 program is debugged by the x64 netcoredbg the macOS package ships, and a 32-bit .NET Framework program says what it needs, as before.

**A short-lived program under netcoredbg isn't started twice.** Found by this checkpoint's validation: the wait for a late runtime (netcoredbg's 5 seconds, `DebugAdapter.WaitForRuntimeAsync`) saw a program gone before the debugger's events about its runtime were handled, took it for one that never started, and started it again. The debugger is now asked a request first and the events read before its answer are handled ([docs/ci-flakes.md](../ci-flakes.md)).

**Tests that are one debugger's.** The Blazor Web App tests of the `dotnet watch` path choose netcoredbg through the setting instead of skipping under the default, and the Codalus debugger's own test of that class skips where `CODALUS_DEBUG_ADAPTER` forces netcoredbg, as the terminal's does.

**CI and the smoke test.** The shard that ran the parity classes under the Codalus debugger runs them under netcoredbg (`debug-netcoredbg`, `eng/ci-debug-parity.txt`); Linux arm64 runs them under the default. Linux and macOS shards build the bundle for the remote-target tests. The smoke test's debug steps run under the default, with a second pass under netcoredbg (`.netcoredbg`).

**Docs.** The user guide (Debugging rewritten around the default, with the fallback and the other builds; .NET Framework, Remote, Web, MAUI, Getting started, Settings, Troubleshooting, .NET versions), the Features and Home pages, `docs/environment-variables.md` (`CODALUS_DEBUGGER_<PLATFORM>`), `docs/protocol.md`, `docs/release/releasing.md`, ADR 0094's "What M58b built", `THIRD-PARTY-NOTICES.md` (dbgshim for `osx-x64`), the README and the roadmap.

## After the checkpoint (2026-11-12)

What the runs after the merge found, each in its own pull request:

- **The nightly of the merge wasn't published** (run 43113076593): a folder view test with a fixed second for its limit, on a busy macOS runner; and, in the fix's own run, the Git Repository document leaving Pull Requests at "Loading…" when a status read replaced its first read. Both fixed (#327); the next nightly was published, with both of the debugger's downloaded builds among its assets.
- **Sessions under the bundles in CI** (#329). `win-x86` debugs a .NET Framework program built for x86 on the Windows runner. `osx-x64` crashed on its first session, an x64 .NET 11 program under Rosetta 2, inside Microsoft's dbgshim ([docs/ci-flakes.md](../ci-flakes.md)); the test is a row per x64 runtime, .NET Core 3.1 to .NET 11, to find which it debugs.
- **The bundle's working directory.** Started in its own folder, the bundle failed to debug whenever the current directory was among the places libraries are looked for (an empty entry in `LD_LIBRARY_PATH` on Linux, any library opened by name on macOS): the debugged runtime's debugging libraries were taken from the bundle's own runtime. The shell starts the downloaded builds in their folder. The adapter now leaves the folder it was started in; `DebuggerBundleTests` starts it that way.
- **Old runtimes under the default.** The old-.NET matrix isn't part of a pull request's run and hadn't run since the default changed. On Linux x64 the Codalus debugger debugs every one of its frameworks, .NET Core 2.0 to .NET 10 (11 of 11), and netcoredbg still does (11 of 11); the whole matrix: 71 tests, 68 passed, 2 skipped, 1 failed (a restore, not the debugger; in the ledger). Its debug test hadn't found the Codalus debugger outside the shell's fixture: it names the built one now, and runs under both debuggers. Not run: the matrix on Windows and macOS (`compat.yml`, by hand).
- **A compiled expression before the project's references arrived** answered with the compiler's errors for a program with no core library; it says the references are still loading.
