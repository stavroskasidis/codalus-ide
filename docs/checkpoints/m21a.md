# M21a checkpoint: remote development over SSH and WSL

Date: 2026-10-12. Decisions: [ADR 0050](../adr/0050-remote-development-architecture.md) (remote development architecture, with the threat model) and [ADR 0051](../adr/0051-transport-and-multiplexing.md) (transport and multiplexing). M21 is split (roadmap rule 5) into M21a (this) and M21b (below).

## Built

**`daedalus-server`** (`src/DaedalusStudio.Remote.Server`, protocol in [docs/remote-protocol.md](../remote-protocol.md), contracts in `src/DaedalusStudio.Remote.Protocol`). It prints its preamble, then speaks frames on stdio until stdin ends, and never listens on a port. It hosts:
- **processes** with their stdio on channels, and stderr and exit as notifications (`process/spawn`, `process/kill`);
- **pseudo-terminals** (`pty/open`, `pty/resize`, with ADR 0014's ConPTY and `openpty`);
- **the file system**: stat, read, atomic write, list, create, delete, rename, and watches gathered for 100 ms;
- **listening ports**: `/proc/net/tcp*` with the owning process on Linux, `lsof` on macOS, the OS's table elsewhere, polled while watched;
- **tunnels** (`tunnel/open`: a TCP connection it makes to a port on its machine);
- **`server/hello`**, the version lock (server version, protocol, OS, architecture, home, user, the `dotnet` it found and its version).

`--echo` is a test program.

**The transport** (`DaedalusStudio.Rpc/Multiplexing`):
- `ChannelMultiplexer` and `MuxChannel` carry 9-byte-header frames: Data, Close (a half-close), Credit, Ping and Pong.
- Each channel and direction has its own 1 MB window, so a reader that stops reading stalls only its own writer.
- The read loop never waits on a write. Data for an unknown channel is dropped and its credit returned.
- The end of the stream ends every channel.
- `LatencyStream` simulates an adjustable round trip.
- `SupervisedProcess` and `DebugAdapter` start through `IProcessLauncher`/`IHostProcess` (`LocalProcessLauncher` here), so a host or netcoredbg can run anywhere with its supervision unchanged.

**Workbench** (`src/DaedalusStudio.Workbench/Remote`, `FileSystem/`):
- **Connecting.** `RemoteConnection` starts the transport (ssh, `wsl.exe`, or the server here), skips to the preamble, and runs the control channel. `RemoteSession` connects (installing first), maps paths, mounts the file system, places hosts, starts terminals, forwards ports and measures latency. `RemoteTargetSpec` parses `ssh:user@host:port`, `ssh://…`, `wsl:Distribution` and `local`.
- **The bundle.** `RemoteServerBundle` packs the server and the build, C# and markup hosts as a `.tar.gz`, cached by file sizes and times. It probes the target, copies the bundle with its SHA-256 checked there, and installs into `~/.daedalus-server/<version>/` with a `.bundle` checksum.
- **Paths.** `RemotePathMap` and `MappedJsonStream` rewrite paths and `file:` URIs in host JSON, both ways, under `\\wsl.localhost\<distro>`, `\\daedalus-remote.invalid\<id>` or `/daedalus-remote/<id>`.
- **Processes, files and terminals.** `RemoteProcessLauncher` and `ChannelProcess` run hosts and netcoredbg on the server. `RemoteFileSystem` is the server's file system as an `IFileSystemProvider`; `FileSystems` mounts providers by root (F2). `RemotePseudoTerminal` is a usable terminal at once, with input sent once the server starts it.
- **Ports.** `PortForwarder` forwards on loopback and auto-forwards ports that start listening (same number when free). It leaves alone ports that were already listening, ports stopped by the user, and its own listeners.
- **Hooks.** `SolutionService.Placement`, `LanguageService.Placement` and `TerminalService.PtyFactory`. `SshTarget.Options` is used for `BatchMode=yes`.

**The shell**:
- **Opening.** File → **Open Remote Window…** (`remote.open`: SSH or a WSL distribution, then a remote path; this window when it's empty, otherwise another `daedalus --remote <target> <path>`). Also **Close Remote Connection** (`remote.close`).
- **Status and log.** The remote status bar item (`$(link) WSL: Ubuntu · 3 ms`, a warning when the connection drops) opens the remote actions (`remote.menu`). The **Remote** output channel shows the log.
- **Ports.** The **Ports** window (`remote.ports`: forwarded and listening ports, Forward a Port, Stop Forwarding, Open in Browser), with an auto-forward notification that offers the browser. The setting is `remote.autoForwardPorts`.
- **Command line and screenshots.** `--remote <target>`. The remote window doesn't take single-instance requests, and `--screenshot` in a remote window waits for its C# service.
- **Opening files and solutions.** Opening a remote folder, solution, project or file goes through the server's file system. The trust prompt names the remote folder.
- **The editor.** It reads, saves and watches remote files through it (`TextFiles`, `CodeDocument`).
- **Run and debug.** Run Without Debugging runs the launch plan in a terminal on the server. F5 runs netcoredbg there through the server, installed by M14c's `RemoteDebuggers` with consent. An apphost gets `DOTNET_ROOT`. A web app's URL opens once its port is forwarded.
- **Packaging.** A published install carries `remote/server/` (framework-dependent) and `remote/linux-x64/`, `remote/linux-arm64/` (self-contained, single-file, trimmed, about 16 MB; `$(DaedalusServerRids)`).

**Docs**: ADR 0050 and 0051, [docs/remote-protocol.md](../remote-protocol.md), the user guide's [remote.md](../user-guide/remote.md), CLAUDE.md.

## Tests

Remote tests never reach another machine. Their stand-ins are:
- **the server started here** (every OS);
- **WSL** on Windows (`DAEDALUS_TEST_WSL`, default `Ubuntu`, with .NET);
- **a fake `ssh`** on Linux and macOS, which runs the command here, as M14c's tests do.

A test whose stand-in is missing skips and says which. On Windows there is no fake ssh (as in M14c), so the SSH installer path is covered by the fake ssh on Linux and macOS and by WSL on Windows.

- **Rpc** `MultiplexerTests` (8):
  - bytes both ways and half-closes;
  - six channels moving several megabytes each through flow control, intact (SHA-256);
  - a channel nobody reads doesn't stall another, and closing it returns its credit;
  - a closed channel's data is dropped and its writer released;
  - the end of the stream ends every channel;
  - a ping includes the simulated latency;
  - JSON-RPC on a channel;
  - a `SupervisedProcess` through a custom launcher restarts when its channel ends.
- **Workbench** `RemoteServerTests` (12):
  - hello, the version lock and a refused protocol;
  - the preamble after a login shell's banner;
  - a spawned process's stdio, stderr and exit code, and an error for a missing program;
  - files read, written, listed, renamed, watched and deleted, and a missing file is `FileNotFoundException`;
  - a terminal on the server;
  - a port that starts listening is detected, forwarded and tunnelled, and stops;
  - a host restarted on the server after it was killed;
  - paths and URIs rewritten both ways (spaces, escapes, non-paths kept);
  - target parsing;
  - the transport budget at a simulated 50 and 150 ms;
  - **the bundle copied, checked and started on a stand-in once per version** (WSL here, the fake ssh on Linux and macOS);
  - **a damaged bundle refused by its checksum**.
- **Headless UI** `RemoteShellTests` (4):
  - **a remote window on the local stand-in.** It connects, opens BuildAndRun through the server: projects from the build host there, remote paths under the root on Linux and macOS. It reads Program.cs through the server and completes `Console.` from the C# host there, with **the completion budget at 50 and 150 ms**. It saves an edit to the file, builds, and runs the program in the server's terminal with its launch profile. It opens a remote shell, sees a new port forwarded and listed in the Ports window (Open in Browser on the local port), and disconnects.
  - **F5 in a remote window** stops at a breakpoint with netcoredbg started through the server.
  - **A remote window on WSL** (`\\wsl.localhost\Ubuntu` paths, the bundle copied into a test folder there) loads, completes, builds, and runs with a Linux working folder. With netcoredbg for Linux in this checkout's WSL mirror, F5 stops at a breakpoint in the distribution.
  - **Open Remote** starts another window with `--remote <target> <path>`.
- **Smoke** `remote.session` (M21), on the shipped `remote/server` as the local stand-in. It connects, opens a copy of BuildAndRun, checks the status bar, completes and saves through the server, builds, runs Hello in the server's terminal (exit 0 with its greeting), sees a new port forwarded, and disconnects. Every wait is bounded with a message.

## M21b (planned)

- **Dev Containers**: the `devcontainer.json` subset (image, Dockerfile, compose, features, ports, `postCreateCommand`), with an ADR "Dev Containers support" (the Dev Containers CLI or a C# subset).
- **Attaching to a running container**: a remote window in a container through `docker exec`/`podman exec` (M14c's `ContainerTarget` as a transport).
- **Remote test environments** (`testenvironments.json`): tests from a local solution run and debug in WSL, a container or over SSH through a test runner the server starts.
- **Plugin placement**: `runsOn: "ui" | "workspace"` in the manifest, workspace plugin hosts on the server.
- **Reconnect and resync**: the server outlives a dropped ssh (a socket in the user's runtime folder that a new session re-attaches), and the client resyncs open documents, hosts and sessions. Budget ≤ 5 s.

## Deviations and gaps

- **Only part of the IDE runs in a remote window yet.** These still read this machine's files and fail there (on WSL some work through the share): Git, NuGet's package manager, Find in Files, the Test Explorer, the data, profiler, T4, XAML previewer, container and Aspire tools, C# Interactive, Hot Reload, multiple startup projects, browser and compound debugging, the debug companion's visualizers, plugins, Node-based web language servers, workspace settings, recent lists, and the editor session's restore. `TODO(issue)` each, moved by what remote use needs first.
- **The hosts aren't self-contained.** They run on the target's `dotnet`: the build host must load the target's SDK and roll forward with it (ADR 0025). The self-contained per-platform part is the server itself (`remote/<rid>/`), which runs without .NET. Without .NET, projects don't load.
- **Copy, not download**: bundles are copied from this install. Downloading them from the releases (for targets reached through a slow link) is `TODO(issue)`.
- **SSH uses keys and agents only** (`BatchMode=yes`): a password host fails with ssh's message. The roadmap's "the IDE never sees passwords" is kept strictly. M14c's attach still offers askpass.
- **Remote Windows machines** (SSH to Windows) aren't supported: the path map is Unix-only. `TODO(issue)`
- **Path rewriting** covers whole strings only: a path inside a longer string (a build output line, a hover's link) stays remote, and a remote path with whitespace is rewritten only as a URI. `TODO(issue)`
- **Auto-forwarding** takes every port that starts listening on the remote machine, not only the session's programs' (VS Code's process filter). `TODO(issue)`
- **Terminals** in a remote window have no shell integration (the scripts aren't in the bundle). `TODO(issue)`
- **File contents** travel base64-encoded on the control channel: fine for source files, slow for very large ones. `TODO(issue)`
- **SSH stand-in on Windows**: none, as in M14c (WSL covers the same installer path there). CI's Linux runner uses the fake ssh, not an SSH server in a container. `TODO(issue)`
