# M64b checkpoint: XAML breakpoints, break at a failed binding, the style explanation

Date: 2026-11-14. Three of [M64](m64.md)'s deferred items, pulled into 0.13 by the maintainer on 2026-11-14 (D56's confirmation; [ADR 0103](../adr/0103-xaml-depth.md#what-m64b-built-2026-11-14)). One pull request.

## Done

**XAML breakpoints** (the live agent breaks into the debugger; the IDE shows the XAML line).
- A breakpoint in a `.axaml` or `.xaml` file's margin is a XAML breakpoint: never sent to the debug adapter (`DebugService.ExternalBreakpointFiles`), but to the app's live agent, in the app's environment at launch (`CODALUS_LIVE_AGENT_BREAKPOINTS`, so the first window's elements are caught) and by the `xbreaks` request on each change. The agent answers each one's state, which the glyph shows (bound, or hollow with why).
- What a line is (`XamlBreakpoints.Resolve`, a tolerant scanner): an element breakpoint where a start tag begins; an attribute breakpoint on a line of a start tag's attributes, or on a property element (`<ListBox.ItemTemplate>`, its parent's property); `x:Name` is `Name`, attached attributes are their owner's; directives and design-time attributes can't stop.
- Avalonia (12, Debug builds): the agent watches `XamlSourceInfo`, the file and line Avalonia's XAML compiler gives each object right after its constructor, from `Avalonia.Markup.Xaml`'s load on. An element breakpoint stops at the object's creation, before XAML sets its properties; an attribute breakpoint stops when the property changes during the object's initialization, and for a binding or dynamic resource at each value after. An event's breakpoint says it can't stop.
- WPF (Windows only): `VisualDiagnostics` (the IDE sets `ENABLE_XAML_DIAGNOSTICS_SOURCE_INFO`): an element breakpoint stops when the element joins the visual tree; an attribute breakpoint only at a binding's or dynamic resource's values.
- The stop: the agent sends `event xstop …`, then `Debugger.Break()` on the UI thread. `DebugService.StopExplainer` (the shell's `XamlStopExplainer`) recognizes the agent's frames, takes its last `xstop`, drops the agent's frames and puts a frame for the XAML line on top (the agent frame's id: Locals are `stop` and `element`). The status bar and the Debug output say what stopped.
- XAML Hot Reload compiles with source information and the file's path, so reloaded elements still stop.

**Break When Value Changes** (the Live Property Explorer's context menu on a property, a red dot while on): the agent watches the element's property (Avalonia's `PropertyChanged`, WPF's `DependencyPropertyDescriptor`); a change stops the app as a data breakpoint, at the first frame with source under the agent's.

**Break when a binding fails** (`debug.breakOnFailedBinding`, off by default): each new failure the agent's binding log sees stops the app as an exception (`codalus/xamlBindingFailure`), at the binding's attribute (on the element's own source line when the agent finds the element, else as the Error List finds it, `XamlBindingLocator.FindAtElement` / `Find`); the exception helper says **Binding Failed** with **Break when a binding fails**.

**The style explanation** (the Live Property Explorer's **Styles**).
- Avalonia: the control theme and its nested styles for the element, and each style of its scope whose selector's last part names its type, a base or no type; the state from Avalonia's value store (applies, inactive now, doesn't apply), and for one that doesn't, the selector part that fails and why (the agent's reading of `Selector.ToString`'s text: types, `:is()`, classes, pseudo-classes, names, `[Property=Value]`, `:not()`, child, descendant and `/template/` combinators); setters, with those a local value or an animation overrides; Go to the style's XAML.
- WPF: the element's style and its `BasedOn` chain, setters (overrides marked), property and multi-triggers with the false condition and the element's value, data triggers by whether their setters are in effect, event triggers by their event.

**A fix on the way**: under F5 with the Codalus debugger, its launcher (`codalus-debughost --launch`) ran the live agent too, and the IDE's one connection was the launcher's: the app's agent waited unread behind it, so under the debugger the live tools, failed bindings and XAML Hot Reload had no app (M64's tests ran with `Ctrl+F5`). Both agents now skip the launcher, as the debugger's own startup hook does.

**Docs.** ADR 0103's section "What M64b built", the user guide (Avalonia: XAML breakpoints, Why a style applies; WPF: the same, Windows only; debugging: breakpoints and settings), the website's Features page, `CODALUS_LIVE_AGENT_BREAKPOINTS` in [environment variables](../environment-variables.md), the new texts in `en.json`.
