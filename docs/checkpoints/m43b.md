# M43b checkpoint: the desktop-CLR debugger and tests on .NET Framework

Date: 2026-10-17. The second and last part of M43, the last milestone of the Windows desktop phase (D31: Windows-only features; "M43 includes its debugger"). With it, M43 is done. Decisions: [ADR 0076](../adr/0076-debugging-the-desktop-clr.md) (it amends ADR 0007, 0032 and 0075).

## The spike

The roadmap planned a desktop-CLR port of netcoredbg (MIT), after a spike. The spike compared it with a managed DAP adapter of our own in the debug companion, M20b's precedent (ADR 0065), and chose the adapter:
- **The desktop CLR's debugging API comes with every install:** `mscoree.dll`'s `CLRCreateInstance` → `ICLRMetaHost::GetRuntime("v4.0.30319")` → `ICLRRuntimeInfo::GetInterface(CLSID_CLRDebuggingLegacy)` gives that runtime's `mscordbi` `ICorDebug`, the same interface CoreCLR's debuggers use. Nothing to ship; CLR 2 the same way with `v2.0.50727`.
- **The port** means replacing netcoredbg's dbgshim start path in C++, keeping its managed part (symbols, evaluation) hosted on CoreCLR inside a process debugging the desktop CLR, and a Windows-only native build in CI, packaged and signed under `debugger/netfx/`, none of it buildable or testable on Linux.
- **The adapter** drives ICorDebug from C# through **ClrDebug** (lordmilko, NuGet 0.4.2, MIT, maintained, no dependencies; source-generated COM interop, compiles on every OS), reads metadata and portable PDBs with System.Reflection.Metadata, and evaluates C# itself. Everything above the ICorDebug calls runs on every OS against a fake. MDbg's CorApi (unclear licence) and dnSpy's `dndbg` (GPL) weren't used; vsdbg is proprietary.

## Done

**The adapter** (`codalus-debughost --netfx-dap`, `src/Codalus.Debugging.Host/NetFx`):
- **`CorDebugTarget`/`CorDebugger`** (Windows, ClrDebug): the runtime version from the program's `.config` `supportedRuntime` (first installed) or `GetVersionFromFile`, or for an attach from `clr.dll`/`mscorwks.dll` in the process; `CreateProcess` with a Unicode environment block and pipes for stdout and stderr (the Debug Console) or a console window of its own (`NewConsole`), `DebugActiveProcess` to attach; the adapter's own standard handles kept out of the debuggee. Callbacks become `ClrEvent`s in a channel, the process stopped until the session continues; during a func-eval the other callbacks continue at once (modules and threads still reported). ICorDebug neuters its values and frames whenever the process runs, a func-eval included (CI's first Windows run: `item`'s members were unavailable once `this`'s getter had run): values the session keeps are `ClrLiveValue`s, read again from the frame, their parent's field or element, the static field or the thread's exception; frames are found again by method and stack range; func-eval results are held by strong handles until the program goes on (primitive results kept). The fake ICorDebug neuters its values the same way. The program's last output is drained before the exit is reported. 32-bit programs and processes are refused with what to change. COM errors become messages with the HRESULT's name.
- **`ClrModuleInfo`:** a module's metadata and portable PDB (next to it, from the debug directory, or embedded): type, method, field and property names, signatures as C# names, enums and attributes, sequence points both ways, local scopes; Windows PDBs reported in the symbol status, not read.
- **`NetFxDebugSession`** (the DAP layer, every OS): breakpoints bound as modules load (each method's first offset on the line, or the next line with code; set while the program runs, it's stopped for the change and goes on), conditions evaluated, function breakpoints; line stepping (`StepRange` over the sequence point, hidden lines and mid-line stops step on), Just My Code (user code is what has symbols and isn't optimized; `SetJMCStatus`, JMC steppers, stepping out of code without symbols or marked non-user), step filtering of accessors and operators; threads (names from `Thread.m_Name`), stacks (internal frames as labels, frames without source dimmed); locals and arguments by the PDB, `this`, an async method's or iterator's hoisted variables; members by fields and getters (5 s func-eval limit, the rest skipped after a timeout); enums (flags), `decimal`, `DateTime`, `TimeSpan`, `Nullable<T>`, boxed primitives, arrays (100 elements, several dimensions); setting primitives; exceptions (`all` with netcoredbg's type-name condition, `user-unhandled`; with Just My Code, once per exception where it's thrown in user code) with message, stack trace (the thread's frames when `StackTrace` isn't filled in yet) and inner exceptions; pause; output and `Debugger.Log`; detach and terminate.
- **`ExpressionParser` and `ClrEvaluator`:** a C# subset (literals with C#'s types, names, `this`, members, `?.`, indexers, calls, unary and binary operators with C#'s precedence and numeric promotion, `?:`, `??`, casts); names resolve to locals, arguments, `this`'s members, static members of the method's types, types (keywords, the method's namespace, `System`, a unique name) and namespaces; overloads picked by argument types; calls through `ICorDebugEval` with the generic class's type arguments.
- Off Windows the mode answers DAP and refuses launch and attach: ".NET Framework programs run and debug only on Windows."

**Wiring** (`DebugService`, `DesktopClr`, `ProcessList`, the shell):
- The debug service sends a launch whose program is a managed `.exe` (`DesktopClr.IsManagedExecutable`: a PE with a CLI header; .NET Core's apphosts are native) and an attach to a process with `clr.dll` or `mscorwks.dll` and no `coreclr.dll` to the desktop-CLR adapter (`DesktopClrAdapter`, `IsDesktopClrProgram`, `IsDesktopClrProcess`, settable for tests). F5, multiple startup projects, test hosts and plugins' launches take it without knowing. A terminal launch uses the Debug Console and says why.
- M43a's "debugging comes later" offer and its multiple-startup exclusion are gone. Attach to Process shows ".NET Framework" for desktop-CLR processes (`ProcessEntry.IsDesktopClr`).
- **Old-style projects build portable PDBs:** the build host's targets file sets `DebugType` `portable` where a non-SDK-style .NET Framework project asks for `full` or `pdbonly` (`CodalusKeepDebugType=true` keeps it).

**Tests on .NET Framework:**
- Old-style test projects are test projects by Visual Studio's test project type GUID in `ProjectTypeGuids` (or `IsTestProject`), on VSTest. An import of Visual Studio's targets conditioned on `Exists(...)` no longer makes a project unbuildable (the TeamTest targets of MSTest's old template).
- A debugged .NET Framework test host runs as the IDE's architecture (`TargetPlatform` x64 or ARM64) unless `testing.architecture` chose one.
- Fixtures: `samples/NetFramework` gains **NUnitTests** (NUnit 3.14 on `net48`) and **LegacyTests** (old-style MSTest v2 2.2.10 with `packages.config`, as Visual Studio's Unit Test Project (.NET Framework) template writes it); `samples/Debugging/NetFxDebuggee` is the debugger's `net48` console app (a list loop, auto-properties and a getter, a `[Flags]` enum, an array, a method to call, an async method, `Debug.WriteLine`, a caught exception, exit code 3, and `wait` for attach tests).

**Smoke:** `netfx.projects` on Windows now also debugs the console app with F5 to a breakpoint in `Main`, evaluates `greeter.Greet()` and saves `netfx-debugging.png`.

**Found by PR #27's Windows CI:** `NetFrameworkTests.Net_framework_projects_restore_load_and_build_on_every_os` read `NUnitTests`' test platform as none: a design-time build queued before the evaluations that follow the restore had reported first (M43a's checkpoint has the race). The test now waits for `NUnitTests`' and `LegacyTests`' evaluations after the restore too.

**Found by PR #33's Windows CI:** `NetFxDebuggerTests.Attach_to_a_running_net48_process_stops_evaluates_and_detaches` found the waiting net48 process in the Attach to Process list without ".NET Framework" (`IsDesktopClr` false), intermittently, after 1m 47s. Both flags came from `Process.Modules`, which reads each module's information, base name and path by walking the loader list again (three walks a module), leaves out a module whose read fails with ERROR_PARTIAL_COPY or ERROR_INVALID_HANDLE while the process loads or unloads one (a snapshot without `clr.dll`, and no error), and retries a process it can't read 50 times a millisecond apart (once for `LoadedRuntime` and again for `IsDotnet`, since a failure isn't cached): a second or more for every such process on a loaded runner. Now `Codalus.Platform.ProcessModules` reads the names in one pass (`EnumProcessModulesEx` and one `GetModuleBaseNameW` a module; `/proc/<id>/maps` on Linux), takes a snapshot with a failed read again up to 8 times, 1 to 8 ms apart, and stops at once when the process has exited; `ProcessList` classifies each process from that one snapshot (`ProcessList.Classify`), `DesktopClr.LoadedRuntime`/`RunsDesktopClr` (the debug service's attach routing, the adapter's attach) read the same way, and `ProcessEntry.IsDotnet` is true whenever `IsDesktopClr` is.

**Found again by PR #38's Windows CI** (develop 8e6d3247, job 117609042036; after the change above): the same assertion, after 1m 43s. The cause wasn't the module reads' reliability but the list's speed. The test spends nothing but the program's start, its "waiting" line (60 s at most) and `ProcessList.Get()` before that assertion, so the list took well over a minute on the loaded 4-core runner, and the net48 program's wait mode lasted exactly 600 ticks of 100 ms: a minute. `Process.GetProcesses()` lists the processes first, newest last, so the program was in the snapshot (the `Single` found it) but had ended by the time its modules were read: no modules, so not .NET (`ProcessModules.Names` returns null once a process has exited). That explains both failures (1m 47s with `Process.Modules`, 1m 43s with its replacement) and why the replacement, which made the reads reliable but not fast, changed nothing. What made the list slow: every module's name was read by walking the process's loader list again through its memory (`GetModuleBaseNameW`, like `Process.Modules`'s three reads a module), a walk times the modules for every process, and `Process.MainWindowTitle` enumerated every window again for each process and read titles with `GetWindowTextLengthW`, which can wait for a window's process to answer. Now `ProcessModules` walks a process's loader list once (`EnumProcessModulesEx`) and names each module by the file mapped at its address (`GetMappedFileNameW`, a kernel lookup in the address map that reads nothing of the process's memory and works the same for a WOW64 process's 32-bit modules; a module unloaded meanwhile is left out rather than the snapshot taken again), retries only a list that couldn't be walked, 4 times with at most a timer tick or two between (no more sleeps across every process); `ProcessWindows.MainWindowTitles` enumerates the windows once for all processes and reads titles with `InternalGetWindowText`, which never sends a message. The debuggee's wait mode lasts ten minutes (the test kills it), and the test says when the program ended during the list and how long the list took. New tests: `ProcessModulesTests` (Workbench, 4): a running .NET process's modules name its runtime and the list calls it .NET, an ended one's are unknown (the CI failure's state), NT paths' file names (a WOW64 32-bit runtime's too), `/proc/<id>/maps` names, the window titles. Not validated on Windows here (no Windows machine in that session): needs the PR's Windows CI.

**Needs validating on Windows** (CI's `windows-latest`): everything that calls ICorDebug: `NetFxDebuggerTests`, `NetFrameworkTestingTests`, `NetFrameworkShellTests.Windows_starts_and_debugs_the_net48_console_app`, the smoke step's debugging and `netfx-debugging.png` (the website's screenshot once a run has made it), and the build host's portable PDBs for old-style projects with Windows' compiler. **macOS:** the cross-OS tests above.
