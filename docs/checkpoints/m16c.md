# M16c checkpoint: Blazor WebAssembly and browser debugging

Date: 2026-10-10. Decision: [ADR 0026](../adr/0026-browser-debugging.md). The maintainer moved M16c ahead of M31–M33 after M30a. M16d (below) finishes M16.

## Built

**Debugger library** (`DaedalusStudio.Debugging`)
- **`DapConnection`:** accepts reverse requests a client opts into (`Accept("startDebugging")`). They are answered at once and raised in order with the events, so a handler can't hold up the connection. The rest are still refused.
- **`IDebugAdapter`:** what `DebugService` uses. netcoredbg's `DebugAdapter` implements it, with launch and attach on the class.
- **`JsDebugAdapter`:** vscode-js-debug's DAP server as one adapter:
  - it starts `dapDebugServer.js` on Node and connects over TCP;
  - it opens a connection for each child session `js-debug` asks for (`startDebugging`: the page, workers), replays the breakpoints and exception settings to it, then sends `configurationDone`;
  - it routes requests to the child that stopped last, and maps every child's breakpoint ids onto its own;
  - js-debug's exception filters are kept, netcoredbg's dropped; function breakpoints report "not supported".
- **DAP records:** `BrowserLaunchArguments`, `StartDebuggingArguments`, and `supportsStartDebuggingRequest` in `initialize`.

**Workbench**
- **`JsDebug`** (`Node/JsDebug.cs`): `js-debug-dap` 1.140.0 from the GitHub release, verified by SHA-256 and unpacked into the Node cache. `VerifiedDownload` is shared with `NodeRuntime`.
- **`Browsers`:** Chrome, Edge and Chromium at their usual places on each OS, or the setting `debug.browser`. `DAEDALUS_BROWSER_HEADLESS=1` runs them headless.
- **`DebugService`:**
  - `LaunchBrowserAsync`;
  - sessions start in DAP's order (launch, then configure while it runs), because `js-debug` answers its launch only after `configurationDone`;
  - telemetry output events aren't shown.
- **`LaunchPlanner.BrowserDebugTarget`:** a project on the WebAssembly dev server whose profile has `inspectUri` debugs in the browser. Profiles keep `inspectUri`.
- **`RunService`:**
  - `StartAsync(openBrowser: false)`, so F5's dev server doesn't also open the default browser;
  - `RunningProgram.Listening`, the first "Now listening on" URL.

**Shell** (`ShellHost.BrowserDebug.cs`)
- **F5 on a Blazor WebAssembly app:**
  - installs `js-debug` (and Node.js) on first use, with progress in the Debug Console;
  - starts the dev server and waits for it to listen;
  - launches the browser through the debugging proxy, with the project as the web root.
  - The session and the dev server end together.
- **The setting** Browser (`debug.browser`).
- **Hot Reload** for WebAssembly works through M15b's `dotnet watch` once a browser has the page open. No code change was needed; it is now tested.

**Fixture:** `samples/BlazorWasm` (`dotnet new blazorwasm --empty`): `Counter.razor` with `// [initialized]` and `// [increment]` markers, `launchBrowser` off, and `launchUrl: counter` on the `http` profile.

**Tests**
- **Workbench:** `BrowserDebugTests`:
  - in a static page in headless Chrome: a JavaScript breakpoint binds and stops, then the frames, evaluation and step over;
  - browser discovery by kind and path, and which projects debug in the browser.
- **Headless UI:** `BlazorWasmTests`:
  - F5 on the fixture stops at the breakpoint in `Counter.razor` with `Counter.OnInitialized` on top, the editor at the line and `this` in the locals; stopping closes the browser and the dev server;
  - Hot Reload applies a markup edit of `Counter.razor` with the page open in headless Chrome.
- **Smoke test:** step `blazor.wasmDebug` (M16): F5 on the fixture stops at the `.razor` breakpoint in the browser, and the dev server stops with the session. Without a Chromium browser it's skipped, except in CI. `eng/smoke-test.sh` runs the browser headless.

**Docs:** ADR 0026, [User guide: Web development](../user-guide/web.md) (Blazor WebAssembly), the debugging guide's limitations, `THIRD-PARTY-NOTICES.md` (vscode-js-debug, MIT), CLAUDE.md, the roadmap.

## Found along the way

- **The spike:**
  - a small Node DAP client drove `js-debug` through both paths, a JavaScript breakpoint in headless Chrome and a C# breakpoint in a Blazor WebAssembly component through the proxy, before any design was written (ADR 0026);
  - **headless Edge** couldn't be attached to on the development machine, where Edge was running, with either headless flag. Chrome comes first; Edge is tried when Chrome is missing.
- **`DebugService.StopAsync` could return before the session ended:** when the adapter had already reported that it terminated (`js-debug` does on disconnect), the end ran in the background and `StopAsync` found nothing to do. A per-session task now completes when the session has ended, and `StopAsync` waits for it.
- **The exception helper could stay open** after Run to Cursor or a step from an exception. It closed only if the program was still running when its check ran, and a quick stop at the next line beat it. It now also closes when the stop isn't the one it was shown for. M14a's `DebugDepthTests` caught it once sessions started in DAP's order.
- **`NavigationDepthTests`'s Peek Definition** (the CI failure after M16a) kept the editor's view from the moment the file opened. When the view was attached later, Peek opened in the current view and the test watched the stale one for minutes. A probe showed the definition answering in 30–110 ms and Peek opening. The test reads the current view now.
- **Inlay hints could stay empty:** a hint request that came back empty (asked before the language host had the document's semantics) was retried only when new diagnostics arrived. On CI's runner none did, and `NavigationDepthTests` waited in vain. An empty answer is now asked again after 1, 2 and 3 seconds, and an edit resets the count.
- **`TerminalTests`** pressed Ctrl+C half a second after starting `ping`; on a busy machine that was before `ping` ran. It waits for `ping`'s output now.
- **Paths from js-debug** come back with a lower-case drive letter on Windows (`c:\…`). The shell opens the right file at the stopped line from them, as `BlazorWasmTests` checks. Whether a file already open under the other spelling gets a second editor isn't tested.
