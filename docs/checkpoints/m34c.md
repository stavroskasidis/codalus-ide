# M34c checkpoint: performance pass, round 2

Date: 2026-10-13. Round 2 of the performance pass (round 1: [m34b](m34b.md)), built beside M34a's UI work; the roadmap entry is under [M34](../roadmap.md#m34--ui-polish). Decision: [ADR 0049](../adr/0049-language-state-between-sessions.md).

## Where round 1 left it

On the maintainer's 96-project web solution (mostly Blazor and ASP.NET Core; Razor and other source generators), cold / warm: the open files' first real diagnostics after 52 s / 35–38 s, the whole solution ready after 76 s / 53–58 s. The rest was Roslyn. Their solution was used only to measure and diagnose; nothing from it is in the repository.

## Where the time went

Measured with the M34b probe (the build host and the C# language host driven through the workbench as the shell drives them, Debug hosts, this machine's 20 logical processors, the four documents the maintainer had open, completion and Quick Info asked every 2 s from the moment they open; another IDE had the solution open):

- **Every session compiled every project again**: the background pass took 43–48 s on half the processors. Nothing of it outlived the process.
- **Source generators are a minority of it.** Run again alone, one project at a time (`DAEDALUS_GENERATOR_TIMINGS=1`): 13 s in all, of which the Razor generator 12.2 s over 28 projects (5.2 s in the largest), a validation generator 0.6 s over 73 projects, and every other generator (JSON, regex, logging, interop, options, two of the solution's own) under 0.2 s each. The rest is binding: the declaration and method-body diagnostics of 5,239 documents.
- **The open documents waited for the chain below them**: their project compiles against its references' *compilations*, so its first semantic model waited for every project under it, one level after another. Completion asked 4 s after opening answered after 29 s.
- **Memory**: the language host held 3.7 GB after the pass, compilations of 96 projects, though only 53 are under the open documents.
- **The three CS4014 errors** (round 1 blamed the host's newer Roslyn) come from the same compilation references: the compiler reports CS4014 outside an `async` method only for a call to a method it sees as `async`, and a method of another project is `async` only in source. The build compiles against that project's assembly and reports nothing; the workspace reported the warning, which the solution turns into an error. The SDK's own compilers (10.0.1xx to 11.0 preview) agree with each other: a three-line program warns with a compilation reference and not with the assembly.

## Built

**Language state between sessions** (`LanguageStateCache`, `ProjectKeys`, ADR 0049). After a background pass, each project's diagnostics go to `obj/<config>/<tfm>/daedalus.language.json`, and a referenced project's metadata (internals and documentation comments included) to `daedalus.language.ref.dll` and `.xml`, under a key of its compiler command line, every input file by length and time written (an open document by its text when it differs from the file), the host's Roslyn, the analysis scope and the keys of the projects it references. The next session's first pass takes the diagnostics of every project whose key matches without compiling it. `DAEDALUS_LANGUAGE_CACHE=0` turns it off.

**The analysis solution** (`AnalysisSolution`). While the projects an open document's project references haven't compiled in the workspace, the document's diagnostics, completion, Quick Info, signature help, highlights, semantic tokens and inlay hints, and the background pass's compilations, use a copy of the solution in which every unchanged referenced project stands as its reference assembly: the cache's, or the project's last build's when that is newer than every input (the first session after this change). The open document's project then compiles with its own sources and generators only. Edits carry over to it as they come; an edit to a project that stands as an assembly rebuilds it with that project from source. Navigation, references, rename and code actions keep the workspace's solution.

**Then the workspace catches up**: once the open documents' diagnostics are done, the projects under them compile in the workspace on a quarter of the processors (edits don't cancel it), and the analysis solution is dropped. The other 43 projects compile only when something asks for them.

**CS4014 the build wouldn't report** is left out (`BuildDivergence`): outside an `async` method or lambda, on a call into another assembly. The analysis solution, whose references are assemblies like the build's, doesn't report it at all.

**Smaller things.** The first background pass after loading starts after 200 ms instead of the 1.5 s that lets edits settle. The design-time build host builds again a result whose key went stale while its batch ran, and the projects that reference a re-evaluated project (the Linux CI failure of M34b's cache test: on Linux the restore's assets files arrive one evaluation at a time, and a test project's cache entry kept a key from before its referenced project's last evaluation). The design-time build cache's hits and misses, with reasons, are in the build host log and in the bench event `designtime_done` (`cache_hits`, `cache_misses`, `cache_miss_reasons`), for the Mac's benchmarks.

**Tried and dropped: frozen partial semantics.** Roslyn's (internal) frozen partial semantics answered completion while compilations were still building, but its semantic-model reuse kept the frozen model once the compilation was complete: completion returned nothing for the rest of the session. Not used (ADR 0049).

## Deviations and gaps

- **Generator outputs aren't cached as such**: Roslyn has no public way to seed a generator driver's state from another process. A project whose key matches skips its generators with its compilation; one that changed runs them.
- **Frozen partial semantics weren't used** (above): the first completion in a project waits for that project's own compilation in the analysis solution (5 s on the large solution when warm, 1.6–1.9 s on Solution50).
- **Typing while a solution loads**: the in-app keystroke-to-frame time is 12 ms at p50 but 45–47 ms at p99 on Solution50 while it loads, with or without the language state, so it comes from the shell's own work during loading, not the language host. `TODO(issue)`: profile the UI thread during a solution load.
- **A build's reference assembly carries no documentation** unless the project writes a documentation file: Quick Info on another project's symbols shows none in the first session until the workspace catches up.
- **The key leaves out environment variables** (as M34b's cache does), and a file rewritten within the same tick and to the same length keeps the old state.
- **Measurements of the large solution** ran while another IDE had it open, and the benchmarks while other sessions validated on this machine; the before and after rounds were interleaved.
