# M61b checkpoint: the async call stack for state machines

Date: 2026-11-14. Decided by the maintainer on 2026-11-14 as a follow-up of [M61](m61.md) (D53, [ADR 0100](../adr/0100-debugging-runtime-async-code.md#what-m61b-built-2026-11-14)), before 0.13: the Codalus debugger's Call Stack shows the calls awaiting an async method built as a state machine, as the classic IDE's does. Runtime async keeps its limit. One pull request, with the fix of a flaky step over an await found by CI on the way.

## Done

**The async call stack.** Stopped in an async method, below the thread's own frames (which end in the thread pool once the method has resumed), the methods awaiting it, the nearest first, out to `Main`:
- found from the outermost state machine on the thread's stack whose task something awaits: its task's continuation (`m_continuationObject`) leads to the awaiting state machine, through its box (`AsyncStateMachineBox<…>.StateMachine`, the .NET Framework's `MoveNextRunner`), a delegate whose target is one, a `ContinuationWrapper`, an `AwaitTaskContinuation` or a list of continuations; that one's task names the next. A task without a continuation yet is looked for on another thread's stack, as M61's step out does (`NetFxDebugSession.AsyncStack.cs`);
- each frame is `[Async] Ns.Type.Method` (`Program.Main`, not `Program.<Main>d__0.MoveNext`), at the line of the await it waits in: its state indexes the portable PDB's async stepping information (`ClrModuleInfo.AsyncYieldOffsets`); one running on another thread's stack is at that frame's line, one without the information has no source;
- under Just My Code an awaiting state machine that isn't the user's code is `subtle`, as the thread's own frames are: the Call Stack dims it as external code;
- read once per stop and thread, and only for a `stackTrace` that reaches the stack's end (not the Threads window's top frame).

**Its frames' variables.** Selecting an awaiting frame shows its state machine's fields in Locals (its parameters, hoisted locals and `this`), held by a strong handle on its box until the program runs on; Watch, the Debug Console and data tips evaluate in its scope (func-evals on the stopped thread). It has no `MoveNext` locals, registers or machine code, and Set Next Statement doesn't move it.

**No change in the shell.** Its Call Stack (`FrameRow`) shows the awaiting frames as frames with a source: their location opens the file at the await's line, and a dimmed one is external code.

**Runtime async.** No async call stack: the runtime doesn't expose a runtime-async call's continuations (ADR 0100's limit 2, reported upstream). Its frames end in the dispatcher, as before, and the tests assert it as the documented limit.

**A flaky step over an await, fixed** (Linux CI, runs 43568784192 and 43570667240; [docs/ci-flakes.md](../ci-flakes.md); its own commit, so it could ship ahead). `RuntimeAsyncDebuggingTests.Step_into_an_awaited_call_and_step_out_back_to_the_awaiting_caller(AsyncDebuggee)` stopped in the caller, on the await's line, after a Step Over of `await Task.Yield()`: a pool thread had resumed the method before the stepping thread had left it, and when the stepper ended in the caller the state machine's state read -1, running, which M61 took for a method that had returned. A state machine running on no frame of the stepping thread has resumed elsewhere, so it did suspend (`Suspended`). Reproduced locally about once in 35 loops of the scenario, from the adapter's log; the fixture's new `race` scenario (`Elsewhere.cs`: an awaiter that resumes the method on a new thread and returns from `OnCompleted` only once the method is in its `GetResult`) makes it certain.

**The program's race, one step earlier.** Ten runs of the classes found `RuntimeAsyncDebuggingTests.Step_into_an_awaited_call_and_step_out_back_to_the_awaiting_caller(AsyncDebuggee)` failing once more (its Step Out ran the program to its end), and runs under CPU load (two busy processes on the session's four cores) also the chain of `AsyncCallStackTests` stopping after `MiddleAsync`. Both were M61's race of the program one step earlier: the method had resumed elsewhere before its caller had taken its task at all (the caller's thread still on its way back from the method's await), so no continuation and no awaiter named the caller. `AwaiterOnAStack` now also finds the caller below the method's own `MoveNext`, or its kickoff, on another thread's stack, past code that isn't the user's; the chain goes on below a caller found there by that stack. The fixture's `held` scenario makes it certain (the awaiter's `OnCompleted` holds the caller until the resumed method releases it): `Step_out_of_a_resumed_method_whose_caller_doesnt_have_its_task_yet_stops_in_the_caller` and `A_caller_that_doesnt_have_the_methods_task_yet_is_found_on_its_threads_stack` fail without it and pass with it.

**The fixture.** `samples/Debugging/Async.slnx` gets the `race` and `held` scenarios and markers (`[main-chain]`, `[main-held]`, `[chain-inner-return]`, `[race-…]`, `[held-…]`); no line of the earlier markers moved.

**Docs.** ADR 0100's "What M61b built (2026-11-14)" and its table, the user guide's [Async code and runtime async](../user-guide/debugging.md#async-code-and-runtime-async-net-11) and the Codalus debugger's limits, a line on the website's Features page.
