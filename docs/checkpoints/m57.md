# M57 checkpoint: 0.11, document sync off the UI thread, Open Folder listed as you expand, virtualized Git trees

Date: 2026-10-31. The scope is the roadmap's [M57](../roadmap.md#m57--011-document-sync-off-the-ui-thread-open-folder-listed-as-you-expand-virtualized-git-trees). These were the three suggestions left after [M56](m56.md), and the maintainer asked for all three ("do the three you suggested, grill me"):
1. `didOpen` and `didChange` built and serialized off the UI thread;
2. Open Folder lists folders lazily, as they're expanded;
3. the Git Repository, Commit Details and Compare trees virtualized.

The maintainer's decisions, in the grilling:
- **Delivery:** one milestone pull request.
- **Language services:**
  - one writer loop per JSON-RPC connection;
  - the UI thread hands over a snapshot, and the string is made on the writer;
  - for a server that syncs whole documents, the latest whole text still queued wins;
  - Razor's HTML projection is included.
- **Open Folder:**
  - one level per folder, through the existing `fs/listTree`;
  - a non-empty search box takes one whole listing off the UI thread;
  - collapsed folders keep their rows and stop updating;
  - `node_modules`, `.vs` and `.idea` show dimmed, listed only when expanded, in the folder view and in Show All Files.
- **Git:**
  - the trees reuse Git Changes' rows;
  - the Git Repository document reads nothing while hidden;
  - a proper automation peer for every virtualized tree.

Branch `claude/practical-mendel-20hupn`, from `develop` at `e28d3b3f` (M56's merge). Each item was built in its own worktree, then reviewed adversarially and fixed. The integrated branch then had its own review.

## Done

**Document sync off the UI thread** (item 1, [ADR 0005's amendment](../adr/0005-editor-and-language-services.md#amendment-2026-10-31-document-sync-off-the-ui-thread-m57), [protocol](../protocol.md)).
- **`JsonRpcConnection`** has one writer loop. `InvokeAsync`, `NotifyAsync`, responses and cancellations only queue, synchronously and in call order. The loop makes each message's JSON, writes it whole and flushes once for what was queued meanwhile.
  - A request cancelled while queued sends nothing, not even `$/cancelRequest`. A queued notification is never dropped: its token only stops the caller waiting.
  - Disposal fails what is queued with `JsonRpcConnectionLostException`.
  - A stream failure of any type fails what was written, what is queued and what comes later. Before the review, a non-I/O failure (a remote window's path rewrite) stopped the loop silently and left them all waiting.
  - The stuck-write watchdog stays, and now tells a message waiting behind others from the one being written.
  - The file is also compiled into the .NET 8 Windows Forms designer, so it uses nothing newer.
  - A new lazy `NotifyAsync(method, Func<TParams?>, info, replaces, ct)` makes its parameters on the loop; null sends nothing. A `replaces` key replaces a queued notification with the same key only when nothing but responses or cancellations is queued after it, so it never moves past a request.
- **`LanguageHostClient`:**
  - It tracks, per connection, the version each server has of each document (`DocumentVersions`). A change at or below that version is skipped, and so is a change for a document not open there.
  - `DidChangeTextAsync` sends a whole text made from its own change's snapshot, coalesced per document.
  - `DidOpenAsync` sends the snapshot taken when it was queued. It sends the latest one only when the loop has already skipped a newer change because the document wasn't open yet. That happens when a change is queued from the editor's thread between the snapshot and the `didOpen`, and the latest snapshot makes sure the edit isn't lost.
- **The editor** keeps each document's AvaloniaEdit snapshot and version together under one lock. Before, they were written without it, and the text was paired with the live version, so a `didOpen` could carry a version newer than its text.
- **`LanguageService.ChangeAsync`** queues every client's change before awaiting any. A document's linter could get two quick changes in the wrong order.
- **Razor's HTML** is projected from a snapshot in the background, at the Razor file's own version.
  - A projection older than the one already sent is dropped.
  - One that finishes after its file closed opens nothing.
- **Found in the integration review and fixed here:** the `didOpen` read the editor's latest snapshot when it was written, so a hover or completion queued behind it read a later key's text. That key's own change was then skipped as already sent. `LspBridgeTests.A_request_queued_behind_a_didOpen_reads_the_text_it_was_queued_with` fails without the fix: the hover read `!b = 1` instead of `b = 1`.
- **Found in the branch review and fixed here:** after a crash, the restarted server's replay read every open document's text when it began and sent that. An edit made while earlier documents were written was skipped (the document wasn't open on the new server yet) and never reached it, so an incremental server applied the next edits to a text one edit behind. The replay now opens each document as a document opened now is: the snapshot taken when its `didOpen` is queued, the latest read when it is written, and nothing sent for a document closed since the replay began (it sent the text read at the start, after the close). `LspBridgeTests.An_edit_made_while_a_restarted_server_reopens_documents_reaches_it` fails without the fix (the server ended on `!b = 1` instead of `!!b = 1`), and `A_document_closed_while_a_restarted_server_reopens_documents_is_not_opened_there` without the close check (the server kept `b = 1`).
- **Local stall tests** (Debug, a shared 4-core container; they decide nothing):

  | Test | Before | After |
  |---|---|---|
  | `didOpen` of a 19 MB XML file just under the large-file limits | 707–780 ms | 11 ms |
  | 20 keys in a 15 MB file under a whole-text server, longest UI wait | 312–325 ms | 18–24 ms |
- **Tests:**
  - `JsonRpcConnectionTests`: ordering from 8 threads, queued cancellation, notifications never dropped, coalescing never moving past a request, disposal, the stuck-write report, a stream failing with any exception.
  - `LspBridgeTests`, through the conformance server's new `--log` and `--incremental`: whole texts end on the final text with increasing versions; an incremental server gets one change per version; no change at or below the opened version; a server and its linter get every change in order; a request between two changes reads the first one's text; a request queued behind a `didOpen` reads its text; a `didOpen` after a skipped newer change sends the latest text; after a crash, an edit made during the replay reaches the new server, and a document closed during it isn't opened there.
  - `RemoteServerTests`: a 4 MB `didOpen` through `MappedJsonStream` doesn't hold its caller.
  - `EditorLargeTextTests`: the two stall tests, and edits made while a `didOpen` is queued reaching an incremental server once at their versions.
  - `RazorHtmlTests`: an older projection is dropped; a projection finishing after its file closed opens nothing.

**Open Folder listed as you expand** (item 2, [ADR 0033's amendment](../adr/0033-project-items-templates-and-folder-mode.md#amendment-2026-10-31-the-folder-view-lists-each-folder-once-its-expanded), [project protocol](../project-protocol.md)).
- **The folder view lists each folder when it's expanded**, with `fs/listTree(folder, folders: [])`, one level at a time, "Loading…" until it arrives.
  - It used to list the whole folder (cut at 20,000 entries, so the folders past the cut looked empty) and build every node again on the UI thread at each change, build and project load.
  - A change on disk lists again only the expanded folders it touched, four at a time, off the UI thread.
  - A collapsed folder keeps its rows, shows them at once when expanded again, and is listed again then.
- **A folder over 20,000 entries** shows the first 20,000 and a muted row saying the rest isn't shown, with a next step (Find in Files or the terminal).
- **The search box** takes one whole listing (up to 20,000 entries) off the UI thread and keeps it while the box has text. When that listing stops at the limit, its row gives the real count, and a folder it didn't go into says "Not searched" instead of looking empty.
- **`node_modules`, `.vs` and `.idea`** show dimmed and are listed only when expanded, in the folder view and in Show All Files, even when a plain SDK project makes `node_modules`' files items (dimmed with what is in them, as in the folder view). Show All Files left on in the folder view leaves the folder view's `node_modules` alone (it added a "Loading…" row and listed the project). `.git` stays hidden, and folder project discovery still skips them all.
- **`bin` and `obj`** are listed again after the IDE's builds; their changes aren't watched. After the build host restarts, the folders shown are listed again. A change or a build while a folder's first listing is on its way lists it again with the next batch (it was dropped, and the folder kept a listing older than the change).
- **Sync with Active Document and Track Active Item** expand down to a file in a folder not listed yet.
  - A file outside the folder, or under `.git`, gets "The active document isn't in the folder."
  - In folder mode's solution view, a file no loaded project has gets "The active document isn't in a loaded project."
  - They do go into `node_modules`, `.vs` and `.idea`: those folders are visible now, and expanding one is what the user would do by hand. The amendment records this reading of the decision.
- **Fixed on the way:** a Sync waiting for its listings could be dropped, with a false "isn't in the folder", when another folder's batch looked for the file before the tree was built with those listings. Show All Files had the same race since M56 (`ResolveSyncWhenListed` now waits while a tree build is queued; [ci-flakes](../ci-flakes.md)).
- **Tests:**
  - `SolutionExplorerHostTests`: one level per folder; a cut listing says so; IDE and package folders marked and gone into only when named; `.git` never.
  - `SolutionTreeTests`: the view built from each folder's own listing; dimming; the cut row; a whole listing split per folder for the search box, and its count when cut.
  - `SolutionExplorerFolderViewTests` (new, 15 tests), `SolutionExplorerShowAllFilesTests`.
  - `EverydayResponsivenessTests.Folder_view_flows_on_thirty_thousand_entries`: open, a deep expand, 20 bursts of changes, a build, a filter and a Sync into an unlisted folder, within the 1,000 ms stall budget.

**Virtualized Git trees** (item 3, [ADR 0089's amendment](../adr/0089-manage-branches.md#amendment-2026-10-31-the-trees-as-rows-and-nothing-read-while-hidden)). This was M56's deferred "Windows not virtualized yet".
- **The Git Repository tree, a commit's changed files and Compare are virtualized lists**, as Git Changes is.
  - A commit's files and Compare reuse Git Changes' rows (`GitChangeNode` and `GitChangeRow` through `BuildTree`, with a read-only template).
  - The Git Repository tree has its own row, patched in place with `ResettableCollection.Patch`.
  - All four trees share one keyboard and chevron behavior (`TreeRows`): `Left`, `Right` (with `Ctrl`, everything under), `+`, `−`, `*`, `/`, `Enter`, `Ctrl+Enter`, the chevron and a double-click.
  - The review found three regressions from the tree views, fixed: a click on the chevron selected the folder, which dropped the Git Repository's history (its press now never reaches the row, as a tree view's expander, and focuses the selected row); a double-click below the rows checked out the selected branch (off the rows it now does nothing, except in Git Changes and Compare, which open the selected file as their lists do); and a build running as the document closed started a history nothing disposed.
- **The Git Repository document:**
  - It reads nothing from git while its tab is hidden; it used to run four or five git processes and rebuild the whole tree at every status read. It reads once when shown, and menus read first if what they act on is stale.
  - A status read with the same refs changes nothing; deleting one tag is one removal.
  - The filter applies 150 ms after the last key, built off the UI thread, with every match's folders expanded.
  - A deleted selected branch leaves nothing selected.
- **Commit Details** stays fully expanded and keeps its selection across tab switches. **Compare** builds only the view shown (Tree or List). Its Refresh keeps collapsed folders and the selection, and switching views while it builds no longer leaves the list empty.
- **The Branch / Tag column shows a commit's first eight refs**, and the tooltip and the accessible name list them all.
  - The review found the keyboard test failing in 3 of 4 runs. In its fixture every ref points at one commit, so selecting a branch built 320 chips on the UI thread: 470–1,084 ms, longer than the double-click time.
  - With 7,000 refs, one selection stalled 4.9 s.
  - The column is 130 px wide, so no more than eight chips ever showed ([ci-flakes](../ci-flakes.md)).
- **Local stall tests**, the longest UI stall per flow (Debug, headless, a shared 4-core container; they decide nothing). The "before" figures include 9–24 s of garbage collection each.

  | Flow | Before | After |
  |---|---|---|
  | 7,000 refs (5,000 tags, 2,000 branches): typing in the filter | 17–25 s | 24 ms |
  | The same: status reads with the tags expanded | 24–31 s | 18 ms |
  | A 10,000-file commit: open and four tab switches | 29 s to open, 17–21 s per switch | 109 ms |
  | Compare 10,000 files apart: open, Refresh, Tree and List | 16–21 s | 81 ms |
- **Tests:**
  - `GitTreesRowsTests` (new): 7,000 refs, with rows in place, nothing read while hidden and the filter debounced; the keyboard, chevron (which selects nothing) and double-click; a double-click below the rows; a close during a build; a 10,000-file commit; Compare 10,000 files apart.
  - `EverydayResponsivenessTests`: `Git_repository_flows_on_seven_thousand_refs`, with selecting branches at the commit all 7,000 refs point at, and `Commit_details_and_compare_flows_on_ten_thousand_files`.

**Screen readers read the trees as trees** (the maintainer's "proper peer for all trees"; [accessibility](../accessibility.md), [UI guidelines](../ui-guidelines.md)).
- **`TreeRowsList`** is a `ListBox` whose rows have a tree item automation peer: role TreeItem, the ExpandCollapse pattern for a row that has children (wired to the view's own expand and collapse), and level, position and size. Eight trees use it:
  - the Solution Explorer, Git Changes and the Document Outline;
  - the Git Repository tree, a commit's changed files and Compare;
  - the Test Explorer and Coverage Results.
- **Row names no longer end in ", expanded" or ", collapsed"**, except on macOS. Avalonia 12.1 gives VoiceOver `AXExpanded` but not the `AXDisclosing` it reads on outline rows, so on macOS a folder's name keeps its state.
- **A row's place ("3 of 12")** reaches Orca on Linux. On Windows and macOS, Avalonia 12.1 doesn't pass the level and place yet.
- **Recycled rows** take their new row's place at once and announce no expansion change while the list scrolls. The review found both wrong: a root that is 5 of 40 read as "4 of 9", and each scroll step raised changes nobody made.
- **A tree item follows its row only while the row is on screen.** The review found that the rows, which outlive their views, held every view Dock built again while a screen reader ran. It also found that Coverage Results made every row again on a toggle, so the toggled folder announced nothing; it now patches its rows in place. And a batch of single-row changes (the Test Explorer's) worked out every row's place once per change; it now does so once per batch.
- **Tests:** `TreeRowsAutomationTests` (new, 10 tests): the control on its own, recycling while scrolling, macOS names, a view let go once it's gone, places worked out once per batch, and the Solution Explorer, Outline, Test Explorer and Coverage Results through their keys. The Git Changes and Git trees tests check level, place and expansion through the peer.
