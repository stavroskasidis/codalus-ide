## Done

**.NET 11 RC3** ([docs/release/dotnet-upgrade.md](../release/dotnet-upgrade.md)):

- The hosts ask for the runtime they're built with, so users with only RC2 get M49's one notification and **Install .NET 11.0**, and the update feed's `CodalusFrameworks` holds the update back until it's installed. The user guide's prerequisites and the website's Download page say RC3.
- The build has no new warnings on the RC3 SDK.

**No name of the classic IDE in the current files** (item 2): 226 files, every mention of the product's name and its two-letter abbreviation now "the classic IDE" ("Classic IDE" in headings and names), the roadmap's M29 title and parity matrix with their anchors included. Git history, tags and releases are unchanged. `ProductNameTests` (Workbench tests) scans `git ls-files` and fails on any line naming it, a name wrapped over two lines too. It allows the `.sln` format's own text, `THIRD-PARTY-NOTICES.md`, and functional strings with their reasons: vswhere.exe's install folder (the benchmark harness, `pipeline.yml`'s `PATH`), VS Code's theme names that the settings importer maps, and the UI tests that check the name is absent. CLAUDE.md's UI rule now covers every current file.

**A tool window dragged across keeps its width** (item 3, `Docking/DockDropSizer.cs`): Dock gives a new pane half its neighbour's proportion, or `DockSettings.GlobalDockingProportion` (0.5) at the window's edges, next to siblings whose proportions came from a saved layout, so the pane could get none. After a drop that makes a pane (Left, Right, Top or Bottom), once the layout has run, the pane gets the width (or height) its tool window had before the drag, read from each tool window frame's last bounds, or a quarter of the window when it had none, never under 200 px, and its neighbours keep their proportions to each other. `A_tool_window_dragged_across_keeps_its_width` drops Solution Explorer at the window's left edge and beside the documents, with Dock's proportion and with none.

**CPU** (item 4): `open-solution-50` reports `cpu_open_s`, the process tree's CPU seconds until the solution is ready (each process sampled every 250 ms, so a design-time build's worker node that exits still counts), and `cpu_idle_percent`, its CPU over the 10 s after, as a share of one core. No budget yet: CI measures them first on each OS (deferred, below).

**Tool window header buttons** (item 5): Dock's chrome resources (`DockChromeButtonWidth`, `Height`, `Padding`, `DockToolIconCloseGeometry`, `DockIconPinGeometry`, `DockIconPinnedGeometry`) make the pin, X and menu 16 px buttons with a 12 px glyph area, the document tab's X and its Fluent pin (upright while docked, lying down while auto-hidden). Dock's were 18 × 28 with a 12 × 19 pin. Checked in every theme.

**The website** (item 6):
- Each page has its own preview image (`og:image`, `og:image:alt`, `twitter:image`): the guide's pages the screenshot of what they describe, Features IntelliSense, Download the setup.
- The docs have a `BreadcrumbList` (Home › Documentation › page). No page is a list of questions, so there's no `FAQPage`.
- Lighthouse 95+ on every page: `eng/lighthouse.sh <site>` serves an export and fails when a page scores under 95 in performance, accessibility, best practices or SEO; `pages.yml` runs it on a second export after the site's. The home page and Features were at 88 and 83 in performance: the web font's late swap repainted the hero text (`font-display: optional` now, the font preloaded as before), and Features' first screenshot loaded eagerly under the intro (lazy now; in view it loads at once).

**Back and Forward** (item 7): they only had steps from jumps (Go to Definition, search results, bookmarks), so after switching documents they did nothing. Leaving a document for another and a caret move of more than ten lines are steps too, as in the classic IDE; the caret's placement in a document a jump just opened isn't (it settles at background priority first). The mouse's back and forward buttons (`XButton1`, `XButton2`) run them anywhere in the main window.

**Blazor component parameters** (item 8): the classifier already gave them `razorComponentAttribute`; every theme gave it the HTML attribute's color. Classic has the classic IDE's Razor Component Attribute colors (Light `#800080`, Dark `#C8C8C8`, High Contrast white), bold (`EditorTheme.IsBold`, applied by the semantic colorizer, kept under the user's colors); the families give it their number color.

**Track Active Item** (item 9): `solutionExplorer.trackActiveItem` (off by default) and a toggle on Solution Explorer's toolbar; on, each active document's file is selected, without the "isn't in the solution" message, the search's filter cleared only when the file isn't among its matches.

**Sync with Active Document** (item 10): a reveal raises `RevealRequested`, and the view scrolls the row into view at once, so a row already selected but scrolled away comes back. A reveal rebuilds the tree only when a parent has to expand or the row is missing, which made the sync slow in a large solution.

**The Output window** (item 11): ANSI bold is the bright color at the regular weight. The colors already met 4.5:1 (7:1 in High Contrast) on the theme's background; the test now covers dark and bold blue.

**The Help menu** (item 12): Get Started is off it (the Welcome plugin's `welcome.showOnboarding` stays, for key bindings and the palette); Set Up Codalus IDE stays.

**What the 0.6 release left open** (item 1), the parts done here:
- Connect to *agent*'s view, which 0.6.0 put in the main window, hidden, is made the first time it opens: one of the things 0.6.0 started building at every start.
- CI: the Shell shards rebalanced from the classes' times (`eng/ci-shell-second-half.txt`).
- The merged branches were already gone.
