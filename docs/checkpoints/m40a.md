# M40a checkpoint: WinForms and WPF projects, run, debug and WPF XAML editing

Date: 2026-10-16. The first part of M40 (the Windows desktop phase; D31, decided 2026-10-16: Windows-only features, the other OSes decided later). Decisions: [ADR 0069](../adr/0069-wpf-xaml-language-service.md) (the WPF XAML language service and Windows targeting; it amends ADR 0047). M40b (the WPF previewer and the Live Visual Tree for WPF) follows.

## Done

**Projects on every OS** (build host):
- **`EnableWindowsTargeting`:** on Linux and macOS the build host sets it as an environment variable at start (`WindowsDesktop.EnableWindowsTargeting`), the lowest-priority property source, so a project's or the user's own value wins. Its evaluations, design-time builds and builds, their worker nodes, and the `dotnet restore` it starts all see it: `net*-windows` projects restore (the Windows Desktop reference packs come from NuGet), load with IntelliSense and build, instead of failing with NETSDK1100.
- **`ProjectInfo.UsesWpf`** and **`UsesWindowsForms`** (`UseWPF`, `UseWindowsForms`).
- **WPF's XAML as additional files:** the design-time build asks for the `Page` and `ApplicationDefinition` items and adds each `.xaml` to the compiler's command line as `/additionalfile:` (`WindowsDesktop.WithWpfXaml`; WPF's targets don't, unlike Avalonia's and MAUI's). The markup compiler's design-time pass already writes `obj/*.g.i.cs` (the `x:Class`'s other part, the named elements' fields), so the code-behind compiles. The design-time cache's schema is now `codalus-designtime-2`.
- **The markup compiler's errors:** `XamlBuildDiagnostics` takes `.xaml` files, so a build's `MC…` errors are squiggles in their files at their lines, as `AVLN` errors are in `.axaml` files.

**Run, debug, tests and Hot Reload** (shell, test plugin):
- **On Windows** nothing is special: WPF and Windows Forms apps are CoreCLR apps, so Start Without Debugging, Start (netcoredbg), Hot Reload (`dotnet watch`) and `net*-windows` test projects take the usual paths. `WindowsDesktopShellTests.Windows_runs_debugs_and_tests_the_desktop_apps` and the smoke step `windows.desktop` prove it on CI's Windows runner (not run here).
- **On Linux and macOS** (`ShellHost.WarnIfWindowsOnly`, `WindowsDesktopProjects`): Start, Start Without Debugging (with or without Hot Reload), multiple startup projects (the others still start) and the Performance Profiler's launch say "*WpfApp is a WPF project: it runs, debugs and tests only on Windows. On this OS it opens, edits and builds.*" before building anything. A project whose every target framework is `-windows` gets the same with its frameworks. Remote windows aren't gated (a Windows remote target is decided later).
- **The test plugin** leaves out test projects whose every framework targets Windows when it isn't on Windows (`WindowsFrameworks.OnlyWindows`): their tests show from source, the project says "*… targets Windows (net11.0-windows): its tests run only on Windows.*", and a run says so in its output and runs the others.

**Templates and items:**
- **New Project** names `wpf`, `wpflib`, `wpfusercontrollib`, `wpfcustomcontrollib`, `winforms`, `winformslib` and `winformscontrollib` (the SDK brings them on every OS), with default names (`WpfApp1`, `WinFormsApp1`…). On Linux and macOS they come last, marked "Windows only: it edits and builds here, and runs on Windows".
- **Add New Item** (built in, so offline and previewed): **Window**, **Page**, **User Control** and **Resource Dictionary** in WPF projects; **Form** and **User Control** in Windows Forms projects. Item templates can now make companion files (`ItemTemplate.Companions`): a window's `.xaml.cs`, a form's `.Designer.cs`. The XAML's `x:Class` is in the folder's namespace.
- **Nesting:** `.xaml.cs` under `.xaml` and `Form.Designer.cs` under `Form.cs` already nested; now a form's `Form.resx` nests under `Form.cs` (or `.vb`), and `Resources.Designer.cs` or `Settings.Designer.cs` under its `.resx` or `.settings`.

**WPF XAML editing** (C# host, the M19a engine with WPF's dialect; ADR 0069). A `.xaml` file is WPF's when its compilation references WPF and neither Avalonia nor MAUI (`XamlContext.IsWpf`):
- **Types and members:** WPF's namespaces through `[XmlnsDefinition]` and `clr-namespace:`; dependency properties with and without CLR wrappers; attached properties (a `DependencyProperty` field with a static `GetXxx`) and attached events (`AddXxxHandler`); `[ContentProperty]`; WPF's markup extensions; named colors, and the values of WPF's static holder classes (`FontWeights`, `Cursors`…).
- **Completion:** elements, attributes, values; WPF's markup extensions and binding arguments; `RelativeSource` modes and `AncestorType`; `d:DesignInstance` types and options, and `d:DataContext` as a snippet; setters', triggers' and conditions' properties and values from the target type or the element their `TargetName` names; `EventSetter`; `TargetName`; `TemplateBinding`; `StartupUri` and `ResourceDictionary.Source` from the project's XAML files; `xmlns` with WPF's namespace and `clr-namespace:`; WPF's `x:` directives.
- **Resources** (`XamlResources`): keys from the file, the dictionaries it merges (relative, rooted and pack URIs within the solution), `App.xaml` and its merged dictionaries, and the files that merge it.
- **Binding paths** from the data context the editor can see: `d:DataContext` with `d:DesignInstance`, a `<X.DataContext>` element, a `DataContext` binding followed from above, a data template's `DataType`, or the source the binding names (`ElementName`, `RelativeSource Self`, `TemplatedParent`, `AncestorType`, `Source={StaticResource}`); a user control's root is its `x:Class`.
- **Diagnostics:** syntax errors, unknown types, members and setter or trigger properties, invalid enum values (errors); a binding path the data context lacks (`XAML0006`), an unresolved `d:DesignInstance` type, and a `StaticResource` key outside a complete resource list (`XAML0007`, new) as **warnings**, since WPF resolves them only at run time.
- **Hover, Go to Definition** (preferring the code-behind to the markup compiler's `obj/*.g.cs`), **`x:Name` rename** (the name, `ElementName=`, the code-behind's uses; not the generated files), **formatting**, folding, the outline.
- Avalonia's `.axaml` and `.xaml` and MAUI's `.xaml` keep their behaviour (their tests pass unchanged).

**Fixture** `samples/WindowsDesktop` ([README](../../samples/WindowsDesktop/README.md)): `WpfApp` (MVVM, `App.xaml` merging colors and styles, a user control with dependency properties and an attached property, a typed data template, `d:DataContext`), `WpfApp.Tests` (xUnit v3 on Microsoft.Testing.Platform), `WinFormsApp` (a form, a user control, strongly typed resources), `WinFormsApp.Tests` (MSTest.Sdk); all `net11.0-windows`. `WpfApp.slnx` has the WPF app alone for the C# host's tests.

## Tests

- **Language host integration** `WpfXamlTests` (8, on `WpfApp.slnx` in the real build and C# hosts, every OS): no false alarms in the fixture's five XAML files; errors and warnings at their places (unknown type and attribute, a binding path in the window, in a data template and through `ElementName`, an unknown resource, a setter's and a trigger's property); elements, attributes (attached properties and events, directives), values; markup extensions, resources through `App.xaml` and merged dictionaries, binding paths from `d:DesignInstance`, data templates, `ElementName` and `RelativeSource AncestorType`, modes, `UpdateSourceTrigger`; setters, triggers, `TargetName`, `TemplateBinding`, `StartupUri`, dictionary sources; hover and definition (WPF's types, the view model, the control, resources, the code-behind not the `.g.cs`, an event handler, the design instance's type); `x:Name` rename; formatting.
- **Build host integration** `WindowsDesktopTests` (3, every OS): `EnableWindowsTargeting` set off Windows unless set; WPF's XAML added to the command line once; the fixture restores and loads (flags, items, references, XAML as additional files, the generated code), builds, and a planted `MC` error lands in `MainWindow.xaml` at its line, as a squiggle.
- **Test plugin** `OlderFrameworksTests.Test_projects_whose_every_framework_targets_windows_run_only_there`.
- **Workbench** `WindowsDesktopTests` (10): Windows frameworks, which projects run only on Windows, the WPF and Windows Forms item templates (offered by project kind, XAML that parses with its `x:Class`, code-behind, designer files), `MC` errors to squiggles. `NestingTests` gain the `.resx` and `.Designer.cs` rules; `TemplateCatalogTests` the WPF and Windows Forms templates and their order off Windows.
- **Headless UI** `WindowsDesktopShellTests` (3): the fixture opens with its flags, nesting, `.xaml` as XAML with binding path completion; off Windows, Start and Start Without Debugging say Windows only and build nothing; Add New Item makes a WPF window and a form with their companions, nested, and the solution builds with them. Off Windows, the test projects say they run only on Windows. On Windows (skipped elsewhere): Start Without Debugging runs the WPF app, Hot Reload runs it under `dotnet watch`, F5 stops at a breakpoint in the view model, and both test projects' four tests pass.
- **Smoke** `windows.desktop` (Windows; skipped elsewhere): the WPF fixture opens, `MainWindow.xaml` completes a binding path, `wpf-xaml.png`, then Start Without Debugging builds and runs the app until it's stopped.

## Gaps

- The WPF XAML previewer and the Live Visual Tree and Live Property Explorer for WPF: M40b. What it needs from M40a: `ProjectInfo.UsesWpf` to pick the host, the WPF dialect's `XamlContext.IsWpf`, and `XamlAnalysis.LogicalTree`, which already counts `FrameworkElement`s as controls (untested for WPF).
- XAML Hot Reload (a candidate, as for Avalonia).
- Running, debugging and testing from Linux and macOS through a Windows machine (the remote target, decided later under D31).
- A field added or renamed through `x:Name` reaches the code-behind's IntelliSense after the file is saved and the next design-time build (the markup compiler reads the XAML on disk). `TODO(issue)`
- Resources from compiled theme dictionaries (another assembly's BAML) aren't offered or checked; nor are the keys of a library without an `App.xaml`. `TODO(issue)`
- Binding paths are checked only where the editor sees the data context (not a data context set in code); `MultiBinding`, `PriorityBinding` and XPath paths aren't checked. `TODO(issue)`
- Test projects that target both a Windows and another framework run all their frameworks off Windows, the Windows one failing as before (only projects whose every framework is `-windows` say "Windows only"). `TODO(issue)`
- WinForms and WPF on .NET Framework: M43. The Windows Forms designer: M41.
