Data tip: the classic IDE's layout, on what netcoredbg can give

Task #82, the design before it is built: the debugger's data tip (the variable inspect pop-up) laid out as the classic IDE's. A header box over the hovered expression with its icon, its name, a View drop-down where a visualizer applies and an editable value; each expansion a tip of its own, below and to the right; rows of expander, member icon, name, a separator, a View drop-down and the value; no type column. Drawn on the user's Startup.cs (an ASP.NET Core server's Configure, stopped at app.UseDeveloperExceptionPage()) and the same solution's WeatherForecastController.cs, with the values netcoredbg and the companion host report; the lists the screenshots don't show are illustrative. netcoredbg 3.2 can't build a [DebuggerTypeProxy] (section P), so section A, what 0.6 ships, shows each object's own members, grouped, and the shell's own element rows for List, Dictionary, HashSet, Queue and Stack. What each engine gives the tip

The layout is the shell's alone; the data isn't. netcoredbg (every .NET and .NET Core program, on every OS, Windows included) sends a variable's name, value, type, evaluateName and reference, nothing about its kind or visibility; it evaluates member access, indexers and instance calls, but not new, typeof or extension methods, and it matches overloads by exact runtime type. Green: there today; red: not possible on that engine as it is; plain: new work.
