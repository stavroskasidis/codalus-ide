# 0078. Code Search and its persistent index

- **Status:** accepted (M47, 2026-10-17)
- **Date:** 2026-10-17
- **Deciders:** maintainer
- **Amends:** [ADR 0005](0005-editor-and-language-services.md) (Go To All becomes Code Search), [ADR 0070](0070-per-solution-state.md) (the state folder gains the index)

## Context

On 2026-10-16 the maintainer compared Go To All (`Ctrl+,`, a flat drop-down under the title row's search: the command palette's `QuickPickViewModel` fed by the C# host's `workspace/symbol` and the solution's file names) with the classic IDE's Code Search and asked for the latter ([roadmap M47](../roadmap.md#m47--code-search)): a floating window with Code Search and Feature Search tabs, filter chips that are also prefixes, two-line results, an editable preview of the selected result, an "Incomplete results" notice, a scope, and buttons to pin, dock and hide the preview. M47 also takes in Go To All's persistent index, deferred since M12 with the instruction to try Roslyn's own persistent storage first, so that "the first search after opening a large solution is fast and complete". What had to be decided:
- what the window is, and how it shares the editor with the documents;
- where results come from, and how they rank;
- what the index holds, who builds it, where it is kept and how it stays current;
- what "incomplete" means;
- what plugins get.

## Decisions

**One window, in the main window.** Code Search is a view model (`CodeSearchViewModel`) shown by one view (`CodeSearchView`) in two places: a floating layer over the documents, centered under the title row (like Find and Replace, M3b: an in-window surface, so it needs no OS window, works the same headless, in remote windows and under Native AOT, and never ends up behind the main window), and the **Code Search** tool window when docked. Only the view that shows hosts the preview. The window's size, offset, pin, preview and docked state are the shell's small state (`state.json`), not settings. `Ctrl+T` and `Ctrl+,` (Go To All) open the Code Search tab; `Ctrl+Q` and the title row's search box open Feature Search, which replaces the search box's mixed list: commands with their key bindings, settings and Options pages. Go To File, Type, Member and Text (`Ctrl+1` then the letter) open it on their chip. The command palette (`Ctrl+Shift+P`) and the quick picks stay as they were.

**Sources, each a batch.** A query yields batches, each the ranked union so far, so the window shows the fast results at once and refines:
1. the index (below) and the solution's files (the projects' items; while projects evaluate, also the index's saved file list), in memory, on a background thread;
2. `workspace/symbol` of every running language service that offers it (the C# host, which adds source-generated declarations; F#; the LSP bridge's servers and plugins' languages), de-duplicated against the index by kind, name, file and line;
3. with **include external items**, `codalus/externalSymbols`: the referenced assemblies' public types, opened through `codalus/metadataText` (embedded source, Source Link, or decompiled) like Go to Definition's;
4. text: Find in Files' engine (its file filter and its line matching, plain text, any case) over the same files, open documents as edited, up to `codeSearch.textResults` lines, for queries of three characters or more (any length after `x:`).

The prefixes are the classic IDE's (`f:`, `t:`, `m:`, `x:`, and `:` for a line of the active document); a typed prefix shows as its chip, and choosing a chip removes the prefix. The scope (entire solution, current project, current document) is a filter of files applied to every source.

**Ranking.** Names match with the command palette's `FuzzyMatcher` (camel-case humps and word starts first, then any characters in order; the matched characters are the highlights), scored without allocating for the whole index and matched again only for the results kept. The score adds a weight per kind (types, then files, then members; external items below the solution's; text last) and boosts for the recently opened files and the active document's project. Results are interleaved by score, as in the classic IDE, or grouped by kind with headers (`codeSearch.grouping`).

**The index is ours, from syntax, kept next to the solution.** Roslyn's persistent storage was investigated first, as M12 planned. Its SQLite storage service and the indexes it caches (`SyntaxTreeIndex`, `SymbolTreeInfo`) are internal services of `Microsoft.CodeAnalysis.Workspaces`, enabled only by the classic IDE's MEF composition: there is no public API to turn them on or read them, and using them would take reflection or `InternalsVisibleTo`. They also live in the language host's process, and the requirement is that a search answer before that host has loaded the solution, so the shell must be able to read the index itself. So:
- **The C# host builds it** (`codalus/symbolIndex`, [protocol](../protocol.md#extensions)): every type and member declared in each document, walked from the syntax tree through `SyntaxGenerator`'s language-neutral view of declarations (C# and Visual Basic alike), with the containing type (or a type's namespace), the project's name and the name's position. Syntax only: no compilation, so it answers as soon as the projects are in the workspace, and one document costs a parse. Source-generated declarations aren't in it (they need the generators to run); `workspace/symbol` brings them while the host runs.
- **The shell keeps it** (`Codalus.Workbench.Search.CodeSearchIndex`): in memory, an immutable snapshot built for typing: its distinct names (names repeat, members above all), each with a mask of its ASCII letters and digits, and each name's declarations in the ranking's tie order (path, then line), with their documents' numbers. A query matches only the names whose mask has every letter of the query's (a name the previous query didn't match, when the user types on), scores each once, and takes them best first: their declarations take their kind's weight and their file's boost (found from the recent files and the active project, not by comparing every document with them) into a heap bounded by the result limit and ordered as the ranking orders results, and a name that can no longer reach the heap ends the walk. The file search scores names as spans of paths into the same kind of heap; results and highlights are built for the kept alone. The loops are compiled fully optimized at once (`AggressiveOptimization`): a search runs them too few times for tiered compilation to replace their first code (the shell is Native AOT, but the tests and any JIT host aren't); on disk, `.codalus/state/<solution>/code-search-index.json` (the per-solution state folder of ADR 0070, written through `SolutionStateStore`, with its fallback folder), source-generated JSON with short property names, and the solution's file list. Each document is stamped with its file's length and time written when indexed; reading the index leaves out the documents whose files changed or are gone, so a saved index never shows declarations that moved.
- **Freshness.** The whole solution is asked for once the C# host has its projects (`IsLoading` over) and again whenever it reports ready (a restart, a reload); an edit to a C# or Visual Basic document asks for that document 800 ms after typing stops; a closed file changed outside the IDE is caught by the next full refresh. The index is saved after a full refresh and, when edits changed it, as the solution closes and the window closes. A file of another format version is ignored and rebuilt.

**Incomplete results.** The window says results may be missing while a solution is opening (the saved index answers meanwhile), or while a trusted solution with C# or Visual Basic projects is loading or hasn't been indexed in this session; when that ends, an open window runs its query again. An untrusted solution has no language host and isn't incomplete: it searches files (and a saved index, if one was written while it was trusted).

**The preview is the document.** Selecting a result holds the file's text model the way a designer does (ADR 0073's `AcquireModelAsync`): the model an editor tab of the file shares, tracked by the language services, so the preview is a full `CodeEditorView` (colors, completion, diagnostics) and its edits are the document's, with its undo and its save (`Ctrl+S` in the preview). The preview scrolls to the result and selects the match without taking the focus from the box. When the preview moves on or the window closes, an unsaved edit opens the document in a tab before the model is let go, as editing a preview tab keeps it. Keys in the preview are the editor's, except Esc and `Ctrl+S`; the main window's key bindings don't act on the active document from there.

**Plugins: no API change.** Plugins already reach Code Search through what they contribute: a language served through the LSP bridge answers `workspace/symbol`, and commands and settings appear in Feature Search. Nothing in the roadmap's scope needed a new contract; a proposed search-provider API (results of a plugin's own kind, such as work items) waits for a plugin that needs it. `TODO(issue)`

## Consequences

- The index of the 96-project benchmark's shape (5,760 files, over 140,000 symbols) answers its worst query (`Inv`, which nearly every name matches) with the file search in about 5 ms on a 4-core container (median of five, Release; about 7 ms with four busy loops on its four cores, at a load average of 14), under the 100 ms budget. The first version, which scored every distinct name in parallel chunks and kept the best in a priority queue, took 30 to 40 ms there, mostly in code tiered compilation hadn't yet optimized, and over 200 ms on CI's runners (`CodeSearchTests.A_query_on_a_96_project_index_answers_within_100_ms`); its file is a few megabytes, written in the background.
- Go To All's quick pick and the search box's list are gone; `workbench.action.gotoAll` and `workbench.action.featureSearch` keep their ids, keys and menus, so key bindings, settings imported from the classic IDE and plugins that run them keep working.
- External items cover types, not members, and open at the type's file start until it is decompiled; members of external types are a `TODO(issue)`.
- The harness has no Code Search scenario yet: the budget is checked by the unit test on a generated index, not in the running app on a generated 96-project solution. `TODO(issue)`
