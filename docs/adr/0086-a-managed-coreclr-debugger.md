# 0086. A managed CoreCLR debugger adapter, and Hot Reload while debugging

- **Status:** accepted (2026-10-28, D48 in the [roadmap](../roadmap.md#decision-register)), after three spikes on Linux (x64, arm64), macOS (arm64, x64) and Windows x64. Phase 1 is planned as [M54](../roadmap.md#m54--a-managed-coreclr-debugger-phase-1) (2026-10-28); nothing is built yet.
- **Date:** 2026-10-28
- **Deciders:** maintainer (D48: accepted as proposed)
- **Amends, as each phase lands:** [ADR 0007](0007-debugging.md) (netcoredbg as the .NET debugger), [ADR 0040](0040-hot-reload-while-debugging.md) (Hot Reload while debugging), [ADR 0076](0076-debugging-the-desktop-clr.md) (ClrDebug only on Windows)

## Context

Every .NET Core and .NET program is debugged by netcoredbg (Samsung, MIT; ADR 0007). Most of what it can't do, and most of what had to be built around it, comes from netcoredbg itself, not from the runtime:

- **Gaps** (ADR 0007, 0021, 0032): no hit counts or logpoints (emulated in the client, a stop per hit), no exception settings per type, no Set Next Statement, no `[DebuggerTypeProxy]` (`new` can't be evaluated), no `new`, casts or lambdas in expressions, every exit code 0 on macOS, and no macOS x64 build since 3.2.0: x64 programs on Apple silicon (.NET 5 and earlier, under Rosetta) get its last one, 3.1.3, frozen (ADR 0030).
- **Workarounds** (ADR 0007): its fixed 5-second wait for a launched runtime and 15-second "Command execution timed out." answers (`DebugAdapter.ConfigurationDoneAsync`, `IsStartupTimeout`, `EvaluateAsync`'s second ask), Break All retried while `threads` fails, `codalus/wake` every 250 ms on macOS (its CreateProcess callback waits on a stdin lock), a zombie read from `/proc`.
- **Upstream fixes wait on its releases:** the Debug Console loses a program's last lines now and then until the pinned version moves to the release with [Samsung/netcoredbg#258](https://github.com/Samsung/netcoredbg/pull/258) (`docs/ci-flakes.md`).
- **Hot Reload while debugging** (ADR 0040): the runtime refuses `MetadataUpdater.ApplyUpdate` while a debugger is attached; the debugger has to apply the change through `ICorDebugModule2::ApplyChanges`. netcoredbg does that only on its MI interpreter, not on the DAP one Codalus uses, so programs under netcoredbg can't take Hot Reload, and a Blazor Web App's server is detached from and attached to again around every restart (`WatchedServerSession`, ADR 0040's 2026-10-22 update).

Since M43b Codalus has its own managed DAP adapter on ICorDebug, for .NET Framework (`codalus-debughost --netfx-dap`, ADR 0076): ClrDebug (MIT) over source-generated COM interop, symbols through System.Reflection.Metadata, our own C# expression evaluator (literals, members, `?.`, indexers, calls through func-eval, operators with C#'s promotion, `?:`, `??`, casts), stepping with Just My Code, exceptions with M14a's settings. Only its start and attach path (`mscoree`'s `ICLRMetaHost`, `CorDebugTarget.cs`) is specific to the desktop CLR. CoreCLR exposes the same ICorDebug through `dbgshim`, which Microsoft ships as `Microsoft.Diagnostics.DbgShim.<rid>` packages (MIT) for Windows, Linux and macOS on x64 and Arm64; ICorDebug itself (`mscordbi`) comes with every runtime.

## The spikes (2026-10-28)

Throwaway programs on ClrDebug 0.4.2 and dbgshim 10.0.750501, kept on the branch `spike/coreclr-dbgshim` (`spikes/coreclr-dbgshim`, standalone, never merged; `bash run.sh [rid]` runs them all and prints a summary, in Git Bash on Windows; on Linux arm64 the branch's workflow `spike-coreclr-arm64.yml` runs it on GitHub's hosted `ubuntu-24.04-arm` runner):

**1. Debugging.** A console debuggee (a loop, a local object with auto-properties and a computed `Label` property) on .NET 9, 10 and 11, with three ways to start a session:
- *launch*: dbgshim's `CreateProcessForLaunch` (suspended), `RegisterForRuntimeStartup`, resume; the startup callback hands over the debuggee's own runtime's `ICorDebug` (wrapped with `Extensions.GetObjectForIUnknown<ICorDebug>`), then `DebugActiveProcess`;
- *attach*: to a program already running, through `EnumerateCLRs`, `CreateVersionStringFromModule` and `CreateDebuggingInterfaceFromVersion`;
- *held launch*: the program started by us with `DOTNET_DefaultDiagnosticPortSuspend=1`, `RegisterForRuntimeStartup`, then the diagnostics IPC's `Process/ResumeRuntime` command.

Each session bound a line breakpoint when the module loaded (the PDB's sequence point by System.Reflection.Metadata, `ICorDebugCode::CreateBreakpoint`), read the locals by the PDB's names and the object's fields, called the `Label` getter through `ICorDebugEval` (`"#42 for Ada"`), stepped over twice with a stepper over the line's IL range, ran to the end and read the exit code. The callback continues every event itself (`e.Continue = false` and `Controller.Continue`, as `CorDebugTarget` does).

|---|---|---|---|---|---|
| .NET 9 | 5/5 in each mode | 5/5 in each mode | not run (no .NET 9 x64 install) | 5/5 in each mode | 5/5 in each mode |
| .NET 10 | 5/5 in each mode | 5/5 in each mode | 5/5 in each mode | 5/5 in each mode | 5/5 in each mode |
| .NET 11 | 5/5 in each mode | 5/5 in each mode (RC3, second round) | not run | 5/5 in each mode (RC3) | 5/5 in each mode (RC3) |

| A breakpoint on `Main`'s first line, held launch | stops | stops | stops | stops | stops |

On Linux: 110 sessions in the first round, including 25 held launches each on .NET 10 and 11 (.NET 11's runtime deadlocks at its start under netcoredbg now and then, ADR 0007; never here), then the scripted rounds. One attach run printed nothing at all, not even the spike's first line, written before anything is debugged; it didn't come back in 90 more, nor in 110 more attach runs on WSL's Ubuntu 24.04 (.NET 9.0.14 and 10.0.13) in the second round. One of those failed differently: the program ran past the breakpoint's line before the breakpoint was bound. The spike's attach let the program go on as soon as `DebugActiveProcess` returned, and off Windows the attach's `LoadModule` events, where the breakpoint is bound, come after that; the spike now lets it go once the breakpoint is bound (50/50 on Linux x64, 75/75 on Linux arm64 and on Windows, and 100/100 on the Mac that way; the old way failed once in 60 Linux x64 runs, and never in 75 on Linux arm64, 90 on Windows or 120 on the Mac). An adapter has nothing to release, but breakpoints set before an attach bind only when those events arrive, as in any attach. The breakpoint is hit about 90 ms after the start; nothing like netcoredbg's 5-second wait, 15-second answers or macOS wake requests was needed.

On Windows (Windows 11, .NET 9.0.22, 10.0.14 and 11 RC3, `dbgshim.dll` from `Microsoft.Diagnostics.DbgShim.win-x64`): the same program unchanged but for the diagnostic port, the named pipe `\\.\pipe\dotnet-diagnostic-<pid>` instead of a socket in `$TMPDIR`, and the launched program's exit code from its process handle (opened before it runs) instead of `waitpid`. The Mac's second round (macOS 27.0.1; arm64 with .NET 9, 10 and 11 RC3, x64 under Rosetta with .NET 10.0.11) matched its first. On Linux arm64 (GitHub's hosted runner, as no arm64 machine was at hand for a Remote Control session: Ubuntu 24.04.5, kernel 7.0, 4 Neoverse-N2 cores, .NET 9.0.22, 10.0.14 and 11 RC3, `libdbgshim.so` from `Microsoft.Diagnostics.DbgShim.linux-arm64`; [run 40733538102](https://github.com/stavroskasidis/codalus-ide/actions/runs/40733538102)) the program ran unchanged, and every spike and check matched Linux x64, with no failure in any of its runs. A hosted runner is a shared virtual machine, so its times say only that nothing waits.

What the spike found:
- **The launch path loses the exit code** off Windows: after `DebugActiveProcess`, mscordbi's own runtime layer reaps its child, and `waitpid` finds nothing (`ECHILD`; dbgshim alone doesn't reap). netcoredbg survives that by interposing `waitpid` (`src/debugger/waitpid.cpp`), which macOS's two-level namespace doesn't allow: hence its exit code 0 there. On Windows any process holding a handle reads it.
- **The held launch keeps it**, as the program is our own child, and catches the first line of `Main`. Its costs: the variable is inherited by the program's own .NET children, which wait to be resumed (spike 3), and the runtime prints a "configured to pause" notice on the program's stdout once it has been held 5 seconds (not at once: spike 3). Attaching *while* it is held times out (`CORDBG_E_TIMEOUT`): the hold comes before the runtime's debugger side starts, so the order is register, resume, attach.

**2. Hot Reload through the debugger.** A program compiled by Roslyn (Debug, portable PDB with its Edit and Continue information), debugged, stopped at a breakpoint before it calls `Message()`. Roslyn's `EmitDifference` against `EmitBaseline.CreateInitialBaseline(compilation, the module, the PDB's EnC maps, the methods' local signatures)` made the delta for a new body with a new local and one more line; `ICorDebugModule2::ApplyChanges` applied it; a breakpoint on a line only the new version has, placed from the PDB delta's sequence points (its EncMap gives the method), stopped with the new local's value; a second edit on the first one's baseline applied too, and every later call ran the latest code.

| How the program runs | `ApplyChanges` |
|---|---|
| debugged from before its module loads, the debugger setting `CORDEBUG_JIT_ENABLE_ENC` there | applied (with or without `DOTNET_MODIFIABLE_ASSEMBLIES`) |
| started with `DOTNET_MODIFIABLE_ASSEMBLIES=debug`, debugged from the start without the flag | applied |
| **started with `DOTNET_MODIFIABLE_ASSEMBLIES=debug`, attached to later** (setting the flag then fails with `CORDBG_E_CANNOT_BE_ON_ATTACH`) | **applied** |
| neither | `CORDBG_E_ENC_MODULE_NOT_ENC_ENABLED`; the old code goes on |

Identical on Linux x64, Linux arm64, macOS arm64, macOS x64 and Windows x64. ADR 0040's "can't be enabled for an attached process" is netcoredbg's rule, not the runtime's. `dotnet watch` (SDK 10.0.401 and 11 RC3) starts the app with `DOTNET_MODIFIABLE_ASSEMBLIES=debug`, confirmed by an app printing it, so the Blazor Web App's server, which the IDE attaches to after `dotnet watch` starts it, could take edits through the debugger.

**3. The launch.** Phase 1's launch must keep the program a child of ours for its exit code (spike 1's launch loses it off Windows), stop on `Main`'s first line, leave no hold for the program's own .NET children, and print nothing into the program's output. Two candidates, as modes of spike 1's session:
- *(a) a launcher process* (`--launcher`): the adapter starts a small launcher (the spike's own executable in a launcher mode) and hands it a pipe's name. The launcher starts the program through `CreateProcessForLaunch`, suspended, sends its id, waits for the adapter to register for its runtime's startup and say "resume", resumes it, waits for it (`waitpid`; its handle on Windows) and sends the exit code. The program inherits the launcher's standard handles and environment, with no variable and no hook.
- *(b) the held launch with a startup hook* (`--hook`): `DOTNET_DefaultDiagnosticPortSuspend=1`, and `DOTNET_STARTUP_HOOKS` naming a hook that, before `Main`, clears the variable and removes itself from the hook list, through `Environment.SetEnvironmentVariable` and, off Windows, libc's `unsetenv` and `setenv`.

The debuggee, after its last line, starts itself again as a child twice: through `Process.Start`, and natively (`posix_spawn` with libc's `environ`; `CreateProcessW` inheriting the process's environment block). Each run of a candidate has to be a full session (spike 1's breakpoint, locals, func-eval and steps) with exit code 7, both children exiting on their own without seeing the variable, and no "configured to pause" line in the output, followed by a second session with a breakpoint on `Main`'s first line. 25 runs of each, per runtime:

| | Linux x64 (.NET 9, 10) | Linux arm64 (.NET 9, 10, 11) | Windows x64 (.NET 9, 10, 11) | macOS arm64 | macOS x64 (Rosetta) |
|---|---|---|---|---|---|
| (a) launcher: every check / first line | 50/50 / 50/50 | 75/75 / 75/75 | 75/75 / 75/75 | 150/150 / 150/150 (.NET 9, 10, 11; two rounds) | 50/50 / 50/50 (.NET 10; two rounds) |
| (b) held launch and hook: every check / first line | 50/50 / 50/50 | 75/75 / 75/75 | 75/75 / 75/75 | 148/150 / 150/150 (the two: the spike's stale-socket bug, below; 75/75 once fixed) | 50/50 / 50/50 |
| Median ms to the first-line stop, (a) / (b) | .NET 9: 225 / 202; 10: 183 / 147 | .NET 9: 157 / 146; 10: 113 / 95; 11: 114 / 89 (hosted runner) | .NET 9: 484 / 306; 10: 255 / 267; 11: 423 / 322 | .NET 9: 634 / 634; 10: 624 / 623; 11: 628 / 624 | 788 / 781 |
| The plain held launch, for comparison | both children held, each printing the notice | the same | the same | the same | the same |

What it found:
- **Both candidates pass every check on every platform run**, but for (b)'s two runs lost to the spike's own socket lookup on the Mac (below). Neither held a child, every exit code was 7, and no run printed the notice.
- **The notice comes only after 5 seconds held.** A held launch resumed after 4 s prints nothing; one resumed after 6 s prints the runtime's three lines (`The runtime has been configured to pause during startup…`, `DOTNET_DiagnosticPorts=""`, `DOTNET_DefaultDiagnosticPortSuspend=1`) on Linux, Windows and macOS. In (b) it is a timing risk, not a constant: it prints whenever the adapter takes more than 5 s from the start to the resume (a slow or loaded machine).
- **(b) has to clear libc's environment too.** With `Environment.SetEnvironmentVariable` alone, the `Process.Start` child runs but the `posix_spawn` child is held on Linux and macOS: off Windows, .NET keeps its own copy of the environment. On Windows that call changes the process's block, and both children run. `unsetenv` in a startup hook runs while the runtime's own threads may read the environment (glibc's `getenv` isn't safe against it), and a program with startup hooks turned off (`System.StartupHookProvider.IsSupported=false`) would leave the variable to every child, which then waits forever.
- **(b) has to find the right diagnostic socket.** Off Windows the port is `$TMPDIR/dotnet-diagnostic-<pid>-<key>-socket`, and macOS never removes the sockets of processes that have ended: the Mac's `$TMPDIR` held about 3,000, all but six from dead processes, so a reused pid can have two. The spike took the first match, and four times on the Mac it was a stale one (three in the second round's 160 or so held launches): the resume was refused, the spike's process ended with the exception, and the program, held before any managed code, stayed held for good, re-parented to `launchd`. The spike now takes the newest socket and tries the next on a refused connection (15/15 on Linux with stale sockets planted for every pid it would get, and every design run on the Mac with its 3,000 left in place), and kills a program it couldn't resume. An adapter would match the key (the process's start time) and need the same care. (a) never uses the port. A program held at startup also ignored `SIGTERM` on the Mac (26 of them over 8 minutes); only `SIGKILL` ended it, so whatever ends a program that hasn't been resumed has to use `SIGKILL` (.NET's `Process.Kill` does).
- **(a) costs a second process start:** 20 to 40 ms more to the first stop on Linux x64, 10 to 25 ms on Linux arm64, nothing to 180 ms on Windows, under 10 ms on the Mac (medians), against (b). Off Windows the program is the launcher's child, so mscordbi in the adapter can't reap it, and the launcher's `waitpid` gets the code.

**Not tried:** exceptions, threads, async methods, Just My Code on CoreCLR, remote targets, the integrated terminal and compound sessions; deltas from the SDK's build and the language host's Hot Reload service (with rude edits), edits to methods on the stack, added members and types.

## Options

| | (a) Stay on netcoredbg | (b) Contribute upstream | (c) Our adapter for CoreCLR too |
|---|---|---|---|
| Hot Reload while debugging | not possible | after a DAP apply-deltas request is accepted and released (`TODO(issue)` in ADR 0040) | ours to build: the runtime side works (spike 2) |
| Gaps and workarounds | stay | each one a PR and a release away | the gaps become ours to close; netcoredbg's workarounds go with it |
| macOS | exit code 0; x64 programs on netcoredbg 3.1.3, frozen | needs a fix they can't make by interposing, and an x64 build again | the launcher's exit code (spike 3); x64 programs through dbgshim's osx-x64 package, with the adapter run as x64 (the spike's Rosetta run) |
| Expressions | no `new`, casts or lambdas | as today | ADR 0076's evaluator (casts, operators, `?.`, `??`); `new` and lambdas are gaps in both |
| Code to keep | netcoredbg's DAP quirks (`DebugAdapter`) | the same, plus PRs | one adapter for both CLRs, about 6,000 lines today; ICorDebug's semantics are ours |
| Shipping | a downloaded, pinned native binary per platform (`eng/get-netcoredbg.sh`, `RemoteDebuggers`) | the same | ClrDebug back into the Linux and macOS packages (8 MB, left out since 0.3.0) and dbgshim from NuGet per platform |
| Risk | none new | slow; not ours to schedule | parity with what netcoredbg does today, on three OSes, remote targets included |

## Decision

**(c), in phases, with netcoredbg the default until the new adapter matches it.**

1. **The adapter.** `codalus-debughost --clr-dap`: ADR 0076's session (`NetFxDebugSession`, the evaluator, `ClrModuleInfo`) over a second target beside `CorDebugTarget`, started through dbgshim. ClrDebug ships again on every OS; dbgshim comes from `Microsoft.Diagnostics.DbgShim.<rid>` in the debug companion's output for its runtime identifier.
   - **Launch: a launcher process** (spike 3's (a)). The adapter starts `codalus-debughost --launch <pipe> <program> [args]` with the launch's environment, working directory and standard handles (the Debug Console's pipes or a console of its own). The launcher starts the program through dbgshim's `CreateProcessForLaunch`, suspended, sends its id over the pipe, resumes it once the adapter has registered for its runtime's startup, and sends its exit code (`waitpid`; the process handle on Windows). It ends the program if the pipe closes first (the spike does that only before the resume). The program stays the launcher's child, so its exit code survives mscordbi, and nothing reaches its environment or output. Against (b), which passed the same checks: no diagnostic port to find and no program left held forever when the resume fails or the adapter dies before it (spike 3, on the Mac), no 5-second window for the notice, no dependence on startup hooks being turned on, no `unsetenv` racing the runtime's threads, and the program's environment and `DOTNET_STARTUP_HOOKS` as the user set them. One path on every OS, though on Windows the adapter could read the exit code itself. The integrated terminal could run the same launcher, and so stop on `Main`'s first line there too, instead of ADR 0039's attach after a startup hook.
   - **Opt-in:** a setting `debug.adapter` (`netcoredbg` by default, `codalus`). x64 programs on Apple silicon keep netcoredbg 3.1.3 until the companion can run as x64 there. Session routing stays where ADR 0076 put it (`DebugService` picks the adapter from the program).
   - **Parity tests:** the existing debugger suites (`DebugService`, data tips, compound sessions, the terminal, test debugging, Blazor) run against both adapters on every CI OS. Remote targets keep netcoredbg in this phase.
2. **Apply Code Changes while debugging.** A DAP request of ours (`codalus/applyChanges`); deltas and rude edits from the language host's Hot Reload service (Roslyn Features, already referenced); every module of a launched program gets `CORDEBUG_JIT_ENABLE_ENC` as it loads; programs the IDE starts to attach to later (the terminal, a console window, `dotnet watch`'s server) get `DOTNET_MODIFIABLE_ASSEMBLIES=debug`. Breakpoints in updated methods move with the PDB delta. For a Blazor Web App's server, edits the runtime can apply are applied in place instead of waiting for Restart: open question for this phase, since `dotnet watch` still sends the server its own update, which the runtime refuses.
3. **The default, then netcoredbg's removal.** When the parity suites pass on Windows, Linux and macOS, the new adapter's CI failure rate over some weeks of nightlies is no worse than netcoredbg's, remote targets run it (`codalus-server` carries the adapter and dbgshim for its platform), and the user guide's gaps list is rewritten: the default changes, and a later release removes netcoredbg, `eng/get-netcoredbg.sh`, its copy in `RemoteDebuggers` and its workarounds in `DebugAdapter`.

## Consequences

- Once built: Hot Reload while debugging becomes possible for launched programs, the terminal, and the Blazor Web App's server; macOS exit codes become correct; x64 programs on Apple silicon can leave netcoredbg 3.1.3 for a maintained dbgshim; the gaps netcoredbg can't close (per-type exception settings, Set Next Statement through `ICorDebugILFrame::SetIP`, type proxies through func-eval of `new`, hit counts and logpoints without a stop per hit) become work we can schedule.
- Every fix to the debugger becomes ours, on three OSes. ICorDebug's behavior off Windows is known only from these spikes until phase 1's suites run on CI.
- The Linux and macOS packages grow by ClrDebug (about 8 MB) and dbgshim (0.3 to 0.4 MB per platform) during phases 1 and 2, while netcoredbg still ships; the size gate counts both.
- The Linux arm64 run that was a `TODO(issue)` here ran on 2026-10-28, on GitHub's hosted runner (no arm64 machine for a Remote Control session), and passed every check. Phase 1's suites can run on that runner too; today only the smoke test and the packages do.
- `TODO(issue)`: the one silent attach failure on Linux, if it comes back under the phase 1 suites (not seen again in 200 more Linux x64 attach runs, nor in 165 on Linux arm64).
- The launch spike that was a `TODO(issue)` here ran on 2026-10-28 (spike 3); the launcher process is the decision above.
- Worth revisiting if netcoredbg gains a DAP request for Hot Reload before phase 1 is built, which would leave (a) or (b) the cheaper way to most of this.
