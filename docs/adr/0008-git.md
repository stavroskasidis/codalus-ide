# 0008. Git

- **Status:** accepted (M6, continuing autonomously toward the MVP)
- **Date:** 2026-10-09
- **Deciders:** maintainer (goal: "keep going until MVP is reached")

## Context

The project brief's M6 asks for:
- a Changes view with staging per file and per hunk
- commit (and amend)
- branches: create, switch, merge
- fetch, pull and push
- a side-by-side and inline diff viewer
- gutter change markers
- blame

It also asks for an ADR choosing between LibGit2Sharp and the git CLI.

**LibGit2Sharp** (MIT) wraps **libgit2**, which is GPL-2.0 with a linking exception. That license is OSI-approved and allows linking, but it adds a copyleft component to the distribution. LibGit2Sharp also has these drawbacks:
- It has no SSH transport in its shipped native binaries.
- It doesn't use the user's credential helpers (such as Git Credential Manager).
- It doesn't run hooks.
- It lags behind git on newer repository formats (SHA-256, reftable, partial clone, sparse checkout, some worktree setups).
- Native binaries are needed per OS, and P/Invoke under Native AOT needs care.
- It runs in-process, so a crash in libgit2 takes the shell down.

**The git CLI** is what developers already have and configure. It brings:
- the user's configuration, credential helpers, SSH, hooks and signing
- every repository format, through stable machine-readable outputs: `status --porcelain=v2 -z`, `diff` and `apply`, `blame --porcelain`, `for-each-ref --format`

It runs out of process by nature. Its costs:
- a process start per operation (about 10–30 ms on Windows)
- a dependency on an installed git

## Decision

**Use the git CLI.** `git` (2.30 or newer) must be on the `PATH`; `DAEDALUS_GIT` overrides it. Without git, source control is hidden and a notification says why.

**`GitService`** (workbench, `src/DaedalusStudio.Workbench/Git`) runs one `git` process per operation, asynchronously and cancellably, with these settings:
- `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0` for read operations
- `-c core.quotepath=false`
- `-c color.ui=false`

It parses only porcelain or plumbing output, never messages meant for humans. Failures carry git's stderr, which is shown to the user.

- **Repository**: the one containing the open solution (`rev-parse --show-toplevel`). Its status is refreshed after every operation and on file changes: the work tree, `.git/index` and `.git/HEAD`, debounced.
- **Changes view** (tool window): branch with ahead/behind, commit message, Amend, Commit Staged / Commit All, staged and unstaged files, merge conflicts. Per file: stage, unstage, discard; open the diff.
- **Diff** (`git diff`, parsed into hunks):
  - a diff document, inline or side by side, in read-only editors with added and removed lines colored
  - the side-by-side view has aligned rows and synchronized scrolling
  - per-hunk Stage, Unstage and Discard build a one-hunk patch and run `git apply --cached` (or `-R`)
- **Gutter markers**: the editor's text against the index version (`git show :path`), diffed in-process (Myers), so markers follow unsaved edits: added, modified and deleted lines in the margin.
- **Blame**: `git blame --porcelain` on demand. Each line group is annotated with its commit, author and date in a margin; it toggles off.
- **Branches** (status bar, quick picks): switch (`git switch`), create from the current branch (`switch -c`), merge into the current branch (`merge --no-edit`; conflicts appear in the Changes view, with Abort Merge).
- **Remotes**:
  - fetch (`fetch --prune`)
  - pull (`pull`, following the user's pull configuration)
  - push (`push`, or `push -u origin <branch>` the first time)
  - Credentials come from the user's credential helper. With terminal prompts disabled, a missing helper fails with git's message instead of hanging.

**Plugin API**: Git is built in. A source-control contribution point for plugins (other version control systems) is post-MVP: `TODO(issue)`. The project brief asked for built-ins on the plugin API "where practical"; diff documents, gutter markers and blame margins need editor extension points that the plugin API doesn't have yet.

## Consequences

- No new package dependencies. git itself is a prerequisite, like the .NET SDK.
- Status of a large repository costs one `git status` per refresh. It is debounced, and only the Changes view and gutter markers depend on it.
- Interactive features (rebase, stash UI, cherry-pick, history graph) are post-MVP and can use the same service.

## Amendment (2026-10-22): the diff document redesigned after the classic IDE's

The user's report (#86): "Git compare is missing the code coloring, also the whole page needs redesign". The design, `docs/design/controls/DiffDocument.dc.html`, was approved as drawn with every question as recommended ([D45](../roadmap.md#decision-register), [controls.md](../design/controls.md#the-git-diff-document-06)). Diffing in-process and applying patches with `git apply` stay as decided above; what changes:

- **Colors.** Each side is colored like the editor: by its language's TextMate grammar, tokenized from the file's real text off the UI thread (C# and Visual Basic into the editor's token types, other languages in their TextMate theme's colors), and, on the side whose text is the open document's, by the language service's semantic tokens. A pane line is colored from the file line it shows, never from the composed text with its filler rows. The merge editor's panes use the same tokenizer.
- **A change is a run of changed rows, and its patch is built from those rows** over the old side's bytes (the index, or HEAD) and the new side's (the saved file, or the index): staging forward to the index, unstaging and discarding in reverse. Two changes in one git hunk stage separately, and what is staged is what is drawn. Per-line staging works the same way on the selected rows. This replaces the per-hunk patches above.
- **The working-tree side is the open buffer.** Every Stage, Discard, Stage All and Discard All… saves it first, reads the diff again, and applies nothing when the saved text isn't the text drawn (format on save). Discarding asks first, every time.
- **Layout and commands**: one status bar per side, Side by Side or Inline in `git.diff.layout`, the staging column behind `git.diff.showStagingControls` (off), Summary, and the registered `git.diff.*` commands (`F8`, `Shift+F8` while the diff has the focus; the staging commands have no default keys). Files over 10 MB or 100,000 lines wait for Compare Anyway; binary files show their sizes.
- **Colors of the diff itself**: opaque tokens in every theme (`Shell.Diff.Added.Line`, `.Removed.Line`, `.Added.Word`, `.Removed.Word`, `.Added.WordBorder`, `.Removed.WordBorder`, `Shell.Diff.Filler`), with the editor's text at 4.5:1 and the syntax colors at 3:1 on the fills; changed words, from a character diff widened to whole words, get a 1 px border (High Contrast: the borders alone).
- Deferred, each with a `TODO(issue)`: CodeLens and diagnostics on the working-tree side, editing inside the diff, Ignore Trim Whitespace, image previews of binary files, and the classic IDE's project drop-down.
