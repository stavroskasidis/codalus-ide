# 0089. Manage Branches: the Git Repository document

- **Status:** accepted (2026-10-29)
- **Date:** 2026-10-29
- **Deciders:** maintainer (the decisions of 2026-10-29: a document as the classic IDE's Git Repository window; branches, remotes, tags, pull requests and submodules in its tree; a root per repository; the links in the Git menu, Git Changes' ⋯ and the branch drop-down; the classic IDE's behavior on a double-click and in the menus)
- **Builds on:** [ADR 0008](0008-git.md), [ADR 0020](0020-git-depth.md) (the history), [ADR 0031](0031-git-hosting-and-repository-features.md) (hosting), [ADR 0085](0085-all-repositories.md) (All Repositories)

## Context

Codalus has a branch drop-down in Git Changes (D38) and a History document with a graph (M13), but nowhere to see every branch at once with its history beside it. The classic IDE's Git Repository window (Git → Manage Branches, `Ctrl+0 Ctrl+R`) does that: a tree of the branches in folders, the remotes, the tags, the pull requests and the submodules on the left, and the selected branch's history on the right, with its incoming commits above it and its outgoing count, Fetch, Pull, Push and Sync.

Constraints: git is the user's CLI, one process per operation (ADR 0008); nothing reaches a Git host until the user signs in to it (ADR 0031); with several repositories every command runs in the repository it comes from (ADR 0085, `ShellHost.Repo`).

## Options

| Question | Options | Verdict |
|---|---|---|
| Shape | A document as the classic IDE's window; the same as a tool window; a tree-only tool window that opens the History document | **A document.** The history needs the width. The right side is the History document's view (`GitHistoryView`) with its branch box hidden, so the graph, details and commit menu are the same. |
| The tree | Branches, remotes and tags; also pull requests; also pull requests and submodules | **All of them**, as the classic IDE's. Pull requests come from the host the repository's remotes are on, only once the user is signed in to it; until then the node offers Sign In. |
| Several repositories | A root per repository; the repository Git Changes shows | **A root per repository**, each with its Branches / Tags, Pull Requests and Submodules; with one repository the tree is the classic IDE's (Branches / Tags with the repository under it). Fetch, Pull, Push and Sync from the document run in that repository alone. |
| The links | Git menu only; Git Changes' ⋯; the branch drop-down; both | **Both**, and Git → Manage Branches, Git → Branches → Manage Branches, `Ctrl+0 Ctrl+R`. |
| Behavior | The classic IDE's; no incoming section; a double-click that only shows the history | **The classic IDE's.** A double-click (Enter) checks a branch out; a branch's menu is the drop-down's (`gitChanges/branch`, so plugins' entries show too, with the same when-clauses); a tag, a pull request, a submodule and the repository have menus of the document's own. |

### The history, consolidated (2026-10-29, the maintainer's review of the first build)

| Question | Options | Verdict |
|---|---|---|
| What moves into the document | The repository's and a branch's history; everything, file and line history as a path filter | **The repository's and a branch's.** View History, View all commits, a branch's or tag's View History and Compare's View History open the document with that ref selected (the current branch by default). A file's, a folder's and lines' history keep a tab of their own (the classic IDE's File History), with the same columns, filter and commit details. |
| A commit's details | In the document, replacing the history (Back); a tab of its own | **A tab of its own**, "Commit 98aa44a1", as the classic IDE's: the selected file's diff (`DiffView`) on the left, the details pane on the right (ID, Revert, Reset, ⋯, the message, author and committer, Changes as a folder tree). Opened by a double-click, Enter, View Commit Details, and Show Commit for Line. |
| A single click | Just selects; a side pane | **Just selects.** The pane under the history is gone; the history uses the whole height. |
| Searching | One Filter History box; the fields plus an ID box | **One box**: the message or the author contains the text (`git log --grep`, `--author`, fixed strings, any case), or it's a commit id or a prefix of one (`rev-parse`), found even off the branch. A filtered list draws each match as a dot of its own. |
| All branches | The current branch with a toggle; the current branch only; an All branches node | **A toggle**, Show All Branches, in the history's toolbar with Refresh and the remote branches' and tags' toggles for the Branch / Tag column; all three are user settings. |
| Explain | When AI is on; not yet | **When AI is on** (off by default): AI Chat gets the commit's message and its diff through `AiActions.FilterDiffAsync` (the exclusions), as a Changes context item. |

Incoming and Local History are header rows of the history's list (`GitHistorySection`), each with a chevron and its links, its commits drawn with the graph like the rest, as the classic IDE's.

## Decision

`GitRepositoryViewModel` reads each repository's branches (`BranchDetailsAsync`), tags, remotes and submodules (only when `.gitmodules` exists), builds the tree, and keeps the expanded nodes and the selection by key across reloads. The shell reloads the refs when a repository's status changes (the watcher sees `HEAD` and `refs/`), debounced, and the pull requests on open and Refresh. A local branch with an upstream lists its incoming commits (`branch..upstream`, at most 100) under the Incoming header of its history; a pull request whose source branch is fetched shows `target..source`; a submodule's history is read through a `GitService` of its own, not watched, while it's selected.

The branch menu's context (`GitBranchScope`) and titles (`GitBranchTitle`) now take the repository, its local branch of a remote branch's name, and whether it has a remote, so the document builds them from its own data; the drop-down passes its own. Checkout on a remote branch finds the local branch of its name in the branches it reads, not the drop-down's last list (which was empty when the drop-down had never opened).

## Consequences

- No plugin API change: the document reuses `gitChanges/branch`; tags, pull requests and submodules have no menu location yet. `TODO(issue)`: a `gitRepository/*` menu location per node kind, if plugins need one.
- The website's Features page shows the document and a commit's tab (`git-repository.png`, `git-commit.png`), from the `git.repository` smoke step of CI run 40931330284.
- Pull Requests has the Pull Requests window's filters as folders (the maintainer's choice of 2026-10-29): **Mine**, **Review requested** and **All open**, each with its count, the first two expanded. The three are asked of the host at once; one the host can't answer leaves only its folder empty ("The host didn't say").

## Amendment (2026-10-31): the trees as rows, and nothing read while hidden

M56 made Git Changes' sections virtualized lists of a flattened tree's rows and deferred the Git Repository, Commit Details and Compare trees ([m56](../checkpoints/m56.md#deferred)). Their tree views made an item per branch, tag or file on the UI thread: the Git Repository tree was rebuilt whole at every filter keystroke and at every status read, even with its tab in the background (four or five git processes each time), and a commit or a comparison of 10,000 files took seconds. The maintainer's decisions of 2026-10-31, as built in M57:

- **Rows, one code path.** The Git Repository tree is a list of `GitRepositoryRow`s (16 px a level, `Shell.Size.TreeRow` high, folders first), built off the UI thread and shown in place (`ResettableCollection.Patch`): a row whose node is still in its place stays, so its control, the selection and the scroll stay, and only what changed is raised. A commit's changes and Compare reuse Git Changes' `GitChangeNode` and `GitChangeRow` through `GitChangesViewModel.BuildTree` (the same compaction, `src\Data`), with a read-only row template (no hover buttons); `GitCommitTreeNode` is gone. The chevron and the keys (`Left`, `Right`, `Ctrl` with each, `+`, `-`, `*`, `/`, `Enter`, `Ctrl+Enter`, a double-click) are one attached helper, `TreeRows`, which Git Changes uses too; each view keeps its own keys (F2, Delete, the menu keys) and menus. The chevron's press is handled before the row hears it, so a click on it toggles the folder and selects nothing, as a tree view's expander (selecting the folder dropped the Git Repository's history beside the tree). A double-click off the rows does nothing (in the Git Repository it checked out the selected branch); Git Changes' and Compare's trees open the selected file there, as their lists do. A build still running when the document closes shows nothing and starts no history. The list is a `TreeRowsList` (below).
- **A tree to a screen reader** (the maintainer's "proper peer for all trees", 2026-10-31). The eight trees shown as rows (the Solution Explorer, Git Changes' sections, the Document Outline, the Git Repository tree, a commit's changes, Compare, the Test Explorer, Coverage Results) are one control, `TreeRowsList`: a `ListBox` to styles and the theme, whose automation peer is a `Tree`'s and whose rows' (`TreeRowItem`) are `TreeItem`s with the ExpandCollapse pattern on a folder (Expand and Collapse are the view's own `SetExpanded`, as `Left` and `Right`; a file has no pattern, which AT-SPI would read as expandable), their level and their place among their siblings, worked out in one pass over the flattened rows when they change and only once a screen reader has asked for a row. A row's name is its name alone: the ", expanded" and ", collapsed" M56 put in it are gone. Avalonia 12.1 reports the role and the expansion on UI Automation and AT-SPI; of the level and the place it passes only AT-SPI's `posinset` and `setsize`, which it reads from the row's control (`AutomationProperties.PositionInSet`, `SizeOfSet`), so the list sets them on a row's control as it's prepared or moves (a recycled container would otherwise keep its last row's place until a deferred pass, and Avalonia's AT-SPI answers at Default priority, before it), and after a change to the rows at `Loaded` priority for the siblings that neither move nor are prepared again. Its UI Automation and macOS peers have no level, position or size, and its AT-SPI `level` is a heading's. On macOS its native peer passes `AXExpanded` but not `AXDisclosing` or `AXDisclosureLevel`, which VoiceOver reads on an outline's row, so there a folder's tree item keeps ", expanded" or ", collapsed" in its name (`NamesCarryState`). A container recycled by a scroll raises no expansion change; only the same row's does, and only while the row's control is on screen (the rows outlive their views: Dock builds a view again and the panel pools a container out of the tree, and a tree item that kept following its row held the old view). A view's model keeps a toggled folder's row (Coverage Results patches its rows in place, as the others do), so its tree item announces the change. After a change to the rows, the places are written by the pass it queues, once for a batch of changes, not on each moved row (the Test Explorer changes rows one at a time). Lists with headers that open in place (Find Results, Find All References, the Error List, Git History) aren't trees and keep the state in their headers' names. `TODO(issue)`: the level and the place on UI Automation and NSAccessibility when Avalonia's peer has them, the state out of macOS names once VoiceOver reads it, and manual checks with Narrator, VoiceOver and Orca.
- **Nothing read while hidden.** The Git Repository document tells whether a view shows it (`ShownTracker`, as M56's tool windows): behind another tab, git's changes only mark it stale, and showing it reads the refs once. Refs the same as the last read's build nothing. `SelectAsync` (the menus' View History, the smoke test) reads first when stale, and brings the selected row into view (the list doesn't scroll to its selection by itself, M56). The current branch is selected only until something is: a selected branch that's deleted leaves nothing selected, and later builds (a filter, another ref's change) don't select the current branch again.
- **The filter** still expands every match, applied 150 ms after the last keystroke and built off the UI thread. Folders are found by key as branches are placed (a look through the parent's children for each was folders × branches).
- **A commit's changes** are built off the UI thread with every folder expanded, and stay with the tab: switching away and back keeps the expansion and the selection, and brings the selected row into view.
- **Compare** builds only the view shown (the list filled with one reset), and **Refresh** keeps the folders the user collapsed and the selection, by key. Tree and List can be switched while a tree is built: once it's built, the view shown then is built too, and one tree is built at a time (again when a folder was collapsed or expanded meanwhile).
- The history is as it was, except its **Branch / Tag** column, which makes at most 8 chips (it's 130 px wide; every name is in its tooltip): the one commit of a repository with thousands of refs made a chip for each at every selection, 4.9 s of UI thread for 7,000 refs (320 took 0.5 to 1 s). `TODO(issue)`: one streamed `git log` instead of a page at a time with `--skip`.
