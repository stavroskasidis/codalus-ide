# 0048. Avalonia previewer hosting

- **Status:** accepted (M19a, 2026-10-12; the maintainer's standing go-ahead for the milestones)
- **Date:** 2026-10-12
- **Deciders:** maintainer
- **Extended by:** [ADR 0072](0072-wpf-previewer-hosting.md) (WPF, M40b)

## Context

M19's live previewer renders the edited `.axaml` file next to the editor, follows edits, supports design-time data (`d:DataContext`, `d:DesignWidth`, `d:DesignHeight`), zoom, theme variants and scale, and selects in the XAML what is clicked in the preview and the reverse. The roadmap fixes the architecture: the user's app runs out of process under Avalonia's designer host with Avalonia's remote protocol, XAML in and frames out over a local transport. Out of process is required: it runs the user's code, possibly on another Avalonia version than the shell's.

Avalonia ships the designer host in its package (`tools/net8.0/designer/Avalonia.Designer.HostApp.dll`, the project's `AvaloniaPreviewerNetCoreToolPath`). Started with `dotnet exec` and the app's `runtimeconfig.json` and `deps.json`, it loads the app, calls its `BuildAvaloniaApp`, connects to `--transport tcp-bson://127.0.0.1:<port>/`, says `StartDesignerSessionMessage` with the `--session-id` it was given, and then loads each `UpdateXamlMessage` (the XAML, the assembly it belongs to, its path in the project) into a window rendered off screen, answering `UpdateXamlResultMessage` (an error with the exception's line and column, or none) and `FrameMessage`s, each acknowledged with `FrameReceivedMessage`. Design-time properties are its own (`Design.*`, the `d:` attributes). The protocol says nothing about elements.

## Decisions

**The protocol client is in the workbench** (`src/DaedalusStudio.Workbench/Previewer`), in process: `RemoteProtocol` (the messages the previewer uses), `PreviewerSession` (one designer host) and `PreviewService` (targets, builds, the running session). Avalonia's own transport (`Avalonia.Remote.Protocol`, MIT) serializes with reflection (a BSON library, Metsys.Bson), which the Native AOT shell can't use, so the codec is ours: a little-endian int32 length, the message type's GUID (from its `[AvaloniaRemoteMessageGuid]`), and the BSON subset the messages use. `PreviewProtocolTests` check it against Avalonia's transport in both directions. Frames go straight from the socket into a bitmap; no second host relays them (a JSON-RPC relay would copy every frame twice).

**A session** listens on two loopback ports chosen by the OS and starts `dotnet exec --runtimeconfig … --depsfile … Avalonia.Designer.HostApp.dll --transport tcp-bson://127.0.0.1:<port>/ --session-id <guid> --method avalonia-remote <app.dll>`. The first message must name its session id, or the connection is dropped; the second port is the agent's (below), which must say its random token. It asks for `Rgba8888` frames at `96 × scale` DPI. Every wait has a timeout with a message (60 s to connect and to answer an update); a crash ends the session and the tool window says so. Updates run one at a time, and only frames after the update's answer count as its frame.

**What runs.** A file's **target** is its project (whose output is the assembly the XAML compiles into) and the **host app**: that project when it is an executable, else an app that references it, the startup project first, so a library's XAML previews through the app with the library's assembly in the update. The designer host comes from the host app's packages (its version is the app's). It runs the user's code, so it starts only for **trusted** folders (ADR 0004's rule). It needs a build: `PreviewService` builds the host app (through the Build output and the Error List) when its outputs are missing or older than any item of the two projects, the previewed file aside (its text is sent live). A save of C# or XAML in those projects stops the session and rebuilds; the session holds the app's assemblies, which Windows locks, so it always stops before a build.

**The agent.** For selection and the theme variant the previewer needs the element tree, which the protocol doesn't carry. `DaedalusStudio.Previewer.Agent` (netstandard2.0, shipped in `debughost/` beside the debugging startup hook, `DAEDALUS_PREVIEWER_AGENT` to override) is a startup hook (`DOTNET_STARTUP_HOOKS`) loaded into the designer host. It connects back to the session's agent port and answers tab-separated lines: `hit x y` (the element under a point and its logical path from the previewed window: type, index among its same-type logical siblings, name), `bounds path` and `theme Default|Light|Dark`. It reaches Avalonia only by reflection (`Dispatcher.UIThread`, the designer's current window, the logical and visual trees, `Application.RequestedThemeVariant`), so one agent serves every Avalonia version. Without it the preview still renders, without selection and themes (the XAML Previewer output says why). M19b's Live Visual Tree takes the same technique into running apps.

**Selection** maps paths, not coordinates: the C# host's `daedalus/xaml/logicalTree` (ADR 0047) gives the XAML's controls nested as their logical parents, with the root named by its `x:Class`; a step is a type and its index among siblings of that type, on which the XAML and the running tree agree (`PreviewSelection`). A click hit-tests in the agent and selects the deepest element the XAML declares on the path (a button's generated text selects the button) as its start tag; the caret's element is outlined in the preview through `bounds`.

**The tool window** (XAML Previewer, docked right; Shift+F7 in an `.axaml` editor, View → Other Windows, the editor's context menu) follows the active `.axaml` editor while open, sends the editor's text 150 ms after the last edit, and has Refresh (rebuild and render), zoom (25–400%, the frame scaled in the window), the render scale (100–200%, the designer renders at that DPI) and the theme variant. The loader's error and its line show above the last good frame. Pointer moves go to the preview (hover styles); clicks select.

**Accessibility.** The preview is a picture: what it shows is the XAML, which the editor reads. The window states in a polite live region what the preview is doing (building, starting, rendering, ready: "click an element to select it in the XAML") and in an assertive one the loader's error; its controls (Refresh, zoom, scale, theme) are labelled buttons and combo boxes. Selecting from the keyboard is the caret in the XAML, which the outline follows; the outline's element is the one the editor's caret is in. A screen-reader description of the preview's elements comes with M19b's Live Visual Tree, which exposes the element tree as a tree view.

## Consequences

- The first frame needs a build (the budget is build to first frame ≤ 3 s, measured without the build); later edits render in tens of milliseconds (budget p95 ≤ 300 ms).
- Previews of a library's XAML need an app that references it; a solution without one says so.
- The agent relies on the designer host's current window field (`RemoteDesignerEntryPoint.s_currentWindow`); a future Avalonia that renames it loses selection and themes, not the preview (`TODO(issue)`: ask Avalonia for an element query in the remote protocol).
- Code-behind edits show after a save and a rebuild, not as typed.
