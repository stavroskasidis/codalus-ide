# 0072. WPF previewer hosting

- **Status:** accepted (M40b, 2026-10-16; the maintainer's standing go-ahead for the milestones, D31)
- **Date:** 2026-10-16
- **Deciders:** maintainer
- **Builds on:** [ADR 0048](0048-avalonia-previewer-hosting.md) (the Avalonia previewer), [ADR 0052](0052-live-visual-tree.md) (the live tools), [ADR 0071](0071-wpf-xaml-language-service.md) (WPF XAML)

## Context

M40a made WPF projects open, build, run and debug, and gave WPF XAML the M19a language service. M40b adds what M19 gave Avalonia: a previewer of the XAML being edited (design-time data, zoom, scale, selection both ways) and the Live Visual Tree and Live Property Explorer for a running app. D31 makes both Windows only for now: WPF draws only on Windows, and the other OSes are decided later.

Four facts shape it:
- **WPF has no designer host to borrow.** the classic IDE's XAML designer is proprietary ([known traps](../roadmap.md#known-proprietary-traps)). WPF itself has what a designer needs: `XamlReader` loads XAML at run time, and `RenderTargetBitmap` draws a visual off screen.
- **WPF's loader refuses what only the markup compiler wires up:** `x:Class` (the loaded root isn't the class), event handlers (`Click="OnClick"`), `EventSetter`s and `x:Code`. A `clr-namespace:` without `assembly=` means "the assembly being compiled", which loose XAML has no notion of.
- **A `Window` or `Page` can't be a child of another element,** and an unshown window draws nothing.
- **The IDE side already exists:** `PreviewerSession` speaks Avalonia's remote protocol (XAML in, frames out) with our own AOT-safe codec, the previewer agent's line protocol answers hit tests and bounds, and selection maps XAML paths (`PreviewSelection`). The live tools' `LiveSession` and tool windows are protocol-driven too.

## Decisions

**One WPF assembly, two roles.** `src/Codalus.Previewer.Wpf` (`codalus-wpfpreviewer.dll`, `net8.0-windows`, `UseWPF`, framework references only) is both the designer host (`Main`) and the live agent (a `StartupHook` class). It targets .NET 8, the oldest supported .NET, because it loads into the user's .NET and WPF: the IDE uses it for apps on .NET 8 or later and says so for older ones and for .NET Framework (M43). It builds on every OS with `EnableWindowsTargeting`, so `dotnet build Codalus.slnx` compiles it on Linux and macOS, and it ships only in the Windows package: the shell copies it to `wpfpreviewer/` on a Windows build and on a `win-*` publish.

**The designer host speaks Avalonia's remote protocol.** It links the workbench's `RemoteProtocol.cs`, so the IDE drives it with the same `PreviewerSession` as Avalonia's designer host: started the same way, `dotnet exec --runtimeconfig App.runtimeconfig.json --depsfile App.deps.json codalus-wpfpreviewer.dll --transport tcp-bson://127.0.0.1:<port>/ --session-id <id> … App.dll`, on the app's own .NET and WPF; `StartDesignerSessionMessage`, then `UpdateXamlMessage` → `UpdateXamlResultMessage` (the loader's error with its line and column) and a `FrameMessage` (BGRA, or swapped to the RGBA the IDE asks for), at `96 × scale` DPI from `ClientRenderInfoMessage`. It serves the agent's commands itself on the agent port (`PreviewerLaunch.AgentInHost`: the port and token, no startup hook). Every wait, timeout, crash report and the one-update-at-a-time rule are the session's, unchanged.

**Loading the edited text** (on an STA thread running the dispatcher):
- **The app first.** The host loads the app's assembly (its folder and the previewed library's are searched for references), sets `Application.ResourceAssembly` to it, and creates the app's own `Application` class and calls its `InitializeComponent`, which loads App.xaml's compiled resources and merged dictionaries. It never runs it: no `Startup`, no `StartupUri`. If that class fails, a plain `Application`.
- **WPF's own loader,** without what designers leave out. `XamlXmlReader` with WPF's schema context, the file's assembly as `LocalAssembly` (so `clr-namespace:` without `assembly=` resolves to it) and the file's pack URI as base, through `DesignTimeXamlReader`, a node filter that skips `x:Class`, `x:Subclass`, `x:ClassModifier`, `x:FieldModifier`, `x:Code`, event members (WPF's own `XamlMember.IsEvent`, attached events included) and `EventSetter` objects, into `XamlReader.Load`. Line information passes through, so errors point at the edited text. The compiled `x:Class` isn't instantiated: what shows is the edited XAML, and controls the XAML uses (the app's user controls) are the compiled ones.
- **Windows and pages** move into a stand-in: their content goes into a border that keeps their background, resources, name scope (`ElementName`), data context and text properties; the window is closed unshown. Other elements are shown as they are; a resource dictionary and App.xaml draw a short description.
- **Design time.** Markup compatibility hides `d:` from the loader, so the host reads the root's start tag first (`DesignXaml`, WPF-free): `x:Class` names the root in selection paths, `d:DesignWidth`/`d:DesignHeight` size it (else the root's own size, else its content's), and `d:DataContext="{d:DesignInstance …}"` gives the root a data context: an instance of the type when `IsDesignTimeCreatable=True` (a list of one with `CreateList`), and none otherwise, as the classic IDE does. `d:DesignData` and design data on nested elements aren't supported (the previewer's log says so).
- **Drawing.** The preview's elements are the root of a hidden `HwndSource` (never shown, so they're loaded as in an app: templates, `Loaded`), laid out at the design size and drawn with `RenderTargetBitmap` at background priority after the update (bindings and layout done), and once more half a second later if the pixels changed (late content). The last good preview stays when an update fails. Unhandled exceptions from the user's code after the load are logged, not fatal.

**Selection** is the Avalonia previewer's model (ADR 0048) over WPF's trees (`WpfTree`): a step is an element's type and its index among its logical siblings of that type (`LogicalTreeHelper`; `FrameworkElement` and `FrameworkContentElement`, not data items), and the root's step is named by its `x:Class`, as the C# host's `codalus/xaml/logicalTree` names it. `hit x y` hit-tests the frame (`VisualTreeHelper.HitTest`) and climbs out of templates (`TemplatedParent`) and up the visual tree to the nearest element of the root's logical tree, so a button's text selects the button and an item of a list selects the list; `bounds path` returns an element's bounds in the frame. The C# host's logical tree leaves out WPF's non-logical property elements (`ToolTip`, `Style`, `Triggers`, transforms, bindings collections) as it does Avalonia's.

**The previewer service routes by dialect.** `PreviewService.DialectOf`: an `.axaml` file, or a file of a project that references Avalonia, is Avalonia's; another `.xaml` of a `UseWPF` project is WPF's (as `XamlContext.IsWpf`, ADR 0071); .NET MAUI's XAML has no previewer and says so. A WPF target: on Windows only (off Windows: "The WPF previewer runs on Windows only…", before trust, build or start), trusted folders only, hosted by the file's project when it's an app or else by a WPF app that references it (the startup project first), on .NET 8 or later, with the shipped host (`CODALUS_WPF_PREVIEWER` overrides it). Builds, rebuild on saves of the preview's C# and XAML, scale and zoom are the Avalonia previewer's. WPF has no theme variants: the tool window hides the picker. The XAML Previewer follows `.xaml` editors as well as `.axaml` ones, and Shift+F7 works in both.

**The live agent for WPF** (the startup hook): `RunService.ProgramPlan` adds it, as it adds Avalonia's agent, to a WPF app run or debugged on Windows when its .NET is 8 or later (`debug.liveVisualTree`). It speaks the Avalonia agent's protocol (ADR 0052), so `LiveSession` and both tool windows serve it unchanged. It connects on its own thread and touches nothing of the app's dispatcher until `Application.Current` exists (the IDE asks again until the first window opens); every command runs on the app's UI thread at `Loaded` priority, after the bindings and layout the app has queued (so a window that has just opened shows its bound title and laid-out items), with a 10-second limit (a thread paused in the debugger doesn't answer):
- `windows` (`Application.Windows`), `tree` (`LogicalTreeHelper` or `VisualTreeHelper`, with the templated flag), `path` (out of templates, then the logical path from the window, which Go to XAML resolves in the file whose `x:Class` is the window's class, `.xaml` files included);
- `props`: the element type's dependency properties (its and its bases' `XxxProperty` fields) and the attached properties set on it, each value's source from `DependencyPropertyHelper.GetValueSource` (Local, Style, Style trigger, Implicit style, Theme style, Template, Template trigger, Inherited, Default; "animated" when so);
- `set`: the value converted as XAML would (the property's own converter, such as Width's `LengthConverter`, else its type's) and set as a local value; read-only properties are refused;
- `highlight`: an adorner over the element; `pick`: a class handler on windows' `PreviewMouseDown`, so the next click selects instead of reaching the app.

## Consequences

- The WPF previewer and live tools need no package or code in the user's app and no Windows SDK beyond the app's own .NET; one host serves every WPF on .NET 8 and later.
- What shows is the edited XAML, not the compiled class: code-behind (the constructor, event handlers) doesn't run in the preview, and a code-behind change shows after a save and a rebuild, as for Avalonia.
- Types the preview creates by reflection must be public (loose XAML's access rules); `d:DesignInstance` without `IsDesignTimeCreatable=True` shows no data, by design.
- Pointer moves aren't applied to the preview: WPF's hover state follows the real mouse, which the hidden window never has. Clicks select, as in the Avalonia previewer.
- Linux and macOS packages don't carry the host, and the IDE there says Windows only (D31). A Windows remote target (the phase's shared prerequisite) would run the same host there and stream its frames.
- The Windows-only code is proven by the Windows CI runner's tests (the designer host and the live agent on the fixture, the shell end to end) and the smoke step `wpf.preview`; the routing, the start-tag reading and the protocol are tested on every OS.
