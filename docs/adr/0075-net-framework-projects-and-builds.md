# 0075. .NET Framework projects and builds

- **Status:** accepted (M43a, 2026-10-17; the maintainer's standing go-ahead for the milestones, D31)
- **Date:** 2026-10-17
- **Deciders:** maintainer
- **Amends:** [ADR 0004](0004-project-system.md) and [ADR 0006](0006-build-and-run.md) (only SDK-style projects loaded), [ADR 0012](0012-package-management.md) (NuGet in the build host), [ADR 0030](0030-older-dotnet.md) (.NET Framework was out of scope)

## Context

D31 moved the Windows desktop phase into scope as Windows-only features, M43 (.NET Framework) last, with its debugger (M43b). M43a is projects, builds, IntelliSense and running. What the current SDK (.NET 11 RC2) does with .NET Framework projects, found before deciding:

- **SDK-style `net4x` projects build on every OS.** The SDK adds `Microsoft.NETFramework.ReferenceAssemblies` (Microsoft, MIT; 1.0.3, every framework from 2.0 to 4.8.1) to the restore wherever the targeting pack isn't installed (`IncludeTargetingPackReference`, a target: so it isn't in an evaluation's items, only in the assets file). The package's targets set `TargetFrameworkRootPath`. Roslyn's targets default `LangVersion` to 7.3 for .NET Framework. The SDK sets `AutoGenerateBindingRedirects` for executables, generates `supportedRuntime`, and on Windows sets `RunCommand` to the `.exe` (empty elsewhere, where `dotnet run` fails with the SDK's `RunCommandRequiresWindowsForNetFramework` error). `UseWindowsForms` works for `net48` on Linux without `EnableWindowsTargeting`.
- **Non-SDK-style ("old-style") projects evaluate with the SDK's MSBuild** (`Microsoft.Common.props` and `Microsoft.CSharp.targets` are in the SDK) but fail in `GetReferenceAssemblyPaths` (MSB3644): MSBuild looks for reference assemblies only where the Developer Packs install them. `TargetFrameworkIdentifier` is often empty until Microsoft.Common.CurrentVersion.targets defaults it, after `CustomBeforeMicrosoftCommonTargets` is imported and before `FrameworkPathOverride` is computed from `TargetFrameworkRootPath`. Pointed at the reference assemblies package, they build, project references to SDK-style projects included.
- **`packages.config` restore isn't in the SDK's NuGet:** `dotnet restore -p:RestorePackagesConfig=true` (or `msbuild -t:restore`) finds the projects' `packages.config` and says "Nothing to do": that restore is in Visual Studio's and nuget.exe's NuGet (on .NET Framework) only.
- **Visual Studio's own targets** (`$(VSToolsPath)`, under `MSBuild\Microsoft\VisualStudio`: web applications, SQL, Service Fabric…) come only with Visual Studio and its Build Tools. Their MSBuild is proprietary and its licence for driving it from a third-party IDE hasn't been checked.
- **MSBuild's project collections read the environment once,** when they are created; build nodes get the environment of each build.
- **The SDK's `console` and `classlib` templates don't target .NET Framework.** `--target-framework-override net48` gives projects with top-level statements, implicit usings and nullable annotations, which C# 7.3 rejects.

## Decisions

**SDK-style `net4x` projects take the usual path** on every OS: evaluation, design-time builds and builds. The Dependencies node shows the reference assemblies package under Frameworks, from the assets file (or the installed framework's moniker when it wasn't used), and hides the `mscorlib` reference the package's targets add.

**Non-SDK-style projects load for .NET Framework** (`ProjectInfo.IsNonSdkStyle`) instead of being unsupported:
- one evaluation, with the moniker of `TargetFrameworkVersion` as the target framework (`v4.7.2` → `net472`); other non-SDK-style projects stay unsupported, saying why;
- items as evaluated (they list their files), and a Dependencies node of the framework, the `packages.config` packages (resolved once in the repository path), the `<Reference>` items (a `HintPath` resolved when the file is there) and project references;
- the fingerprint of the design-time cache includes `packages.config` and the hint paths' files, which a restore changes.

**Their reference assemblies come from the same NuGet package as SDK-style projects'.** The build host writes `Codalus.NetFramework.targets` (temp folder, once) and sets, at start and as environment variables (the lowest-priority property source, as `EnableWindowsTargeting` in ADR 0071), `CustomBeforeMicrosoftCommonTargets` to it, unless the user set that variable, and `CodalusNuGetPackageRoot` to the global packages folder of the solution's NuGet settings. For a project that isn't SDK-style, targets .NET Framework and has no reference assemblies installed (`GetPathToStandardLibraries` finds none: a Developer Pack wins), the file sets `TargetFrameworkRootPath` to the package's `build/` folder, turns off `FrameworkPathOverride`, sets `NoStdLib` and references `mscorlib`, as the package's own targets do. Environment variables apply to evaluations, design-time builds, builds and their nodes without touching projects; a global property would change every project's cache key.

**Codalus restores what `dotnet restore` doesn't, in the build host, through the SDK's NuGet libraries** (as ADR 0012's feed access), after `dotnet restore` (on open, Restore, and before builds that restore): the `packages.config` packages into the repository path (NuGet's `repositoryPath`, else `packages` next to the solution), in packages.config's layout, the global packages folder first and then the solution's sources with its package source mapping and credentials; and the reference assemblies package of each project's framework into the global packages folder, in its own layout. Each package is a line of the restore's output; a failure fails the restore with a count. The projects whose packages came are evaluated and design-time built again. This is the one restore that isn't the user's CLI, because the SDK's CLI has none for `packages.config`; nuget.exe needs Mono off Windows and isn't installed with the SDK.

**Projects on Visual Studio's targets open but don't build** (`ProjectInfo.CannotBuildReason`): an import, not `Condition="false"`, whose expanded path is under `Microsoft/VisualStudio` and doesn't exist. They get IntelliSense (their design-time build loads them with missing imports ignored), Solution Explorer says why under the project, solution builds and restores leave them out (the solution filter that already leaves out compose projects) with a warning in the Build output, and building one alone fails with the reason. Codalus doesn't drive Visual Studio's MSBuild or Build Tools: the licence check is a gap (below). Where the targets exist (the user's Visual Studio install on Windows), nothing is reported and the build tries.

**Running (D31):** .NET Framework projects run only on Windows (`WindowsDesktopProjects.RunsOnlyOnWindows`), where Start Without Debugging starts the `.exe` (the SDK's `RunCommand`, or the target path of an old-style project, which has none), on the desktop CLR, with no `DOTNET_ROOT` (the runtime selection of ADR 0030 applies to .NET Core only). F5 on Windows says debugging the desktop CLR comes later and offers Start Without Debugging (netcoredbg debugs CoreCLR only; M43b). Hot Reload says it needs .NET 6. Off Windows Start, Start Without Debugging, the profiler and the test plugin say "Windows only", the same gate as WPF's. Running on Mono isn't offered (a later decision).

**Convert to SDK-style** is Codalus's own converter (`SdkStyleConverter`, in the workbench, pure XML and file reads), in the spirit of try-convert (MIT): its approach, none of its code. The project file becomes `Microsoft.NET.Sdk` with `TargetFramework`; properties the SDK sets the same way, globbed items, implicit framework references, NuGet's package imports and its check target go; files in the folder that weren't in the project are removed from the globs (folders of other projects and `packages` too); items with metadata become `Update`s; `packages.config` becomes `PackageReference` items, leaving out packages another listed package depends on when the `.nuspec` files are in the repository path; `AssemblyInfo.cs`'s generated attributes become properties (a wildcard version or a non-literal stays, with its `Generate…Attribute` false). It refuses SDK-style projects and projects that need Visual Studio's targets. The shell previews it with the refactoring preview (line-diff edits, the deletions, the converter's notes) and applies it as a workspace edit, then restores. Golden files keep its output stable.

**New Project** writes SDK-style .NET Framework console apps and class libraries itself (`net48` by default, or `net481`, `net472`, `net462`), in C# 7.3 with a `Main` method.

**Check Environment** (on Windows, when the solution has .NET Framework projects) reads the installed .NET Framework 4.x from the registry's `Release` DWORD (`HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full`, Microsoft's documented way) against the highest targeted version, and .NET Framework 3.5 (`NDP\v3.5` `Install`) when a project targets 2.0 to 3.5; the fix is the download page. Building needs neither.

## Consequences

- .NET Framework projects open, restore and build on every OS without a targeting pack, proven by the build host's tests on every CI runner (SDK-style `net48`, an old-style `v4.7.2` app with `packages.config`, a `v3.5` library whose reference assemblies Codalus installs, the converted project). Running is proven only on Windows (a Windows-only shell test and the smoke step `netfx.projects`).
- Old-style projects build in Codalus where `dotnet build` alone fails (no Developer Pack): the reference assemblies come from Codalus's targets, which the command line doesn't import. The user guide says so and offers conversion.
- A user who sets `CustomBeforeMicrosoftCommonTargets` in the environment keeps it, and old-style projects then need the Developer Pack.
- **Gaps:** debugging and tests on the desktop CLR (M43b, after the netcoredbg port spike); running on Mono; Visual Studio's targets and Build Tools (`TODO(issue)`: check whether its licence allows a third-party IDE to drive the user's own install before any work on it); COM references, ClickOnce, the EF6 designer, Web Forms, C++/CLI and VSTO; the Windows Forms designer and WPF previewer against .NET Framework apps (unvalidated); VB projects' `AssemblyInfo.vb` isn't converted (it keeps `GenerateAssemblyInfo` false).
- Worth revisiting when: the SDK's NuGet gains a `packages.config` restore, or Microsoft publishes a newer reference assemblies package.
