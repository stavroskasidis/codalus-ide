# 0076. Debugging the desktop CLR

- **Status:** accepted (M43b, 2026-10-17; the maintainer's standing go-ahead for the milestones, D31)
- **Date:** 2026-10-17
- **Deciders:** maintainer
- **Amends:** [ADR 0007](0007-debugging.md) (netcoredbg as the one .NET debugger), [ADR 0032](0032-debug-companion-host.md) (the debug companion's modes), [ADR 0075](0075-net-framework-projects-and-builds.md) (F5 offered Start Without Debugging)

## Context

D31 puts .NET Framework in scope on Windows, "M43 with its debugger". netcoredbg (ADR 0007) debugs CoreCLR only, vsdbg is proprietary and can't be used, and the roadmap's plan was a desktop-CLR port of netcoredbg (MIT), after a spike. The milestone needs breakpoints, stepping, the call stack, locals and watch with basic expressions (member access, literals, operators, method calls through func-eval), first-chance and unhandled exceptions with M14a's settings, threads, attaching to a running .NET Framework process, and Just My Code where it's cheap.

What the spike found:

- **The desktop CLR has its debugging API in every install.** `mscoree.dll` (Windows) exports `CLRCreateInstance`; `ICLRMetaHost::GetRuntime("v4.0.30319")` gives the installed runtime, whose `ICLRRuntimeInfo::GetInterface(CLSID_CLRDebuggingLegacy, IID_ICorDebug)` loads that runtime's own `mscordbi.dll` and returns `ICorDebug`, the interface CoreCLR's debuggers use too. `ICorDebug::CreateProcess` and `DebugActiveProcess` start or attach (managed-only debugging, no Win32 debug loop). CLR 2 (.NET 2.0 to 3.5) works the same way with `v2.0.50727`, when .NET 3.5 is installed. Nothing has to be shipped.
- **ICorDebug debugs processes of its own bitness:** a 64-bit debugger can't debug a 32-bit process (x86, or AnyCPU with `Prefer32Bit`). SDK-style `net4x` executables are AnyCPU without `Prefer32Bit` by default; the classic IDE's old templates often set `Prefer32Bit`.
- **netcoredbg is a C++ program on CoreCLR's `dbgshim`** (start and attach through `RegisterForRuntimeStartup` and `CreateDebuggingInterfaceFromVersion`) **with a managed part** (symbol reading and expression evaluation) that it runs by hosting CoreCLR in its own process. A desktop-CLR port needs another start path, a managed part that still runs on .NET while the debuggee runs on the desktop CLR, and a Windows-only native build (CMake, MSVC) in CI, packaged and signed under `debugger/netfx/`; none of it can be built, run or tested on Linux, where most of this repository's work happens.
- **ClrDebug** ([lordmilko/ClrDebug](https://github.com/lordmilko/ClrDebug), NuGet 0.4.2, MIT, maintained, no dependencies) wraps every ICorDebug interface, the CLR hosting interfaces (`ICLRMetaHost`, `ICLRRuntimeInfo`) and the managed callback, on .NET 8's source-generated COM interop (`GeneratedComInterface`, `StrategyBasedComWrappers`): no built-in COM, compiles on every OS, the wrappers compile-check our calls. Its `net8.0` assembly is 8 MB. MDbg's CorApi sources are older and their licence is unclear (debugger-libs carries a copy under Microsoft's sample terms); dnSpy's `dndbg` is GPL. Neither is used.
- **Metadata and symbols don't need ICorDebug.** System.Reflection.Metadata (in .NET) reads a module's file and its portable PDB (next to it, where its debug directory says, or embedded): types, methods, fields and properties, sequence points, local scopes and names. Windows PDBs need DIA or the native `diasymreader` (Microsoft's, proprietary to redistribute; `diasymreader.dll` of the installed .NET Framework could be driven, but adds a second symbol path). SDK-style projects build portable PDBs; the classic IDE's old projects ask for Windows PDBs (`DebugType` `full`).
- **M20b's Mono adapter is the precedent:** a DAP adapter of our own in C#, in `codalus-debughost --mono-dap`, on `Codalus.Debugging`'s source-generated contracts (`DapServer`), tested against the real runtime and a protocol-level client.

## Options

| | (a) Port netcoredbg to the desktop CLR | (b) A managed DAP adapter in the debug companion |
|---|---|---|
| Start and attach | Replace dbgshim's start path with `ICLRMetaHost`/`ICLRDebugging` in C++ | `ICLRMetaHost` → `ICorDebug` through ClrDebug, in C# |
| Symbols and evaluation | netcoredbg's managed part, hosted on CoreCLR inside a process that debugs the desktop CLR | System.Reflection.Metadata for portable PDBs; our own C# expression evaluator over func-eval (the Mono adapter has none beyond member paths) |
| Build and ship | A Windows-only native build in CI, a new binary to package and sign (`debugger/netfx/`) | Managed code in `codalus-debughost`, already shipped; one MIT package |
| Testing | Windows only | Everything above ICorDebug on every OS, against a fake ICorDebug and the real metadata and PDB of a `net48` debuggee built on Linux; the rest on Windows |
| Depth | netcoredbg's (expression evaluation, stepping, JMC) once ported | What we write: the milestone's list, more later |
| Risk | The port's size, and the CoreCLR-hosted managed part in a desktop-CLR debugger | ICorDebug's semantics (callbacks, func-eval, neutering), verified only on Windows CI |

## Decision

**(b): a managed DAP adapter, `codalus-debughost --netfx-dap`** (`Codalus.Debugging.Host/NetFx`), Windows only (off Windows it answers DAP and refuses to launch, saying .NET Framework runs only on Windows). (a) would put a native Windows-only build into a repository that is validated mostly on Linux, for a debugger whose interesting parts (symbols, evaluation, the DAP layer) are as much work in either; (b) reuses the companion host, adds no binary, and leaves only the ICorDebug calls untestable here.

- **The ICorDebug side** (`CorDebugTarget`, through ClrDebug) is behind small interfaces (`IClrProcess`, `IClrThread`, `IClrFrame`, `IClrValue`, `IClrModule`): callbacks become events in a channel; the process stays stopped until the session continues it; during a func-eval every other callback continues at once (module loads and threads are still reported). ICorDebug neuters the frames and values it handed out whenever the process runs, a func-eval included: the session reads a value it keeps (a variable to expand, an expression's operand, a stop's exception) again from where it came from (the frame, its parent's field or element, the static field, the thread's exception), frames are found again by their method and place on the stack, and a func-eval's result is held by a strong handle until the program goes on (a primitive result is kept). The runtime version is the program's: the first installed `supportedRuntime` of its `.config`, else the version it was built for (`GetVersionFromFile`); for an attach, `clr.dll` or `mscorwks.dll` among the process's modules. A 32-bit program or process is refused before starting, with what to change.
- **Launch:** `ICorDebug::CreateProcess` with a Unicode environment block (the launch's variables over the IDE's), and either pipes for stdout and stderr (the Debug Console; stdin at its end) or a console window of its own (`debug.console` `externalConsole`, the Windows default). The adapter keeps its own standard handles out of the debuggee. The integrated terminal's held start needs CoreCLR's startup hooks, so a terminal launch uses the Debug Console and says so.
- **Symbols:** portable PDBs through System.Reflection.Metadata (`ClrModuleInfo`); a Windows PDB is reported in the module's symbol status and not read. **Old-style .NET Framework projects build portable PDBs in Codalus**: the build host's targets file (ADR 0075) sets `DebugType` to `portable` where such a project asks for `full` or `pdbonly`, unless `CodalusKeepDebugType` is `true`.
- **Breakpoints** bind when their module loads (or at once): the PDB's document by path (or the only one with that file name), each method's first offset on the line or the next line with code in a method that spans it, as an `ICorDebugFunctionBreakpoint` at that IL offset. Conditions are evaluated by the adapter; hit counts and logpoints stay the debug service's. Function breakpoints (`Method`, `Type.Method`, `Ns.Type.Method`) bind at each match's first line.
- **Stepping** by source line: `StepRange` over the current sequence point's IL range (into or over), `StepOut`; a hidden sequence point or the middle of a line steps on. **Just My Code:** modules with symbols that aren't optimized are the user's (`SetJMCStatus`), steppers are JMC steppers, and a step that ends in code without symbols (or `[DebuggerNonUserCode]`, `[DebuggerStepThrough]`, `[DebuggerHidden]`) steps out. **Step filtering** steps over property accessors and operators.
- **Values:** locals by the PDB's scopes and slots, arguments by metadata, `this`; an async method's or iterator's state machine shows its hoisted variables and the original `this`. Members: fields (auto-properties' backing fields by the property's name), then properties through their getters (func-eval, a 5-second limit; after one times out, the rest aren't evaluated). Enums by name (flags combined), `decimal`, `DateTime`, `TimeSpan` and `Nullable<T>` by value, arrays (the first 100 elements, several dimensions). Primitive values can be changed.
- **Evaluation:** our own parser for a C# subset (literals with C#'s types, names, `this`, members, `?.`, indexers, calls, unary and binary operators with C#'s precedence and numeric promotion, `?:`, `??`, casts) and evaluator: names are locals, arguments, `this`'s members, static members of the method's types, types (keywords, the method's namespace, `System`, a unique name) and namespaces; method calls pick an overload by the arguments' types and run through `ICorDebugEval` (generic classes' type arguments passed), the other threads suspended, aborted after the time limit; string, array and primitive operations are computed in the adapter.
- **Exceptions:** M14a's settings as netcoredbg's filters (`all` with a type-name condition, `user-unhandled`). With Just My Code, an exception breaks where it's thrown in the user's code (a first chance there, or the runtime's user first chance when it reaches the user's code), once; without, at every first chance. Exception info has the type, the message, the stack trace (its getter) and inner exceptions.
- **The debug service** sends a launch whose program is a managed `.exe` (on Windows: a PE with a CLI header, which .NET Core's native apphosts never are) and an attach to a process that loaded `clr.dll` or `mscorwks.dll` and not `coreclr.dll`, to this adapter. That covers F5, multiple startup projects, test hosts (`testhost.net48.exe`) and plugins' launches without the callers knowing. Attach to Process lists .NET Framework processes with the .NET ones.
- **Tests on .NET Framework:** VSTest's .NET Framework test hosts run xUnit 2, NUnit 3 and MSTest v2; old-style test projects are found by the classic IDE's test project type GUID (`{3AC096D0-A1C2-E12C-1390-A8335801FDAB}` in `ProjectTypeGuids`) or `IsTestProject`. A debugged .NET Framework test host runs as the IDE's architecture (`TargetPlatform`), since VSTest may pick the 32-bit host.

## Consequences

- F5, multiple startup projects, Attach to Process and Debug Test work for .NET Framework programs on Windows, with no new binary and no proprietary component. The adapter's DAP layer, evaluator and symbol reading are tested on every OS; the ICorDebug calls only on Windows (CI's `windows-latest`, which has .NET Framework 4.8), by the integration tests, the headless shell test and the smoke step.
- `codalus-debughost` grows by ClrDebug's 8 MB (15 MB after ReadyToRun) on Windows. *Update 2026-10-18:* a publish for Linux or macOS leaves ClrDebug out (`Publish="false"` for a non-Windows runtime identifier), so those packages don't carry it; off Windows the adapter never loads a ClrDebug type ([the 0.3.0 size gate](../benchmarks/net11-release-gate.md#the-030-releases-content-2026-10-18)).
- **Gaps:** 32-bit processes (an x86 debug companion would debug them) `TODO(issue)`; Windows PDBs (old projects built outside Codalus) `TODO(issue)`; CLR 2 (.NET 2.0 to 3.5) is wired but untested (no runner with .NET 3.5 turned on) `TODO(issue)`; mixed-mode (native) debugging, Edit and Continue, Set Next Statement, data breakpoints, the integrated terminal, `DebuggerDisplay`/visualizers beyond what the debug service does with evaluation, and expressions beyond the subset (lambdas, `new`, `typeof`, generic methods, assignments) `TODO(issue)`; code coverage on .NET Framework test hosts (Coverlet's collector is unvalidated there) `TODO(issue)`; running and debugging on Mono stays a later decision (D31).
- Worth revisiting when: an MIT desktop-CLR debugger appears, or netcoredbg gains a desktop-CLR mode.
