# 0073. Windows Forms designer

- **Status:** accepted (M41a, 2026-10-16; the maintainer's standing go-ahead for the milestones, D31); amended for M41b, 2026-10-17 ([below](#m41b-the-rest-of-the-designer))
- **Date:** 2026-10-16
- **Deciders:** maintainer
- **Builds on:** [ADR 0071](0071-wpf-xaml-language-service.md) (WinForms and WPF projects), [ADR 0072](0072-wpf-previewer-hosting.md) (the WPF previewer's host, whose shape this follows), [ADR 0033](0033-project-items-templates-and-folder-mode.md) (the Properties window)

## Context

M40 made Windows Forms projects open, build, run and debug. M41 adds what Visual Studio's Windows Forms designer does: a form or user control designed on a surface, with the Toolbox and the Properties window, and `InitializeComponent` written back as Visual Studio writes it. D31 makes it Windows only for now: Windows Forms draws only on Windows, and the other OSes are decided later. M41 is split: M41a (this ADR) is a working designer for common forms; M41b adds snap lines, tab order, the full component tray, smart tags, menu and tool strip editing, localizable forms and images into resources.

Five facts shape it:
- **Visual Studio's designer is proprietary**, but its parts are in dotnet/winforms (MIT) and ship in the Windows Desktop runtime the user already has: `DesignSurface`, `IDesignerHost`, the control designers, `UndoEngine` and the CodeDOM serializers. SharpDevelop 5's designer (MIT) was a whole designer built on them.
- **The code is the document.** A designer file is source code under version control. Visual Studio regenerates all of `InitializeComponent` on every change, which is the main source of noisy diffs; and its loader refuses code it didn't write ("the designer cannot process unknown name…").
- **The .NET SDK has Visual Studio's rules as analyzers.** `WFO3000` and its family flag what the designer can't round-trip in `InitializeComponent` (loops, lambdas…) as errors, so a project rarely has such code; a project that turns them off does.
- **The C# host has the project's compilation** (Roslyn), so it can tell `DockStyle.Fill` (an enum member) from `Color.Red` (a static property) and name every type fully, and it already writes code edits.
- **The IDE's side of a hosted process exists:** `SupervisedProcess` and JSON-RPC (ADR 0004), and the M26a Properties window.

## Decisions

**A CodeDOM-like model, read and written in the C# host.** `codalus/winforms/read` reads a form's `InitializeComponent` (from its code or designer file) into a `DesignerModel`: the class, its base type (what the designer creates, as Visual Studio does), its components (fields created with `new`, locals such as a `ListViewItem`, the root) and the method's statements in order: creations, assignments to a property path (`FlatAppearance.BorderSize`), calls (`Controls.Add` with a `TableLayoutPanel`'s cell or a `SplitContainer`'s `Panel1.Controls.Add`, `Items.AddRange`, `ColumnStyles.Add`, extender calls such as `toolTip1.SetToolTip`), layout calls (`SuspendLayout`, `ResumeLayout`, `PerformLayout`, `ISupportInitialize`'s `BeginInit` and `EndInit`), event hookups (method groups and `new EventHandler(this.M)`), `resources.ApplyResources` and `GetObject`, and Visual Studio's section comments. Values are expression trees: literals, enum members (ored for flags), static members, `new`, static calls, arrays, resources, references to components, `typeof`. Types are named through the compilation (a syntactic fallback names the common ones when the project isn't loaded). Anything else (control flow, lambdas, calls to the class's own methods, names that aren't components, property reads, object initializers) fails with the reason and its line: the designer closes and the file opens as code at that line, with the reason in a notification, as Visual Studio does.

**Writing is the smallest edit, not a regeneration.** `codalus/winforms/edit` takes the designer's changes (`setProperty`, `addComponent`, `removeComponent`, `renameComponent`, `setParent`, `addEvent`, `removeEvent`) and applies each to the designer file's text as Visual Studio would place it, touching nothing else:
- a property: its assignment's value replaced in place; a new one inserted in its component's section where Visual Studio sorts it (properties by name, `Controls` and collections among them, extender properties by their name, events after); a default value's assignment removed, and a section left empty goes with its comment;
- a component: its field after the last component's (after `#endregion` in a form without any), its creation after the last creation (`components = new Container()` first when it's created in it), its section before the next component's (the root's last), its `Controls.Add` first in its parent's (new controls go to the front), its parent's `SuspendLayout` and `ResumeLayout` by the root's when it's the parent's first child, `BeginInit` and `EndInit` for `ISupportInitialize`;
- a removal takes the controls inside and every statement that mentions them (an `AddRange` array loses the item); a rename changes the field, every use, the section comments and `Name`, and through Roslyn's rename its uses in the class's other files; a new event handler is written at the end of the class in the code file with the event's own parameters (`object? sender` when the file has nullable annotations), and an existing one is shown.
The text is rewritten in the file's own style, detected when read: Visual Studio for .NET (no `this.`, types shortened through the file's usings, global usings and namespace, `A.X | A.Y`, method groups) or for .NET Framework (`this.`, full type names, CodeDOM's parenthesized casts and line breaks, `((byte)(0))`, `Color.FromArgb(((int)(((byte)(255)))), …)`, multi-line arrays, `new System.EventHandler(this.M)`), its indentation, line endings and section comment rules. The new text is diffed line by line against the old (`LineDiff`), so the edit the IDE applies is the changed lines. The model after the edit comes back with it.

**Round trips are tested on files Visual Studio wrote.** Writing every statement of a read file again gives the file back byte for byte, in both styles and with CRLF; nothing changed is no edit; each kind of change is checked as the exact lines it adds and removes. These tests run on every OS (Roslyn only).

**The designer host follows the WPF previewer's shape (ADR 0072).** `src/Codalus.WinForms.Designer` (`codalus-winformsdesigner.dll`, `net8.0-windows`, `UseWindowsForms`, framework references only) runs on the designed project's app's own .NET and Windows Forms (`dotnet exec --runtimeconfig App.runtimeconfig.json --depsfile App.deps.json`; a library with no app that references it runs on the host's own runtimeconfig, rolled forward, its output folder searched for references), loads the project's build output (built first when the sources are newer), and runs only for trusted folders. It builds on every OS (`EnableWindowsTargeting`) and ships only in the Windows package (`winformsdesigner/` next to the shell; `CODALUS_WINFORMS_DESIGNER` overrides it). Unlike the previewer it speaks the IDE's own JSON-RPC on stdio (it links `Codalus.Rpc`'s connection and the protocol's source-generated records) under `SupervisedProcess`: a crash restarts it, and the document loads the form again ([protocol](../winforms-designer-protocol.md)).
- **Loading:** a `DesignSurface` loads the root (an instance of the base type, named as the class), the components are created through `IDesignerHost.CreateComponent` (so each gets its designer and is in design mode: a user control shows as at design time), and the model's statements run in order against them, properties through their property descriptors (the designers' shadow properties apply), calls by reflection, `ApplyResources` and `GetObject` through the class's compiled resources. A statement that fails is listed with its line; the rest load.
- **Drawing:** the surface's view lives in a hidden, off-screen window (so controls have handles and lay out), the process is DPI unaware (a pixel is a unit of the code), and the root is drawn with `DrawToBitmap` into a PNG. Every control's bounds and client origin in the frame come with it (a `SplitContainer`'s panels as parts), and the non-visual components.
- **Changes come back as code:** a create (with the control designer's `InitializeNewComponent`, so a button's `Text` is its name and `UseVisualStyleBackColor` is set, at the front of its parent, in a `TableLayoutPanel`'s cell under the point, with the next tab index), a property set (from the Properties window's text through the property's type converter, or a value), a reparent and a delete answer with what changed: every component's serializable properties (visible to serialization, not design-only, not extended, `ShouldSerializeValue`, content properties one level down) are compared before and after, so a docking or a resize that moves siblings is written too. Values are serialized as Visual Studio's serializers do: literals, enum members, colors by name or `FromArgb`, components by name, and `InstanceDescriptor`s' constructors and static members (`new Point(12, 9)`, `new Font("Segoe UI", 9F, …)`, `new decimal(new int[] {…})`, `Cursors.Hand`). A value code can't say (an image) is left to the resources.

**Gestures are the shell's; the host gets operations, not mouse messages.** The surface, its adorners (selection rectangles, the primary selection's eight grab handles, the rubber band, the drawn rectangle) and the hit testing are drawn and done in the shell over the frame, from the bounds the host reported, so a drag needs no round trip per mouse move; when a gesture ends, the host is asked for the operation it amounts to (select, move, resize, reparent, create, delete). The designer host's own selection service follows the IDE's selection (a tab page shows when selected).

**Undo is the designer file's text undo, not `UndoEngine`.** Every change is applied to the designer file's text model (the same one an editor of the file uses, kept while the designer is open) as one undoable edit. Undo and redo in the designer are that model's; the designer notices the text changed and loads the form again from it, which is also what happens when the code is changed in the code view, by source control or by another tool. Reasons: the code is the only state, so the surface can't drift from it; one undo stack serves the designer and the code view, local history and source control see ordinary edits; and `UndoEngine` would keep a second history of serialized component state that must then be mapped to text edits both ways. The cost: an undo reloads the form (a few hundred milliseconds for a common form). The designer's own edits don't reload it (the host already shows them).

**The Toolbox and the Properties window.** The Toolbox (`Ctrl+Alt+X`) lists Windows Forms' common controls in Visual Studio's categories (Common Controls, Containers, Menus & Toolbars, Data, Components, Printing, Dialogs) and the project's own components and those of the projects it references (`codalus/winforms/toolbox`: public, or internal in the project, non-abstract, parameterless constructor, a `Component` that isn't a form, not `[ToolboxItem(false)]` or `[DesignTimeVisible(false)]`). A click arms an item for a click or a drag on the surface; an item can be dragged onto it; new components get Visual Studio's names (`button1`). The M26a Properties window shows the designer's selection while the designer is the last place something was selected: the host's property descriptors (merged for several components, differing values blank), by category or alphabetically, bold when the code sets them, edited as text through the type converter, with choices (enums, `bool`, `Dock`, known colors), flags toggles (`Anchor` and other flags), a color swatch; `(Name)` renames. Its Events view lists the component's events with their handlers: a name typed hooks it, its button (or a double-click on the control, its default event as Visual Studio does) writes the handler and shows it.

**Opening.** A `.cs` file of a Windows Forms project with a `.Designer.cs` that has `InitializeComponent` opens in the designer on Windows (`windowsForms.openInDesigner`, default on); the designer file itself opens as code. View Code (`F7`) and View Designer (`Shift+F7`, which the XAML Previewer keeps in XAML files) switch, as Visual Studio's. The Solution Explorer shows such files with a form icon. A class that isn't a control (a component) opens as code (the component designer stays a gap after M41b).

**What's Windows only (D31).** The designer host, the surface and the Toolbox. Off Windows a form opens as code (the status bar says once why), View Designer says the designer is Windows only and opens the code, and the reader, writer and Toolbox listing (the C# host) still run there, so the code side is tested on every OS.

## Consequences

- The designer needs nothing in the user's project and nothing shipped but our host; it uses the Windows Forms the app runs on, so it designs what the app shows.
- Diffs are what changed: a moved button is one line, a new one its field, creation, section and `Controls.Add`. Code the designer didn't write outside the edited statements stays as it is (even code a full regeneration would reorder).
- Code Visual Studio's designer wouldn't read opens as code, with the reason; the SDK's `WFO3000` analyzers already keep most projects from having it.
- Localizable forms load (their resources applied) but their localizable properties aren't edited: the designer says so (M41b writes them to the `.resx`). Images in resources show and aren't edited. (Superseded by M41b, below.)
- An undo reloads the form from the code.
- The Windows-only code is proven by the Windows CI runner's tests (the designer host on the fixture, end to end with the writer) and the smoke step `winforms.designer`; the reader, writer, Toolbox listing, protocol and the shell's wiring (with a fake designer host) are tested on every OS.

## M41b: the rest of the designer

Amended 2026-10-17 for M41b, which completes M41: snap lines and the Format menu, tab order mode, Dock and Anchor pickers and adorners, the component tray, extender properties, smart tags, menu and tool strip editing, collection editors, localizable forms and images into resources, paste with event hookups, and simple data binding. No new ADR: these extend the decisions above (the code is the document, the smallest edit, the shell's gestures, the text's undo).

**The host answers with the surface's difference, not per operation.** Before and after each operation the designer host captures what the code says about the whole surface: every component's serializable properties (and values only the resources can hold, such as images), the extender properties its providers give it (`ToolTip` on `toolTip1`, through `ExtenderProvidedPropertyAttribute`), its data bindings, the components themselves, every control's parent and place among its siblings, and every collection the designer edits with the locals it holds. The answer is the difference: changed properties, created components (`added`), moved controls, parents whose controls' order changed (`reordered`), collections (their items as the code writes them, with new locals), removed components and locals, and a localizable form's resources. So whatever runs in the host (a smart tag's task, a designer's `InitializeNewComponent`, a collection edit that creates or destroys items, a tool strip's standard items) is written in full without the IDE knowing what it did, as Visual Studio's serializers would see it.

**Collections are a table, written as Visual Studio writes each.** `DesignerCollections` (in the protocol, shared by both hosts) names each collection the designer edits, its kind and its method: values (`ListBox`, `ComboBox` and `DomainUpDown` `Items`, `TableLayoutPanel` `ColumnStyles` and `RowStyles` with `Add`), components (tool strips' `Items` and drop-downs' `DropDownItems`, `ListView` `Columns`, `DataGridView` `Columns` with `AddRange`; a `TabControl`'s pages as its `Controls.Add`), locals (`ListView` `Items`: `ListViewItem` locals) and an `ImageList`'s `Images` (`SetKeyName`, the bitmaps in its `ImageStream`). The writer replaces the collection's statements where they were (a strip's first items bring its layout calls) and declares locals after the creations. Editors that would be Windows Forms dialogs are the IDE's own (an Avalonia panel over the surface: text a line, members with their properties and types, styles, image keys), and so are smart tag tasks that open a dialog: a task whose name ends with "…" opens the matching collection's editor or the image import, or says it isn't available (a grid's Add Column…, data source wizards).

**Smart tags run in the host.** The IDE asks for a component's designer actions (`DesignerActionService`'s lists, which include the verbs; a designer's own lists and verbs when there's no service), shows them in its own popup (headers, texts, properties with their editors, methods), and asks the host to set a property or run a method; the difference writes what it did.

**Resources are the `.resx` files' text, edited like the code.** The C# host reads and writes a form's `.resx` files (the default `Form.resx` and each culture's `Form.<culture>.resx`) as text (`ResxText`): only the entries that change are touched, placed as Visual Studio's serializer orders them (by component, metadata first, the properties alphabetically, the `>>` records last, new components alphabetically with `$this` last), the file's line endings and its assembly aliases kept. The writer's `setResource` sets or removes a key in a culture's file (creating it when needed), renames and removals reach every culture's keys, and the `resources` variable (`ComponentResourceManager`) comes and goes with its uses. Changed files come back in the edit's workspace edit, so the shell applies them to text models it holds with the designer file's: saved together, and undone together (the designer's undo steps record every model a change touched; an undo with a model changed elsewhere since falls back to the designer file's own undo). The designer host reads the resources from the shell's texts too (a `ComponentResourceManager` over them, falling back from a culture to its parents), so an unsaved `.resx` edit shows at once, and the C# host gets them with each read and edit (`resourceFiles`), since they aren't open documents there.

**Localizable forms work as Visual Studio's.** The root's `Localizable` (a property the host adds, as Visual Studio's designer does) moves every localizable property between the code and the default resources (each component's section starts with `ApplyResources`, the `>>` records of its controls are written). The root's `Language` is the IDE's: the form loads with that culture's resources applied, and a change of a localizable property goes to that culture's file, only where it differs from the value it would inherit (equal: the key goes). Moves and z-order changes update the default resources' `Parent` and `ZOrder` records. Images (and other values code can't say) go to the default `.resx` read with `GetObject`, or, imported "into the project", to the `Resources` folder and `Properties/Resources.resx` (a `ResXFileRef`), read as `Properties.Resources.Name` after the ResX generator runs.

**Snap lines are the shell's, from the host's data.** Each control's view carries its margin, its container's padding (a form's empty padding is the designer's 9, so with a control's margin of 3 the line is at 12, as in Visual Studio) and its text baseline (the control designer's `SnapLines`), and the shell snaps a moving or resized control within 8 pixels to its siblings' edges, baselines and margins and its container's padding, drawing the lines that hold (Alt turns them off). Alignment, sizing, spacing and centering (the Format menu) are computed in the shell from the primary selection and written as `Location` and `Size` changes; Bring to Front and Send to Back are the host's `SetChildIndex`, written as the order of the parent's `Controls.Add` (and `ZOrder` records in a localizable form).

**The component tray's order is Visual Studio's `TrayLocation`.** The tray shows components that are design-time visible and the tool strips (as Visual Studio does), ordered by the `TrayLocation` metadata in the form's `.resx`; dragging or Line Up Icons writes that metadata, so both IDEs agree.

**Paste keeps event hookups within the same form only.** A pasted component brings its properties, its controls, its collections and locals, its extender properties and its bindings; its event hookups come with it when pasted into the form it was copied from (the handlers are there), and are left out in another form, where they would name methods that don't exist (Visual Studio keeps them and leaves the code uncompilable).

**Data binding is simple binding only.** `(DataBindings)` in the Properties window binds a control's bindable properties to a member of one of the form's binding sources (a `BindingSource`, a list source; its members from the data source's type, `typeof(Customer)`), written as `DataBindings.Add(new Binding("Text", customerBindingSource, "Name", true))`. Visual Studio's Data Sources window and its data source wizards stay a gap: set a binding source's `DataSource` in the Properties window or the code.

**The WPF design surface is deferred.** M41's optional WPF design surface (selection, dragging and the Properties window over dependency properties, on M40b's previewer) isn't built: the WPF XAML Previewer already shows the window and selects both ways, the XAML editor is where WPF is designed in practice, and a surface that writes XAML well (minimal edits, as for `InitializeComponent`) is a milestone of its own. It stays a gap, to be proposed separately. The component designer (designing a class that is a component but not a control, its tray only) stays a gap too.

**Consequences (M41b).**
- A form's code and resources change together as minimal edits, saved and undone together; a localizable form's diffs are the changed `.resx` entries.
- The designer host never needs to tell the IDE what a designer did: the state difference covers designers' side effects, at the cost of capturing the surface twice per operation (a few milliseconds for a common form).
- What Windows Forms shows as dialogs (collection editors, the image selector, smart tag dialogs) is the IDE's own UI, so they theme and localize like the rest; dialogs without an IDE counterpart say they're unavailable.
- The Windows-only parts are proven by `WinFormsDesignerDepthHostTests` on the Windows CI runner and the smoke step `winforms.designerDepth`; the writer, the `.resx` text editing and the shell's side (with a fake host) are tested on every OS.
