# 0073. Windows Forms designer

- **Status:** accepted (M41a, 2026-10-16; the maintainer's standing go-ahead for the milestones, D31); amended for M41b, 2026-10-17 ([below](#m41b-the-rest-of-the-designer)); amended for 0.6, 2026-10-21 (#66, [a copy of the build output](#06-a-copy-of-the-build-output-and-a-reload-after-builds) and [the Toolbox as in the classic IDE](#06-the-toolbox-as-in-the-classic-ide); #78, [overlapping controls drawn in their order](#06-overlapping-controls-drawn-in-their-order); #67, [the context menus and locked controls](#06-the-context-menus-and-locked-controls))
- **Date:** 2026-10-16
- **Deciders:** maintainer
- **Builds on:** [ADR 0071](0071-wpf-xaml-language-service.md) (WinForms and WPF projects), [ADR 0072](0072-wpf-previewer-hosting.md) (the WPF previewer's host, whose shape this follows), [ADR 0033](0033-project-items-templates-and-folder-mode.md) (the Properties window)

## Context

M40 made Windows Forms projects open, build, run and debug. M41 adds what the classic IDE's Windows Forms designer does: a form or user control designed on a surface, with the Toolbox and the Properties window, and `InitializeComponent` written back as the classic IDE writes it. D31 makes it Windows only for now: Windows Forms draws only on Windows, and the other OSes are decided later. M41 is split: M41a (this ADR) is a working designer for common forms; M41b adds snap lines, tab order, the full component tray, smart tags, menu and tool strip editing, localizable forms and images into resources.

Five facts shape it:
- **The classic IDE's designer is proprietary**, but its parts are in dotnet/winforms (MIT) and ship in the Windows Desktop runtime the user already has: `DesignSurface`, `IDesignerHost`, the control designers, `UndoEngine` and the CodeDOM serializers. SharpDevelop 5's designer (MIT) was a whole designer built on them.
- **The code is the document.** A designer file is source code under version control. The classic IDE regenerates all of `InitializeComponent` on every change, which is the main source of noisy diffs; and its loader refuses code it didn't write ("the designer cannot process unknown name…").
- **The .NET SDK has the classic IDE's rules as analyzers.** `WFO3000` and its family flag what the designer can't round-trip in `InitializeComponent` (loops, lambdas…) as errors, so a project rarely has such code; a project that turns them off does.
- **The C# host has the project's compilation** (Roslyn), so it can tell `DockStyle.Fill` (an enum member) from `Color.Red` (a static property) and name every type fully, and it already writes code edits.
- **The IDE's side of a hosted process exists:** `SupervisedProcess` and JSON-RPC (ADR 0004), and the M26a Properties window.

## Decisions

**A CodeDOM-like model, read and written in the C# host.** `codalus/winforms/read` reads a form's `InitializeComponent` (from its code or designer file) into a `DesignerModel`: the class, its base type (what the designer creates, as the classic IDE does), its components (fields created with `new`, locals such as a `ListViewItem`, the root) and the method's statements in order: creations, assignments to a property path (`FlatAppearance.BorderSize`), calls (`Controls.Add` with a `TableLayoutPanel`'s cell or a `SplitContainer`'s `Panel1.Controls.Add`, `Items.AddRange`, `ColumnStyles.Add`, extender calls such as `toolTip1.SetToolTip`), layout calls (`SuspendLayout`, `ResumeLayout`, `PerformLayout`, `ISupportInitialize`'s `BeginInit` and `EndInit`), event hookups (method groups and `new EventHandler(this.M)`), `resources.ApplyResources` and `GetObject`, and the classic IDE's section comments. Values are expression trees: literals, enum members (ored for flags), static members, `new`, static calls, arrays, resources, references to components, `typeof`. Types are named through the compilation (a syntactic fallback names the common ones when the project isn't loaded). Anything else (control flow, lambdas, calls to the class's own methods, names that aren't components, property reads, object initializers) fails with the reason and its line: the designer closes and the file opens as code at that line, with the reason in a notification, as the classic IDE does.

**Writing is the smallest edit, not a regeneration.** `codalus/winforms/edit` takes the designer's changes (`setProperty`, `addComponent`, `removeComponent`, `renameComponent`, `setParent`, `addEvent`, `removeEvent`) and applies each to the designer file's text as the classic IDE would place it, touching nothing else:
- a property: its assignment's value replaced in place; a new one inserted in its component's section where the classic IDE sorts it (properties by name, `Controls` and collections among them, extender properties by their name, events after); a default value's assignment removed, and a section left empty goes with its comment;
- a component: its field after the last component's (after `#endregion` in a form without any), its creation after the last creation (`components = new Container()` first when it's created in it), its section before the next component's (the root's last), its `Controls.Add` first in its parent's (new controls go to the front), its parent's `SuspendLayout` and `ResumeLayout` by the root's when it's the parent's first child, `BeginInit` and `EndInit` for `ISupportInitialize`;
- a removal takes the controls inside and every statement that mentions them (an `AddRange` array loses the item); a rename changes the field, every use, the section comments and `Name`, and through Roslyn's rename its uses in the class's other files; a new event handler is written at the end of the class in the code file with the event's own parameters (`object? sender` when the file has nullable annotations), and an existing one is shown.
The text is rewritten in the file's own style, detected when read: the classic IDE for .NET (no `this.`, types shortened through the file's usings, global usings and namespace, `A.X | A.Y`, method groups) or for .NET Framework (`this.`, full type names, CodeDOM's parenthesized casts and line breaks, `((byte)(0))`, `Color.FromArgb(((int)(((byte)(255)))), …)`, multi-line arrays, `new System.EventHandler(this.M)`), its indentation, line endings and section comment rules. The new text is diffed line by line against the old (`LineDiff`), so the edit the IDE applies is the changed lines. The model after the edit comes back with it.

**Round trips are tested on files the classic IDE wrote.** Writing every statement of a read file again gives the file back byte for byte, in both styles and with CRLF; nothing changed is no edit; each kind of change is checked as the exact lines it adds and removes. These tests run on every OS (Roslyn only).

**The designer host follows the WPF previewer's shape (ADR 0072).** `src/Codalus.WinForms.Designer` (`codalus-winformsdesigner.dll`, `net8.0-windows`, `UseWindowsForms`, framework references only) runs on the designed project's app's own .NET and Windows Forms (`dotnet exec --runtimeconfig App.runtimeconfig.json --depsfile App.deps.json`; a library with no app that references it runs on the host's own runtimeconfig, rolled forward, its output folder searched for references), loads the project's build output (built first when the sources are newer; since 0.6 from a copy of it, [below](#06-a-copy-of-the-build-output-and-a-reload-after-builds)), and runs only for trusted folders. It builds on every OS (`EnableWindowsTargeting`) and ships only in the Windows package (`winformsdesigner/` next to the shell; `CODALUS_WINFORMS_DESIGNER` overrides it). Unlike the previewer it speaks the IDE's own JSON-RPC on stdio (it links `Codalus.Rpc`'s connection and the protocol's source-generated records) under `SupervisedProcess`: a crash restarts it, and the document loads the form again ([protocol](../winforms-designer-protocol.md)).
- **Loading:** a `DesignSurface` loads the root (an instance of the base type, named as the class), the components are created through `IDesignerHost.CreateComponent` (so each gets its designer and is in design mode: a user control shows as at design time), and the model's statements run in order against them, properties through their property descriptors (the designers' shadow properties apply), calls by reflection, `ApplyResources` and `GetObject` through the class's compiled resources. A statement that fails is listed with its line; the rest load.
- **Drawing:** the surface's view lives in a hidden, off-screen window (so controls have handles and lay out), the process is DPI unaware (a pixel is a unit of the code), and the root is drawn with `DrawToBitmap` into a PNG. Every control's bounds and client origin in the frame come with it (a `SplitContainer`'s panels as parts), and the non-visual components. Since 0.6, controls that overlap are drawn again in their order over that first pass ([below](#06-overlapping-controls-drawn-in-their-order)).
- **Changes come back as code:** a create (with the control designer's `InitializeNewComponent`, so a button's `Text` is its name and `UseVisualStyleBackColor` is set, at the front of its parent, in a `TableLayoutPanel`'s cell under the point, with the next tab index; since 0.6 through the type's Toolbox item and the container designer's `CreateToolCore`, [below](#06-the-toolbox-as-in-the-classic-ide)), a property set (from the Properties window's text through the property's type converter, or a value), a reparent and a delete answer with what changed: every component's serializable properties (visible to serialization, not design-only, not extended, `ShouldSerializeValue`, content properties one level down) are compared before and after, so a docking or a resize that moves siblings is written too. Values are serialized as the classic IDE's serializers do: literals, enum members, colors by name or `FromArgb`, components by name, and `InstanceDescriptor`s' constructors and static members (`new Point(12, 9)`, `new Font("Segoe UI", 9F, …)`, `new decimal(new int[] {…})`, `Cursors.Hand`). A value code can't say (an image) is left to the resources.

**Gestures are the shell's; the host gets operations, not mouse messages.** The surface, its adorners (selection rectangles, the primary selection's eight grab handles, the rubber band, the drawn rectangle) and the hit testing are drawn and done in the shell over the frame, from the bounds the host reported, so a drag needs no round trip per mouse move; when a gesture ends, the host is asked for the operation it amounts to (select, move, resize, reparent, create, delete). The designer host's own selection service follows the IDE's selection (a tab page shows when selected).

**Undo is the designer file's text undo, not `UndoEngine`.** Every change is applied to the designer file's text model (the same one an editor of the file uses, kept while the designer is open) as one undoable edit. Undo and redo in the designer are that model's; the designer notices the text changed and loads the form again from it, which is also what happens when the code is changed in the code view, by source control or by another tool. Reasons: the code is the only state, so the surface can't drift from it; one undo stack serves the designer and the code view, local history and source control see ordinary edits; and `UndoEngine` would keep a second history of serialized component state that must then be mapped to text edits both ways. The cost: an undo reloads the form (a few hundred milliseconds for a common form). The designer's own edits don't reload it (the host already shows them).

**The Toolbox and the Properties window.** The Toolbox (`Ctrl+Alt+X`) lists Windows Forms' common controls in the classic IDE's categories (Common Controls, Containers, Menus & Toolbars, Data, Components, Printing, Dialogs) and the project's own components and those of the projects it references (`codalus/winforms/toolbox`: public, or internal in the project, non-abstract, parameterless constructor, a `Component` that isn't a form, not `[ToolboxItem(false)]` or `[DesignTimeVisible(false)]`). A click arms an item for a click or a drag on the surface; an item can be dragged onto it; new components get the classic IDE's names (`button1`). Since 0.6 the armed item is drawn as the selection and a double-click or Enter adds an item at once ([below](#06-the-toolbox-as-in-the-classic-ide)). The M26a Properties window shows the designer's selection while the designer is the last place something was selected: the host's property descriptors (merged for several components, differing values blank), by category or alphabetically, bold when the code sets them, edited as text through the type converter, with choices (enums, `bool`, `Dock`, known colors), flags toggles (`Anchor` and other flags), a color swatch; `(Name)` renames. Its Events view lists the component's events with their handlers: a name typed hooks it, its button (or a double-click on the control, its default event as the classic IDE does) writes the handler and shows it.

**Opening.** A `.cs` file of a Windows Forms project with a `.Designer.cs` that has `InitializeComponent` opens in the designer on Windows (`windowsForms.openInDesigner`, default on); the designer file itself opens as code. View Code (`F7`) and View Designer (`Shift+F7`, which the XAML Previewer keeps in XAML files) switch, as the classic IDE's. The Solution Explorer shows such files with a form icon. A class that isn't a control (a component) opens as code (the component designer stays a gap after M41b).

**What's Windows only (D31).** The designer host, the surface and the Toolbox. Off Windows a form opens as code (the status bar says once why), View Designer says the designer is Windows only and opens the code, and the reader, writer and Toolbox listing (the C# host) still run there, so the code side is tested on every OS.

## Consequences

- The designer needs nothing in the user's project and nothing shipped but our host; it uses the Windows Forms the app runs on, so it designs what the app shows.
- Diffs are what changed: a moved button is one line, a new one its field, creation, section and `Controls.Add`. Code the designer didn't write outside the edited statements stays as it is (even code a full regeneration would reorder).
- Code the classic IDE's designer wouldn't read opens as code, with the reason; the SDK's `WFO3000` analyzers already keep most projects from having it.
- Localizable forms load (their resources applied) but their localizable properties aren't edited: the designer says so (M41b writes them to the `.resx`). Images in resources show and aren't edited. (Superseded by M41b, below.)
- An undo reloads the form from the code.
- The Windows-only code is proven by the Windows CI runner's tests (the designer host on the fixture, end to end with the writer) and the smoke step `winforms.designer`; the reader, writer, Toolbox listing, protocol and the shell's wiring (with a fake designer host) are tested on every OS.

## M41b: the rest of the designer

Amended 2026-10-17 for M41b, which completes M41: snap lines and the Format menu, tab order mode, Dock and Anchor pickers and adorners, the component tray, extender properties, smart tags, menu and tool strip editing, collection editors, localizable forms and images into resources, paste with event hookups, and simple data binding. No new ADR: these extend the decisions above (the code is the document, the smallest edit, the shell's gestures, the text's undo).

**The host answers with the surface's difference, not per operation.** Before and after each operation the designer host captures what the code says about the whole surface: every component's serializable properties (and values only the resources can hold, such as images), the extender properties its providers give it (`ToolTip` on `toolTip1`, through `ExtenderProvidedPropertyAttribute`), its data bindings, the components themselves, every control's parent and place among its siblings, and every collection the designer edits with the locals it holds. The answer is the difference: changed properties, created components (`added`), moved controls, parents whose controls' order changed (`reordered`), collections (their items as the code writes them, with new locals), removed components and locals, and a localizable form's resources. So whatever runs in the host (a smart tag's task, a designer's `InitializeNewComponent`, a collection edit that creates or destroys items, a tool strip's standard items) is written in full without the IDE knowing what it did, as the classic IDE's serializers would see it.

**Collections are a table, written as the classic IDE writes each.** `DesignerCollections` (in the protocol, shared by both hosts) names each collection the designer edits, its kind and its method: values (`ListBox`, `ComboBox` and `DomainUpDown` `Items`, `TableLayoutPanel` `ColumnStyles` and `RowStyles` with `Add`), components (tool strips' `Items` and drop-downs' `DropDownItems`, `ListView` `Columns`, `DataGridView` `Columns` with `AddRange`; a `TabControl`'s pages as its `Controls.Add`), locals (`ListView` `Items`: `ListViewItem` locals) and an `ImageList`'s `Images` (`SetKeyName`, the bitmaps in its `ImageStream`). The writer replaces the collection's statements where they were (a strip's first items bring its layout calls) and declares locals after the creations. Editors that would be Windows Forms dialogs are the IDE's own (an Avalonia panel over the surface: text a line, members with their properties and types, styles, image keys), and so are smart tag tasks that open a dialog: a task whose name ends with "…" opens the matching collection's editor or the image import, or says it isn't available (a grid's Add Column…, data source wizards).

**Smart tags run in the host.** The IDE asks for a component's designer actions (`DesignerActionService`'s lists, which include the verbs; a designer's own lists and verbs when there's no service), shows them in its own popup (headers, texts, properties with their editors, methods), and asks the host to set a property or run a method; the difference writes what it did.

**Resources are the `.resx` files' text, edited like the code.** The C# host reads and writes a form's `.resx` files (the default `Form.resx` and each culture's `Form.<culture>.resx`) as text (`ResxText`): only the entries that change are touched, placed as the classic IDE's serializer orders them (by component, metadata first, the properties alphabetically, the `>>` records last, new components alphabetically with `$this` last), the file's line endings and its assembly aliases kept. The writer's `setResource` sets or removes a key in a culture's file (creating it when needed), renames and removals reach every culture's keys, and the `resources` variable (`ComponentResourceManager`) comes and goes with its uses. Changed files come back in the edit's workspace edit, so the shell applies them to text models it holds with the designer file's: saved together, and undone together (the designer's undo steps record every model a change touched; an undo with a model changed elsewhere since falls back to the designer file's own undo). The designer host reads the resources from the shell's texts too (a `ComponentResourceManager` over them, falling back from a culture to its parents), so an unsaved `.resx` edit shows at once, and the C# host gets them with each read and edit (`resourceFiles`), since they aren't open documents there.

**Localizable forms work as the classic IDE's.** The root's `Localizable` (a property the host adds, as the classic IDE's designer does) moves every localizable property between the code and the default resources (each component's section starts with `ApplyResources`, the `>>` records of its controls are written). The root's `Language` is the IDE's: the form loads with that culture's resources applied, and a change of a localizable property goes to that culture's file, only where it differs from the value it would inherit (equal: the key goes). Moves and z-order changes update the default resources' `Parent` and `ZOrder` records. Images (and other values code can't say) go to the default `.resx` read with `GetObject`, or, imported "into the project", to the `Resources` folder and `Properties/Resources.resx` (a `ResXFileRef`), read as `Properties.Resources.Name` after the ResX generator runs.

**Snap lines are the shell's, from the host's data.** Each control's view carries its margin, its container's padding (a form's empty padding is the designer's 9, so with a control's margin of 3 the line is at 12, as in the classic IDE) and its text baseline (the control designer's `SnapLines`), and the shell snaps a moving or resized control within 8 pixels to its siblings' edges, baselines and margins and its container's padding, drawing the lines that hold (Alt turns them off). Alignment, sizing, spacing and centering (the Format menu) are computed in the shell from the primary selection and written as `Location` and `Size` changes; Bring to Front and Send to Back are the host's `SetChildIndex`, written as the order of the parent's `Controls.Add` (and `ZOrder` records in a localizable form).

**The component tray's order is the classic IDE's `TrayLocation`.** The tray shows components that are design-time visible and the tool strips (as the classic IDE does), ordered by the `TrayLocation` metadata in the form's `.resx`; dragging or Line Up Icons writes that metadata, so both IDEs agree.

**Paste keeps event hookups within the same form only.** A pasted component brings its properties, its controls, its collections and locals, its extender properties and its bindings; its event hookups come with it when pasted into the form it was copied from (the handlers are there), and are left out in another form, where they would name methods that don't exist (the classic IDE keeps them and leaves the code uncompilable).

**Data binding is simple binding only.** `(DataBindings)` in the Properties window binds a control's bindable properties to a member of one of the form's binding sources (a `BindingSource`, a list source; its members from the data source's type, `typeof(Customer)`), written as `DataBindings.Add(new Binding("Text", customerBindingSource, "Name", true))`. The classic IDE's Data Sources window and its data source wizards stay a gap: set a binding source's `DataSource` in the Properties window or the code.

**The WPF design surface is deferred.** M41's optional WPF design surface (selection, dragging and the Properties window over dependency properties, on M40b's previewer) isn't built: the WPF XAML Previewer already shows the window and selects both ways, the XAML editor is where WPF is designed in practice, and a surface that writes XAML well (minimal edits, as for `InitializeComponent`) is a milestone of its own. It stays a gap, to be proposed separately. The component designer (designing a class that is a component but not a control, its tray only) stays a gap too.

**Consequences (M41b).**
- A form's code and resources change together as minimal edits, saved and undone together; a localizable form's diffs are the changed `.resx` entries.
- The designer host never needs to tell the IDE what a designer did: the state difference covers designers' side effects, at the cost of capturing the surface twice per operation (a few milliseconds for a common form).
- What Windows Forms shows as dialogs (collection editors, the image selector, smart tag dialogs) is the IDE's own UI, so they theme and localize like the rest; dialogs without an IDE counterpart say they're unavailable.
- The Windows-only parts are proven by `WinFormsDesignerDepthHostTests` on the Windows CI runner and the smoke step `winforms.designerDepth`; the writer, the `.resx` text editing and the shell's side (with a fake host) are tested on every OS.

## 0.6: a copy of the build output and a reload after builds

Amended 2026-10-21 (#66). The host loaded the app's build output in place, so while a form was open its assemblies (and the pdb a printed stack trace had read) stayed open, and the next build failed with MSB3027 until the designer closed. The classic IDE designs on a shadow copy; so does this one now.

**The shell copies before the host starts.** The host is started on the app's runtimeconfig and deps file, and with `--depsfile` the app's own assemblies (the app, its project references, its app-local packages and satellites) are on the runtime's trusted list from the deps file's folder: the default load context binds them before any resolving handler runs, so a copy made inside the host couldn't redirect those loads. `WinFormsDesignerProcess.StartAsync(target)` therefore copies first (`BuildOutputShadowCopy`, in `Codalus.Workbench.Previewer` so the previewers can reuse it), starts the host on the copy's runtimeconfig, deps file and folder, and maps `designer/load`'s `projectAssembly` and `searchFolders` to the copy; the document keeps the real paths. The copy is `%TEMP%/codalus-winformsdesigner/<pid>-<id>/<n>/`, one numbered folder per source folder (the app's first, then a designed library's when it's elsewhere), without `publish/` and `app.publish/` folders at any depth and without another build's output inside it (a folder with its own deps or runtimeconfig file, such as the `win-x64/` a `dotnet publish -r win-x64` leaves next to the designer's output in a project with no RuntimeIdentifier): the host never loads from them. It goes when the host ends (read-only files made writable first, retried while the process lets go) or when its start fails. The IDE's exit stops the open designers' hosts too: closing the window doesn't close the documents (the session reopens them), so without that every exit left a copy, and the exit's own budget (it waits three seconds) can still cut a deletion short. A sweep deletes copies whose process has ended, and this process's that a failed deletion left: on Windows once at startup (in the background), and at each copy.

**Two classes of files.** What the host needs must copy, tried again while it's held (ten tries a second apart, MSBuild's Copy defaults: an antivirus scan right after the build, a build's last writes), or the designer doesn't start with the file and the reason: deps and runtimeconfig files, top-level assemblies and executables, `runtimes/`, and satellite assemblies in a folder named like a culture (by its form: the shell has no culture data). Everything else (pdbs, XML docs, config and content files, databases, logs) is copied when it can be: a file another process holds (a LocalDB `.mdf` that `sqlservr.exe` keeps attached, a running instance's SQLite database or log) is skipped and logged, never fatal.

**What makes the copy outdated.** The copy records, before copying, the length and time of the app's and the designed project's assemblies, their deps and runtimeconfig files, and every assembly (and satellite) their deps files list as runtime or resource assets. A watched file with another length or time means a build replaced it; a deleted one doesn't count (a Clean leaves the designer running until the next build). Content the app writes into its output and other projects' assemblies in a shared output folder aren't watched, so they don't restart the designer. Without a deps file, every top-level assembly counts, and a new one too.

**After a build, the form loads on the new build once.** When a build finishes, whatever its result (a failed or canceled build may have replaced the app's or a referenced library's assembly before it stopped), the active designer checks its host's copy; another designer checks when it becomes active (which also catches builds made outside the IDE). The check and the restart run under the document's gate, so a build's end and an activation in the same turn start one host: the second check sees the new host's copy. While the host starts again, the surface takes no gestures (the wait cursor shows); changes from the Properties window (and the Toolbox) wait on the gate and apply on the new host, never dropped and never sent to the old one; a change with no host after a failed start says so. Unsaved designer changes survive the restart (the form is read from the editor's text) and the selection is kept. A designer that starts while a build runs waits for it before checking whether the output needs a build, instead of failing with "A build is already running."; a build that starts just before the designer's own makes it wait and check again.

**A designer without a host starts again.** A start or restart can fail (the designer's own build fails, a file the host needs stays held, the host doesn't get ready), and the designer then has no host to check after a build. It records the number of the last build that had ended and its target's assemblies' lengths and times, and starts again after the next successful build that ends after the failure (the designer's own build ended before it, so a host that never gets ready isn't retried on its own), or when it becomes active and those assemblies changed (a build in another tab or outside the IDE); not on every activation, which would build again a project that doesn't build. Load the form again on the toolbar starts it at once. Closing the designer (or the IDE's exit) cancels its start: the wait for a running build, the designer's own build, the copy and the host's launch, so a closed designer never builds the project or starts a host.

**Consequences (0.6).**
- Builds work with forms open, as in the classic IDE. Each host start copies the output folder: seconds for a large or self-contained output (logged with its size, time and skipped files), and every build that changes the app's assemblies restarts the active designer's host. Hard-linking unchanged files is deferred (TODO in `BuildOutputShadowCopy`).
- At design time, the app's types see the copy's paths: `Assembly.Location`, `AppContext.BaseDirectory` and the working directory point into the temp copy (the classic IDE's shadow copy has the same effect); content files next to the assembly are there when they could be copied.
- The Avalonia previewer (`PreviewerSession`) and the WPF previewer (`WpfDesigner`) still load the output in place and lock it the same way; they could start on a `BuildOutputShadowCopy` (deferred).
- Proven on every OS by `BuildOutputShadowCopyTests` (the copy's classes, mapping, outdated set, sweep and read-only files, a held file the host needs tried again, publish folders and other builds' outputs left out), `WinFormsDesignerServiceTests` (the launch names only the copy, `designer/load` gets the copy's paths, the copy goes with the host and after a failed start or launch, the wait for a running build, the output stamp) and `WinFormsDesignerToolboxShellTests`, whose builds run through the shell's own build service with a stand-in for the build host (a restart after a build exactly once, also after a canceled one, deferred to activation, a change made during a restart applied on the new host, a designer opened during a build; a failed start or restart started again after a build or on activation, not after a failed or canceled build; a designer closed while it waits for a build, opening or starting again, builds and starts nothing; the exit stops the hosts); on Windows by `WinFormsDesignerBuildHostTests` (a real build while the form is loaded, with no MSB3027, and the assembly and pdb free) and the smoke step `winforms.toolboxAndBuild` (Build Project in the shipped app with a form open and an unsaved change, then the form on the new build).

## 0.6: the Toolbox as in the classic IDE

Amended 2026-10-21 (#66), with the copy above. Dragging from the Toolbox didn't start a drag, there was no double-click or keyboard add, and the shell's creation skipped what the classic IDE's Toolbox does, so a label from the Toolbox didn't size itself to its text and a control added to a tab control went to the form.

**The drag starts from the view, not the item.** Each Toolbox item is a `Button`, which handles the left press itself, so a handler on the item never saw it. The press, the move and the release are watched as they tunnel through `ToolboxView` (as the component tray's buttons already were); a move of 4 px with the button down and the pointer still captured by the item starts the drag (`StartDrag`, which headless tests replace: Avalonia.Headless has no drag source). The release after a drag and the second click of a double-click don't toggle the item.

**The armed item is the selection; the list never moves.** Arming an item showed a hint above the list, which moved every item down by a line or two: a double-click's second press landed on another element, and Avalonia raises `DoubleTapped` only when both presses have the same source. The armed item is now drawn as the selection (`Shell.Selection`, `Shell.Selection.Inactive` when the Toolbox hasn't the focus), as the classic IDE highlights its selected tool, and the hint is the designer's status line (a polite live region, so screen readers still hear it). The design came first: [`docs/design/controls/Toolbox.dc.html`](../design/controls.md#the-design-files).

**Double-click and Enter add at once.** As the classic IDE's tool pick, the item goes into the selection's container (the primary selection if it's a control, else the first selected control, walked up to the first control whose designer takes controls, with no CanParent filter; else the form), at the container's default place (its top-left corner when it's selected itself, else a grid step below and right of the selected control, back to the corner when that runs off it), selected; then the designer is activated with its surface focused, so the arrow keys, Delete and F4 act on the new control. Space and a click still arm an item. Nothing is added in tab order mode. During a restart the add waits on the document's gate and applies on the new host.

**One creation path in the host, the classic one.** Every gesture (a drop, a drawn rectangle, a double-click, Enter) creates through the type's own Toolbox item (its `[ToolboxItem]`'s; Label's and LinkLabel's `AutoSizeToolboxItem`, which .NET's Windows Forms names but doesn't ship, is the host's own) and the container designer's `CreateToolCore`, called by reflection with virtual dispatch: the container may route the tool (`TabControlDesigner` to its selected page, `SplitContainerDesigner` to its panel), and its drag and drop handler creates the component with the defaults the designers act on: `Parent` (so a split container or tool strip container added to a container whose other controls are all docked fills it, and `ToolStripDesigner` makes the first menu strip the form's `MainMenuStrip`), `Location` in screen coordinates for a drop (as the drag and drop handler takes it), and `Size` for a drawn rectangle. The component takes the IDE's name through the session's name service (once, for its type); a table still gets the cell under the drop point. `designer/create` gained `atDefaultLocation` and `selected`; `x` and `y` are then the form's client origin, so a host that doesn't know the field puts the control at the form's corner instead of a negative place ([protocol](../winforms-designer-protocol.md)). The session also has an `IUIService` (what a designer would show as an error or a message is the change's `error` and the output's line, never a modal message box in the hidden host; a dialog it would open is refused) and an `ITypeResolutionService` (types found as the form's code finds them, deterministically).

**Drops.** The surface takes a Toolbox item only on the form (outside it the cursor says no drop), not in tab order mode and not while the host starts again; a drop focuses the surface. The component tray takes Toolbox drops of components that aren't controls (a Timer), as the classic tray does; a control dropped there is refused (the classic tray's handling of controls is unverified, a manual check).

**Consequences (Toolbox).**
- The code a gesture writes changes from 0.5's, toward the classic IDE's: a label from the Toolbox writes `AutoSize = true`, a split container fills an empty container, the first menu strip writes `MainMenuStrip`, and a control added to a tab control goes into its selected page. Enter on a Toolbox item adds it instead of arming it, and the hint line is gone from the Toolbox.
- `CreateToolCore` is a protected member reached by reflection (stable since .NET Framework 2.0, on the app's own Windows Forms); if it's missing, a create fails with a clear error. Designers that now get a `Parent` may ask for services the host lacks; the Windows host tests cover the common ones.
- Deferred, with a `TODO(issue)` and a row under the roadmap's Deferred work: the tool's outline and snap lines while an item is dragged over the form (`WinFormsDesignerView.cs`), and a control dropped on a `FlowLayoutPanel` inserted at the point under the cursor (`DesignerSession.cs`).
- Proven on every OS by `WinFormsDesignerToolboxShellTests` (real pointer and key input: the drag, the armed row with no item moving and the status line, drops refused in tab order mode and off the form, a Timer on the tray, a double-click into the selected control's container, Enter and Space, an add during a restart) and the protocol round trip in `WinFormsDesignerServiceTests`; on Windows by `WinFormsDesignerHostTests.Toolbox_items_are_created_as_the_classic_ide_creates_them` (the default place and the cascade from the render, a panel's container, AutoSize, the selected tab page, AutoDock, `MainMenuStrip`, the tray, a table's cell; the existing drop expectations hold) and the smoke step `winforms.toolboxAndBuild` (Enter and a drop through the real host). A real mouse drag from the Toolbox in the Windows package, and the placement compared once with the classic IDE, are manual checks.

## 0.6: overlapping controls drawn in their order

Amended 2026-10-21 (#78). `Control.DrawToBitmap` draws a container's controls in reverse order (its documented limitation), so of two overlapping siblings the front one came out behind: a button dropped on a user control was hidden by it (M34h's open "designer picture" item), and Send to Back seemed to bring a control to the front.

**The first pass, then the overlaps again.** After the root's `DrawToBitmap`, `DesignerSession.Restack` walks each container's visible controls from the back (the last in `Controls`) to the front; each one that overlaps a sibling, with some of it inside its parent's client area (within its ancestors'), is drawn again by its own `DrawToBitmap` and copied pixel for pixel (`CompositingMode.SourceCopy`, no scaling) inside that area, and each control with controls of its own is looked into right after it, before the siblings in front of it. So overlaps are fixed at every depth (the form's, a group box's, a panel's, a tab page's, a split container panel's controls), placed as the bounds the frame reports are. Which controls are drawn again, and in what order, is geometry over their bounds (`Restacking.BackToFront`, controls that only touch don't overlap), tested on every OS. A control that can't be drawn alone (GDI+ refuses a bitmap that large, or runs out of memory for it) keeps the first pass's pixels, out of its order, and the host logs it: the frame is never lost to the redraw. The frame says how many controls were drawn again (`restacked`), so a form without overlaps is provably the first pass alone.

**Rejected.** `PrintWindow` with `PW_RENDERFULLCONTENT`, which needs the window composed on screen (the view is off screen); a test-only switch that turns the redraw off (the count gives the same guarantee without a path only tests take).

**Consequences (overlaps).**
- A frame with overlaps costs one more `DrawToBitmap` per overlapping control (a bitmap of its size); forms without overlaps cost nothing more.
- A control whose own `WM_PRINT` differs from what its parent's pass drew for it shows its own drawing; a transparent control shows its parent, not the siblings behind it, as at run time.
- Tested on every OS by `WinFormsDesignerRestackTests` (the order and which controls are drawn again); the picture is to be proven on Windows by `WinFormsDesignerHostTests` (two overlap tests, committed before the fix to be run red, and `Forms_without_overlapping_controls_are_drawn_once`) and the `winforms.designer` smoke step, which have not run yet: until they have, M34h's item stays open with its `TODO(issue)`.

## 0.6: the context menus and locked controls

Amended 2026-10-21 (#67, part 2), as the maintainer approved its design as drawn (D40: `WinFormsDesignerMenus.dc.html` and its twelve questions in the controls design notes). Part 1, Type Here only on tool strips, came first: a strip is decided by the collection table (`DesignerCollections.IsStripItems`: `Items` of tool strip items), not by type names. Part 2 makes the surface's and the tray's menus, Edit's commands, Select All, Paste and Lock Controls behave as the classic IDE's command set (dotnet/winforms' `ControlCommandSet`, `CommandSet` and `MenuCommandService`, read for their behavior; none of their code is copied).

**The context menus come from the menu registry.** The surface's menu (`winforms/surface`) is the classic one: the component's verbs and Show Smart Tag in one group (the one entry the classic menu doesn't have: the smart tag's property tasks have no menu form), View Code, Bring to Front, Send to Back, Align to Grid, Lock Controls, Select '<parent>', Cut, Copy, Paste, Delete, Properties. Align, Make Same Size and Tab Order are in Format and View only, as there. A tray item's menu (`winforms/tray`) has View Code, the clipboard, Rename (F2, kept as a difference) with Line Up Icons, and Properties; the tray's background (`winforms/trayBackground`) Paste, then Line Up Icons. A tool strip item gets the surface's menu until the classic item menu (Convert To, Insert, Set Image…, Edit DropDownItems…) is built. A right-click selects a menu row or a strip's item first, then the control under it; Shift+F10 and the Menu key open the menu under the selection. A rule's new `Checked` clause makes a check entry, and a check entry has no icon (the check takes the icon column), so Lock Controls has none in a menu; `MenuBuilder.Context` takes a title of the moment ("Select 'shippingGroupBox'").

**Designer-bound commands with the classic enablement.** The menus' clipboard entries are commands of their own (`winforms.cut`, `copy`, `paste`, `delete`, `selectParent`, `lineUpIcons`, `lockControls`) on the designer's selection, not on the keyboard focus, so a tray item's menu can't act on the text box that last had the focus. The active designer publishes eleven context keys after every change of its selection, its surface or the clipboard (cleared when another kind of document becomes active); as in `CommandSet`, a selection with the form in it counts as empty. Copy needs something besides the form and a split container's panels, Delete everything selected to be components, Cut both, Paste a copy. Format: Lefts…Bottoms and Make Same Size two controls or more with a primary (`OnStatusMultiSelectPrimary`), to Grid, Size to Grid and Center in Form any control, spacing two or more with one parent, Order controls when the form has two components or more (`OnStatusZOrder`), Lock Controls controls only (`OnStatusLockControls`).

**Verbs as `EnsureVerbs` lists them.** `designer/actions` also answers `verbs`: none for an inherited read-only component; the action methods marked `IncludeAsDesignerVerb`, then the designer's visible `Verbs` (a disabled one listed as unavailable and grayed); of two with the same text without its mnemonic, ignoring case, the later stays. A verb keeps the designer's text, mnemonic included (`&Insert Standard Items`): the menu shows the mnemonic as the entry's access key and the smart tag panel drops it, as the classic labels do (`DesignerMnemonics`). An image list's Choose images opens the IDE's Images editor although its text has no "..." (the host's UI service shows no dialog, so the framework's editor did nothing). Fetching them only when the menu opens would leave the most common case, a right-click on an unselected control, without them: the selection changes on that same press. So the shell fetches them as the selection settles (150 ms) and at once on a right press, keeps them per component and surface (a change can enable one, Remove Tab once there's a tab page), and gives an answer still on its way 300 ms when the menu opens; an answer for another selection is never shown. With two or more components selected there are none, as there.

**Edit's commands, Select All and Paste.** Edit → Undo, Redo, Cut, Copy, Paste and Select All act on a focused designer's surface or tray (`EditTarget`; a text box inside it, Type Here or a tray rename, keeps its text; its collection editor and smart tag panel aren't the components), and on the active designer when nothing is focused. Select All (and Ctrl+A) takes every component but the form, the tray's and tool strip items included, as `OnMenuSelectAll`; a split container's panels aren't components. A drag or an arrow key moves a selected control inside a selected container only with its container (Shift+arrow still resizes each). Paste goes into the nearest container of the primary selection (`OnMenuPaste`'s nearest drag client): a selected container, else a container it's in, a split container's panel included (its owner and `ParentPath`), else the form. Esc and Select '…' select the primary selection's parent: a tool strip item's owner, a control's container (`notesSplit.Panel1` for a control in a split container's panel).

**Lock Controls is the control designers' `Locked`.** `ControlDesigner.PreFilterProperties` adds a bool, design-only `Locked`; tray components, a context menu strip (`ToolStripDropDownDesigner` is a component designer), tool strip items and parts have none, so the protocol's `locked` is null for them and the host skips an edit of it, as `OnMenuLockControls` does (`if (prop is null || prop.IsReadOnly) continue`): before, one batch over a form with a context menu strip would have failed. Lock Controls is checked while the form or any of its own controls (the root designer's associated components) is locked, and choosing it sets every lockable component to the opposite, in one host change, so one undo step. The host keeps it as the classic IDE does, in the default `.resx`: the state difference writes `name.Locked` (`$this.Locked`) metadata with `ResourceValues`' type name (False removes it), never code (the capture skips design-only properties), whatever language is shown; a load sets it from that metadata, as with `TrayLocation` and `$this.Localizable` (only Locked is applied: old forms' grid settings stay ignored), read as XML (`DesignerResx.Metadata`): a `ResXResourceReader` deserializes every data value to list the metadata, and one it can't (a binary-formatted `TreeNode` on .NET 9 and later) would fail the load instead of one statement. A form without a default `.resx` gets the empty one (`DesignerResx.Empty`, the C# host's template, now in the protocol) written in the designer file's line endings and held before the write, so the metadata edit changes a held model and undoes with it; a model acquired after the C# host had created the file would have no undo history.

**On the surface.** A locked control isn't moved by a drag or the arrow keys and has no grab handles (the form's included); its lock is a 12 px tile centered on the frame's top-left corner, where the handle it replaces would be, in the panel color with an accent edge, with Fluent's filled lock at 10 px in the palette's yellow (a bare yellow glyph wouldn't show on the form's light colors in the dark themes); its smart tag glyph stays. Align and Make Same Size keep a locked primary as the reference (`OnMenuAlignByPrimary`, `OnMenuSizingCommand`); every Format command moves or sizes unlocked controls only, and stays enabled when everything selected is locked; Bring to Front, Send to Back and the clipboard act on locked controls. The Properties window still sets a locked control's `Location` and `Size`.

**Deliberate differences.** Align to Grid and Size to Grid stay enabled: the classic IDE enables them only in its SnapToGrid layout mode, and Codalus has snap lines and an 8 px grid without that mode. Show Smart Tag in the menu, Rename in the tray's, and Lock Controls left out of the tray's menu. The clipboard stays in-process (no OS clipboard), and multi-select z-order is one undo step per control.

**Consequences (menus).**
- Format entries that were always enabled are now grayed when the selection doesn't fit (a single control grays Align Lefts; a tray component in the selection grays what is for controls), and Select All takes tray components, so Ctrl+A then Delete deletes them too.
- Every designer change also asks the host for the selection's verbs (one `designer/actions` per settled single selection or render); if that shows in the host's latency, the fetch can move to the right press alone.
- Deferred, with a `TODO(issue)` and rows under the roadmap's Deferred work: a tool strip item's classic menu; icons for Make Same Size, spacing and Center in Form; the Dock text drawn over a docked strip's items and under 4.5:1 on the form's light colors in some themes (D40, question 12); a new `.resx`'s project item in a .NET Framework (non-SDK) project; the Properties window for a split container's panel (the host's `Target` doesn't resolve part names, with #68); the OS clipboard; one undo step for a multi-selection's z-order; a new culture's `.resx` undone with the designer's step.
- Proven on every OS by `WinFormsDesignerMenuShellTests` (the red-first Edit, Select All and paste fact; the menus' entries, labels, icons and enablement; the entries acting on the designer; Lock Controls' toggle, metadata and undo; a locked primary as Format's reference; a form without a `.resx`), the protocol round trip in `WinFormsDesignerServiceTests`, `MenuRegistryTests`, the command sweep and `WinFormsDesignerCodeTests` (the metadata's placement, removal and rename; a precreated `.resx` written as one the C# host creates); to be proven on Windows by `WinFormsDesignerDepthHostTests` (`Locked_is_the_resx_metadata_both_ways`, `Context_menu_verbs_are_the_classic_ides`, Locked in the snap-data test) and the smoke step `winforms.designerMenus`, which have not run yet.

## 0.6: the Properties window as the classic IDE's

Amended 2026-10-22 (#68), as the maintainer approved its design as drawn (D41: `PropertiesWindow.dc.html` and its twenty questions in the controls design notes). M41a's grid listed a component's properties flat, each edited as text, so a font was typed as `Segoe UI, 9pt, style=Bold`, a color as numbers, and a collection or an image behind buttons of its own. The Properties window now works as the classic IDE's property grid (dotnet/winforms' `PropertyGrid`, `GridEntry` and the `System.Drawing.Design` editors, read for their behavior; none of their code is copied).

**Parts described eagerly, two levels deep (D41 question 1).** The host describes a property's parts from its `TypeConverter.GetProperties`, with a real type descriptor context (`DesignerTypeDescriptorContext`: the instance, the property's descriptor, the design surface's services and container), in the converter's order and two levels deep, with the properties (Font's nine parts, Padding's five, FlatAppearance's colors and border); a collection, a string, a null value or a type already on the way down has none. One request answers the whole grid, so expanding a row costs nothing; a level deeper would need a request per expansion (deferred). Several selected components merge as the grid merges them (`DesignerPropertyMerge` in the linked protocol file): the properties they share, a value they differ in mixed (blank), parts merged the same way.

**One assignment of the whole value.** A part is set by a dotted path (`Font.Bold`): converted with its own converter, then each parent is built again through its converter's `CreateInstance` from every part's current value, with the parent's context (so `PaddingConverter` tells an `All` edit from a side's), up to the component's property, which is set once; a parent that is a reference type (`FlatAppearance`) takes the part itself. So the code gets `notesTextBox.Font = new Font("Segoe UI", 9F, FontStyle.Bold | FontStyle.Italic, GraphicsUnit.Point, 0);`, one undo step, and the parts not edited (GdiCharSet, Unit) are kept. The edits of one request apply in order as one change, which the font editor's OK uses for its parts, all or none: each property's value (or that the code doesn't set it, so an ambient value stays ambient) is kept before its edit, and when a later edit fails the earlier ones are put back. A converter's or a setter's refusal is the request's `error` with its own message, and nothing is set. A null value is sent as its converter writes it, as its standard values are (`(none)` for an unset component reference).

**Editors from the `UITypeEditor`.** A property's editor kind comes from its `UITypeEditor`'s type and base types, matched by full name in the linked protocol file (`DesignerEditors.FromEditorType`), after `bool`, `AnchorStyles` and `DockStyle` and before flags and enums, so `ShortcutKeys` (a flags `Keys`) gets the shortcut keys editor and `TextAlign` (a `ContentAlignment`) the alignment picker: colors, fonts, content alignment, multi-line strings, string arrays and collections, shortcut keys, dates, images and the collections the IDE edits. Standard values, read with the context (so AcceptButton lists the form's buttons and `(none)`), make a choice editor; `choicesEditable` marks a list that isn't exclusive (Cursor); Font's Name is an exclusive list (`FontNameConverter`), typed in the font editor's Font box. Any other modal editor is one of Windows Forms' own dialogs, which the host can't show (its UI service shows none): the cell takes text when the converter reads it, with a description that says so, and is read-only otherwise (D41 question 8). `canReset` is `CanResetValue`, for Reset.

**The IDE's own editors.** Drop-downs under the value cell (one control per kind, built the first time it opens): a choice list (cursors with the shell's own drawings of Windows' cursors), flags, Dock and Anchor, colors in Custom, Web and System tabs with Define Color (D41 question 18), the alignment grid, multi-line text (CRLF, as the classic editor writes it), shortcut keys and a month calendar (D41 question 20). Modal editors are panels over the designer surface in the in-window dialog's frame (D41 question 2), placed as the collection editor is: the font editor (only the changed parts sent, in one request), the String Collection Editor for string arrays, and Select Resource for images (a local resource imported into the form's `.resx`, or an image of the project's `Properties/Resources.resx`, referenced or imported); while one is open, the Properties window and the collection editor's grid take no input and read the values again when it closes. The collection editor's item properties use the same grid.

**One grid for every source.** `PropertyGridViewModel` and `PropertyGridView` (one virtualized list of rows, flattened from the categories and expanded rows; one editor control per row; refreshed in place by each row's path, so an edit doesn't rebuild the grid or lose the selection, the expanded rows or the collapsed categories) are the Properties window's for a designer, a file, a project or the solution, and the collection editor's. Categorized and Alphabetical are for every source and sort as the classic IDE does (ordinal, ignoring case, so `(Name)` leads); the toolbar is in its order; Property Pages is enabled only for a project (Project Properties) and the solution (Configuration Manager) (D41 questions 4, 7 and 15). The shell nests the host's flat data binding rows under one `(DataBindings)` row in Data (D41 question 6); `(ApplicationSettings)` and `(Advanced)` are left out. The component selector replaces the title for a designer (D41 question 5). An invalid value opens the in-window dialog with the converter's message, OK going back to the typed text and Cancel putting the old value back (D41 question 14). After a reload of the code (an undo, a typed change), the grid reads the values again.

**Rejected.** A request per expansion (deferred for deeper levels); Windows Forms' own `PropertyGrid` drawn by the host (the shell's theme, keyboard and accessibility would stop at its picture); a "…" that only says an editor is unavailable; one dialog over the whole window for the modal editors.

**Consequences (Properties window).**
- `designer/properties` answers grow with the parts (a font's nine, two levels), and a font family list up to 2000 names; the host builds them for every selection change.
- A part's edit is one assignment of the whole value, never a statement of the part: a value whose converter has no `CreateInstance` and isn't a reference type has read-only parts.
- Deferred, with a `TODO(issue)` and rows under the roadmap's Deferred work: Modifiers, GenerateMember and Locked in the grid (Design shows `(Name)` only) and the events of a multi-selection (Events grayed with two components) (D41 question 9); the Events drop-down of the code's compatible methods; `(ApplicationSettings)` and `(Advanced)` bindings; component editors (Property Pages on a control); a data grid view's cell style builder; parts deeper than two levels; a search box; the description pane's size, the name column's split and the sort mode kept between sessions.
- Proven on every OS by `PropertyGridTests`, `PropertyGridViewTests`, `WinFormsPropertiesShellTests` (the fake host with the real host's shapes, through the real build and C# hosts, so the code is the real writer's), the protocol tests (`WinFormsDesignerPropertiesProtocolTests`, the service round trip), `WinFormsDesignerCodeTests` (`AutoCompleteCustomSource`), the designer's other shell tests and the theme inspection in `PolishTests`; to be proven on Windows by `WinFormsDesignerPropertiesHostTests` and the smoke step `winforms.properties` (which also confirms the real host's code strings for Font, Padding and Lines), which have not run yet.
