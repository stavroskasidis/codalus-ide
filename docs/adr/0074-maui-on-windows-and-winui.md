# 0074. MAUI on Windows and WinUI 3

- **Status:** accepted (M44, 2026-10-16; the maintainer's standing go-ahead for the milestones, D31)
- **Date:** 2026-10-16
- **Deciders:** maintainer
- **Amends:** [ADR 0064](0064-maui-devices-and-mobile-runs.md) (MAUI's Windows target was out of scope), [ADR 0071](0071-wpf-xaml-language-service.md) (the XAML dialects)

## Context

D31 moved the Windows desktop phase into scope as Windows-only features, the other OSes decided later; M44 is .NET MAUI's Windows target and WinUI 3 apps (the Windows App SDK). Facts found at plan time (Windows App SDK 1.8, the version MAUI 10.0.110 references):
- **The packages restore on every OS** with `EnableWindowsTargeting` (ADR 0071): `Microsoft.WindowsAppSDK` and its component packages, the Windows SDK projection (`Microsoft.Windows.SDK.NET.Ref`). WinUI's reference assembly (`Microsoft.WinUI.dll`) is a C#/WinRT projection: dependency properties are static *properties*, attached properties have static `GetXxx`/`SetXxx`, `[ContentProperty(Name = "…")]` is a field, and there is no `[XmlnsDefinition]`.
- **WinUI's XAML compiler is a Windows program.** On `dotnet` MSBuild it runs `XamlCompiler.exe` (`net472`); its design-time pass (`DesignTimeMarkupCompilation`, added to `CoreCompileDependsOn` when `BuildingInsideVisualStudio`) fails on Linux and macOS and fails the whole design-time build with it. Its in-process task doesn't load on .NET either. So off Windows a WinUI project builds nowhere, but it can still load.
- **Packaging** (`Microsoft.Windows.SDK.BuildTools.MSIX`): `WindowsPackageType` is `MSIX` when the project has a `Package.appxmanifest` and doesn't set it, else `None`; a packaged build writes `AppxManifest.xml` next to its output (`FinalAppxManifestName`), and that output is a loose layout Windows can register in Developer Mode (`Add-AppxPackage -Register`). A packaged app gets its identity only from an activation: it can't be started as a plain process.
- **WinUI apps run on CoreCLR**, so netcoredbg debugs them, unlike MAUI's Mono targets. Unpackaged apps (`WindowsPackageType=None`) start like any program; the Windows App SDK runtime comes from an installed framework package or with the app (`WindowsAppSDKSelfContained`).
- **Templates:** no Microsoft template pack for WinUI 3 exists for `dotnet new`. The community `VijayAnand.WinUITemplates` (MIT) generates Windows App SDK 1.2 projects with `win10-*` runtime identifiers, which .NET 8 and later reject.

## Decisions

**Loading everywhere.** The build host reports `ProjectInfo.UsesWinUI` (`UseWinUI`) and `WindowsPackageType` (from the Windows framework's evaluation, so MAUI's too), and `RunInfo.WindowsPackageType` and `RunInfo.AppxManifest`. Off Windows, a WinUI project's design-time build gets the global property `CustomAfterDirectoryBuildTargets`, which MSBuild imports right after the package targets: a file the build host writes with an empty `DesignTimeMarkupCompilation` target, replacing WinUI's; and `WindowsAppSDKSelfContained=false` (self-contained needs a Windows runtime identifier only Windows infers; a design-time build writes nothing). The project loads with WinUI's references and its `Page`/`ApplicationDefinition` XAML as additional files (ADR 0071's step), without the compiler's generated code. The design-time cache's schema moves to 3. On Windows nothing changes: the compiler's design-time pass runs.

**Windows only (D31).** A WinUI project, off Windows, says "builds, runs and debugs only on Windows" on Start, Start Without Debugging, Build and Rebuild (not Clean), without building; it opens and edits. MAUI's Windows framework is conditioned on Windows by the templates, so elsewhere it isn't there; when a project lists it anyway, the device picker shows "Windows Machine" marked Windows only, so the target is visible but not chosen (the same choice as M40a's templates, listed last and marked). No Windows remote target yet.

**The Windows target in the device picker.** `MobileTargets.RunsOn(Windows)` is true on Windows; the device list there has "Windows Machine" (`MobileDeviceKind.ThisPc`). With no framework chosen, a run on Windows goes to the Windows framework (other IDEs start MAUI apps on "Windows Machine"); a choice in the picker wins. Check Environment's MAUI rows gain `maui-windows`.

**Unpackaged apps run as programs.** A WinUI project takes the usual paths (build, `RunCommand`, netcoredbg, `dotnet watch`). MAUI's Windows target builds that framework alone (the build host's build with `TargetFramework`, so the other frameworks' workloads aren't needed), then runs or debugs `RunInfo` for it, or runs `dotnet watch run --framework <tfm>` for Hot Reload.

**Packaged apps are registered and activated.** For `WindowsPackageType=MSIX` (a WinUI project, or MAUI's Windows target):
1. **Developer Mode** (`HKLM\…\AppModelUnlock\AllowDevelopmentWithoutDevLicense`) is checked first; when it's off the IDE explains why it's needed, offers Settings → System → For developers (`ms-settings:developers`) or `WindowsPackageType=None`, and builds nothing.
2. The build (or the framework's build), then the layout's manifest: `AppX\AppxManifest.xml` when a deployment made one, else the build's `AppxManifest.xml`.
3. **Registration** through the user's PowerShell, one process: `Add-AppxPackage -Path <framework>` (one already installed at a higher version, `0x80073D06`, is fine), then `Add-AppxPackage -Register <manifest> -ForceApplicationShutdown -ForceUpdateFromAnyVersion`, where the framework is the Windows App SDK runtime's framework MSIX from the restored NuGet package (`Microsoft.WindowsAppSDK.Runtime`'s `tools\MSIX\win10-<arch>`), as a deployment from Visual Studio installs it. Not `-Register … -DependencyPath <framework>`: with `-Register`, Windows registers each dependency path as a layout too and rejects a package file ("the manifest is not in the package root", `0x80073CF9`, the first Windows run). A failure's output goes to the Run channel, with a hint for Developer Mode (`0x80073CFF`) and missing dependencies (`0x80073CF3`).
4. **Activation** through `IApplicationActivationManager::ActivateApplication` with the AUMID, which the IDE computes from the manifest (the family name: the name and the publisher id, the first 8 bytes of the SHA-256 of the publisher in UTF-16LE as 13 characters of Crockford's base 32; then `!` and the application's id). It runs in **`codalus-debughost --activate-app <AUMID> [--arguments …]`**, which prints the process id. The debug companion ships in every package, already starts debugging-related processes, and keeps COM interop (source-generated `[GeneratedComInterface]`, `LibraryImport`) out of the Native AOT shell; a dedicated helper would add a binary for 80 lines, and PowerShell has no way to get the process id of an activation.
5. **Following or debugging:** Start Without Debugging follows the process (`RunService.Track`: listed as running, Stop ends it); Start attaches netcoredbg to it (`DebugService.AttachAsync`). Hot Reload says it isn't available for packaged apps (`dotnet watch` starts programs).

**Check Environment** (on Windows, when the solution has Windows App SDK apps): Developer Mode, when one is packaged (fix: the Settings page); the Windows App SDK runtime of each `Microsoft.WindowsAppSDK` channel the apps reference, from `Get-AppxPackage Microsoft.WindowsAppRuntime.*` (fix: winget's `Microsoft.WindowsAppRuntime.<channel>`, or the download page). Nothing installs without the user's yes.

**WinUI XAML in the same engine** (`XamlContext.IsWinUI`): a `.xaml` file is WinUI's when its compilation references WinUI (`Microsoft.UI.Xaml.DependencyObject`, `FrameworkElement`) and not Avalonia, and not MAUI unless it's under `Platforms/Windows` (MAUI's own WinUI `App.xaml`); WPF's, MAUI's and Avalonia's files keep their dialects. On top of ADR 0047 and 0071:
- **Types and members:** the presentation namespace maps to `Microsoft.UI.Xaml`'s namespaces (Controls, Primitives, Data, Documents, Input, Media, Animation, Imaging, Navigation, Shapes…), `using:` to the project's; the projection's attached properties (a static `XxxProperty` property with `GetXxx`) and user dependency properties (fields); `[ContentProperty(Name)]`; `Microsoft.UI.Colors` and `FontWeights` for values.
- **`x:Bind`** is compiled, so its path is checked as an **error** (WinUI's compiler reports `WMC1110`): from the page's class (`x:Class`), where named elements and private members count, or from the closest data template's `x:DataType`; properties, fields and methods (function bindings, event handlers). Paths with a function call, a cast, an attached property or a static type aren't checked. `{Binding}` resolves at run time: its paths are warnings, from `d:DataContext` or a data template's `x:DataType`, as in WPF.
- **Directives:** `x:Load` (Boolean or an `x:Bind`, checked), `x:DefaultBindMode` (`OneTime`, `OneWay`, `TwoWay`, checked), `x:Phase`, `x:Uid`, `x:FieldModifier`, `x:DataType`; completion of each.
- **Markup extensions:** `x:Bind` (with `Mode`, `BindBack`, converters…), `Binding`, `StaticResource`, `ThemeResource`, `CustomResource`, `TemplateBinding`, `RelativeSource`, `x:Null`.
- **Resources** (ADR 0071's `XamlResources`): the file's own, `App.xaml`'s and the dictionaries merged with `ms-appx:///` sources (the project's root; a library's under its assembly name), completed and navigated, never reported missing: `StaticResource` and `ThemeResource` also find the framework's theme resources (`XamlControlsResources`), which no file lists.
- **WinUI's XAML compiler errors** (`WMC…`) map to their files from builds, as `MC…` and `AVLN` errors do (`XamlBuildDiagnostics` takes any `.xaml`), when they name one. On `dotnet` MSBuild they don't (the first Windows run): `XamlCompiler.exe` embeds its messages under another name (`Microsoft.Windows.UI.Xaml.Build.Tasks.ErrorMessages.resources`) than the one it looks up, so every error becomes `WMC9999` ("Could not find any resources…") on the compiler task's line in the package's targets.

**Templates.** No template pack is offered (no reliable MIT one exists; New Project has no WinUI template, a gap). Add New Item has WinUI 3's Blank Window, Blank Page, User Control and Resource Dictionary built in, as WPF's are, with the code-behind nested.

## Consequences

- WinUI XAML is edited, checked and navigated on every OS, and its tests run on every CI runner; building, running, deploying and debugging are proven only on Windows (the Windows-only tests and the smoke step `maui.windows`).
- A WinUI build's XAML errors say only `WMC9999`, without their file (a Windows App SDK defect, 1.8 and 2.3 alike); the editor's live checks (`x:Bind` paths, types, properties) are what point at the XAML. `TODO(issue)`
- Off Windows, a WinUI project's code-behind shows C# errors for `InitializeComponent` and the named elements' fields until it's built on Windows (the compiler that writes them doesn't run there). `TODO(issue)`
- A packaged app registered from the IDE stays registered (as after a deployment), and the Windows App SDK runtime's framework package it depends on may be installed by the registration.
- Breakpoints in a packaged app's start-up code are missed: netcoredbg attaches after the activation. Launching suspended through `IPackageDebugSettings` would fix it. `TODO(issue)`
- Gaps by design: a WinUI previewer (Microsoft has none), XAML Hot Reload, UWP (a non-goal; .NET Native is retired). Packaged apps in multiple startup projects run the usual way. `TODO(issue)`
