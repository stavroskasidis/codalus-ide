# 0046. The profiler's other tools: events, memory, activities and benchmarks

- **Status:** accepted (M18b, 2026-10-12; the maintainer's standing go-ahead for the milestones)
- **Date:** 2026-10-12
- **Deciders:** maintainer

## Context

M18a ([ADR 0044](0044-diagnostics-host-and-trace-processing.md), [ADR 0045](0045-profiler-views.md)) built `daedalus-diaghost`, CPU sampling with its views, counters and the Diagnostic Tools window. M18b adds the rest of Visual Studio's profiler and memory tools: allocations, memory snapshots and their diffs, full-dump inspection, .NET Async, threads and contention, exceptions, file I/O, an events viewer with exports, activity views, comparing sessions, and BenchmarkDotNet. The constraints don't change: the shell is Native AOT, traces stay in the host and are answered a page at a time, every dependency is OSI-licensed, and nothing native or proprietary ships.

## Options and decisions

| Question | Options | Verdict |
|---|---|---|
| How a session records several tools | One EventPipe session per tool; one session with every tool's providers | **One session, one `.nettrace`**: the tools' providers and keywords are merged (`DiagnosticsPort.TraceProviders`), with the runtime's method events and rundown always on so every stack has names. The session folder keeps `trace.nettrace` (`cpu.nettrace` before M18b) and the trace stays the single source of every view. |
| Allocations, contention, exceptions | Their own views; the CPU views over other events | **Stack profiles.** Each becomes a `CpuProfile` with a **weight** per sample: allocation ticks (`GC/AllocationTick`, about one per 100 KB, weighed in KB) with the allocated type as a pseudo leaf frame; lock contention (`Contention/Start` with its stack, weighed in microseconds from `Contention/Stop`'s `DurationNs`) under a "Lock contention" frame; first-chance exceptions (one each) with the exception's type as the leaf, the runtime's own throwing frames (`System.Runtime.EH`, throw helpers) removed so the leaf's caller is the throw site. The report's **Stacks of** choice shows any of them in the Call Tree, Bottom-Up (allocated types, contended locks and exception types first), Functions, Flame Graph and timeline; `CpuFilter.Profile` picks it on the wire. Allocation *sampling* with exact object sizes (.NET 10's `AllocationSampled`) is a later refinement. |
| One pass | Reading the trace once per view; once | **Once**: `NettraceReader` walks the `TraceLog` once into `TraceData`: the four profiles, the TPL's tasks, the thread pool's events, contentions, exceptions, HTTP requests, database commands, spans, and an index of every event (time, provider and name, thread, the event's index in the log) for the events viewer. Payloads and task stacks are read from the log only for the rows a page shows. |
| .NET Async | Task lifetimes from `TaskScheduled`/`TaskCompleted`; the causality events | **The causality events** (`TplEventSource`, keywords `AsyncCausalityOperation` and `Relation`): `TraceOperation/Start` names the operation (`Async: <FetchAsync>d__0` for async methods, `Task.Delay`, `Task.WhenAll`…) with the stack that created it, `TraceOperation/Stop` ends it with its status. The method is named from the state machine's `MoveNext` frame on that stack (`Worker.FetchAsync`). The view lists the longest first, with a bar on the trace's time axis and the creating stack. |
| Threads | ETW context switches; what EventPipe has | **What EventPipe has**: each thread's buckets are running (managed samples), waiting or native (the sampler's external samples) or blocked (contention intervals; a third of a bucket blocked wins, because a blocked thread is also "external" to the sampler). The thread pool's `Adjustment` events (with their reason: starvation, cooperative blocking, hill climbing) and worker starts and stops are listed. |
| File I/O | ETW kernel file events; `perf`/eBPF; the process's I/O counters | **The process's I/O counters**, sampled four times a second during the recording into `trace.io.json`: Windows `GetProcessIoCounters` (bytes and operations, all I/O); Linux `/proc/<pid>/io` (`rchar`/`wchar` and `syscr`/`syscw`: read and write calls, files, pipes and sockets); macOS `proc_pid_rusage` (disk bytes only, no operation counts). Per-file detail needs the kernel (an administrator ETW session and the proprietary KernelTraceControl we exclude; `perf`, eBPF or DTrace with privileges): `TODO(issue)`. |
| Activities | Our own EventListener in the app; EventPipe's sources | **EventPipe's sources**, no code in the app: HTTP requests from `System.Net.Http`'s `Request/Start`/`Stop` (correlated by activity id, so the TPL's `TasksFlowActivityIds` is on); database commands from DiagnosticSource through `Microsoft-Diagnostics-DiagnosticSource`'s `FilterAndPayloadSpecs` (SqlClient's `WriteCommandBefore`/`After`/`Error` and EF Core's `CommandExecuting`/`Executed`/`Error` as start and stop pairs with the command's text), plus spans with `db.*` tags; and every `ActivitySource`'s spans (`[AS]*/Stop` with their ids, kind, duration, status and tags), nested by parent span. |
| Events viewer and exports | A separate viewer; the report | **The report's Events tab**: counts by provider and event, a page of events filtered by provider, name, payload text, the report's time range; extra EventSource or EventPipe providers can be recorded (`TraceStartParams.Providers`). Exports are written by the host from a profile and its filter: **Speedscope** (a sampled profile per thread, shared frames, weights in the profile's unit) and **Chromium trace events** (CPU samples merged into nested complete events per thread, other profiles' samples as instant events, spans, requests and commands on their own tracks). Save Trace As copies the `.nettrace` (and its I/O counters). |
| Heap snapshots | dotnet-gcdump's `.gcdump` format (FastSerialization, PerfView's graph code, not in the TraceEvent package); ClrMD on a dump; the runtime's heap events | **The runtime's heap events, as dotnet-gcdump takes them**: a session with the `GCHeapSnapshot` keywords makes the runtime run a full blocking GC that reports every live object (`GCBulkNode`), its references (`GCBulkEdge`), the roots (`GCBulkRootEdge`, static variables, conditional weak tables) and the types (`TypeBulkType`); the session stops when that GC ends and the events are kept as `heap-N.nettrace`. `HeapGraph` (our code) links them, names generic types (`Dictionary<Int32, Order>`), and walks breadth-first from the roots so every reachable object has the referrer that first reached it. Views: types by size; types by growth against another snapshot (matched by name: snapshots can come from different processes); **paths to roots** as a tree from a type up through its referrers' types to a root kind (stack, handle, finalizer queue, static…) or "not reached". Reading `.gcdump` files and retained sizes (a dominator tree) are `TODO(issue)`. |
| Full-dump object inspection | Our own; M14's | **M14's**: Create Full Dump (Memory Usage, while collecting) asks the debug companion host to write `full.dmp` into the session; the report's Inspect Objects opens it in M14's dump view (heap by type, instances, fields through ClrMD). |
| Comparing sessions | Diffing samples; comparing shares | **Shares**: each function's self and total share of its own session, matched by name and module, the largest change of the total share first (`diag/cpu/compare`); with snapshots in both, the heap's growth from the baseline's last snapshot to the session's last. The Performance Profiler's Compare opens the comparison. |
| BenchmarkDotNet | A test-adapter-like runner in a host; running the user's program | **The user's program**: BenchmarkDotNet projects are programs. Benchmarks are found in the source of projects that reference BenchmarkDotNet (`BenchmarkFinder`: attribute lists naming `Benchmark`, the method after them, the enclosing types and namespaces; comments and strings skipped), so the gutter glyphs follow edits without Roslyn in the shell. A glyph or the Benchmarks window runs `dotnet run -c Release --project … -- --filter <type.method> --exporters json --artifacts .daedalus/benchmarks/runs/<time> [--job …] [--inProcess]` (a trusted solution only), shows BenchmarkDotNet's output, reads its JSON report (mean, error, deviation, median, allocations) and appends the run to `.daedalus/benchmarks/history.json` (the last 200 runs), from which a benchmark's history is shown. The project is built first by the IDE's build (in Release) and `dotnet run` gets `--no-build`, as `dotnet ef` and test runs do: that build waits for the build host's restore and holds off restores meanwhile, where `dotnet run`'s own restore could run at the same time as the restore after opening the solution, both writing `obj/*.nuget.g.props` ("already exists", seen on Linux CI). |

## Protocol

New requests on the same host (`docs/diagnostics-protocol.md`): `diag/trace/start` takes `tools` and `providers`; `diag/trace/open` reports the profiles and what else the trace has; `diag/cpu/*` take `filter.profile`; `diag/cpu/compare`, `diag/async/tasks`, `diag/threads`, `diag/exceptions`, `diag/activities`, `diag/fileio`, `diag/events/stats`, `diag/events/list`, `diag/trace/export`, and `diag/heap/snapshot|open|close|types|roots`. The protocol version stays 1: every change is an addition, and a session from M18a opens unchanged.

## Accessibility

The new lists are list boxes and tree views whose items carry their whole meaning in `AutomationProperties.Name` (a task's duration, start and status; a thread's milliseconds running, waiting and blocked; an exception group's type, count, site and line; a type's growth). The custom `StateStrip` (a thread's states) and `SpanBar` (a task's or request's place in time) only draw what each row's text also says.

## Consequences

- Every new tool works on the three OSes from EventPipe and public OS calls; File I/O differs by OS as described, and the Windows-only per-file detail stays out (`TODO(issue)`).
- Allocation ticks sample every ~100 KB per allocating thread: small, rare allocations can be missed; the report says the weights are KB the samples stand for.
- A heap snapshot is a full blocking GC of the target; it pauses the program for as long as the heap takes to walk.
- Benchmark runs build and run the user's code: trusted solutions only, like Run.
