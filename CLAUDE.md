# CLAUDE.md

Guidance for working in this repository. The MVP (milestones M0–M7) is done; the milestone notes are in `docs/checkpoints/`, the post-MVP plan (M8 onward) in `docs/roadmap.md`, and decisions in `docs/adr/`.

## Build and test

```bash
dotnet build DaedalusStudio.slnx                          # everything .NET (warnings are errors)
dotnet test --solution DaedalusStudio.slnx                # unit + host integration + Avalonia headless UI test
dotnet run --project benchmarks/DaedalusStudio.Benchmarks.FixtureGen -- all samples   # generate Large100k/ and Solution50/
```

NativeAOT publish on Windows needs `vswhere.exe` on `PATH` (`%ProgramFiles(x86)%\Microsoft Visual Studio\Installer`).

## Running the shell

```bash
dotnet run --project src/DaedalusStudio.Shell -- --user-data-dir .work/user-data          # Debug; plugin host and built-in plugins are copied next to the build
dotnet publish src/DaedalusStudio.Shell -c Release -r win-x64 -o artifacts/shell           # Native AOT, with pluginhost/, buildhost/, lshost/ and plugins/ next to daedalus.exe
```

Arguments: an optional solution, project or folder to open. Options: `--user-data-dir <dir>` (settings, state and plugins under one folder), `--plugin-dir <dir>` (repeatable; load a plugin under development), `--enable-proposed-api`, `--dev`, `--version`, `--open <file>`, `--remote <ssh:host|wsl:distro|local>` (a remote window, M21), `--screenshot <png>`; for benchmarks `--bench typing|scroll` (on the `--open` file) and `--exit-on interactive|highlight|done|language`; for CI `--smoke-test <samples dir>` (below). With `DAEDALUS_BENCH_EVENTS=<file>` the shell writes timestamped bench events. `DAEDALUS_PLUGINHOST`, `DAEDALUS_BUILDHOST`, `DAEDALUS_LSHOST`, `DAEDALUS_REPLHOST`, `DAEDALUS_MARKUPHOST`, `DAEDALUS_DEBUGHOST`, `DAEDALUS_T4HOST`, `DAEDALUS_DATAHOST` and `DAEDALUS_DIAGHOST` point at a host `.exe` or `.dll`; `DAEDALUS_TRASH_DIR` sends deletes to a folder instead of the OS trash (tests). `DAEDALUS_NODE_CACHE` holds the on-demand Node.js and web language servers (ADR 0024) in a shared folder; `eng/smoke-test.sh` uses `.work/node-cache`. Plugin authoring: `docs/plugins.md`; build host protocol: `docs/project-protocol.md`.

## End-to-end smoke test

`eng/smoke-test.sh <daedalus executable>` runs the real, windowed app through one feature of each MVP milestone (`--smoke-test samples`, driven by `SmokeTest` in `src/DaedalusStudio.Shell/Infrastructure`): settings, themes, palette, plugins, opening and evaluating a solution, highlighting, diagnostics, completion, navigation, rename and formatting, build, run, debugging and Git, on a copy of `samples/BuildAndRun`. It writes `smoke-test.md`/`.json` and screenshots under the results folder (default `artifacts/smoke-test`) and fails when any step does. `ci.yml` runs it on the published Native AOT app on every OS it builds; `release.yml` runs `eng/smoke-test.sh --packages artifacts/packages` on the installed packages (zip, `.app` from the dmg, `.deb`). Add a step there when a feature should be proven in the shipped app, not just in the in-process headless tests. On Linux without a display it uses `xvfb-run`.

## Packaging

Releases are automatic (M31, ADR 0028). `VERSION` holds the next release's version, and `eng/DaedalusStudio.Release` (`daedalus-release version|check-tag|bump|notes`) holds the rules: nightlies are `X.Y.Z-nightly.YYYYMMDD.N` from `develop`, stable releases `X.Y.Z` from `master`. `eng/package.sh [version] [stable|nightly|dev]` builds the current platform's packages into `artifacts/packages` with Velopack's `vpk` (pinned with the `Velopack` library): a per-user `Setup.exe` and a zip on Windows, a `.pkg` and an `.app` zip on macOS, an AppImage, `.deb`, `.rpm` and `.tar.gz` on Linux, plus the update channel `<rid>-<kind>` (feed and packages in `velopack/`) and `SHA256SUMS-<rid>.txt`. `eng/smoke-test.sh --packages` installs them as a user would, runs the smoke test, uninstalls and checks nothing is left; the shell's `Installation` hook (first thing in `Main`) handles Velopack's install events and puts `daedalus` on the Windows PATH. Workflows: `packages.yml` (reusable, every platform), `nightly.yml` and `release.yml` (manual dispatch while the repository is private, dry run by default; they publish through `eng/publish-release.sh`), and `linux-repos.yml` (signed apt and dnf repositories on Pages, `eng/linux-repos.sh` and `eng/test-linux-repos.sh`, once public).

Self-update (M32, ADR 0029): the policy is `UpdateService` in `src/DaedalusStudio.Workbench/Updates` (with the release stores and `FeedSignature`), the Velopack client is `Infrastructure/Updates.cs`, the UI `ShellHost.Updates.cs`. Feeds are signed with ECDSA P-256 (`FEED_SIGNING_KEY` secret → `DAEDALUS_FEED_KEY` for `eng/package.sh`; the public key is `FeedSignature.ProjectKey`). `eng/test-update.sh` builds N and N+1, installs N and updates it through a signed local feed (`DAEDALUS_UPDATE_SOURCE`, `DAEDALUS_UPDATE_TEST_KEY`, `daedalus --update-now`). `DAEDALUS_UPDATE_TOKEN` (or `gh auth token`) reads a private repository's releases.

## Website

The website is an ASP.NET Core Blazor app, static SSR only (no interactivity, no `blazor.web.js`): `website/` (`SiteHost` sets it up; pages in `Components/Pages`, the layout in `Components/Layout`; the user guide is `docs/user-guide/*.md` rendered by Markdig in `Site/UserGuide.cs` behind `/docs/{slug}`, with GitHub-style heading ids; `Releases` makes the download links from `--stable`/`--nightly` tags). Develop with `dotnet watch --project website` (http://localhost:5180). GitHub Pages can't run it, so `dotnet run --project website --no-launch-profile -- --export <dir>` starts it on a loopback port and `SiteExporter` crawls every route and local link into static files (`download/` → `download/index.html`), failing on any broken link or `#anchor`. Every page has `<base href>` (`/` live, `/daedalus-studio/` exported), so **links are written relative to the site, never rooted, and a link within a page carries its path** (`docs/git/#stash`, not `#stash`); page links end with `/`. Pages (`https://stavroskasidis.com/daedalus-studio/`) serves the export and the apt/dnf repositories together, built by `linux-repos.yml` (after each nightly and release, and on pushes to `develop` that touch `website/` or `docs/user-guide/`; only `develop` may deploy). Tests: `tests/DaedalusStudio.Website.Tests`. Screenshots in `website/wwwroot/assets/screenshots/` are copies of the smoke test's (`artifacts/smoke-test/`); fonts are self-hosted (no third-party requests).

**Always keep the website up to date** (the maintainer's rule, 2026-10-13). A change users can see updates the site in the same push:
- A new feature or milestone goes on the Features page (`Components/Pages/Features.razor`), and on Home when it's a headline.
- A changed behaviour updates its user guide page in `docs/user-guide/`; the site renders the guide, so the guide is the documentation.
- New or changed UI gets fresh screenshots in `website/wwwroot/assets/screenshots/`, taken from the smoke test's run; add a smoke step when a feature has none.
- Platforms, packages and install commands stay correct on the Download page.

A milestone's checkpoint isn't done until the site shows it. Run `tests/DaedalusStudio.Website.Tests` and the export (`--export`) before pushing site changes.

## Project-system depth

Items and folder mode (M26a, ADR 0033): item edits are the build host's `items/*` (`ProjectManagement/ProjectItems.cs`: edit the construction model, evaluate it again in memory, write what Visual Studio writes under globbing), `fs/move` carries a file's items into the project it moves to, `fs/listTree` feeds Show All Files and the folder view; the shell side is `ProjectItemService` (workbench `Projects/`), the Properties window `PropertiesWindowViewModel`, and `ShellHost.ProjectSystem.cs`/`ShellHost.Folder.cs`. Folder mode is `solution/open` on a folder (format `folder`, an in-memory solution of the loaded projects, `.daedalus/folder.json`); `.daedalus/tasks.json` and `launch.json` are `FolderConfiguration`. Item templates: the built-in set is `ItemTemplates`, `dotnet new` listing, packages and Export Template are `TemplateService` (the CLI from the workbench; `DAEDALUS_TEMPLATE_HIVE` gives tests their own hive), instantiation is the host's `templates/instantiate`. External Tools: `ExternalToolStore` (`<config>/externalTools.json`). Fixtures: `samples/ProjectSystem/src/Items` (every Build Action, opened on its own) and `samples/ProjectSystem/FolderOnly`.

Build depth (M26b, ADR 0034, 0035): `build/run` takes `BuildOptions` (verbosity, log file, parallel nodes, binary log, the up-to-date check, extra properties) that the shell builds from settings (`ShellHost.BuildDepth.cs`). The fast up-to-date check is `Building/UpToDateCheck.cs` in the build host: state per project in `obj/.../daedalus.uptodate.json`, recorded after builds with options and compared before a Build; its tests run real MSBuild builds to confirm each verdict (`BuildDepthIntegrationTests`). Timings are `TimingLogger` (a forwarding logger passes only start and finish events), binary logs `BinaryLogs` (MSBuild.StructuredLogger, read in the host, sent a level at a time), batch builds and build events `SolutionSession.Building.cs`/`ProjectManagement/BuildEvents.cs`; the shell side is `BuildService`/`BuildDepthService` (workbench `Build/`) and `BuildDepthViewModels.cs`. Custom tools are `CustomToolService` and `ResXGenerator` (workbench `CustomTools/`); T4 templates run in `daedalus-t4host` (`src/DaedalusStudio.TextTemplating.Host`, Mono.TextTemplating, supervised, started on the first template and only for trusted folders; `DAEDALUS_T4HOST` overrides `t4host/`).

## Language services

The C# language service host (`daedalus-lshost`, ADR 0005) speaks LSP over stdio (`docs/protocol.md`). It gets its projects from the build host's design-time builds, relayed by the shell (`LanguageService` in `src/DaedalusStudio.Workbench/Languages`). `DAEDALUS_LSHOST` points at a host `.exe` or `.dll`; otherwise the shell uses `lshost/` next to it. Fixture: `samples/LanguageFeatures`. Between sessions (M34c, ADR 0049) the host keeps each project's background diagnostics and a reference assembly in its `obj/<config>/<tfm>/daedalus.language.*` under a key of its inputs (`LanguageStateCache`, `ProjectKeys`; `DAEDALUS_LANGUAGE_CACHE=0` turns it off): unchanged projects aren't compiled, and the open documents use the `AnalysisSolution` (unchanged references as assemblies) until the workspace has compiled their references. `DAEDALUS_GENERATOR_TIMINGS=1` logs each source generator's cost.

Web front-end depth (ADR 0027): HTML and CSS in Razor files go to the HTML server as each file's HTML (`RazorHtmlProjection`, a `Counter.razor__virtual.html` document) and merge with the C# host's answers at markup positions; ESLint is a linter service (`LanguageServiceDescriptor.IsLinter`, next to a language's service) whose diagnostics are pulled (servers with a `diagnosticProvider`), and `DiagnosticsStore` keeps each source's per file; Prettier formats through `Prettier` (workbench `Node/WebTools.cs`); npm scripts and restore are `Npm` and the Task Runner Explorer (`ShellHost.Npm.cs`). Fixtures: `samples/WebScripts` (npm), `samples/WebLint` (ESLint and Prettier, `npm ci` in the tests).

Scaffolding and service references (M15c, ADR 0041): `scaffold/*` runs the user's `dotnet aspnet-codegenerator` as a child of the build host (trusted only; `SolutionSession.WebTools.cs`), empty items go through `templates/instantiate`, and the catalog that generates the dialog is `Scaffolders` (workbench `Web/`, with `ScaffoldingService`); `serviceReferences/*` writes `OpenApiReference`/`Protobuf` items and their packages (`ProjectManagement/ServiceReferences.cs`), and `ServiceReferenceService` copies or downloads the documents. The shell side is `ShellHost.WebTools.cs`. Fixture: `samples/Scaffolding` (the codegenerator as a local tool, `contracts/` with an OpenAPI document and a `.proto`).

Other languages (ADR 0016) are registered in `LanguageRegistry` (workbench; built-ins in `src/DaedalusStudio.Shell/Editor/BuiltInLanguages.cs`) and colored with TextMate grammars (`TextMateSupport`); C# keeps Roslyn's semantic tokens. Any LSP server can serve a language: plugins declare `contributes.languageServers`, and `LspNormalizer` turns VS Code-shaped results into our narrowed types. `daedalus-markuphost` (`src/DaedalusStudio.Markup.Host`) serves JSON (schemas), XML/MSBuild, YAML and `.editorconfig`, and asks the shell for evaluated MSBuild values. `tests/DaedalusStudio.LspConformance.Server` is a scripted third-party-style server for the bridge tests; `samples/plugins/TodoLanguage` is a declarative language plugin.

Navigation depth and inline information (ADR 0017): standard LSP requests (document symbols, hierarchies, inlay hints, CodeLens) plus `daedalus/references`, `daedalus/base`, `daedalus/inheritanceMargin` and `daedalus/symbolInfo` in the C# host. In the shell, `EditorInsights` (per editor: hints, CodeLens, inheritance margin, guides, bracket colors, document symbols) and `EditorChrome.cs` (navigation bar, sticky scroll, overview ruler); commands and tool windows in `ShellHost.Navigation.cs`. Library code comes from embedded PDB sources or Source Link (`PdbSources`) before decompiling.

Editing, refactoring UI and analysis (ADR 0018): snippets (`SnippetRegistry` in the workbench, `SnippetEngine` and the built-in `Editor/Snippets/*.json` in the shell, `contributes.snippets` for plugins); refactorings with options through `daedalus/codeActionOptions` (`OptionsRefactorings.cs` in the host, the dialog's checklist in `DialogViewModel`); Code Cleanup (`CodeCleanupFeature`); AutoRecover and local history (`ShellHost.EditingSafety.cs`, `LocalHistory`); bookmarks and the Task List (`ShellHost.Bookmarks.cs`); the Syntax Visualizer and Code Metrics (`daedalus/syntaxTree`, `daedalus/codeMetrics`, `ShellHost.Analysis.cs`); Compare Files and the image viewer (`ShellHost.Files.cs`).

Look and feel (ADR 0019): the title row (menu, search box, solution name; the window's title bar on Windows) and the standard toolbar (`ToolbarViewModel`, `ShellHost.Toolbar.cs`) are in `MainWindow`; themes are tokens in `Theming/Tokens.axaml` (Blue, Light, Dark, High Contrast, with Dock's brushes mapped onto them); the keyboard scheme is the `keyboardScheme` context key that the default bindings' `when` clauses test. Keep "Visual Studio" out of UI strings, setting values and theme names. UX pass (M34a): the menu bar and the editor's context menu are declared in `BuiltIns.Menus.cs` as trees (submenus are menu locations; `UxPassTests` keeps every command reachable and every menu within a 1080p screen); command icons are `Controls/CommandIcons.cs`, colored by family through `Shell.Icon.*` tokens. Command icons are Fluent UI System Icons (`Icons/fluent-icons.txt`, `eng/get-fluent-icons.sh`), file, folder and project icons Material Icon Theme (`Icons/material-icons.txt`, `eng/get-material-icons.sh`, mapped in `Controls/FileIcons.cs` as `mi:` names); add a name to the list, run the script, commit the SVG; the build compiles them with their colors (`eng/icons/`), never parse SVG at runtime. `kind@Family` colors a stroke or Fluent icon with `Shell.Icon.<Family>`. **Every icon is colored, in the Visual Studio palette** (`Shell.Icon.Blue`…`Folder`; the maintainer's rule, `docs/ui-guidelines.md`): give each new icon kind its color in `CommandIcons.s_kindColors` (`IconColorTests` checks), file icons take the palette's nearest color, and tool window tabs show their icon only once collapsed (`FittingTabPanel`). Log views follow their end with `FollowTail`. OS-reserved shortcuts per OS are in `docs/user-guide/keyboard.md`.

Personalization (M23a): color overrides are VS Code's `editor.tokenColorCustomizations` and `workbench.colorCustomizations` (`Theming/ColorCustomizations.cs`, `EditorTheme.WithOverrides`, `ShellHost.Colors.cs`, Tools → Fonts and Colors); keyboard schemes beyond Default and VS Code are `BuiltIns.Keymaps.cs` (only the active scheme's rules are among the defaults; Emacs's caret commands are `CodeEditorController.Caret.cs`); importers are `VsCodeImport` and `VsSettingsImport` (workbench `Settings/`, shell side `ShellHost.Import.cs`), Export/Import Settings `ShellHost.SettingsTransfer.cs`, named layouts, full screen and distraction-free mode `ShellHost.Layouts.cs`; onboarding (Get Started, tips) is in the Welcome plugin. M23b: profiles are `ProfileStore` (workbench `Settings/`; the active profile's files stay in place, others in `<config>/profiles/<name>/`) and `ShellHost.Profiles.cs`; settings sync is `SettingsSync` (a folder or a Git repository, `ShellHost.Sync.cs`); Tools → Customize is `MenuCustomizations` applied by `MenuRegistry`, with `ShellHost.Customize.cs`; `plugins.disabled` turns plugins off, File → Restart is `ShellHost.Restart.cs`. The start window (M38) is `StartWindow` with `StartWindowViewModel` and `ShellHost.StartWindow.cs`, on `RecentSolutions` (workbench `Projects/TrustAndRecents.cs`: entries with times and pins, `Group` by date); `ShellOptions.StartWindow` is false in the test fixture. Localization: `Localizer` (workbench `Localization/`), catalogues `src/DaedalusStudio.Shell/Localization/<locale>.json` (English generated from the code and the views), commands, settings, menus and tool windows translated as they register, views use `{l:T key}` (`eng/localize-xaml.py` moves a view's literals), `--locale qps-ploc`/`qps-plocm` (right to left) are the pseudo-languages; after changing UI text run the shell tests with `DAEDALUS_UPDATE_LOCALIZATION=1` and commit `en.json` and `localization-literals.txt` (`docs/translating.md`).

## Avalonia XAML and the previewer

XAML editing (M19a, ADR 0047) is in the C# host, not the markup host: `.axaml` files (language `axaml`) are additional files of their projects like Razor's, and `src/DaedalusStudio.LanguageServices.Host/Xaml` (`XamlSyntax`, a tolerant parser; `XamlTypeSystem` on the project's Roslyn compilation; `XamlCompletion`, `XamlNavigation`, `XamlAnalysis`, `XamlDiagnostics`) serves completion, binding paths from `x:DataType`, diagnostics `XAML0001`–`XAML0006`, hover, definition, `x:Name` rename and formatting, plus `daedalus/xaml/logicalTree`. The XAML compiler's `AVLN` errors from builds become the `axaml.build` diagnostics source (`XamlBuildDiagnostics`). The previewer (ADR 0048) is in the workbench (`Previewer/`: `RemoteProtocol`, our AOT-safe codec of Avalonia's remote protocol checked against `Avalonia.Remote.Protocol` in the tests; `PreviewerSession`, one designer host from the app's own Avalonia package over loopback TCP; `PreviewService`, targets, trusted folders only, builds when stale; `PreviewSelection`) with the agent `DaedalusStudio.Previewer.Agent` (a netstandard2.0 startup hook in `debughost/`, `DAEDALUS_PREVIEWER_AGENT` overrides) for hit testing, bounds and theme variants. The shell side is `ShellHost.Xaml.cs` and `XamlPreviewViewModel` (XAML Previewer, Shift+F7). Fixture: `samples/Avalonia`. The Live Visual Tree and Live Property Explorer (M19b, ADR 0052): the same agent with `DAEDALUS_LIVE_AGENT_PORT`/`_TOKEN` is `LiveAgent` in a running app (windows, logical and visual trees, properties with their sources, set, highlight, pick, path), added as a startup hook to an Avalonia app's run or debug plan (`RunService.ProgramPlan`, setting `debug.liveVisualTree`); `LiveSession` (workbench `Previewer/`) is the IDE's side, `ShellHost.LiveTree.cs` and `LiveTreeViewModels.cs` the windows; Go to XAML resolves the element's logical path through `PreviewSelection`.
## Data and Entity Framework Core

EF Core (M27a, ADR 0036) runs the user's own `dotnet ef` as a child of the build host (`ef/*` in `docs/project-protocol.md`, `SolutionSession.EntityFramework.cs`, one at a time, trusted solutions only); the model view's data comes from `daedalus-efagent` (`src/DaedalusStudio.EntityFramework.Agent`, net8.0, shipped in `buildhost/efagent/`, `DAEDALUS_EFAGENT` overrides it), started with the app's deps.json and runtimeconfig.json like dotnet-ef's `ef.dll`. DbContexts are found instantly by Roslyn (`daedalus/ef/contexts`). The workbench side is `EntityFrameworkService` and `ConnectionDiscovery` (connection strings from `appsettings*.json` and user secrets) in `src/DaedalusStudio.Workbench/Data`; the UI is `ShellHost.EntityFramework.cs`. Fixture: `samples/Data` (SQLite, `dotnet-ef` as a local tool, `Inventory/inventory.db` for reverse engineering).

The database explorer (M27b, ADR 0037) runs in a new supervised, lazy `daedalus-datahost` (`src/DaedalusStudio.Data.Host`, protocol in `docs/data-protocol.md`): SQL Server through Microsoft.Data.SqlClient with managed networking only (its native SNI is proprietary and excluded), PostgreSQL (Npgsql), MySQL/MariaDB (MySqlConnector), SQLite (Microsoft.Data.Sqlite); the workbench side is `DataService` (connections in the state folder without passwords, which go to the OS credential store; the solution's connection strings from appsettings, user secrets and Aspire AppHosts), the UI `ShellHost.Data.cs` (Database Explorer, table data with explicit commit, the Query Results window, `DataGridView`). The same executable with `--lsp` is the SQL language server (ADR 0038: ScriptDom for T-SQL, schema completion from `daedalus/sql/context`). SDK-style `.sqlproj` files load and build (no design-time build); DacFx is proprietary, so schema compare and publish are a gap. Container tests (`ContainerEngineTests`) start PostgreSQL, MySQL, MariaDB and SQL Server with `docker` (podman's works) and skip where no container runtime is available, except in CI.

## Containers, Aspire and publishing

Containers (M17a, ADR 0042) use the user's `docker` or `podman` CLI (`ContainerEngine` in `src/DaedalusStudio.Workbench/Containers`, the `containers.tool` setting), one process per operation, never the Engine API. The "Container (Dockerfile)" launch profile (`"commandName": "Docker"`) runs a project in a container (`ContainerLaunch`): fast mode builds the Dockerfile's `base` stage, mounts the build output at `/app`, and runs the app through `exec` or under netcoredbg copied in (M14c's remote launch); Add Docker Support (`DockerSupport`) writes the .NET templates' files. `.dcproj` files load from their XML in the build host (`ComposeProject`) and are left out of builds and restores. The shell side is `ShellHost.Containers.cs` and the Containers window (`ContainersViewModel`); the markup host bundles the Compose Specification's schema. Containers we create carry the label `dev.daedalus.project`. Aspire (M17b, ADR 0043): an AppHost (`ProjectInfo.IsAspireHost`) runs or debugs with `IdeExecutionServer` (workbench `Aspire/`, the IDE side of Aspire's IDE execution protocol: `DEBUG_SESSION_PORT`/`_TOKEN`, `PUT /run_session`, the notify WebSocket) starting each project as our program, in the AppHost's compound debug session (`DebugService.AddLaunchAsync`) when debugging; `AspireResourceClient` reads the AppHost's resource service (`DOTNET_RESOURCE_SERVICE_ENDPOINT_URL` and `ASPIRE_DASHBOARD_RESOURCESERVICE_APIKEY` set by us) with our own gRPC framing and protocol buffers reader; the UI is `ShellHost.Aspire.cs` and the Aspire window. Publishing (M17c): `.pubxml` profiles are `PublishProfiles` (workbench `Publishing/`), published by the build host's `BuildTargets.Publish`/`PublishContainer` with `PublishProfile` and `_IsPublishing`; the Publish page is `ShellHost.Publishing.cs`. Fixtures: `samples/Containers` (and `Aspire.slnx`, Aspire 13.1 from nuget.org, a Redis container with `WithExplicitStart()` so tests never pull it). Container tests (`ContainerRuntimeTests`, `ContainerShellTests`) use `DAEDALUS_TEST_CONTAINER_TOOL` or the engine the shell would pick, skip without one that runs Linux containers, and fail on CI's Linux runner only; they pull only `mcr.microsoft.com/dotnet` images and remove what they create.

## Profiling and diagnostics

Profiling (M18a, ADR 0044 and 0045) runs in a supervised, lazy `daedalus-diaghost` (`src/DaedalusStudio.Diagnostics.Host`, protocol in `docs/diagnostics-protocol.md`): EventPipe sessions through Microsoft.Diagnostics.NETCore.Client (counters, meters, GC and exception events pushed live; CPU traces recorded to `.nettrace`), and TraceEvent's `TraceLog` for opened traces, whose views (`CpuProfile`, `CpuViews`: top-down, bottom-up, functions, caller/callee, pruned flame graphs, timeline, source lines) are asked for a page at a time. TraceEvent's native Windows binaries are proprietary and excluded (`ExcludeAssets="build;buildTransitive"`). Profiling from launch starts the startup project with `DOTNET_DefaultDiagnosticPortSuspend=1` and resumes it once the sessions run. The workbench side is `DiagnosticsService`, `CounterMonitor`, `CpuTrace`, `ProfilerSessionStore` (sessions in the solution's `.daedalus/profiler/`) and `HotLineStore` (workbench `Diagnostics/`); the UI is `ShellHost.Profiling.cs` (the Performance Profiler page, reports, the Diagnostic Tools and .NET Counters windows), the `FlameGraph`, `TimeSeriesChart` and `SampleTimeline` controls, and the editor's `HotLineMargin`. Fixtures: `samples/Diagnostics` (`CpuBound` with its `// [hot]` line, an EventCounter and a meter; `Allocations`, `Leaky`, `AsyncHeavy` for M18b). Tests run real EventPipe sessions against `CpuBound` (`DiagnosticsHostTests`, `ProfilerShellTests`).

## Remote development

A remote window (M21a, ADR 0050 and 0051, protocol in `docs/remote-protocol.md`) is this window connected to `daedalus-server` (`src/DaedalusStudio.Remote.Server`) on an SSH machine (the user's `ssh`, `BatchMode=yes`) or a WSL distribution: `daedalus --remote ssh:host|wsl:Ubuntu <path>`, or File → Open Remote Window (`ShellHost.Remote.cs`).
- **Transport.** One stdio stream carries frames of many channels (`DaedalusStudio.Rpc/Multiplexing`, flow control per channel). The server never listens on a port.
- **Hosts and paths.** The build, C# and markup hosts run there through `IProcessLauncher` (`ProcessLaunchInfo.Launcher`; placement in `SolutionService`/`LanguageService.Placement`), as does netcoredbg (`DebugAdapterStartInfo.Launcher`). Their JSON's paths are rewritten under a local root: `\\wsl.localhost\<distro>`, `\\daedalus-remote.invalid\<id>` or `/daedalus-remote/<id>` (`RemotePathMap`, `MappedJsonStream`).
- **Files and terminals.** The editor's files go through `FileSystems` (workbench `FileSystem/`, the server's `RemoteFileSystem` mounted at the root), terminals through `TerminalService.PtyFactory`.
- **Ports.** Ports that start listening there are forwarded on this machine's loopback (`PortForwarder`, the Ports window).
- **The bundle.** Server and hosts are copied as a checksummed `.tar.gz` into `~/.daedalus-server/<version>/` (`RemoteServerBundle`). A published install has `remote/server/` (framework-dependent) and `remote/<rid>/` (self-contained, `$(DaedalusServerRids)`).
- **Development and tests.** `DAEDALUS_SERVER` points at a server build, `DAEDALUS_REMOTE_LATENCY_MS` simulates latency, and `--remote local` is a stand-in server on this machine (tests and the smoke step `remote.session`).
- **Stand-ins.** Remote tests use stand-ins only: the local server, WSL (`DAEDALUS_TEST_WSL`), and a fake `ssh` on Linux and macOS.
- **M21b** adds Dev Containers, attach to a container, `testenvironments.json`, `runsOn` and reconnecting.

## Terminal and C# Interactive

The integrated terminal (ADR 0014) is our own VT engine (`src/DaedalusStudio.Terminal`, UI-agnostic) and pseudo-terminals in `DaedalusStudio.Platform/Pty`: ConPTY on Windows, `openpty` + `posix_spawn` on Unix. Never run managed code in a forked child: that is why it isn't `forkpty`. Sessions live in `TerminalService` (`src/DaedalusStudio.Workbench/Terminal`), the control in `src/DaedalusStudio.Shell/Terminal`, and the shell integration scripts in `src/DaedalusStudio.Shell/ShellIntegration` (copied to `terminal/`). C# Interactive (ADR 0015) runs user code in `daedalus-replhost` (`src/DaedalusStudio.Interactive.Host`, Roslyn scripting, protocol in `docs/interactive-protocol.md`), never in the shell or the language host.

## Debugging

The shell debugs through netcoredbg (Samsung, MIT) over DAP (ADR 0007; client in `src/DaedalusStudio.Debugging`, sessions in `DebugService` in `src/DaedalusStudio.Workbench/Debugging`). Get it with `eng/get-netcoredbg.sh` (pinned, checksummed, into `.work/netcoredbg`); `DAEDALUS_NETCOREDBG` points at another one, and installed builds look in `debugger/` next to the shell. Debugger tests skip without it locally and fail without it in CI. Fixture: `samples/Debugging`. Debugger depth (ADR 0021, 0032): the debug companion host `daedalus-debughost` (`src/DaedalusStudio.Debugging.Host`, `DebugCompanion` in the workbench; `DAEDALUS_DEBUGHOST` overrides) reads debugger attributes from metadata and dumps through ClrMD, never the live process; `[DebuggerDisplay]` is applied by evaluation (`DebuggerDisplays`), visualizers are `CollectionVisualizers` and plugins' (`DebugVisualizerRegistry`, sample `samples/plugins/DictionaryVisualizer`), and breakpoint filters, exception module conditions and pinned data tips (`PinnedDataTipStore`, `PinnedDataTipLayer`) are client-side. Blazor WebAssembly apps debug in the browser instead (ADR 0026): vscode-js-debug (`JsDebugAdapter`, downloaded on demand into the Node cache like the web language servers) drives Chrome, Edge or Chromium through the dev server's debugging proxy. `DAEDALUS_BROWSER_HEADLESS=1` runs the browser headless (tests, `eng/smoke-test.sh`); browser tests skip without a Chromium browser locally and fail without one in CI. Fixture: `samples/BlazorWasm`. A web app's server and its page debug as one session on `CompoundDebugAdapter` (ADR 0027): netcoredbg first, `js-debug` joining once the server listens; fixture `samples/BlazorHosted`. `DAEDALUS_JSDEBUG_TRACE=<folder>` writes `js-debug`'s logs there. Sessions (M14c, ADR 0039):
- **Multiple startup projects** are one independent `CompoundDebugAdapter` session (`DebugService.LaunchAsync(IReadOnlyList<DebugLaunch>)`, the Startup Projects page `run.configureStartupProjects`).
- **`debug.console = integratedTerminal`** starts a console app in the terminal, held before `Main` by `DaedalusStudio.Debugging.StartupHook.dll` (netstandard2.0, shipped in `debughost/`, `DAEDALUS_STARTUP_HOOK` overrides) until netcoredbg attaches (`HeldLaunch`).
- **Remote targets** (`Workbench/Debugging/Remote`: SSH, containers, WSL) run netcoredbg through pipe transports (`DebugAdapterStartInfo`), with `PathMappingDebugAdapter` mapping source paths. netcoredbg is copied there on first use from `DAEDALUS_NETCOREDBG_<PLATFORM>`, `.work/netcoredbg-<platform>` (`eng/get-netcoredbg.sh --platform linux-x64`) or a verified download.
- **Launch profiles**: `WSL2` runs in a WSL distribution; `DebugRoslynComponent` runs the SDK's compiler on its target (`RoslynComponents`).
- **Just-In-Time debugging** sets the runtime's crash-dump variables per user (`JitDebugging`; tests use stand-in environments and must never register for real).
- **`DAEDALUS_NETCOREDBG_LOG=<folder>`** logs netcoredbg's DAP traffic.

Remote tests use local stand-ins only: WSL, a stand-in `ssh` script, and Podman with a local image (`RemoteFixture`). Hot Reload while debugging is a researched gap (ADR 0040).

## Git

Source control uses the git CLI (ADR 0008), not a library: `GitService` in `src/DaedalusStudio.Workbench/Git` runs one `git` process per operation and parses porcelain output only. `DAEDALUS_GIT` points at another git. Tests build throwaway repositories in temp folders (git writes read-only object files; clear the attribute before deleting). Git depth (ADR 0020): history pages and `GitGraph` lanes, operations in progress (continue, skip, abort), conflicts, stash, rebase (interactive through `GIT_SEQUENCE_EDITOR`), tags, remotes and per-line patches in `GitService.History.cs`/`GitService.Operations.cs`; the history window, merge editor and interactive rebase are shell documents (`ShellHost.GitDepth.cs`). `daedalus merge` and `daedalus --wait` are waiting single-instance requests.

Hosting and the rest of Git depth (ADR 0031): worktrees, Git LFS (`check-attr`, pointer files, `git lfs locks`), several repositories, fetch-and-switch for pull requests and publishing are in `GitService.Repositories.cs`. Askpass: `GitService.AskpassEnvironment` points `GIT_ASKPASS`/`SSH_ASKPASS` at the `daedalus` executable, which (with `DAEDALUS_ASKPASS_PIPE`/`_TOKEN` and one argument) answers through `AskpassServer`'s pipe (`Git/Askpass.cs`); nothing is stored. Secrets go only to the OS credential store (`DaedalusStudio.Platform/Credentials`: Credential Manager, Keychain, libsecret; `DAEDALUS_CREDENTIAL_STORE=memory` for tests, which the shell fixture sets) through `SecretStorage` (a `--user-data-dir` profile has its own service). GitHub, Azure DevOps and GitLab are built-in plugins (`src/Plugins/DaedalusStudio.Plugins.GitHub`, `.AzureDevOps`, `.GitLab`, sharing `DaedalusStudio.Plugins.Hosting`) on the proposed `IHosting`/`ISecrets` API, activated only by `onHostingProvider:<id>`; the shell side is `HostingService` (workbench `Hosting/`) and `ShellHost.Hosting.cs` (Accounts page, Pull Requests, Work Items and Worktrees windows, review comments through `EditorInsights`, CI status, `#` completion, Publish). Tests never reach a real host: `tests/Shared/MockHttpServer.cs` and `MockGitHub.cs` (also compiled into the shell for the smoke step `git.hosting`), and the Azure DevOps and GitLab mocks in `tests/DaedalusStudio.Plugins.Tests`.

## Older .NET versions

Projects of .NET Core 2.0 to .NET 10 work with the current SDK, and SDKs down to 2.1.200 pinned in `global.json` open and build (ADR 0030; the support table is `docs/user-guide/dotnet-versions.md`). The build host builds in its own node for MSBuild before 17 (`SolutionBuilder.InProcess`: their worker nodes never connect to a host on .NET 10), and names an SDK below the floor or a missing one (`SdkSelection`, `GlobalJsonSdk`). Programs start through `RuntimeSelection` (workbench `Build/`): `DOTNET_ROOT` for apphosts, the x64 `dotnet` and netcoredbg (`debugger/x64/`, `eng/get-netcoredbg.sh --x64`) for .NET 5 and earlier on Apple silicon, `CLR_ICU_VERSION_OVERRIDE` for .NET Core 2.x and 3.x on Linux. Fixture: `samples/TargetFrameworks` (one app, library and xUnit project per framework, `Sdks/` with pinned SDKs). `eng/get-runtimes.sh` installs the pinned runtimes and SDKs into `.work/dotnet-compat`; `tests/DaedalusStudio.TargetFrameworks.Tests` points its own process at that root (PATH, `DOTNET_ROOT`, `DOTNET_HOST_PATH`) and skips without it, unless `DAEDALUS_DOTNET_COMPAT` names it (`eng/validate.sh` and CI's manual runs). `eng/compat-containers.sh` runs the old runtimes in containers of their distributions (podman in WSL).

## Linux and macOS validation

The development machine is Windows. Validate on Linux and macOS locally, and leave the hosted 3-OS matrix for the milestone dispatch (macOS minutes bill 10×).

- **When**: before every push that touches platform-sensitive code: process launching and paths, the hosts (`pluginhost/`, `buildhost/`, `lshost/`), the debugger, git, packaging (`eng/`), file watching, fonts and rendering, keyboard shortcuts, or `#if`/`OperatingSystem.Is*` branches. Run Linux (WSL) for every such change. Run macOS when the change is UI-, packaging- or debugger-related, or before a milestone checkpoint. Report each platform's result separately, with failing output. Never call a change cross-platform when a platform was skipped.
- **Linux (WSL 2, Ubuntu 24.04)**: `wsl -d Ubuntu -- bash eng/wsl-test.sh [--smoke] [dotnet test args]`. It mirrors the working tree, uncommitted changes included, into `~/daedalus-studio` inside WSL so Linux and Windows never share `bin/`/`obj/`, then runs `eng/validate.sh` there. The SDK pinned by `global.json` installs into `~/.dotnet` (the distro's `/usr/lib/dotnet` is too old). `--smoke` adds the Native AOT publish and `eng/smoke-test.sh`; it needs `clang` and `zlib1g-dev` (`sudo apt install clang zlib1g-dev`, which the user must run because sudo asks for a password). `eng/wsl-display.sh` (sourced by `eng/wsl-test.sh`, no root) supplies:
  - a display: WSLg's when it runs, otherwise Xvfb unpacked from the distro's packages into `~/.local/xvfb`, on `:99`;
  - for the browser tests and smoke steps, a Chromium browser: Chrome for Testing in `~/.local/chrome-for-testing` when none is installed.

  Run it in the background; a full run takes several minutes. Don't build the Linux side straight from `/mnt/d`.
- **macOS (the user's Mac, Apple silicon, a Remote Control session)**: the user's clone is `/Volumes/M2/Projects/daedalus-studio`; leave its checkout alone. A Claude session started with `--name daedalus-mac --remote-control` runs there. With Remote Control on in this session, it shows up in `ListAgents` as `daedalus-mac`.
  1. Push the working tree with `bash eng/push-snapshot.sh`. This force-pushes a snapshot commit to the scratch branch `validate`, the one exception to "no feature branches". It leaves HEAD and the index alone, and costs no CI minutes because workflows only trigger on `develop` and `master`.
  2. `SendMessage` to `daedalus-mac` with the snapshot commit. Ask it to `git fetch origin validate`, create or reuse a git worktree at `FETCH_HEAD` outside the user's checkout, run `bash eng/validate.sh [--smoke]` there, and reply with: the environment, the counts, the failing tests with their messages and our stack frames, the smoke-test steps that failed, and the artifact paths. The first run installs the SDK (10–20 min with `--smoke`).
  3. If `daedalus-mac` is missing or `offline`, say so and ask the user to start it. Don't fall back to the hosted macOS runner without asking. Nothing reports back when the Mac holds a message for approval, so silence isn't a result.
- `eng/validate.sh` is the shared entry point on Linux and macOS: SDK check, netcoredbg, restore, build, test (Release, as CI), and with `--smoke`, publish plus smoke test.

## Git

- Commit directly to `develop`, the default branch (M31, D21); no pull requests for now.
- **Parallel milestones** (the maintainer's go-ahead, 2026-10-11): a session may build a milestone on its own branch in a git worktree. It lands on `develop` by merging `origin/develop` into the branch, re-running the affected tests, and pushing a fast-forward (`git push origin HEAD:develop`); never force-push `develop` or touch `master`. Each worktree validates with its own WSL mirror (`DAEDALUS_WSL_DIR`) and its own Mac snapshot branch (`eng/push-snapshot.sh validate-<name>`). `master` only receives merges from `develop`, each one a stable release, and hotfixes; `release.yml` merges a hotfix back into `develop`.
- Commit messages carry **no** AI co-author or "Generated with" trailers.
- The repository is public (since 2026-10-11), so hosted runners are free: every push to `develop` or `master` builds, tests and smoke-tests on Windows, macOS and Linux (documentation-only pushes are skipped), and the nightly schedule publishes prereleases. Read all three jobs' results after a push. Test locally first, and don't push while a run is in progress (it gets cancelled). Benchmarks still run on the local reference machine.

## Conventions

- Root namespace and assembly/package prefix `DaedalusStudio.*` (`Daedalus.*` is taken on nuget.org). The product name is "Daedalus Studio", and the CLI is `daedalus`. Never use "Visual Studio" branding in the product.
- Central package management (`Directory.Packages.props`). Check and record the license of every new dependency in `THIRD-PARTY-NOTICES.md`.
- Heavy work runs out of process (language service host, build host, debug adapter, plugin hosts). The shell supervises hosts with `DaedalusStudio.Rpc.SupervisedProcess` and restarts them on crashes. MSBuild only ever runs in the build host (ADR 0004), and only for trusted folders.
- Project-system fixtures: `samples/ProjectSystem` (`.sln` and `.slnx`); build and run: `samples/BuildAndRun` (ADR 0006). Tests copy them to a temp folder before changing anything, with the repository's SDK pinned above them (`tests/Shared/FixtureSdk.cs`).
- `samples/Net11` pins the .NET 11 SDK (M30, ADR 0025). Its tests skip without that SDK locally and fail without it in CI; `eng/validate.sh` installs it. Moving to a new .NET follows `docs/release/dotnet-upgrade.md`.
- Wire contracts follow LSP where it fits. Extensions use the `daedalus/` prefix and are documented in `docs/protocol.md`; the plugin host protocol is in `docs/plugin-protocol.md`.
- The plugin API (`DaedalusStudio.Plugins.Abstractions`) is a public contract: changes follow ADR 0003's versioning policy and go into the changelog in `docs/plugins.md`.
- Shell views talk to `DaedalusStudio.Workbench` services; workbench events arrive on any thread, so views marshal through `Ui.Post`. Built-in features register through the same registries as plugins (`BuiltIns.cs`).
- Never block the UI thread, and make everything cancellable.
- The shell must stay Native-AOT clean: use compiled bindings, keep reflection-free view location, and use source-generated JSON.
- Fixtures under `samples/` are standalone. They do not inherit the repo's build settings.
- Deferred work gets a `TODO(issue)` and goes into the next checkpoint summary.
